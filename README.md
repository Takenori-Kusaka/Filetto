# Filetto

<!-- license: code=AGPL-3.0-or-later docs=CC-BY-4.0 -->

**人にも AI にも検索可能なファイル倉庫。** 自分の PC に 1 コマンドで立てられ、**ファイルを置いた瞬間から検索できるようになります。**

いま、AI に手元の資料を読ませたい人は、都度ファイルをチャット画面へアップロードするか、RAG 環境を構築してもらうかのどちらかを選んでいます。前者は毎回やり直しで、資料が増えるほど破綻します。後者は依頼できる相手がいなければ成立しません。

Filetto は、**フォルダにファイルを置くという既存の習慣のまま**、そのファイル群を人にも AI にも検索可能な状態にします。人向けの入口はファイル操作が一級市民の UI、AI 向けの入口は同一のファイル資産に対するセマンティック検索と MCP アクセスです。**この2つが同じ実体を共有していること**が、既存の RAG 製品との差です。既存製品はいずれも「取り込み口」であってエクスプローラーではありません。

| 項目 | 実測 |
| --- | --- |
| 運用時の金銭コスト | **$0**([S0-004](docs/spikes/S0-004-rag-fitness.md)) |
| 実行時の外部通信 | **なし。API キー不要** |
| 初回のモデルダウンロード | 約 1.04 GB |
| 初回構築の所要時間 | 50 ファイルで約 25 分。数千ファイルなら数時間から十数時間 |

**「無料」とは書きません。ゼロなのは金銭だけです。** 初回構築には時間とディスクが要ります。

**想定する利用者はエンジニアです。** Filetto を部品として自分のシステムへ組み込む人を対象にしています。その先の利用者(非エンジニア)は、組み込まれたシステムを使い、Filetto に直接触れません。

## 開発プロセスについて

**本リポジトリは[ピットイン方式](https://takenori-kusaka.github.io/process-compass/phase4-process-design/overview/)(正式名称: AI協調型ソフトウェア開発プロセス標準)で開発しています。**

> マシンは人間より速い。それでも、決められた場所では必ず人間が触る。

F1 のピット作業は 18〜20 名が2秒以下で終えます。レースそのものは止まりません。決められた場所でだけ人の手が入ります。AI が実装を主導する開発でも、この形は変わりません。

**以下はプロセスの説明です。Filetto を使うだけなら読む必要はありません。**

## プロセスに乗るには

### 1. プロセス構成を決める

Claude Code でリポジトリを開き、次を実行します。

```
/process-init
```

チーム規模・事業ステージ・品質要求・開発形態・安全重要度の5つを聞かれます。専門用語は使いません。回答から、あなたの状況に合ったプロセス構成が生成されます。

| 生成されるもの | 中身 |
| --- | --- |
| `PROCESS-PROFILE.md` | 人が読む構成書。標準からの差分と、その理由 |
| `process.config.json` | 機械が読む構成。CI とスキルが参照する |
| `.github/workflows/` | 有効なゲートだけが残る |
| `.github/rulesets/` | 規模に応じたブランチ保護 |
| `context/projects/<案件ID>.md` | 案件層コンテキストの初期ファイル |

### 2. 開発を始める

以降は、次のスキルを順に使うだけでプロセスに乗ります。

```
/spec-write       受入基準を書く          → G-2 / G-4
/task-breakdown   実装計画へ分解する       → G-4
/implement        AI が実装する            → G-5
/human-verify     人が差分を検証する        → G-6 の前段
/gate-record      ゲート判定を記録する      → 全ゲート
/adr-write        設計判断を記録する        → G-3
```

各スキルは `process.config.json` を読み、あなたの構成で不要なゲートには触れません。

## リポジトリの構成

```
.
├── PROCESS-PROFILE.md      人が読むプロセス構成書(/process-init が生成)
├── process.config.json     機械が読むプロセス構成
├── CLAUDE.md / AGENTS.md   恒久層コンテキストの入口
├── .claude/
│   ├── settings.json       強制層。書き込み・ネットワーク・コマンドの既定拒否
│   └── skills/             作業スキル7種
├── .github/
│   ├── workflows/          gate-g5 / gate-entry / ship-evidence / ai-review ほか
│   ├── rulesets/           ブランチ保護(プロファイル別)
│   └── PULL_REQUEST_TEMPLATE.md
├── adapters/               言語ごとの検査コマンド(node / python / go / none)
├── scripts/gate/           ゲートの実装(Node 22、依存パッケージなし)
├── templates/              成果物テンプレート11種
├── context/                恒久層コンテキスト(用語集・判断記録・設計標準)
├── specs/                  機能仕様(F-NNN)
└── docs/gates/             ゲート判定記録
```

### 言語に依存しません

CI が固定するのは**ゲート契約**だけです。

- 必須ステータスチェックの名前は `gate-g5`
- 出荷判定の証跡は `evidence/evidence.json` のキー構造

実際に走るテスト・静的解析・ライセンス検査のコマンドは `adapters/<stack>.json` から差し込みます。同梱するアダプタは `node` / `python` / `go` / `none` の4種です。プロセスの骨格が言語に汚染されません。

ゲートのスクリプトは Node 22 の標準機能だけで動きます。依存パッケージのインストールは要りません。

## 8つのゲート

| ゲート | 判定 | 判定者 |
| --- | --- | --- |
| G-1 企画承認 | 投資判断 | 事業決裁者 |
| G-2 要件合意 | 受入基準が検証可能か | 価値責任者 |
| G-3 技術設計判断 | 設計の可逆性と整合 | 技術判断者 |
| G-4 機能仕様承認 | タスクの粒度と範囲 | 価値責任者 |
| **G-5 自動検証** | **8基準すべて機械判定** | 機械 |
| G-6 独立レビュー | 作成者以外が挙動を確認 | 独立レビュア |
| G-7 出荷判定 | 記録の完備 | QA |
| G-8 リリース決裁 | 事業リスクの受容 | 事業決裁者 |

**G-4 と G-5 はどの構成でも省略できません**。それ以外は事業ステージ・規模に応じて簡略化または省略されます。省略した項目は `PROCESS-PROFILE.md` に理由つきで残ります。

## 1人で開発する場合

1人 + AI エージェントという構成も想定しています。ただし正直に書きます。

**独立レビュー(G-6)だけは、AI で埋められません。**

標準は「AI を独立レビュアの代替に置きません」と規定しています。同じモデルを使う限り、エージェントを分けても事前学習の知識という共通の原因が残るためです。生成物の確認を生成器へ委ねる構成は、自動化バイアスによって見落としを増やす方向に働きます。

G-6 の判定基準5項目のうち、4項目は開発者(検証)として自分で実行できます。埋まらないのは「作成を指示した本人でない」の1項目だけです。作成時に抱えた思い込みを、抱えていない人が見ること。1人ではこれが成立しません。

そこでこのテンプレートは、1〜2名のプロファイルで G-6 を**省略(`omitted`)ではなく未達(`unmet`)**として扱います。

| 状態 | 意味 |
| --- | --- |
| `omitted` | 標準の規則により省略した。調整として成立している |
| `unmet` | **目的を達成する構成を示せていない** |

未達は消えません。`PROCESS-PROFILE.md` の冒頭に常時表示され、出荷判定の証跡にも必ず載ります。隠す経路をテンプレートは持っていません。

### 未達を埋める方法

標準が認める代替は、外部の人間だけです。`process.config.json` の `reviewSourcing` へ調達先を書いてください。

- リポジトリを公開し、コミュニティのレビューを受ける
- 他の個人開発者と相互レビューの取り決めをする
- 有償のコードレビューを利用する
- 仲間が増えたら `/process-init` を再実行する

### 埋まらないまま進める場合

軸A の「事後監査への切替」が使えます。判定を消すのではなく、**リリース前からリリース後の抜き取りへ時点を移す**調整です。対象にできるのは依存パッチ・表示文言・スタイル・既定値内の設定変更に限られ、次の3条件をすべて満たす必要があります。

1. 自動検査(G-5)が全項目を通過し、変更箇所の挙動を既存のテストで検出できる
2. 単独で取り消せる。かつ取り消しの手順を実行した実績がある
3. 確約範囲とコア指定に触れない

CL1 以上および規制業では使えません。

## AI レビューの位置づけ

`ai-review` ワークフローを同梱していますが、**独立レビュー(G-6)の代替ではありません**。

- PR へコメントするだけ。承認(approve)は行わない
- 必須ステータスチェックにしない。合否条件にすると自動化バイアスを招くため
- 出力は監査の**入力**として使える。判定そのものには使わない
