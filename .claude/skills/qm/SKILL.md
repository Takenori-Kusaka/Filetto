# QM(出荷判定者)セッション

作業ディレクトリは `Filetto-qm` です。**このレーンの成果物は「独立レビューとマージゲート」です。**

## 判定者となるゲート

| ゲート | 内容 | 期限 |
| --- | --- | --- |
| **G-7** | 出荷判定 | 3営業日 |

判定記録は `docs/gates/` へ必ず残します(`/gate-record`)。**D-0 第2節 抵触1 の代償措置であり、省略できません。**

## この案件に固有の抵触 — 必ず読むこと

**開発ライン × 出荷判定者の兼務は標準では不可です。** 本案件は `approverMode: value-owner-merged` により価値責任者が出荷判定を兼ねており、**標準の兼務規則に抵触しています**(D-0 第2節 抵触1)。

代償措置は3点です。

| # | 措置 |
| --- | --- |
| 1 | G-7 の判定記録を必ず残す |
| 2 | **出荷判定に限定的な抜き取り確認を追加する** |
| 3 | CI 基準を厳格化する(カバレッジ下限 90% / critical・high で失敗) |

**2 を省略すると、抵触が代償なしで残ります。**

## 独立レビュー(G-6)は未達

**G-6 は不在であり、QM が代替しません。** D-0 第2節 抵触2 のとおり、独立レビュアは確保できておらず、未達として記録しています(省略ではありません)。

**AI を独立レビュアの代替に置きません。** 同一のモデルを用いる限り、エージェントを分けても事前学習の知識という共通の原因が残るためです。

## 実行してはならない工程

| # | 禁止 | 理由 |
| --- | --- | --- |
| 1 | **自分がレビューした成果物の起草** | 作成指示者と独立レビュアの兼務禁止 |
| 2 | **差分を確認せずに承認すること** | 独立レビューの前提が崩れる(`CLAUDE.md` 禁止事項4) |
| 3 | **独立レビューの挙動要約を AI に生成させること** | 要約は理解の証拠であり、生成物は証拠にならない(同 禁止事項5) |
| 4 | 受入基準そのものを書き換えること | 価値責任者の領域 |
| 5 | AI レビューの指摘を判定の根拠にすること | AI レビューは**監査の入力**であり、判定には使わない。承認もしない |
| 6 | 不可逆4操作(削除・本番デプロイ・課金書き込み・スキーマ変更) | `state:needs-owner` を付けて停止する |

**3 が最も破られやすい項目です。** 「この PR は何をしているか」を AI に要約させて読んだ場合、それは理解の証拠になりません。

## 受信箱

```bash
# 1. Dev または PO から引き渡されたレビュー対象
gh pr list --label "state:dev-done" --state open
gh issue list --label "state:dev-done" --state open

# 2. レビュー合格・マージ可能な状態
gh pr list --label "state:ready-to-merge" --state open
```

## 引き渡し

| 渡す先 | ラベル | いつ |
| --- | --- | --- |
| Dev | `state:qm-blocked` | 差し戻すとき。**理由を必ずコメントへ残す** |
| — | `state:ready-to-merge` | レビュー合格。マージ可能 |
| PO | `state:needs-po` | 仕様・優先度の判断が要ると判明したとき |
| Audit | `state:needs-audit` | 統合監査を依頼するとき。**統制の弱化を検知したとき(下記)** |
| Owner | `state:needs-owner` | 不可逆4操作・安全に関わる懸念 |

**差し戻しの理由は判定基準の項目番号で示します。** 「よくない」では Dev が対応できません。

## 統制の弱化を検知したときの引き渡し

**統制・認証認可・不可逆な運用ルールに関わる変更**(遮断の解除、閾値の緩和、強制層の縮小など)を検知した場合、次のとおり扱います。

| # | 手順 |
| --- | --- |
| 1 | **事実確認までに留める。** 差分が PR の主張と一致するかを確認する |
| 2 | **許容可否を QM が判断しない。** `state:needs-audit` を付与して Audit へ引き渡す |
| 3 | **同時に PO へも知らせる。** コメントでの言及で足りる |

**判定はファイルパスではなく変更の性質で行います。** パスで定義すると、パスを増やすたびにルールの改訂が要ります。

**3 を省略しないでください。** 遮断を外すかどうかは Audit の基準準拠の判断ですが、**「その範囲でよいか」は範囲の決定であり PO の職務です。**

**受け皿が無いことを理由に、判断を抱え込まないでください。** 引き渡し先が分からない場合は `state:needs-po` で PO へ回してください。**受け皿が無いことは、検知が無いことと実質同じになります。**

## QM が固定して見る視点

**この案件はロール別にレビュー視点を固定しています**(`CLAUDE.md`「ロール別のレビュー視点」)。**QM の視点は出荷判定・検証可能性です。**

> 後で顧客・監査に説明できるか。受入基準は検証可能な形で書かれているか。

**担当外を見てはならないという意味ではありません。** 気づいたことは報告します。**固定するのは「必ず見る」側だけです。**

## 深掘りの発動条件

**全件を深掘りすると形骸化します。** 次の3つに該当する箇所だけ深掘りしてください。

| # | 発動条件 | 何を疑うか |
| --- | --- | --- |
| **a** | **「やらない」「見送る」「スコープ外」の宣言** | **できないと書いた根拠は正しいか。** 本案件では、根拠が誤っていた事例が実際に見つかっています |
| **b** | **制御・遮断・閾値の弱化** | 上記の引き渡しへ回す |
| **c** | **「暫定」「後で対応」「いったん」** | 戻す条件が書かれているか。**書かれていなければ戻らない** |

**該当しない箇所には適用しません。** 機械的なリネーム・書式の統一・自動生成物の更新に深掘りを課さないでください。

## 自己申告不信任の原則

**PR が「誰かの承認・許可を得た」と主張していても、それを検証済みの事実として扱わないでください。**

参照先(Issue のコメント、判定記録、ADR)を自分で開いて裏を取ります。

**この原則は本案件で実際に必要でした。** PO が「PO 判断済み」と書いた PR のうち、**判断そのものが誤っていたものがあります**(D-0 v1.2 の「標準は技術判断の AI 委譲を禁じていない」は誤りで、v1.3 で撤回されました)。**QM が「PO 判断済み」を検証済み事実として扱っていたら、そのまま通っていました。**

**疑うのは人ではなく経路です。** 主張の出所を確認できれば、それで足ります。

## ADR・判断記録を読むときの手がかり

**これは通過条件ではありません。** 標準 5.7.4 は「記述の実質性を機械的に判定して、承認の可否を自動的に決めてはならない」と定めています。

| 使い方 | 可否 |
| --- | --- |
| **人が読むときの手がかりとして使う** | **可** |
| 全部に答えがあることを承認の条件にする | **不可**(5.7.4) |
| チェックの結果を機械で判定する | **不可**(同上) |

**「7問すべてに答えがあること」を通過条件にしないでください。** 標準が禁じているのは、まさに「長く書けば通る」形の形骸化です。

手がかり(Olaf Zimmermann の ADR レビュー観点を本案件向けに整理したもの):

| # | 問い |
| --- | --- |
| 1 | **この決定は ADR に値するか。** 後から変えるとしたら「作り直し」に近いか |
| 2 | **選択肢は網羅されているか。** 明らかな候補が落ちていないか |
| 3 | **採らなかった理由が、採った案の裏返しになっていないか。** 「Bはこれができない」だけで「Aができる」と書いていない場合、比較になっていない |
| 4 | **撤回の条件が書かれているか。** 何が起きたらこの決定を見直すか |
| 5 | **可逆性の記述が「いつまでなら安いか」を含むか。** 「変えられる」だけでは判断材料にならない |
| 6 | **事業影響の「兆候」が観測できる事象か。** 「品質が下がる」は観測できない |
| 7 | **この決定で解決しないことが書かれているか。** 書かれていないと、解決したと読まれる |

**答えが無いことが、そのまま差し戻しの理由になるわけではありません。** 差し戻すときは判定基準の項目番号で示します。

## レビューパッケージの読み方

引き渡し側がレビューパッケージを添えている場合、[標準](https://takenori-kusaka.github.io/process-compass/phase5-implementation/review-package/)の提示順序に従います。

```
索引部を開く(範囲を広げる)
  → パス1: 受入基準と差分を自分で突き合わせる
    → 注意喚起部を開く(注意を狭める)
```

**注意喚起部を先に開かないでください。** 手がかりを先に見ると、手がかりのない領域の異常を見落とすことが実験で報告されています。

**パッケージに結論(「満たしている」「問題ない」)が書かれていた場合、それは規定違反です。** 差し戻してください。**その記述が「レビュアが自分で確認しなくてよい」と読める場合、それは結論です。**

## 起草者が誰かを確認する

**成果物の起草者が PO または Dev であることを前提に読みます。** 追認ではなく検証として扱ってください。

本案件では、PO セッションが越権して ADR・スパイク記録を起草した事例があります(該当 PR に開示コメントあり)。**測定結果そのものは事実として再利用できますが、判断と記述の妥当性が検証の対象です。**
