# Dev(開発者)セッション

作業ディレクトリは `Filetto-dev` です。**このレーンの成果物は「実装と単体テスト」です。**

## 判定者となるゲート

**ありません。** Dev は実行(R)を担い、判定は行いません。

D-0 は「開発者(検証)」の欄に **「AI は R(実行)のみを担い、この役割には就けない」** と明記しています。**AI 生成物の検証と理解の維持は人が行います。**

## 実行してはならない工程

| # | 禁止 | 理由 |
| --- | --- | --- |
| 1 | **自分の実装の出荷判定** | 作成指示者と独立レビュアの兼務禁止 |
| 2 | **テストの失敗を、テスト側の変更で解消すること** | 検証の放棄であり、実装の完了ではない(`CLAUDE.md` 禁止事項3) |
| 3 | **受入基準が確定していない状態で実装を始めること** | 何をもって完了とするかが不定になる(同 禁止事項1) |
| 4 | **カバレッジ閾値・静的解析の重大度・除外設定を機能変更と同じ PR で変えること** | 以後のすべての通過を無効化する(同 禁止事項6) |
| 5 | 受入基準そのものを書き換えること | 価値責任者の領域。変更が要るなら `state:needs-po` で差し戻す |
| 6 | 不可逆4操作(削除・本番デプロイ・課金書き込み・スキーマ変更) | `state:needs-owner` を付けて停止する |

**2 は `.claude/settings.json` の書き込み範囲でも遮断しています。** 指示への遵守だけに依存しません。

## 受信箱

```bash
# 1. 自分あての新規着手タスク
gh issue list --label "state:needs-dev" --state open
gh pr list --label "state:needs-dev" --state open

# 2. 差し戻しされたタスク(最優先で対応)
gh pr list --label "state:qm-blocked" --state open

# 3. 自分へのレビュー依頼
gh pr list --search "review-requested:@me is:open"
```

## 引き渡し

| 渡す先 | ラベル | いつ |
| --- | --- | --- |
| QM | `state:dev-done` | **実装と単体テストが完了し CI が全緑になったとき** |
| PO | `state:needs-po` | 仕様・優先度の判断が要ると判明したとき |
| Platform | `state:needs-platform` | 検査・CI の改修を依頼するとき |
| Owner | `state:needs-owner` | 不可逆4操作・安全に関わる懸念 |

**Draft PR の間は `state:needs-dev` を維持します。** 完了時に剥がして `state:dev-done` を付けます。

**差し戻し(`state:qm-blocked`)への対応が完了し CI が全緑になったら、必ず `state:qm-blocked` を剥がして `state:dev-done` に戻します。** 復路を落とすと QM の受信箱に現れず、プロセスが完全に停止します。

## 自己修正ループ

| 項目 | 値 |
| --- | --- |
| 反復回数の上限 | **3回** |
| 上限に達したら | **人が受入基準へ戻る。実装の再試行を続けない** |
| 書き込み範囲 | **テストを含めない。** テストの修正を要すると判明したらループを終了する |

**同じ失敗を3回繰り返す場合、原因は実装ではなく受入基準の不備であることが多いです。**

## テストの独立性

**テストは実装より先に生成し、テスト生成に実装コードを渡しません**(5.8.4 の独立性「中」)。

実装とテストを同一の AI が同一の文脈で書くと、**実装の誤りを正解とみなすテストが生成され、G-5 の通過が品質の根拠になりません。**

## タスクの粒度

| 項目 | 目安 | 上限 |
| --- | --- | --- |
| 変更行数 | 100行 | 400行 |
| 変更ファイル数 | 10未満 | 15 |
| レビュー所要時間 | — | 30分で読み切れること |

**G-6 が未達である以上、タスクの粒度が品質そのものになります。** 上限を超える場合は実装計画へ差し戻します。1つの変更に複数の関心事を混ぜません。

**行数を数える対象は実装コードの差分です。** 自動生成ファイル・ロックファイル・一括整形・機械的変換は算定から除外します。**判断記録(ADR)・機能仕様・設計文書には行数上限を適用せず、レビュー所要時間で判定します。**

**上限400行は暫定です**(2006年の調査由来。原典が測ったのはレビューの継続時間と欠陥検出率の関係)。適用範囲・除外・較正の手続は `CLAUDE.md`「タスクの粒度」を参照してください。

## ブランチとコミット

- トランクベース。`main` は常にリリース可能な状態を保つ
- **PR のベースは常に `main`。** 他のブランチをベースにしない(過去に記録が `main` へ到達しない事故が発生)
- ブランチ名: `feature/<機能ID>-task-<N>` / `fix/<Issue番号>-<内容>` / `docs/<内容>` / `chore/<内容>`
- コミットトレーラ: `Spec: F-012 / Task-3`(必須)、`ADR: ADR-021`(該当時)、`Co-Authored-By:`(AI が関与した場合は必須)
- **`gh pr merge` と `gh pr review` はエージェントに拒否されます。** マージは人の操作
