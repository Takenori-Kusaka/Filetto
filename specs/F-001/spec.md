# F-001 ファイル操作を可逆にする倉庫

## 背景

自分の PC に資料を溜めている個人が対象である。フォルダにファイルを置くという既存の習慣を変えずに、倉庫として扱えるようにする。

破壊的操作の経路は2つある。**WebUI から人が呼ぶ経路と、MCP から AI エージェントが呼ぶ経路である。** 後者が存在することが本プロダクト固有の事情であり、人に確認を求める UI は AI が呼ぶ経路に存在しない。したがって可逆性を UI ではなく実装で担保する(ADR-0003)。

**この機能は安全重要度を CL0 とした根拠そのものである。** 可逆性が失われると `process.config.json` の `q-criticality: cl0` が事実と合わなくなり、プロセス構成の前提が崩れる。

## 受入基準

| # | 型 | 受入基準 |
| --- | --- | --- |
| 1 | ユビキタス | システムは原本ディレクトリに対して読み取りのみを行い、原本ファイルを書き換えてはならない |
| 2 | イベント駆動 | 利用者が WebUI からファイルの削除を実行した場合、システムはファイルをゴミ箱へ移動し、原本の実体を削除してはならない |
| 3 | イベント駆動 | AI エージェントが MCP からファイルの削除を実行した場合、システムはファイルをゴミ箱へ移動し、原本の実体を削除してはならない |
| 4 | ユビキタス | システムは物理削除を行う API を WebUI と MCP のいずれにも公開してはならない |
| 5 | イベント駆動 | 利用者がゴミ箱内のファイルに対して復元を実行した場合、システムは削除前のパスへファイルを戻さなければならない |
| 6 | 望ましくない事象 | 復元先のパスに同名のファイルが存在する場合、システムは HTTP 409 を返し、復元を実行してはならない |
| 7 | イベント駆動 | ファイルがゴミ箱へ入ってから保持期間を経過した場合、システムは当該ファイルを完全に削除しなければならない |
| 8 | ユビキタス | システムは保持期間を環境変数から読み取り、既定値を 30 日としなければならない |
| 9 | ユビキタス | システムは保持期間の設定として無期限を受け付けなければならない |
| 10 | ユビキタス | システムは保持期間をソースコード内の定数として持ってはならない |
| 11 | イベント駆動 | 利用者がゴミ箱の一覧を開いた場合、システムは各項目に完全削除までの残日数を表示しなければならない |
| 12 | ユビキタス | システムは完全削除の予告をトースト・ポップアップ・バッジ・メールのいずれによっても通知してはならない |
| 13 | イベント駆動 | 利用者または AI エージェントがファイルのリネームを実行した場合、システムは変更前の名前を操作履歴へ記録しなければならない |
| 14 | イベント駆動 | 利用者または AI エージェントがファイルの移動を実行した場合、システムは変更前のパスを操作履歴へ記録しなければならない |
| 15 | イベント駆動 | ファイルが上書き更新された場合、システムは更新前の内容をバージョンとして保管しなければならない |
| 16 | イベント駆動 | 利用者が過去のバージョンを指定して取得を実行した場合、システムは当該バージョンの内容を返さなければならない |
| 17 | ユビキタス | システムはバージョン保管の呼び出しを `VersionStore` インターフェースの背後で行い、Lore の型・イベント・エラーを他の層へ渡してはならない |
| 18 | ユビキタス | システムは Lore の保管パスを環境変数から読み取らなければならない |
| 19 | 望ましくない事象 | Lore の保管パスが設定されていない状態で起動した場合、システムは起動を中止し、設定が不足していることを標準エラー出力へ記録しなければならない |
| 20 | イベント駆動 | 保管領域の定期検証で破損を検出した場合、システムは破損したバージョンの識別子を記録しなければならない |
| 21 | イベント駆動 | 保管領域に `.~loretemp` が残存している場合、システムは当該ディレクトリを削除しなければならない |
| 22 | 望ましくない事象 | `loreserver` へ接続できない場合、システムはバージョン保管を伴う操作に対して HTTP 503 を返し、検索と閲覧を継続しなければならない |

各基準には、違反すると失敗するテストを1つ以上置く。

## スコープ外

- **バージョン間の差分表示**。「旧版に戻せる」ことのみを保証し、「何が変わったか」を見せる機能は扱わない(ADR-0003)
- **同時編集の排他制御(ファイルロック)**。初版はシングルユーザー前提であり、Auth を合成した後に扱う
- **バージョンの分岐(ブランチ)**。直線的な履歴のみを扱う
- **ゴミ箱の一括操作**(全件復元・全件完全削除)
- **原本ディレクトリの外にあるファイルの取り込み**
- **S3 等のクラウドストレージ**。初版はローカルディスクのみ
- **WebDAV / SMB によるマウント**

## 前提

| # | 前提 | 崩れたときの影響 |
| --- | --- | --- |
| 1 | `loreserver` が同一の `docker compose` 内で常駐する | 基準15〜21 が実装できない |
| 2 | 利用者が原本ディレクトリの読み取り権限を持つ | 基準1 が成立しない |
| 3 | ゴミ箱の実体を原本ディレクトリの外に置ける | 基準2・3 が原本の書き換えを伴う |
| 4 | JWT クレームによるスコープ制御がゴミ箱内にも適用できる | **条件つきで解消**(2026-08-13)。ADR-0004 決定3 により、スコープの解決は Filetto のローカルポリシーが担う。**ただし F-003 基準29 により認可の適用は既定で無効であり、有効にした場合にのみ本前提が要る** |

## 非機能の要求

| 項目 | 要求 |
| --- | --- |
| 応答時間 | 削除・リネーム・移動はメタデータの更新のみで完了する。ファイルの実体を複製してはならない |
| 同時実行 | 初版はシングルユーザー。同一ファイルへの同時操作は扱わない |
| 監査ログ | 削除・リネーム・移動・上書き更新について、実行時刻・操作種別・対象パス・呼び出し経路(WebUI / MCP)を記録する |
| 可用性 | `loreserver` の停止時も、検索と閲覧は継続する(基準22) |

## コア指定

- [x] **コア機能である**(ADR の添付が G-6 で必須になる)

理由: 削除・リネーム・移動の可逆性は、安全重要度を CL1 から CL0 へ下げた根拠そのものである(企画書「コア機能の候補」)。
