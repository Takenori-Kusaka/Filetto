# F-003 人と AI が同じ実体を検索する入口

## 背景

人向けの入口と AI 向けの入口が**同一のファイル資産を共有していること**が本プロダクトの価値であり、既存の RAG 製品との差である。既存製品は「取り込み口」であってエクスプローラーではない。

対外インターフェースは後続の Chat / Auth が依存する境界である。**あとから変えると全サービスへ波及する。** したがって契約を [ADR-0002](../../context/decisions/0002-external-interface-contract.md) で固定する。本仕様は同 ADR の決定4点にもとづく。

| 論点 | 決定 |
| --- | --- |
| 外部が指す識別子 | **安定 ID**。パスは属性にすぎない。安定 ID はメタデータ保管層で発番し、内容ハッシュとは別に持つ |
| ファイル内容の受け渡し | **本文直返しと署名付き URL の両方**。どちらを返すかは要求する側が指定し、サーバは閾値で暗黙に切り替えない |
| MCP の提供形態 | **HTTP を主とし、stdio も提供する** |
| 初回構築中の扱い | **候補に含めず、未完了 N 件を明示する** |

## 受入基準

### 識別子

| # | 型 | 受入基準 |
| --- | --- | --- |
| 1 | ユビキタス | システムは対外へ返す識別子を安定 ID とし、内容ハッシュを安定 ID として返してはならない |
| 2 | イベント駆動 | 原本のパスが変更された場合、システムは当該ファイルの安定 ID を変更してはならない |
| 3 | イベント駆動 | 原本の内容が変更された場合、システムは当該ファイルの安定 ID を変更してはならない |
| 4 | イベント駆動 | 同一の内容を持つ原本が2件存在する場合、システムはそれぞれに異なる安定 ID を割り当てなければならない |
| 5 | ユビキタス | システムは応答にパスを含める場合、パスを識別子ではなく属性として返さなければならない |
| 6 | 望ましくない事象 | 存在しない安定 ID が指定された場合、システムは HTTP 404 を返さなければならない |

### 検索

| # | 型 | 受入基準 |
| --- | --- | --- |
| 7 | イベント駆動 | 利用者または AI エージェントが日本語の自然文で検索を実行した場合、システムは安定 ID・ファイル名・パス・一致した箇所の抜粋を含む候補の一覧を返さなければならない |
| 8 | ユビキタス | システムはゴミ箱内のファイルを検索結果へ含めてはならない |
| 9 | ユビキタス | システムは未処理のファイルを検索候補へ含めてはならない |
| 10 | イベント駆動 | 未処理のファイルが1件以上ある状態で検索が実行された場合、システムは未処理の件数を応答へ含めなければならない |
| 11 | イベント駆動 | 読み取れなかったファイルまたは字形の混入が残ったファイルが候補に含まれる場合、システムはその旨を当該候補へ付記しなければならない |
| 12 | ユビキタス | システムは検索の実行時に外部ネットワークへ接続してはならない |

### 内容の受け渡し

| # | 型 | 受入基準 |
| --- | --- | --- |
| 13 | イベント駆動 | 安定 ID を指定して内容の取得が実行され、**要求する側が本文の直返しを指定した**場合、システムは本文の欄へ抽出テキストを含め、URL の欄を空にして応答しなければならない |
| 14 | イベント駆動 | 安定 ID を指定して内容の取得が実行され、**要求する側が署名付き URL を指定した**場合、システムは URL の欄へ署名付き URL を含め、本文の欄を空にして応答しなければならない |
| 15 | ユビキタス | システムは本文の直返しを許す上限のサイズを環境変数から読み取らなければならない |
| 16 | イベント駆動 | 署名付き URL の有効期限を過ぎた後に当該 URL へアクセスされた場合、システムは HTTP 403 を返さなければならない |
| 17 | ユビキタス | システムは署名付き URL の有効期限を環境変数から読み取らなければならない |
| 18 | イベント駆動 | 原本の実体の取得が要求された場合、システムは署名付き URL を返さなければならない |
| 28 | 望ましくない事象 | 本文の直返しが指定され、抽出テキストのサイズが基準15 の上限を超える場合、システムは署名付き URL へ切り替えてはならず、上限を超えたために本文を返せないことを応答へ明示しなければならない |

**基準の番号は識別子であり、追加時に既存の番号を振り直さない。** 基準28 は「内容の受け渡し」に属する。

### MCP

| # | 型 | 受入基準 |
| --- | --- | --- |
| 19 | ユビキタス | システムは MCP を HTTP 経由で提供しなければならない |
| 20 | ユビキタス | システムは MCP を stdio 経由でも提供しなければならない |
| 21 | ユビキタス | システムは HTTP と stdio のいずれの経路でも同一のツール定義を提供しなければならない |
| 22 | ユビキタス | システムは MCP のツールとして、検索・内容の取得・ファイル操作(削除・リネーム・移動)を提供しなければならない |
| 23 | イベント駆動 | AI エージェントが MCP から削除を実行した場合、システムは確認を求めずにゴミ箱へ移動しなければならない |

### 認可

| # | 型 | 受入基準 |
| --- | --- | --- |
| 24 | イベント駆動 | **認可の適用が有効な状態で** JWT が付与されていない要求を受けた場合、システムは HTTP 401 を返さなければならない |
| 25 | イベント駆動 | **認可の適用が有効な状態で** JWT のスコープが対象ファイルを含まない場合、システムは HTTP 404 を返し、その状態コードと応答の本文を基準6 の応答と同一にしなければならない |
| 26 | ユビキタス | システムはゴミ箱内のファイルに対しても、通常のファイルと同一の規則でスコープを適用しなければならない |
| 27 | ユビキタス | システムは JWT の発行を行ってはならない |
| 29 | ユビキタス | システムは認可の適用の有無を環境変数から読み取り、**既定値を「適用しない」としなければならない** |
| 30 | ユビキタス | システムは JWT の署名検証に非対称鍵の公開鍵のみを用い、**共有秘密による署名方式(HS*)と `alg: none` を受理してはならない** |
| 31 | ユビキタス | システムは JWT の検証に用いる公開鍵を環境変数から読み取らなければならない |
| 32 | ユビキタス | システムはアクセススコープの解決に、JWT のクレームとローカルポリシーの両方を用いなければならない |
| 33 | ユビキタス | システムはローカルポリシーの保管先を環境変数から読み取り、ソースコード内の定数として持ってはならない |
| 34 | イベント駆動 | **認可の適用が有効な状態で**要求を処理した場合、システムは判定に用いたローカルポリシーの版を監査ログへ記録しなければならない |

**基準29 が基準24・25・34 の前提条件である。番号順と適用順は一致しない。**

**24〜27 の番号と意味を変えていない。** ADR-0004・前提2・[#55](https://github.com/Takenori-Kusaka/Filetto/issues/55)・G-2 の判定記録が参照しているためである。24・25 は条件節を足しただけで、指す事象は変わらない。**28 は「内容の受け渡し」節で既に使われているため飛ばした**([PR #62](https://github.com/Takenori-Kusaka/Filetto/pull/62) で追加)。

各基準には、違反すると失敗するテストを1つ以上置く。

## スコープ外

- **認証基盤そのもの**。ユーザー登録・パスワード管理・多要素認証は別マイクロサービス(Auth)の責務
- **Chat / LLM 連携の UI**。別マイクロサービス(Chat)の責務
- **マルチテナント**。初版はシングルユーザー。localhost bind を前提とする
- **JWT クレームの設計そのもの**(クレーム名・スコープの表現・検証の責務分界)。ADR-0004 の対象
- **エンドポイントの完全な一覧と OpenAPI 定義**。実装工程で定める
- **MCP ツールの引数スキーマの詳細**。実装工程で定める
- **検索結果の並び替え・絞り込みの UI**
- **プレビュー表示**。SC-B(調整枠)

## 前提

| # | 前提 | 崩れたときの影響 |
| --- | --- | --- |
| 1 | **ADR-0002 が承認されている** | 基準1〜21 の契約が確定しない。**本仕様の最大の前提** |
| 2 | ~~ADR-0004 が JWT クレームの契約を定める~~ | **解消**(2026-08-13 採用)。基準24〜27・29〜34 は同 ADR の決定に依拠する |
| 3 | メタデータ保管層が安定 ID と内容ハッシュの2段の対応を持つ(F-002 基準2・3) | 基準1〜4 が実装できない |
| 4 | 署名付き URL を発行できる鍵を環境変数から読み取れる | 基準14・16 が実装できない。**ADR-0004 3-2 により、この鍵は JWT の検証鍵とは別体系(短命の HMAC 署名)である** |

## 非機能の要求

| 項目 | 要求 |
| --- | --- |
| 応答時間 | 検索は同期で応答する。初回構築の進行中も応答しなければならない |
| 同時実行 | 初版はシングルユーザー。HTTP と stdio の同時接続は扱う |
| 監査ログ | 検索・内容の取得・ファイル操作について、実行時刻・経路(WebUI / MCP-HTTP / MCP-stdio)・対象の安定 ID を記録する |
| セキュリティ | 署名付き URL をログへ出力してはならない。JWT をログへ出力してはならない |

## コア指定

- [x] **コア機能である**(ADR の添付が G-6 で必須になる)

理由: セマンティック検索と MCP インターフェースは本プロダクトの価値そのものであり、対外インターフェースの契約は後続の Chat / Auth が依存する境界である(企画書「コア機能の候補」)。
