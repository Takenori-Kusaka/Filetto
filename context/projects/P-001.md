# P-001 Filetto

**最終更新: 2026-08-12** / 現在地: **S1 価値確立**(SG-0 通過済み)

## 案件の目的

個人が自分の PC に 1 コマンド(`docker compose up`)で立てられ、**ファイルを置いた瞬間から人にも AI にも検索可能になる**、課金なしのファイル倉庫を作る。

人向けの入口は Windows Explorer / Google Drive 相当の**ファイル操作が一級市民**の UI。AI 向けの入口は同一のファイル資産に対する**セマンティック検索と MCP アクセス**。この 2 つが同じ実体を共有していることが本プロダクトの価値であり、既存の RAG 製品との差である。既存製品はいずれも「取り込み口」であってエクスプローラーではない。

探した先でやることは **RAG** である。**RAG に取り込めないなら、見つけても意味がない。** これが検索精度とは別に、抽出テキストの質を問う理由である。**この問いは S0-004 で実測し、成立を確認した。**

Filetto 完了後に Chat / Auth を別マイクロサービスとして開発し、Docker アーキテクチャへ合成する。最終形は「AI Editor Framework(NotebookLM リスペクト)」。

## 費用に関する事業上の前提

**費用の最小化は、訴求の言い換えではなく目的そのものである。**

同種の機能は有償 SaaS として既に存在する。**費用を出せるならそちらでよい**というのが利用者の合理的判断であり、「一定以上の費用が掛かり、採算性の面で有償 SaaS より良い選択肢にならない」時点で、**本 OSS の経営層観点での差別化は消滅する**。技術者観点(組み込み容易性・拡張性・自由度)での優位は残りうるが、それだけでは中核訴求を支えられない。

ただし **「ゼロ」なのは金銭だけ**である。S0-003 の実測では 50 ファイルの初回構築に約 25 分、モデルのディスク使用量は約 1.04 GB(S0-004 の推奨構成)。数千ファイルなら数時間から十数時間。**企画書 v2.0 では「無料」ではなく「課金なし・自分のマシンで完結」と書く。**

運用時 $0・実行時の外部通信なし・API キー不要は S0-004 が実測で確認した。**金銭の主張は維持し、時間とディスクの主張はしない。**

## 対象とする利用者

**日本国内の利用者と日本語文書を対象とする。**

この前提は技術選定に対する拘束力を持つ。日本語の文書に対して中国語字形を返す OCR は、法務・引用という特定用途の制約ではなく**中核体験そのものの欠陥**として扱う。「読める」と「正しく読める」を分けて売らない([#12](https://github.com/Takenori-Kusaka/Filetto/issues/12))。

## PO が下した判断

### 1. 中核構成は案B(2026-08-12 決定)

パース + BM25 / e5-small を中核に置き、LLM はオプション層に置く。

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 案A パース + BM25 のみ | 不採用 | S0-003 でハイブリッド(3:7)が 10/10。埋め込みを外す理由がない |
| **案B 案A + LLM をオプション層** | **採用** | 運用時 $0・外部通信なしを保ったまま、LLM を持つ利用者だけが上積みを得る |
| 案C GraphRAG 系 | 不採用 | LLM 必須で費用の前提と衝突する。S0-001 で Graphify の実用精度も届かない |

層B・層C は確定。**層A(パース)の OCR のみ #12 待ち。** `.xlsx` は ExStruct(`--mode light`)で確定(S0-004 で 3/3)。

### 2. Lore を VersionStore に採用する(2026-08-12 決定)

**自前 CAS は採らない。履歴管理を独自実装することは技術負債にしかならない。**

[[extensibility]] は最優先事項として拡張性を置いている。履歴管理・重複排除・破損検出を自前で持つと、実装した瞬間から永続的に保守対象となり、**部品として将来的に差し替える余地を自ら潰す**。この観点で自前 CAS は強く否定される。S0-005 が挙げた「`loreserver` の常駐(コンテナ +1)」という費用は、独自実装の保守費用より小さい。

S0-005 の4条件をすべて受け入れる。

| # | 条件 |
| --- | --- |
| 1 | `loreserver` の常駐を受け入れる(`docker compose` に1コンテナ追加) |
| 2 | 保管パスを明示設定する(既定は一時ディレクトリで消える) |
| 3 | 保管領域の定期検証と `.~loretemp` の掃除を Filetto 側で持つ |
| 4 | `VersionStore` 境界の背後に置く(0.x の間は API が非互換に変わりうる) |

**条件4 は条件1 の帰結でもある。** 境界を置く以上、将来 Lore を別実装へ差し替える経路は残る。これが自前 CAS との決定的な差である。

### S0-004 が S0-003 を覆した点

| S0-003 の記述 | S0-004 の実測 |
| --- | --- |
| OCR は EasyOCR(ja) を推奨 | **スキャン PDF 4問すべて回答不能**。RapidOCR 全ページで 4/4 正答・回収率 82%/53%・4.4 倍速い |
| 神エクセルの列見出しとの交差はどのパーサも復元できない | **ExStruct で復元できる**(3/3)。近接判定という測り方の限界だった |
| 「スキャン PDF は探せるが読めない」 | **取り下げ。** 差はエンジンであって設定ではない(対照実験で確認) |

**検索では 10/10 だった構成が、RAG 適合性では 15問中 4問しか正答できなかった。探せることと使えることは別だった。**
