# 設計標準: カスタマイズ性と拡張性

Filetto および後続のマイクロサービス(Chat / Auth)に適用する。

## 原則

> **「MVP だからカスタマイズ性を考慮しない」は認めない。部品として設計する以上、カスタマイズ性と拡張性は常に最優先事項である。**

制定日: 2026-08-12 / 制定者: takenori-kusaka(技術判断者)

## なぜこの原則を置くか

Filetto は単体で完結するプロダクトであると同時に、**後続の Chat / Auth と合成される部品**である。部品として使われるものは、使う側の事情に合わせて設定を変えられなければならない。

段階を理由に拡張点を削ると、次の順で壊れる。

1. 定数として実装される
2. その定数を前提とした呼び出し側が生まれる
3. 設定化しようとすると、呼び出し側もすべて直すことになる
4. 「あとで直す」が返済されない

**拡張点は、あとから足すより先に置くほうが安い。** これは容量の問題ではなく順序の問題である。

## 具体的な要求事項

### 1. 運用に依存する値を定数にしない

利用者・導入先・契約によって変わりうる値は、**デプロイ時に設定できる形**で実装する。ソースコード内の定数にしない。

| 値の性質 | 例 | 扱い |
| --- | --- | --- |
| 契約・規程で決まる | データ保管期限、ゴミ箱の保持期間、バージョンの世代数 | **必ず設定化する。既定値を持ってよいが、定数化してはならない** |
| 環境で決まる | ストレージのパス、ポート、接続先 | 必ず設定化する |
| 仕様で決まる | API のパス、エラーコードの体系 | 定数でよい |

判断に迷う場合は「**この値が導入先ごとに違う可能性はあるか**」で判定する。あるなら設定化する。

### 2. 差し替わる可能性のある実装は境界の背後に置く

実装が1つしかない段階でも、**インターフェースを先に定義する**。

| 境界 | 差し替えの可能性 |
| --- | --- |
| ストレージ(ローカルディスク / S3 / その他) | 高 |
| インデクサ(Graphify / 他の検索エンジン) | 高 |
| バージョン保管(自前 CAS / 外部 VCS) | 中 |
| 認証(JWT の検証方式) | 中 |

**初版で実装を1つに絞ることと、境界を切らないことは別である。** 実装を絞るのは容量の判断であり、境界を切らないのは設計の手抜きである。

### 3. 設定の既定値は「後から大きな注意を要求しない値」に置く

設定できることと、既定値が妥当であることは別の要求である。既定値は、**利用者が何も設定しなかった場合に、後から利用者の注意を奪わずに済む値**とする。

判断の基準は [[calm-technology]] に規定する。安全性(データを失わない)とカーム性(注意を奪わない)が衝突する場合の優先順位も同標準による。

**「安全だから」を理由に無制限の蓄積を既定値にしてはならない。** 静かに溜まり続けるものは、いつか閾値を超えて利用者へ大声で警告することになる。それは安全ではなく、判断の先送りである。

例: ゴミ箱の保持期間の既定値は **30日** とする。無期限(自動削除しない)も設定として選べるが、既定値にはしない。

### 4. 拡張点を削る場合は判断記録を残す

容量の都合で拡張点を落とす判断はありうる。その場合、**ADR に「なぜこの拡張点は不要と判断したか」を記録する**。記録のない削除は認めない。

## レビュー観点

機能仕様(G-4)および技術設計(G-3)のレビューで、次を確認する。

- [ ] 導入先ごとに変わりうる値が、定数として実装されていないか
- [ ] 差し替わる可能性のある実装が、インターフェースの背後に置かれているか
- [ ] 設定の既定値が、最も安全な側に置かれているか
- [ ] 拡張点を落とした箇所に、判断記録があるか
