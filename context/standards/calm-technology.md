# 設計標準: カームテクノロジー

Filetto および後続のマイクロサービス(Chat / Auth)に適用する。

## 原則

> **テクノロジーは、人のアテンション(注意)を必要最小限しか奪ってはならない。**

制定日: 2026-08-12 / 制定者: takenori-kusaka(価値責任者)

利用者の注意は有限で、回復に時間がかかる資源である。機能を足すたびに注意を要求する設計は、機能が増えるほど利用者を疲れさせる。**引き算を先に検討する。**

## 通知の3層構造

通知は次の3層に分類し、**可能な限り下の層へ落とす**。

| 層 | 内容 | 使う場面 |
| --- | --- | --- |
| **Ambient Awareness**(周辺情報) | 利用者が見に行ったときにだけ目に入る。割り込まない | **既定。ほとんどの情報はここに置く** |
| **Status Tones**(短いシグナル) | 控えめな非言語のシグナル。一度だけ注意を引く | 利用者の操作に対する即時の応答など、限定的な場面 |
| **Status Shouts**(緊急警告) | 明示的に注意を奪う | **データが失われる、または回復不能な状態に入る直前のみ** |

出典: Amber Case, *Calm Technology* (O'Reilly, 2015) 第3章の通知パターン分類による。アテンションの最小化と周辺化(periphery)の考え方そのものは Mark Weiser の原典に基づく。

## 具体的な要求事項

### 1. 「今は静かだが、後で叫ぶ」設計を作らない

**最も避けるべきは、静かに悪化して、ある日突然大声で警告する設計である。**

例: ゴミ箱の保持を無期限にすると、ディスクは静かに埋まり続け、ある日「容量が足りません」という Status Shout として突然噴出する。これは「今は通知していない」だけであり、カームではない。**注意の要求を先送りして、利息をつけて返させている。**

| 判定 | 設計 |
| --- | --- |
| カーム | 蓄積しない。または蓄積が利用者の目に入る場所に静かに表示され続ける |
| **カームでない** | 静かに蓄積し、閾値を超えた時点で警告する |

### 2. 既定値は「後から大きな注意を要求しない値」とする

利用者が何も設定しなかった場合に、**後から利用者の注意を奪わずに済む値**を既定値とする。

**安全性(データを失わない)と、カーム性(注意を奪わない)が衝突する場合は、次の順で判断する。**

1. 回復不能な損失が生じる設計は採らない(安全性が優先)
2. そのうえで、注意の要求が最も小さい値を選ぶ
3. どちらも満たせない場合は、**利用者が設定で選べるようにし、既定値はカーム側に置く**

「安全だから」を理由に無制限の蓄積を既定値にしてはならない。それは安全ではなく、判断の先送りである。

### 3. 利用者に管理タスクを暗黙に課さない

「利用者が定期的に手動で片付ける」ことを前提とした設計は、**利用者のタスクリストに項目を1つ増やす**行為である。自動で処理できるものは自動で処理する。

自動処理が危険な場合のみ、利用者の操作を求める。その場合も Ambient に留める。

### 4. 数値化できない価値を、数値の下に置かない

指標に表れない利用者の体験(操作の心地よさ、静けさ、迷わなさ)を、測定可能な指標の劣後に置かない。**測れないことは、価値がないことを意味しない。**

## レビュー観点

機能仕様(G-4)および技術設計(G-3)のレビューで、次を確認する。

- [ ] この機能が要求する通知は、3層のどこに置かれているか。**より下の層へ落とせないか**
- [ ] Status Shouts を使う場合、**データの損失または回復不能な状態が直前にあるか**
- [ ] 静かに蓄積して、後で警告することになる資源(ディスク・ログ・キュー・履歴)はないか
- [ ] 既定値は、後から利用者の注意を要求しない値になっているか
- [ ] 利用者に定期的な手動作業を暗黙に課していないか
