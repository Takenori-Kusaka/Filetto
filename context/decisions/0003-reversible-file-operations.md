# ADR-0003: ファイルの破壊的操作をすべて可逆にする

## ステータス

採用(2026-08-12)

## コンテキスト

`/process-init` のテーラリングで安全重要度 CL1(個人の権利や利益に実質的な影響が及ぶ)を選んだところ、不変条件「CL1 を1〜2名の体制で扱えない」により拒否された。

そこで**回答を書き換えるのではなく、プロダクトの設計を変えて危害の帰結そのものを下げる**判断を採った。すなわち、削除・リネーム・移動・上書き更新を可逆にすることで、最悪の故障の帰結を「経済的な損失や業務の中断にとどまる(CL0)」へ実際に下げる。

**この ADR は、安全重要度を CL0 とした根拠そのものである。** 本 ADR の決定が失われると、`process.config.json` の `q-criticality: cl0` が事実と合わなくなり、プロセス構成の前提が崩れる。

破壊的操作の経路は2つある。

| # | 経路 | 呼び出す主体 |
| --- | --- | --- |
| ① | WebUI のファイル操作 | 人 |
| ② | MCP のツール呼び出し | AI エージェント |

②が存在することが本プロダクト固有の事情である。人に確認を求める UI は、AI が呼ぶ経路には存在しない。

なお企画の口述では「更新履歴、Git 必須」とも述べられていたが、**PDF・Office 文書のようなバイナリは Git の差分ベース・スナップショット方式と構造的に相性が悪い**(コミットのたびにリポジトリが肥大化し、意味のある差分表示もマージもできない)。この課題は Git 本体だけでなく後付けの Git LFS にも共通する。したがって Git は採らない。

## 決定

### 1. 破壊的操作をすべて可逆にする

| 操作 | 可逆性の担保 |
| --- | --- |
| 削除 | 論理削除(ゴミ箱へ移動)。**物理削除の API を公開しない** |
| リネーム | 操作履歴を保持し、元の名前へ戻せる |
| 移動 | 操作履歴を保持し、元の場所へ戻せる |
| 上書き更新 | 旧版をバージョンとして保持する |

### 2. 削除は経路によらずゴミ箱へ入る

- ①②のいずれの経路でも、削除は**ゴミ箱への移動**として実装する。実装は1本にする
- ①では加えて確認ダイアログを表示する。**ただし確認ダイアログは可逆性の担保手段ではない**。誤操作の一次抑止にすぎない
- ②では確認を求めない。求めても AI が承諾するだけであり、抑止にならない

**CL0 の根拠を経路に依らせない。** 経路ごとに可逆性の水準が変わる設計にすると、経路が増えるたびに安全重要度の再評価が必要になる。

### 3. ゴミ箱の中身は検索インデックスから完全に除外する

- 通常の検索、MCP 経由の検索、いずれの結果にも含めない
- 削除済みのファイルが AI の参照対象に残ることを防ぐ
- 復元はファイル名と階層をたどって行う(ゴミ箱の一覧表示)

### 4. 保持期間は定数化しない

**データ保管期限は顧客との契約で決まるため、コード内の定数にできない。**

| 項目 | 決定 |
| --- | --- |
| 設定方法 | デプロイ時の設定(環境変数)で指定する |
| 既定値 | **無期限(自動削除しない)** |
| 既定値の根拠 | 設計標準「設定の既定値は最も安全な側に置く」による。ディスクを消費するが、データが消えるより損害が小さい |

バージョンの世代数・履歴の保持期間についても同様に設定化する。

### 5. バージョン保管はインターフェースの背後に置く

`VersionStore` に相当するインターフェースを定義し、実装を差し替え可能にする。

- **初版の実装**: 自前の軽量な内容アドレス保管(content-addressable store)。実体をハッシュで保管し、バージョン履歴はメタデータ DB で持つ。同一内容の重複を排除する
- **外部 OSS への依存を初版では持たない**。`docker compose up` 一発で起動し、維持費 0 円という前提を守るため
- 将来の差し替え候補は下記「検討した選択肢」に記録する

## 検討した選択肢

### 削除の可逆性について

| 案 | 採らなかった理由 |
| --- | --- |
| 物理削除のみ(確認ダイアログで担保) | AI エージェントが MCP 経由で削除を呼ぶ経路がある以上、人に確認を求める UI では守れない。また安全重要度を CL0 に下げられない |
| ①のみゴミ箱、②は削除 API を提供しない | AI に削除させない選択もありうるが、ファイル操作が一級市民という本プロダクトの位置づけと合わない |
| 両方にゴミ箱を課す(採用) | — |

### バージョン管理の実現方式について

判定者による調査結果(2026-08-12)にもとづく。

| 案 | ライセンス | 採らなかった理由 |
| --- | --- | --- |
| **Git / Git LFS** | MIT | PDF・Office 文書のようなバイナリは Git の差分ベース・スナップショット方式と構造的に相性が悪い。コミットのたびに肥大化し、意味のある差分表示もマージもできない。Git LFS はポインタ方式で仕組みが複雑化し、バイナリ実体と履歴が分離される。重複排除やチャンク単位の差分転送に対応していない |
| **git-annex** | GPL-3+(一部 AGPL) | CLI 中心で学習コストがあり、非エンジニアには扱いにくい。最新版取得の仕組みが複雑。本プロダクトの対象利用者と合わない |
| **Subversion** | Apache-2.0 | オフライン作業ができない。複数の大容量バイナリを同時に扱うと性能が劣化する。ファイルロックは有用だが、個人セルフホストの単一利用者には不要 |
| **Clustta** | MIT 系 | コミュニティ・実績がまだ小さく、企業導入事例やドキュメントが少ない。依存として抱えるには早い |
| **Lore (Epic Games)** | MIT | 設計は本件の要求に最も近い(内容アドレス方式、Merkle ツリー、FastCDC によるチャンク単位の重複排除、完全オフライン)。**ただし 2026-08 時点で v0.8 台のプレ 1.0 段階**であり、エコシステムが未成熟。初版の依存として抱えると、外部プロジェクトの成熟度が本プロダクトの中止条件を引く。**v1.0 到達時に再評価する** |
| **DVC** | Apache-2.0 | Git 依存であり、1万オブジェクト超で性能が落ちる。データサイエンス向けのワークフローが主眼で、汎用ファイル倉庫の用途と合わない |
| **lakeFS** | Apache-2.0 | オブジェクトストア前提の制御面であり、ローカルディスク前提の個人セルフホストには重い |
| **SeedDMS / LogicalDOC** | 各種 | DMS 製品であって部品ではない。Filetto の中へ組み込む対象にならない |
| **ストレージ層の機能(S3 バージョニング / ZFS・Btrfs スナップショット)** | — | 実装は軽いが、初版のローカルディスク前提では環境依存が強すぎる。利用者に特定のファイルシステムを要求できない |
| **自前の軽量 CAS(採用)** | — | — |

理由欄は判定者(takenori-kusaka / 技術判断者)が記入した(2026-08-12)。

## 可逆性

| 項目 | 内容 |
| --- | --- |
| 後から変えられるか | **変えられる**(実装)/ **変えにくい**(方針) |
| 変えるとしたら必要なこと | 実装(自前 CAS)の差し替えは `VersionStore` インターフェースの背後で行えるため安い。**一方、「破壊的操作を可逆にする」という方針そのものを外すと、安全重要度が CL1 へ戻り、1〜2名体制では扱えなくなる**(`/process-init` の不変条件)。方針の変更は体制の変更を伴う |
| いつまでなら安く変えられるか | 実装の差し替えはいつでも。Lore の採用可否は同プロジェクトの v1.0 到達時に再評価する |

## 非機能への影響

| 項目 | 影響 |
| --- | --- |
| 性能 | 削除が O(1) のメタデータ更新になり、物理削除より速い。上書き更新時にハッシュ計算が入るため、書き込みは遅くなる。大容量ファイルでは体感しうる |
| 可用性 | 影響なし |
| セキュリティ | **ゴミ箱の中身にもアクセス制御が必要**。削除したファイルが権限の緩い経路から読めてはならない。JWT クレームによるスコープ制御は、ゴミ箱内にも同じ規則で適用する |
| 運用 | **ディスク消費が増える**。既定値が無期限であるため、放置すると単調に増加する。ゴミ箱の使用量を UI で可視化し、利用者が明示的に空にできる手段を必ず提供する |

## 事業への影響

| 項目 | 内容 |
| --- | --- |
| 顕在化が分かる兆候 | ゴミ箱・バージョン保管の使用量が、実データの使用量を超えること。または利用者から「ディスクが足りない」という報告が出ること |
| 回復に要する時間 | **1日**(ゴミ箱を空にする手段と使用量の可視化は既に備えるため、運用で回復できる) |
| 影響を受ける利用者・業務 | ディスク容量に余裕のない環境で運用する利用者。大容量ファイルを頻繁に更新する利用者 |

## 影響

**この決定によって得られるもの:**

- 安全重要度を CL0 として扱える。1〜2名の体制でプロセスを回せる
- AI エージェントに削除を許可できる。可逆でなければ、MCP から削除ツールを提供する判断自体ができない
- 保持期間が設定化されるため、契約で保管期限が定まる導入先へも展開できる

**トレードオフ:**

- **ディスク消費が単調に増加する**。既定値を無期限としたため、利用者が明示的に空にするまで減らない
- **上書き更新のたびにハッシュ計算が入る**。大容量ファイルでは書き込み性能に影響する
- **実装量が増える**。物理削除なら1行で済むものが、ゴミ箱・復元・一覧・使用量表示・設定読み込みの一式になる

**この決定で解決しないこと:**

- **バージョン間の差分表示**は本 ADR の対象外。「旧版に戻せる」ことのみを保証し、「何が変わったか」を見せる機能は定義していない。必要になった時点で別 ADR とする
- **同時編集の排他制御(ファイルロック)**は対象外。初版はシングルユーザー前提であり、必要になるのは Auth を合成した後
- **バージョンの分岐(ブランチ)**は対象外。直線的な履歴のみを扱う
- Lore の採用可否は先送りしている。同プロジェクトが v1.0 に到達した時点で再評価する
