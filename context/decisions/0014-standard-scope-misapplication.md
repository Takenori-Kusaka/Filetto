# ADR-0014: 標準の条項を適用範囲ごと確認してから課す

## ステータス

採用(2026-08-13)

## コンテキスト

2026-08-13 の G-3 判定で、判定者から次の指摘を受けた。

> **決裁者は読んでハンコ押す、が JTC プロセスとして適当だと思います。そもそも理由を記載させるのもよくわかりません。PO 含むプロダクトチームが決裁直前まで進めて方針や策定をほぼ完了させ、最後 OK と一言もらうのが決裁です。**

**確認したところ、指摘のとおりだった。** PO は標準の 5.7.3 を適用範囲を確かめずに全体へ課しており、**判定者に理由の記入という作業を課していた。**

### 何を取り違えたか

標準 第5章 5.7.3 の全文である。

```
### 5.7.3 選択肢の比較

リスク区分 R1 の決定、および例外承認では、2案以上の比較を経た記録を求めます。
単一の案に対する承認は、判断ではなく追認です。

- AIエージェントは、複数の案と、それぞれのリスクの見積を提示できる
- どの案を選ぶかの理由は、人間が記入しなければならない。この記入をAIに生成させてはならない
```

**冒頭に「リスク区分 R1 の決定、および例外承認では」という限定がある。** 本案件は安全重要度 CL0 であり、**R1 ではない。**

**PO は箇条書きの2行だけを読み、限定の1行を落とした。**

### 何が起きたか

| # | 事象 | 影響 |
| --- | --- | --- |
| 1 | ADR-0005 で案A の理由欄を空欄にして提出した | 判定者に記入作業が発生した |
| 2 | D-0 v1.2 の技術判断者の移譲を撤回した | **撤回の根拠が誤っていた** |
| 3 | D-0 v1.3 で摩擦3(空欄のまま採用としない)を課した | **G-3 の判定が成立しない条件として扱った** |
| 4 | ADR 3本の理由欄44行を「判定の本体」と説明した | **判定者に44行の記入を求めた** |
| 5 | G-3 判定後に「判定は成立していない」と申告した | **成立していた判定を、成立していないと述べた** |

**5 が最も重い。** 判定者が正しく判定した工程を、PO が誤った根拠で否定した。

## なぜ起きたか — なぜなぜ分析

| 段 | 問い | 答え |
| --- | --- | --- |
| 1 | なぜ判定者に記入作業を課したか | 5.7.3 を全体に適用したため |
| 2 | なぜ全体に適用したか | **適用範囲の1行を読まなかったため** |
| 3 | なぜ読まなかったか | **箇条書きの禁止文だけを探して読んだため**。「AI に生成させてはならない」という文言が目的に合致し、そこで読むのを止めた |
| 4 | なぜ禁止文だけを探したか | **v1.2 の移譲を撤回する根拠を探していたため**。既に「撤回すべきだ」という結論を持って読んだ |
| 5 | **なぜ結論を持って読んだか** | **標準チームから「5.5 は規定である」という見解を受け、自分の解釈が誤っていたと理解した直後だったため。** 誤りを正そうとする動きが、**次の誤りを生む方向に働いた** |

**根本原因は「誤りを指摘された直後に、逆方向へ過剰に振れたこと」である。**

同じ機序が本案件で繰り返されている。

| 事象 | 過剰に振れた方向 |
| --- | --- |
| ロール越境を指摘された | **自分の職務まで差し戻すようになった**(判定の分割、チャネルの記入、G-2 の再判定の可否) |
| 5.5 の解釈の誤りを指摘された | **5.7.3 を過剰適用した**(本件) |

**指摘を受けた直後の判断は、逆方向へ振れやすい。**

## 決定

### 1. 標準の条項を課す前に、適用範囲を確認する

**条項の冒頭・節の見出し・章の前提を読む。** 箇条書きだけを根拠にしない。

**確認すべきもの**

| # | 確認 |
| --- | --- |
| 1 | その条項に**適用範囲の限定があるか**(リスク区分・ゲート・成果物の種別) |
| 2 | 限定がある場合、**本案件がその範囲に入るか** |
| 3 | 入らない場合、**課さない** |

### 2. 標準の条項を D-0 や運用へ課すときは、条項番号と適用範囲を併記する

**「5.7.3 による」とだけ書かない。**

```
悪い例: どの案を採るかの理由は技術判断者が記入する(5.7.3)
良い例: どの案を採るかの理由は技術判断者が記入する
        (5.7.3。ただし同条は「リスク区分 R1 の決定、および例外承認」に
         限定されており、本案件は CL0 のため適用されない)
```

**適用範囲を書けない条項は、課さない。**

### 3. 誤りを認めたターンでは、元に戻すことしかしない

**「疑う」では行動にならない。** 本節は行動として書く。

#### 発動条件(いずれかに当てはまるとき)

| # | 条件 |
| --- | --- |
| 1 | 直前のやり取りで、**自分の判断・記述・解釈の誤りを認めた** |
| 2 | 直前のやり取りで、**自分の成果物が差し戻された** |
| 3 | 直前のやり取りで、**自分の越権・過剰を指摘された** |

#### そのターンで行ってよいこと

| 行ってよい | 行ってはならない |
| --- | --- |
| **誤った記述を、誤る前の状態へ戻す** | **新しい制約・禁止・要求を追加する** |
| 誤りの事実を記録する | 新しい様式・チェックリスト・欄を追加する |
| 影響範囲を洗い出す | **既存の制約を強める** |
| **戻せない場合、その旨を記録する** | 「再発防止のため」を理由に手続を増やす |

**「再発防止策を講じる」ことも、同じターンでは行わない。** 分析と記録までとし、**策を講じるのは次のターン以降とする。**

#### 次のターン以降に制約を課す場合

**課す前に、次の3点を書く。**

| # | 書くこと |
| --- | --- |
| 1 | **その制約が無かった場合に、具体的に何が起きるか** |
| 2 | 適用範囲(決定2 による) |
| 3 | **その制約によって誰の作業が増えるか** |

**3 を書けない制約は課さない。** 本件で課した摩擦3 は、**判定者の作業を44行増やしていた。** 課す時点でそれを書いていれば、気づけた。

#### なぜ「同じターンで行わない」が効くか

**過剰は、誤りを正そうとする勢いから生じる。** 本 ADR の5段目の分析がそれを示している。

**勢いは、ターンをまたぐと弱まる。** 弱まった状態で同じ制約を課そうと思えるなら、その制約は勢いによるものではない。

### 4. 決裁の性質を記録する

**R2 / R3 の通常の決定では、決裁者はプロダクトチームが方針をほぼ完了させた状態を読んで承認する。**

| 決裁者に求めること | 求めないこと |
| --- | --- |
| 読んで承認する | **理由を記入する** |
| 疑義があれば理由をつけて質問する | 選択肢を比較する |
| 条件を付す | 代替案を評価する |
| 差し戻す | |

**上表は R2 / R3 の通常の決定に限る。** 当初この限定を書かなかったことが誤りだった(標準チームの指摘、2026-08-13)。

| 場面 | 求めるもの |
| --- | --- |
| **R1 に該当する変更** | **5.7.3 により理由の記入を求める** |
| **例外承認**(第7章 7.3) | 同上 |
| **G-8 / SG** | **5.7.1 の胆識。5.7.2 の決断の記録**(確認した事項 / **確認していない事項** / 判断が変わる条件 / 受容したリスク)。**自由記述の理由ではなく構造化された欄である** |
| R2 / R3 の通常の決定 | 上表のとおり |

**リスク区分の確定は人間が行う**(3.8.1)。**AI は草案までである。**

### R1 の判定が要る ADR(洗い出しのみ。判定はしない)

**本 ADR の作成時点で、R1 に該当しうる ADR を列挙する。** **確定は人間が行う。**

| ADR | R1 の該当条件との対応 | 判定 |
| --- | --- | --- |
| **ADR-0004 JWT クレーム契約** | **「認証・認可の取扱いに影響する」に正面から当たる** | **未判定** |
| ADR-0002 対外インターフェース契約 | 「公開インタフェース」 | **未判定** |
| ADR-0010 データベース層 | 「データ形式」に触れうる | **未判定** |
| ADR-0011 OCR の誤り訂正と図表 | いずれにも当たらないと見える | **未判定** |
| ADR-0008 Lore を VersionStore に | 保管形式は内部。外部との契約ではない | **未判定** |

**R1 と判定された ADR では 5.7.3 が適用され、理由の記入は人が行う。**

### 5. 課した制約を定期的に棚卸しする

**過剰に課した制約は、課した時点では気づけない。** 本件は**判定者からの指摘でしか露見しなかった。**

| # | 棚卸しの手順 |
| --- | --- |
| 1 | `docs/D-0-governance.md` と各セッション定義から、**標準の条項を根拠に課した制約を列挙する** |
| 2 | 各制約について、**根拠の条項に適用範囲の限定があるか**を確認する |
| 3 | 限定があり、本案件が範囲外のものを**外す** |
| 4 | 外した記録を残す |

**時期**: D-0 の定期レビュー(次回 2026-11-12)に合わせる。**この手続を自動化しない**(標準 5.7.4)。

## 検討した選択肢

| 案 | 採らなかった理由 |
| --- | --- |
| **A. 5.7.3 を全体へ適用したまま維持する** | 標準の適用範囲を超えて制約を課すことになる。**本案件では実際に判定が止まりかけた。** 標準より厳しくすること自体は許容されるが、**それを「標準の要求」と偽ることは許容されない** |
| **B. 5.7.3 の要求を全面的に外す** | **例外承認(第7章 7.3)では適用される。** 全面的に外すと、判定基準を満たさないまま進める場合の歯止めが消える |
| **C. 適用範囲ごと確認してから課す(採用)** | — |

理由欄は価値責任者(takenori-kusaka)が記入した(2026-08-13)。

## 影響

**この決定によって得られるもの:**

- **標準より厳しい制約を、標準の要求と偽らなくなる**
- 判定者に不要な作業を課さなくなる
- **指摘を受けた直後の過剰な振れを、記録として持てる**

**トレードオフ:**

- **条項を課すたびに確認の手数が増える**
- **「念のため厳しくしておく」ができなくなる。** 厳しくする場合は、本案件の判断として明示することになる

**この決定で解決しないこと:**

- **既に課した制約の棚卸し**は本 ADR の対象外。D-0 v1.4 で摩擦3 を削除したが、**セッション定義と各 ADR の記述は別途見直す**
- **標準の記述の読みやすさ**は標準側の課題。[process-compass へ論点として返す](https://github.com/Takenori-Kusaka/process-compass/issues)
- **逆方向への過剰を機械的に検出する手段は無い。** 決定3 は指示への遵守に依存する。`CLAUDE.md` は「指示への遵守だけに依存しません」と定めており、**本 ADR はその水準に達していない**
- **決定3 の発動条件は、自分が誤りを認めたかどうかに依存する。** 気づかない誤りには効かない
