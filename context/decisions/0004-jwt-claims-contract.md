## コンテキスト

Filetto は JWT クレームを検証してファイルアクセススコープを制御する。認証基盤そのもの(ユーザー登録・パスワード管理・多要素認証)は別マイクロサービス Auth の責務であり、**Filetto は JWT を発行しない**(F-003 基準27)。

本 ADR は G-3 の判定対象であり、**F-003 基準24〜27 が本 ADR に依存する**(F-003 前提2)。また [ADR-0002](./0002-external-interface-contract.md) が本 ADR へ引き継いだ論点が2つある。

| 引き継がれた論点 | 出典 |
| --- | --- |
| 署名付き URL の署名方式・有効期限 | ADR-0002 決定3 / 影響 |
| MCP の2つの認証モデル(HTTP の OAuth 2.1 / stdio の環境からの取得) | ADR-0002 決定4 |

決めるべき論点は3つある。

| # | 論点 |
| --- | --- |
| 1 | クレーム名 — 独自クレームをどの名前空間・どの命名規則で置くか |
| 2 | スコープの表現 — ファイルアクセススコープをクレーム値としてどう表現するか |
| 3 | 検証の責務分界 — 何を Filetto が検証し、何を Auth が担うか |

### 判定の前に解決を要する矛盾(TA-0004 §2)

**調査の過程で、既存の受入基準・ADR に5件の矛盾または未決が見つかりました。** いずれも本 ADR の内容を左右します。

#### 2-1. 初版にトークンの発行者が存在しない(最も重い)

| 事実 | 出典 |
| --- | --- |
| JWT が付与されていない要求には HTTP 401 を返さなければならない | F-003 基準24 |
| **システムは JWT の発行を行ってはならない** | F-003 基準27 |
| 認証基盤は別マイクロサービス Auth の責務。**Auth は Filetto 完了後に開発する** | F-003 スコープ外 / P-001 |

**この3つは同時に成立しません。** 初版を `docker compose up` で起動した利用者は、JWT を発行する主体を持ちません。基準24 に従えばすべての要求が 401 になり、**「1コマンドで立てられ、ファイルを置いた瞬間から検索可能になる」(P-001 案件の目的)が初版で成立しません。**

**PO 判断済み: 方向イ(認可の適用有無を設定で切り替え、既定は適用しない)**(Issue [#55](https://github.com/Takenori-Kusaka/Filetto/issues/55))。**基準24 を条件付きにする改訂を伴い、G-2 の再判定を要します**([#58](https://github.com/Takenori-Kusaka/Filetto/issues/58))。

TA-0004 が挙げた4方向を、判定の材料として残します。

| # | 方向 | 触れる基準 |
| --- | --- | --- |
| ア | 利用者が自分で JWT を作り、環境変数で与える | 基準24 は満たす。**利用者に鍵管理を課す**([[calm-technology]] と緊張) |
| **イ(PO 判断済み)** | **認可の適用有無を設定で切り替える(既定は適用しない。localhost bind を前提)** | **基準24 を条件付きにする改訂が要る** |
| ウ | 「発行しない」を「利用者向けの認証情報の発行を行わない」と読み替える | 基準27 の改訂が要る |
| エ | 初版では認可を実装せず、Auth の合成時に導入する | 基準24〜27 を初版のスコープから外す改訂が要る。ADR-0003 と衝突 |

**この論点は論点3 と不可分です。** 論点3 の各案は、この答えによって成立の可否が変わります。

#### 2-2. 基準6(404)と基準25(403 + 存在秘匿)が矛盾する

**404 と 403 を打ち分けた時点で「403 = そのファイルは存在する」と判別できます。**

**PO 判断済み: 404 で統一**。[PR #62](https://github.com/Takenori-Kusaka/Filetto/pull/62) で F-003 基準25 を改訂しました。

**ただし本 ADR は、なお決める必要があります。** ADR-0002 決定2-1 の3状態(利用可能 / ゴミ箱 / 存在しない)のうち、**ゴミ箱にあるファイルへスコープ外からアクセスしたとき何を返すか**は、ADR-0002 にも ADR-0003 にも書かれていません。

#### 2-3. 対外へ出す「スコープの対象単位」が決まっていない

ADR-0002 決定2 は安定 ID の発行規則を「パスが初めて索引に入った時点で発行する」と定めています。**これはファイル単位の記述であり、ディレクトリに安定 ID を発行するかは書かれていません。**

論点2 のうち対象をディレクトリ(ルート)で指す案は、**ディレクトリ側の安定 ID が存在することを前提とします。** 存在しない場合、その案は **ADR-0002 の改訂を伴う案**になります。

**本 ADR の決定2-3 で決めます。**

#### 2-4. 「実行時の外部通信なし」に同一 `docker compose` 内の通信が含まれるかの定義がない

P-001 の記述は外部 API・クラウド推論への依存の不在を指しており、**同一ホスト内のプロセス間通信を禁じたものとは読めません。** 実際 ADR-0008 で `loreserver` への常駐接続を受け入れています。**しかし正本にその定義がありません。**

F-003 基準12 は「システムは**検索の実行時に**外部ネットワークへ接続してはならない」と対象を検索に限定しており、認可の経路には及んでいません。

**下位論点3-1(鍵配布を JWKS 取得で行うか)は、この定義に依存します。本 ADR の決定2-4 で決めます。**

#### 2-5. ADR-0002 決定3 と F-003 基準13・14 が矛盾する

**本 ADR の対象外です。** PO 判断済み(ADR-0002 決定3 を正とする)。[PR #62](https://github.com/Takenori-Kusaka/Filetto/pull/62) で F-003 基準13・14・15 を改訂し、基準28 を追加しました。

### 実装ライブラリに関する事実(TA-0004 §6)

**ライブラリ選定は本 ADR の論点ではありませんが、下位論点3-1 の判断材料になります。**

| ライブラリ | 状態(2026-08-13 時点) |
| --- | --- |
| PyJWT | **CVE-2026-48526(high)。公開鍵 JWK が HMAC の秘密鍵として受理され HS256 で偽造できる** |
| Authlib | CVE-2026-27962(critical)署名検証バイパス / CVE-2026-28802(high)`alg: none` |
| python-jose | **実質メンテナンス停止**。依存の `ecdsa` に未修正の high |

**CVE-2026-48526 は、RFC 8725 §2.1 が記述した攻撃が 2026年に主要ライブラリで成立したことを示します。** 対称鍵と非対称鍵を同一システムで併用する構成が攻撃面を作るという事実であり、**下位論点3-1 に直接効きます。**

**PyJWT と `cryptography` は PEP 639 移行で `License ::` classifier を削除済みです。** classifier のみを読む検査系では `UNKNOWN` 判定になり、**ADR-0007 の暫定回避策はこの2件に効きません。** 別途 Platform へ回す対象です。

## 検討した選択肢

**理由欄は技術判断者が記入します。以下の表の左2列は案の列挙と性質の整理であり、採否の推奨を含みません。**

### 論点1: クレーム名

| 案 | 性質(TA-0004 §3) | 採らなかった理由 |
| --- | --- | --- |
| 1-A 独自クレームを置かず IANA 登録済みの `scope` のみ | 標準への準拠が最も高い。トークンサイズ最小。可逆性 高。**Okta の `scp` 問題は残る** | |
| 1-B URI 名前空間を持つ Public Claim Name をフラットに置く | RFC 7519 §4.2 の Public Name。トークンサイズ 大。可逆性 中。**Keycloak で要エスケープ** | |
| 1-C 短い Private Claim Name | RFC 9068 §2.2 の例外に依拠。サイズ 小。**可逆性 低〜中。Auth0 で黙殺されうる** | |
| 1-D 単一の名前空間キーの配下にオブジェクトで束ねる | RFC 7519 §4.2 の Public Name。サイズ 中。可逆性 中〜高。**Keycloak で要エスケープ** | |
| 1-E RFC 9396 の `authorization_details` を用いる | IANA 登録名を使う。サイズ 大。可逆性 中。**RAR 対応 IdP が少ない** | |

**案1-A と案1-D / 1-E は併用できます**(標準クレームで `scope`、名前空間で追加情報)。**案の選択は排他ではありません。**

### 論点2: スコープの表現

| 案 | 性質(TA-0004 §4) | 採らなかった理由 |
| --- | --- | --- |
| 2-A 動詞のみの粗いスコープ。対象範囲は JWT に載せない | 日本語パス・スペース入りパス・移動改名の影響なし。ゴミ箱へ適用可。トークンサイズ 最小。**部分委譲ができない** | |
| 2-B 動詞 × 対象識別子を scope 文字列の1トークンへ詰める | パスの影響なし。安定 ID なら移動改名に耐える。ゴミ箱へ適用可。部分委譲できる。サイズは対象数に比例 | |
| 2-C 構造化クレームで {対象識別子 × 操作} を表現する | 日本語パス・スペース入りパスを表現できる。安定 ID なら移動改名に耐える。ゴミ箱へ適用可。部分委譲できる。サイズは対象数に比例 | |
| 2-D パス接頭辞をスコープ値に入れる | **日本語パス・スペース入りパスを表現できない。移動・改名で壊れる。ゴミ箱へ適用できない**。部分委譲できる。サイズはパス長に比例 | |

**対象をディレクトリで指す案は 2-3(ディレクトリの安定 ID)の決定に依存します。**

### 論点3: 検証の責務分界

| 案 | 性質(TA-0004 §5.3) | 採らなかった理由 |
| --- | --- | --- |
| 3-A Auth が細粒度スコープを発行し、Filetto は検証のみ | **Auth と Filetto の疎結合を捨てる。** Auth が Filetto の内部構造を知る必要がある。**可逆性 低**(2サービスにまたがる契約)。MCP の Common Mistakes「トークン内の scope をサーバ側の認可ロジックなしに十分とみなす」に該当しうる。**ADR-0002 決定2-2 が置いた境界の考え方と逆向き** | |
| 3-B Auth は主体と粗い権限のみ発行し、Filetto がローカルポリシーで解決 | **「JWT を見れば何が許されるか分かる」性質を捨てる**(監査でポリシーの版を併せて記録する必要)。**可逆性 高**(対外契約を変えずに差し替えられる)。**ポリシーの保管先が認可の正本になり保護が要る。** シングルユーザーの初版ではポリシーが1件しかなく、[[extensibility]] 要求4 の対象になる | |
| 3-C 前段に認可プロキシを置き、Filetto は認証済みを前提に動く | **F-003 基準24 を Filetto 自身が満たさなくなる。** 単体 OSS としての完結性を捨て、**コンテナが +1**。可逆性 中。**プロキシを迂回する経路が残ると認可が完全に無効になる。基準24〜27 の大幅な改訂が要る** | |

#### 下位論点3-1: 署名鍵の配布

| 案 | 性質(TA-0004 §5.4) | 採らなかった理由 |
| --- | --- | --- |
| (a) HS256 の共有鍵を環境変数で配布 | **検証と発行の分離を捨てる**(同じ鍵で発行できる)。$0 / 通信なし。可逆性 高。**RFC 8725 §2.2(弱い対称鍵)。基準27 の読みが確定しないと成立の可否が決まらない** | |
| (b) 非対称鍵の公開鍵を環境変数で静的配布 | **鍵ローテーションの自動化を捨てる**(手動更新)。$0 / 通信なし。可逆性 高。**ローテーション手順が利用者の管理タスクになる**([[calm-technology]]) | |
| (c) 非対称鍵 + JWKS を Auth から取得 | **Auth からの独立性を捨てる**(検証が Auth の可用性に依存)。$0 / **同一 compose 内の通信(定義が未確定 → 決定2-4)**。可逆性 中。**F-001 基準22(loreserver 停止時も検索を継続)と同じ考え方から見て一貫しない** | |

**(a) と (b)(c) を併用する構成は攻撃面を自ら作ります**(PyJWT CVE-2026-48526)。**どちらか一方に固定するか両方を許すかが、この攻撃面の有無を決めます。**

**MCP 仕様は (c) の方向を要求しています**(RFC 9728 Protected Resource Metadata の実装を MUST)。**ただしこれは「MCP の HTTP トランスポートを OAuth 2.1 のリソースサーバとして提供する場合」の要求であり、Filetto が MCP の認可仕様に準拠すると宣言するかどうか自体がこの論点の一部です。**

#### 下位論点3-2: 署名付き URL の権限表現

| 案 | 性質(TA-0004 §5.5) | 採らなかった理由 |
| --- | --- | --- |
| (a) JWT 自体をクエリ文字列に載せる | 体系の分離を捨てる。**可逆性 低。F-003 非機能の2項目(署名付き URL をログへ出力しない / JWT をログへ出力しない)に同時に触れる。** ブラウザ履歴・Referer・プロキシログへ残る。**URL の漏洩が API 全体の権限漏洩になる** | |
| (b) 対象1件・操作1つ・短命の別 HMAC 署名(S3 型) | 体系の一本化を捨てる(鍵が2種類)。**可逆性 高**(体系が Filetto 内部に閉じる)。**生成時点の権限が期限まで凍結され、剥奪後も URL が生き残る** | |
| (c) `aud` を配信エンドポイントに固定した短命の子 JWT | 単純さを捨てる。可逆性 中。**RFC 8725 §3.12(同一発行者が複数種類の JWT を出すなら検証規則は相互排他でなければならない MUST)への対応が必須。基準27「JWT の発行を行ってはならない」と正面から衝突する** | |

#### 下位論点3-3: stdio の扱い

**MCP 仕様は「stdio を用いる実装は本仕様に従うべきではなく(SHOULD NOT)、代わりに環境から資格情報を取得すべきである」と定めています。**

| 案 | 性質(TA-0004 §5.6) | 採らなかった理由 |
| --- | --- | --- |
| (a) stdio でも JWT を環境変数から読み、HTTP と同じ検証を通す | 仕様の推奨からの逸脱ではないが、**stdio 利用者に鍵管理を課す**。2-1 の発行者不在問題が stdio でも同じく発生する | |
| (b) stdio はプロセス境界を信頼し、認可を適用しない | **F-003 基準21・基準26 の一貫性を捨てる。ADR-0003 の「削除したファイルが権限の緩い経路から読めてはならない」に正面から抵触する** | |
| (c) stdio 用の資格情報を Filetto が起動時に生成する | **F-003 基準27 と衝突する**(2-1 の方向ウと同じ) | |

**ADR-0002 決定4 は「認証モデルが異なるため実装は分岐する」とトレードオフに明記しています。** 本 ADR はこの分岐を具体化する必要があり、**F-003 基準21 がツール定義に限られ認可の規則に及ばないのかを確定させる必要があります。**

- 論点1 のクレーム名は、**第三者が自分の IdP 設定へ名前を書き込んだ時点**で変えにくくなる
