## コンテキスト

### なぜいま決めるのか

価値責任者が G-2 のレビューで F-002 のスコープ外2件を指摘した。

| # | 指摘 |
| --- | --- |
| 1 | **OCR の誤字・脱字をスコープ外にして簡単に諦めすぎている。** 日本語の誤字脱字チェッカーの OSS があるのではないか |
| 2 | **図・グラフを画像のまま RAG へ渡す運用があるのではないか。RAG のベストプラクティスをちゃんと調査したのか** |

**2件とも当たっていた。特に2 は、スコープ外の前提そのものが崩れている。**

### 論点2 — スコープ外の前提が崩れた事実(TA-0005 §2.1)

**`fig-kakei-02.png` は「文字がほとんど無い図」ではなかった。** 表題・軸目盛・注釈がすべて描かれている。

**取れなかった原因は画像ではなく Docling だった。**

| ファイル | Docling 経由 | **RapidOCR 直接** | 比 |
| --- | --- | --- | --- |
| **fig-kakei-02.png** | **23文字** | **394文字** | **17.1倍** |
| 他の5件 | — | — | 差なし(0.97〜1.16倍) |

**同一の RapidOCR・同一モデルであり、差は Docling を通すかどうかだけである。** 正解に必要な文字列で測ると **9/9 が Docling 経由では失われ、直接呼び出しでは取れる**(正解到達 1/10 → 10/10)。

Docling の技術報告が明記している。

> "Text content inside figures is currently dropped"
> — Docling Technical Report, arXiv:2408.09869v5, 2024-12-09

**[S0-004](../../docs/spikes/S0-004-rag-fitness.md) は「全経路で 56文字」と報告したが、全経路が Docling を通っていた。** 測定結果を画像の性質だと解釈し、部品の仕様を確かめていなかった。

**図表画像を保持して参照時に渡す構成は、LangChain / LlamaIndex / Azure AI Search が定石として提供している。**

### 論点1 — 現行の検出が取りこぼしている類型(TA-0005 §1.1)

「日本語にある字への誤読は検出できない」は、現行の判定方法(CP932)についてのみ真である。**別の類型の誤り(仮名→漢字の同形異字。「電子力ルテ」)がコーパスに実在し、現行の判定方法では 0件と数えられている。**

**本検証で見つけたのは 1件のみ(6ファイル・8,181文字中)であり、頻度の一般化はできない。**

### 費用の前提(P-001)

**運用時 $0・実行時の外部通信なし・API キー不要。** 初回ダウンロードは現状 1.04GB。

**P-001 は「金銭の主張は維持し、時間とディスクの主張はしない」としている。** ディスクの増分そのものは前提違反にならないが、**時間の増分は未検証の前提6(初回構築の所要時間)へ直撃する。**

### 論点1: OCR の誤り訂正

| 案 | 性質(TA-0005 §1.3) | 採らなかった理由 |
| --- | --- | --- |
| 案1-A 現状維持(CP932 対応表のみ)+ スコープ外の記述の訂正 | 初回 DL 増分 **0**。速度への影響なし。誤検出なし。**完全に可逆**。**同形異字(カ→力)と `日`→`目` は素通りし、「電子力ルテ」は今後も混入 0件と数えられ続ける** | |
| 案1-B Unicode confusables を検出に加える(訂正はしない) | 初回 DL 増分 **+0.73MB**(+0.07%)。速度への影響は無視できる(文字列走査のみ)。Unicode License V3(AGPL-3.0 と支障なし)。可逆。**「電子力ルテ」を拾える。`日`→`目` は拾えない**(confusables は漢字同士の字形近似を設計上の対象外とする)。**誤検出あり**(片仮名の「カ」「ロ」「エ」は正当な日本語に出るため、文脈条件との組合せが必須)。**自動置換すると正しい「力(ちから)」を壊し、ADR-0005 決定3 の「正しい日本語の字が壊れることは構造上ありえない」という保証が失われる** | |
| 案1-C 文字レベル言語モデルで検出する(訂正はしない) | 初回 DL 増分 **+413MB**(1.04GB → 約1.45GB、+40%)。Apache-2.0。検出のみなら可逆。**`日`→`目` を検出できた唯一の方法(実測)**。**速度が 112字/秒 → 4.6字/秒(バッチ化後・実文書で実測。24分の1)。抽出テキスト 4.0MB の走査は単純計算で 240時間以上**(外挿であり未実行)。**誤検出が多い(実文書 4,894字中 292字 = 6.0%。本物の混入 0.159% のおおむね37倍)** | |
| 案1-D 小型 LLM にテキストを書き換えさせる | 初回 DL 増分 **+300〜1,600MB**。Apache-2.0 / MIT。**原文との対応を捨てる。抽出テキストを書き換えるため実質的に非可逆**。**JaPOC(PRICAI 2024)の実測: 事前学習の重み違いだけで平均精度が 94.8% と 9.3% に割れる / 元の OCR が良い側では訂正が精度を下げる / `Z` → `ほっかほっか亭` の捏造 / 著者自身が金額・日付を訂正対象から外している**。速度は未測定 | |
| **(実測で落とした)辞書照合(SudachiPy)による未知語検出** | — | **`日`→`目` を検出できない。`7目以内` は全形態素が辞書内(本検証の実測)。CP932 が拾う集合とほぼ同じものを、重い処理で拾い直すだけ** |
| **(実測で落とした)2つの認識モデルの不一致を疑い箇所とする** | — | **疑い箇所が多すぎる。検出枠を揃えた比較で 131枠中 77枠(58.8%)が不一致。差の大半は誤りではない表記差(本検証の実測)** |
| **(実測で落とした)既製の日本語誤字検出器 `recruit-jp/japanese-typo-detector-roberta-base`** | — | **`日`→`目` を検出できない。誤った文の誤り確率(0.043)が正しい文(0.349)より低く、信号の向きが逆。学習データが OCR 誤りではなく人間のタイプミス(本検証の実測)** |
| **(候補が存在しない)日本語の OCR 誤り訂正の既製モデル** | — | **HF 上に商用可・CPU 可のものが実質存在しない。該当2件のうち1件はライセンス記載なし。NDL(ndl-lab)も後処理の誤り訂正モデルを公開していない(全44リポジトリの列挙による不在確認)** |

**「訂正できる」ことは、案1-B・1-C のいずれについても本検証は示していません。** **S0-006 の「検出と修正は別の保証水準である」という指摘は維持されます。**

**JaPOC が報告した「元の OCR が良い側では訂正が精度を下げる」条件に、本案件は該当します。** S0-006 の実測は 8,181文字中 13件(**0.159%**)であり、**S0-004 の 15問のうち R01〜R04・R11・R12 の正解は日数・金額・世帯数そのものです。**

**唯一、緩和策の有効性が実測されているのは JaPOC のルールベースです**(編集距離 < 2 かつ正規化比 < 0.30 のときだけ置換し、それ以外は入力をそのまま返す。平均 87.2%)。**本案件の字形正規化表は、これと同じ「壊さない側に倒す」構造です。**

### 論点2: 図表の扱い

### S0-004「ページ画像は保存しない」との関係(#57 受入基準5)

**この判断は視覚ベース検索(ColPali)を採らないことが根拠であり、参照時に画像を渡さない根拠ではありません。**

| 案 | S0-004「ページ画像は保存しない」との関係 |
| --- | --- |
| 案2-A | **維持する。** 保存も参照時の受け渡しも行わない |
| 案2-B | **維持する。** 画像を保存せず、抽出テキストのみを増やす |
| 案2-C | **触れる。** ただし**保存するのはページ画像ではなく図表画像**であり、S0-004 の判断が禁じた対象と同一かは技術判断者が判断する。**F-002 基準6(ページ画像を保存してはならない)の文言に対して、図表画像が該当するかを決定で明示する必要がある** |

**F-002 基準6 は G-2 の判定対象です。判定後に変えると要件合意のやり直しになります。**
