## コンテキスト

### なぜいま決めるのか

**`index.sqlite` は誰も判断していません。** [S0-004](../../docs/spikes/S0-004-rag-fitness.md)「ミラーディレクトリの構成」で提案された名前が、**比較検討の記録を経ずに** [ADR-0002](./0002-external-interface-contract.md) 決定2 と F-003 基準1 へ流れました。

データベース層の判断記録は存在しません。[ADR-0005](./0005-indexer-selection.md) はインデクサの、[ADR-0008](./0008-lore-as-versionstore.md) は VersionStore の判断であり、いずれもメタデータの保管先を決めていません。

価値責任者が G-2 のレビューで指摘したものです(`docs/gates/g2-P-001-2026-08-13.md`「レビューで見つけたこと」F-003)。

F-003 基準1 の前半(`index.sqlite` 上で発番した)は**対外から観測できず、テストで区別できません**。同じ振る舞いを PostgreSQL でも JSON ファイルでも実現できます。後半(内容ハッシュを安定 ID として返してはならない)は観測できます。

**埋め込みの保存形式は、どの受入基準も指定していません。** `embed/<hash>.npy` は S0-004 の提案であり、受入基準に入っていません。したがって論点3 は受入基準に縛られていません。

## 検討した選択肢

**理由欄は技術判断者が記入します。以下の表の左2列は案の列挙と性質の整理であり、採否の推奨を含みません。**

### 論点1: 初版のメタデータ保管に何を使うか

| 案 | 性質(TA-0006 §3) | 採らなかった理由 |
| --- | --- | --- |
| 案1-A SQLite(Python 標準ライブラリ) | 追加コンテナ 0。パブリックドメイン。**ネットワーク FS 上で WAL が動かない**。本環境の同梱版 3.50.4 は WAL-reset バグの修正版(3.50.7 / 3.51.3)より前。PostgreSQL 方言との互換を捨てる | |
| 案1-B SQLite + sqlite-vec | 追加コンテナ 0。Apache-2.0(**PyPI は MIT/Apache デュアル表記で不一致**)。**pre-1.0 で 0.2.0 に破壊的変更が公式に予告されている**。Docker の Python が拡張ロード対応かは**未確認**。論点3 と不可分 | |
| 案1-C PostgreSQL コンテナ | **追加コンテナ +1(計3)**。PostgreSQL License(**ADR-0007 の許可一覧外。ただしコンテナのため `pip-licenses` の検査対象外**)。Aurora DSQL への可逆性が最も高い。単一ファイルの可搬性を捨てる | |
| 案1-D PGlite(`pglite-server` 経由) | **追加コンテナ +1(計3)**。Apache-2.0。**Python バインディングが存在せず、Node 経由になる**。pre-1.0 で minor release にも破壊的変更がありうる。SSL 非対応。多接続は「not all use cases are guaranteed to work」 | |
| 案1-E DuckDB | 追加コンテナ 0。MIT。**公式が「小さい書き込みに不向き」と明記** | |
| 案1-F LMDB | 追加コンテナ 0。**OLDAP-2.8 は ADR-0007 の許可一覧に無い** | |
| 案1-G 素のファイル + JSON | 追加コンテナ 0。**原子性がない** | |

**4案に共通する事実**: どの案でも制約1($0・外部通信なし・API キー不要)は満たせます。崩れるのは制約2(コンテナ数)であり、案1-C と案1-D が該当します。

### 論点2: 外部の DB へ差し替えられる境界をどう置くか

| 案 | 性質(TA-0006 §4) | 採らなかった理由 |
| --- | --- | --- |
| 案2-A 薄い境界(リポジトリのみ) | 実装量 最小。Aurora DSQL は実装次第。**DynamoDB は受け止めない**。境界はあるが**呼び出し側の書き方は移らない** | |
| 案2-B 中位(薄い境界 + 移行可能性の規律6件) | 実装量 中。**Aurora DSQL を受け止める**。DynamoDB は受け止めない。FK・トリガ・ビューを捨て、参照整合性をアプリ層で持つ。**規律を機械検査する手段は調べていない** | |
| 案2-C 厚い境界(KV 最大公約数) | 実装量 **最大**。**DynamoDB を受け止める**。SQL の表現力を全部捨て、件数は自前カウンタで持つ。**DynamoDB のベクトル検索は FGAC 非対応で、F-003 基準25 と衝突しうる** | |
| 案2-D 用途ごとに境界を分ける(`IdentityMap` / `OperationLog` / `WorkQueue`) | 実装量 中。**境界をまたぐトランザクションを捨てる**。「削除してゴミ箱へ入れ履歴を書く」が1トランザクションにならず、**F-001 の可逆性に直接効く**。可逆性は境界ごとに異なる | |

**4案に共通する事実**: **初版では境界の正しさを検証できません。** 境界の向こうに動く実装が無いためです。検証したい場合、DynamoDB Local(Docker・$0・オフライン)で案2-C の境界を1つ実装する選択肢は存在しますが、**公式に開発・テスト専用と明記され本番と挙動が異なります**。**Aurora DSQL には同等の手段が存在しません**(ローカルエミュレータが公式に無い)。

外部化先の制約(TA-0006 §4.1):

| 差し替え先 | 制約 |
| --- | --- |
| Aurora DSQL | FK・トリガ・拡張なし。1トランザクション **3,000行・10MiB・5分**。OCC リトライ必須。**ローカルエミュレータが公式に存在しない** |
| DynamoDB | `SearchVectors` は実在するが**無料枠外**かつ **FGAC 非対応** |

### 論点3: 埋め込みベクトルの保管をメタデータと同じ層に置くか

| 案 | 性質(TA-0006 §5・§6) | 採らなかった理由 |
| --- | --- | --- |
| 案3-A 個別ファイル(`embed/<hash>.npy`) | **10,000件の初回読み出し 504.50 s**。メタデータとの原子性なし。ファイル数が原本数×チャンク数で増える | |
| 案3-B 連結した単一配列ファイル + 行番号を DB に持つ | **10,000件の読み出し 0.021 s**。原子性なし。削除は tombstone + 再圧縮。**行番号とハッシュの対応が壊れると検索結果が別の文書を指す(気づきにくい誤り)** | |
| 案3-C メタデータ DB の BLOB 列 + NumPy 総当たり | **10,000件の読み出し 0.076 s**。**メタデータとの原子性あり**。10,000件で約15MB が DB に加わる。**Aurora DSQL は `bytea` が 1MiB 上限・インデックス非対応で、移行時にベクトル列だけ切り離すことになる** | |
| 案3-D DB のベクトル索引(sqlite-vec / pgvector / DuckDB VSS) | 原子性あり。**pre-1.0 の依存が1つ増えるか、PG コンテナが要る**。sqlite-vec は総当たりのみで NumPy と同じ。pgvector は **PostgreSQL License(許可一覧外)**。DuckDB VSS は**永続化が実験的でデータ損失の警告あり** | |
| 案3-E 専用 ANN ライブラリ(faiss-cpu / hnswlib / usearch) | 原子性なし。ライセンスはいずれも許可一覧内。**100万件でも総当たりが 79.68 ms であり、本案件の規模では索引の保守コストだけが残る可能性がある**。ANN は近似で再現率が 100% ではない | |

**争点は探索方式ではなくロードの形でした。** 100万件の総当たり類似度計算は 79.68 ms であり、**ベクトル検索の方式(pgvector / sqlite-vec / 総当たり)は速度の争点になりません。** 差が出たのは読み出しの形(504.50 s と 0.021 s、**約24,000倍**)です。

**この実測は Windows ホスト上のものです。個別ファイルの初回と2回目の差(約120倍)はウイルス対策ソフトの初回スキャンで説明でき、Linux コンテナ内では大幅に小さくなると見込まれますが、測定していません。**
