## 決定

### 1. 初版のメタデータ保管に何を使うか

**案1-A SQLite(Python 標準ライブラリ)を採る。**

追加コンテナ 0。パブリックドメイン。**Lore で既に1個増えており**(ADR-0008)、`docker compose up` 一発という前提のもとでコンテナを更に増やさない。

**次の2点は受け入れる。**

| # | 受け入れるもの |
| --- | --- |
| 1 | **ネットワーク FS 上で WAL が動かない。** 初版はローカルディスクのみ(企画書スコープ外)であり、いま実害が出ない |
| 2 | **同梱版 3.50.4 は WAL-reset バグの修正版(3.50.7 / 3.51.3)より前。** バージョンを固定し、修正版が入手できる時点で上げる |

**sqlite-vec(案1-B)は初版で使わない。** 論点3 の決定により、ベクトル索引そのものが要らない。

### 2. 外部の DB へ差し替えられる境界をどう置くか

**案2-B 中位(薄い境界 + 移行可能性の規律6件)を採る。**

**Aurora DSQL を受け止める。DynamoDB は受け止めない。**

**捨てるもの**: FK・トリガ・ビュー。参照整合性はアプリ層で持つ。

**採らなかった案2-D(用途ごとに境界を分ける)について、判断の根拠を残す。** 案2-D は境界をまたぐトランザクションを捨てるため、**「削除してゴミ箱へ入れ、履歴を書く」が1トランザクションにならない。** これは F-001 の可逆性に直接効き、ADR-0003 が安全重要度を CL0 とした根拠に触れる。**可逆性の担保を、境界の設計の都合で弱めない。**

**規律6件を機械検査する手段は調べていない。** 未確認事項として下記へ記録する。

### 3. 埋め込みベクトルの保管場所

**案3-C メタデータ DB の BLOB 列 + NumPy 総当たりを採る。**

| 決め手 | 実測 |
| --- | --- |
| **メタデータとの原子性がある** | 案3-A / 3-B / 3-E には無い |
| 読み出しが速い | **10,000件で 0.076 s**。案3-A は 504.50 s(約6,600倍) |
| **索引が要らない** | **100万件の総当たりが 79.68 ms** |

**S0-004 が提案した案3-A(`embed/<hash>.npy`)を採らない。** 提案は比較検討を経ておらず、実測で 504.50 s だった。

**案3-B(連結した単一配列)は 0.021 s とさらに速いが、採らない。** **行番号とハッシュの対応が壊れると、検索結果が別の文書を指す。** 気づきにくい誤りであり、本案件は同種の誤り(「項番47」の連結・隣の項目の選択肢を拾う)を S0-004 で実測している。**0.076 s と 0.021 s の差は、この危険と釣り合わない。**

**案3-D(DB のベクトル索引)を採らない。** pgvector は許可一覧外、DuckDB VSS は永続化が実験的、sqlite-vec は pre-1.0 かつ総当たりと同じ。**索引が速度の争点でない以上、pre-1.0 の依存を増やす理由がない。**

**Aurora DSQL への移行時に、ベクトル列だけ切り離すことになる**(`bytea` が 1MiB 上限・インデックス非対応)。**移行時の作業として受け入れる。**

### 4. この ADR が決めないこと

| # | 決めないこと | 扱う場所 |
| --- | --- | --- |
| 1 | テーブルのスキーマ、列名、索引の張り方 | 実装工程 |
| 2 | **移行可能性の規律6件を機械検査する手段** | 未確認。Platform |
| 3 | チャンク分割の単位(1文書1ベクトルか、複数か) | ADR-0005 の範囲。実装工程で確定する |
| 4 | 外部化を実際に行う時期と条件 | SG-1 以降 |
| 5 | **F-003 基準1 の実装名(`index.sqlite`)の除去** | [#59](https://github.com/Takenori-Kusaka/Filetto/issues/59) 欠陥4 |

**5 について**: 本決定により保管は SQLite となるが、**受入基準に実装名を書く必要はない。** 基準1 は「安定 ID を返す」「パス変更で変わらない」で足りる。**実装名の除去は本決定と独立に行う。**

### 論点2: 外部の DB へ差し替えられる境界をどう置くか

| 案 | 性質(TA-0006 §4) | 採らなかった理由 |
| --- | --- | --- |
| 案2-A 薄い境界(リポジトリのみ) | 実装量 最小。Aurora DSQL は実装次第。**DynamoDB は受け止めない**。境界はあるが**呼び出し側の書き方は移らない** | | **呼び出し側の書き方が移らない。** 境界を置いた効果が実質的に得られない |
| 案2-B 中位(薄い境界 + 移行可能性の規律6件) | 実装量 中。**Aurora DSQL を受け止める**。DynamoDB は受け止めない。FK・トリガ・ビューを捨て、参照整合性をアプリ層で持つ。**規律を機械検査する手段は調べていない** | | **採用** |

### 論点3: 埋め込みベクトルの保管をメタデータと同じ層に置くか

| 案 | 性質(TA-0006 §5・§6) | 採らなかった理由 |
| --- | --- | --- |
| 案3-A 個別ファイル(`embed/<hash>.npy`) | **10,000件の初回読み出し 504.50 s**。メタデータとの原子性なし。ファイル数が原本数×チャンク数で増える | | **10,000件の読み出しが 504.50 s**(採用案の約6,600倍)。メタデータとの原子性もない |
| 案3-B 連結した単一配列ファイル + 行番号を DB に持つ | **10,000件の読み出し 0.021 s**。原子性なし。削除は tombstone + 再圧縮。**行番号とハッシュの対応が壊れると検索結果が別の文書を指す(気づきにくい誤り)** | | **行番号とハッシュの対応が壊れると、検索結果が別の文書を指す。** 気づきにくい誤りであり、0.021 s と 0.076 s の差はこの危険と釣り合わない |
| 案3-C メタデータ DB の BLOB 列 + NumPy 総当たり | **10,000件の読み出し 0.076 s**。**メタデータとの原子性あり**。10,000件で約15MB が DB に加わる。**Aurora DSQL は `bytea` が 1MiB 上限・インデックス非対応で、移行時にベクトル列だけ切り離すことになる** | | **採用** |
| 案3-D DB のベクトル索引(sqlite-vec / pgvector / DuckDB VSS) | 原子性あり。**pre-1.0 の依存が1つ増えるか、PG コンテナが要る**。sqlite-vec は総当たりのみで NumPy と同じ。pgvector は **PostgreSQL License(許可一覧外)**。DuckDB VSS は**永続化が実験的でデータ損失の警告あり** | | **索引が速度の争点でない**(100万件の総当たりが 79.68 ms)。pgvector は許可一覧外、DuckDB VSS は永続化が実験的、sqlite-vec は pre-1.0 |
| 案3-E 専用 ANN ライブラリ(faiss-cpu / hnswlib / usearch) | 原子性なし。ライセンスはいずれも許可一覧内。**100万件でも総当たりが 79.68 ms であり、本案件の規模では索引の保守コストだけが残る可能性がある**。ANN は近似で再現率が 100% ではない | | 同上。**ANN は近似で再現率が 100% ではない。** 本案件の規模では索引の保守コストだけが残る |

**争点は探索方式ではなくロードの形でした。** 100万件の総当たり類似度計算は 79.68 ms であり、**ベクトル検索の方式(pgvector / sqlite-vec / 総当たり)は速度の争点になりません。** 差が出たのは読み出しの形(504.50 s と 0.021 s、**約24,000倍**)です。

**この実測は Windows ホスト上のものです。個別ファイルの初回と2回目の差(約120倍)はウイルス対策ソフトの初回スキャンで説明でき、Linux コンテナ内では大幅に小さくなると見込まれますが、測定していません。**
