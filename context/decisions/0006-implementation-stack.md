# ADR-0006: 実装スタックを Python バックエンド + TypeScript フロントとする

## ステータス

採用(2026-08-12)

## コンテキスト

`/process-init` の実行時、アダプタとして `node` を選びました。根拠は手書きの構想メモに「TypeScript / Vite」と書かれていたことです。**この選択は技術判断として記録されていませんでした。** プロセス構成の付随項目として、実質的に無自覚に確定させていました。

その後の S0 探索で、**中核となる検索・パース基盤がすべて Python である**ことが実測で判明しました。

| 層 | 実測で採用が確定した実装 | 言語 |
| --- | --- | --- |
| PDF・画像のパース | Docling(OCR: EasyOCR ja) | Python |
| .xlsx のパース | openpyxl(神エクセルは ExStruct 併用) | Python |
| .xls / .doc のパース | xlrd / olefile | Python |
| 形態素解析 | janome | Python |
| 全文検索 | rank-bm25 | Python |
| 埋め込み | multilingual-e5-small(sentence-transformers) | Python |

アダプタ `node` のままでは CI(G-5)が通りません。`actions/setup-node@v4` が `cache: npm` で lockfile を要求し、Node プロジェクトが存在しないため失敗します。**ドキュメントのみの PR が15コミット分、G-5 赤のまま滞留しています**([pit-in-template#6](https://github.com/Takenori-Kusaka/pit-in-template/issues/6))。

### この順序は誤りではありません

当初、私はこれを「`/process-init` の前にスタックを決めておくべきだった、自分の見落とし」と整理しました。**標準チームの確認により、この整理が誤りであることが判明しました。**

標準本文(`phase4-process-design/lifecycle.md`)の工程ゲート適用表では、S0 探索における G-3 技術設計判断は「**主要な選択のみ**」であり、SG-0 の判定基準は「**技術的実現性が確認されている**」です。

**実装スタックは S0 の出力であり、S0 の入力ではありません。** S0 探索の結果として Python が有望と判明したのは、標準どおりの動き方です。

したがって当方の手落ちは順序の誤りではなく、**「構想メモを根拠に `node` を選び、それを判断として記録しなかった」という記録の欠落**のみです。本 ADR がその欠落を埋めます。

## 決定

### 1. 実装スタックを2層に分ける

| 層 | 言語 | 対象 |
| --- | --- | --- |
| **バックエンド** | **Python 3.12** | REST API、MCP サーバ、ファイル操作、パース、インデクシング、検索、VersionStore |
| **フロントエンド** | **TypeScript** | Explorer UI(ヘッドレス UI として提供する部分を含む) |

### 2. アダプタは `python` とする

`process.config.json` の `adapters.stack` を `node` から `python` へ変更します。**`/process-init` の再実行によって行います**(スキルの再設定手順に沿った正規の経路であり、現在の構成の提示と変更点の確認を経るため)。

テーラリングの回答(軸A〜E および補足3問)は変更しません。アダプタ以外の構成は同じ結果になるはずです。

### 3. フロントエンドの検査経路を別に用意する

pit-in-template のアダプタは `process.config.json` の `adapters.stack` に**単一値**しか持てません。したがって G-5 の検査コマンドは Python 側しか回りません。

**TypeScript 側の検査(型検査・lint・テスト)を、G-5 の一部として実行できる経路を用意します。** 具体の方式は実装着手前に決め、必要であれば本 ADR を改訂します。**「フロントエンドは検査対象外」という状態を作りません。**

この制約は標準側へ論点として返すことを検討します。

## 検討した選択肢

### 言語構成

| 案 | 採らなかった理由 |
| --- | --- |
| **Python 単一**(UI も Python から配信) | CI は単純になるが、ヘッドレス UI として第三者が差し替える体験を作りにくい |
| **TypeScript 単一** | S0 の実測資産(Docling / janome / EasyOCR / sentence-transformers / ExStruct)を捨てることになる |
| **Python + TypeScript**(採用) | — |

### 検索・パース基盤に TypeScript / Node を採らなかった理由

判定者(takenori-kusaka / 技術判断者)が記入(2026-08-12)。**次の2点の両方による。**

1. **S0 の実測資産がすべて Python であり、代替が存在しない。** Docling・janome・EasyOCR・sentence-transformers・ExStruct はいずれも Python 実装であり、Node 側に同等の実装がない。移植は現実的でない
2. **機械学習・文書処理のエコシステムが Python に集中している。** 今後 VLM や視覚ベース検索へ広げる際も、選択肢の数が桁で違う。[#7](https://github.com/Takenori-Kusaka/Filetto/issues/7) の検証もすべて Python 前提である

### Go を採らなかった理由

判定者が記入(2026-08-12)。

**将来の候補として残す。今は決めない。** 性能が問題になった箇所だけ Go へ切り出す可能性を残すが、初版では採らない。

## 可逆性

| 項目 | 内容 |
| --- | --- |
| 後から変えられるか | **変えにくい** |
| 変えるとしたら必要なこと | バックエンドの言語変更は、パース・検索基盤の全面的な作り直しを意味する。Python 以外に移す合理的な理由は現時点で存在しない。**フロントエンドの言語変更は比較的安い**(ヘッドレス UI 方針により、UI は差し替え可能な層として設計するため) |
| いつまでなら安く変えられるか | バックエンド: **実装着手前まで**。着手後は実質不可。フロントエンド: 継続的に変更可能 |

## 非機能への影響

| 項目 | 影響 |
| --- | --- |
| 性能 | Python は CPU バウンドな処理で不利。S0-003 の実測ではパースに 50 件 25 分を要しており、**この遅さは言語ではなく OCR / レイアウト解析モデルの計算量に由来する**。言語選択で改善する部分は小さい |
| 可用性 | 影響なし |
| セキュリティ | 依存の数が増える(Python + npm の二系統)。**両方のエコシステムに対して脆弱性検査とライセンス検査が必要**になる |
| 運用 | **`docker compose up` 一発という前提に影響する**。Python ランタイム・モデル(約 1.07 GB)・Node のビルド成果物を、単一イメージまたは最小構成のコンテナ群へ収める設計が要る。ここは ADR-0002 と合わせて検討する |

## 事業への影響

| 項目 | 内容 |
| --- | --- |
| 顕在化が分かる兆候 | フロントエンド側の検査が G-5 に組み込まれないまま実装が進むこと。または `docker compose up` の起動時間・イメージサイズが利用者の許容を超えること |
| 回復に要する時間 | **3日**(フロントエンドの検査経路の追加。バックエンドの言語変更は回復ではなく作り直しであり、算定しない) |
| 影響を受ける利用者・業務 | 本プロダクトを自ら改造する第三者。Python と TypeScript の両方を扱える必要が生じる |

## 影響

**この決定によって得られるもの:**

- S0 で実測した構成をそのまま実装へ持ち込める。作り直しが発生しない
- CI(G-5)の赤を解消する道筋が立つ。滞留している PR をマージできる
- ヘッドレス UI 方針と整合する。UI は差し替え可能な層として TypeScript で持てる

**トレードオフ:**

- **2言語になり、依存の管理・検査が二系統になる**。脆弱性検査もライセンス検査も両方に必要
- **アダプタが単一値のため、G-5 の標準経路ではフロントエンドを検査できない**。別経路の用意が必要
- **`docker compose up` 一発の実現が難しくなる**。Python ランタイム + モデル + Node ビルド成果物を収める設計が要る

**この決定で解決しないこと:**

- **フロントエンド側の検査を G-5 へどう組み込むか**は決めていない。実装着手前に決め、必要なら本 ADR を改訂する
- **コンテナ構成**(単一イメージか複数コンテナか)は決めていない。ADR-0002 と合わせて検討する
- **Python のパッケージ管理**(uv / pip / poetry)と**フロントエンドのビルド**(Vite 等)の具体は決めていない。実装計画で定める
