# ADR-0001: Filetto のライセンスを AGPL-3.0 とする

## ステータス

採用(2026-08-12)

## コンテキスト

Filetto は個人がセルフホストするファイル管理 + セマンティック検索の OSS である。公開にあたりライセンスを確定させる必要がある。

現在のリポジトリの `LICENSE` は MIT だが、これは pit-in-template から生成した際の初期値であり、Filetto のために選んだものではない。

判断を要する背景は次のとおり。

- 事前調査(`tmp/md (1).md`)は「既存の統合型ファイルエクスプローラー OSS(Filestash / Pydio Cells / Seafile)はいずれも AGPLv3 であり、SaaS への深い組み込みに法的リスクを伴う」として、**許諾型ライセンスの組み合わせで自作する**方針を結論としていた
- 一方、企画の口述(`tmp/20260808-transcript-*.md`)では「AGPL ライセンスでやってもらうつもり」と述べられていた
- 両者は逆の結論であり、どちらかを選ばなければならない

依存する OSS(Graphify / Apache Tika / OpenSearch / Meilisearch CE / Uppy / tus 等)はいずれも Apache-2.0 / MIT / BSD 3-Clause であり、AGPL-3.0 のプロダクトから利用することに支障はない。制約は Filetto 自身の配布条件の問題である。

なお本 ADR はライセンスの選択のみを扱う。**法的助言ではない**。

## 決定

**Filetto を AGPL-3.0 で公開する。**

- リポジトリの `LICENSE` を MIT から AGPL-3.0 へ差し替える
- ドキュメント(`*.md`)は現行どおり CC BY 4.0 を維持する(`LICENSE-docs`)
- 依存 OSS は CI の `allowedLicenses`(MIT / Apache-2.0 / BSD-2-Clause / BSD-3-Clause / ISC)の範囲に限る。**コピーレフト系の依存を新たに持ち込まない**
- 後続のマイクロサービス(Chat / Auth)も AGPL-3.0 で揃える方針とする。ただしそれぞれの ADR で改めて判断する

## 検討した選択肢

| 案 | 採らなかった理由 |
| --- | --- |
| **Apache-2.0** | 勝手に商用サービスに組み込まれるのを避けたい |
| **MIT** | Apache-2.0 と同じ理由。加えて特許条項がない |
| **デュアルライセンス(AGPL-3.0 + 商用)** | 1名体制で運用コストを背負えない |
| AGPL-3.0(採用) | — |

理由欄は判定者(takenori-kusaka / 技術判断者)が記入した(2026-08-12)。

## 可逆性

| 項目 | 内容 |
| --- | --- |
| 後から変えられるか | **変えにくい**(方向による) |
| 変えるとしたら必要なこと | **緩める方向(AGPL → 許諾型)は、単独著作権者である間は可能**。外部コントリビュータのコードが入った後は、全員の同意または CLA が必要になる。**厳しくする方向(許諾型 → AGPL)は、既に配布した版には遡及しない** |
| いつまでなら安く変えられるか | **最初の外部コントリビューションを受け入れるまで**。それ以降は同意の取得コストが発生する。公開後にコントリビューションが発生する前であれば、実質いつでも変更できる |

**この非対称性が、AGPL を先に選ぶ根拠でもある。** 緩めるのは後からできるが、締めるのは後からできない。

## 非機能への影響

| 項目 | 影響 |
| --- | --- |
| 性能 | なし |
| 可用性 | なし |
| セキュリティ | なし。ただしソース公開義務があるため、**設定ファイルへ秘密情報を直接書く設計を採れない**(利用者がフォークを公開する際に漏れる)。環境変数または外部シークレットストアを前提とする |
| 運用 | **依存追加のたびにライセンス検査が必要**。CI の `allowedLicenses` 検査が実質的な防波堤になる。コピーレフト系の依存が混入した場合、置き換え先を探すコストが発生する |

## 事業への影響

| 項目 | 内容 |
| --- | --- |
| 顕在化が分かる兆候 | 企業からの問い合わせで「AGPL では社内利用の承認が下りない」という反応が出ること。または GitHub の Issue / Discussion で、ライセンス変更の要望が複数件立つこと |
| 回復に要する時間 | **2週間**(単独著作権者である場合。`LICENSE` の差し替えと再リリースのみ)。外部コントリビューションが入った後は算定できない |
| 影響を受ける利用者・業務 | Filetto を自社製品へ組み込みたい第三者、および Filetto をネットワーク越しにサービス提供したい第三者。**個人セルフホスト利用者には影響しない**(主戦場は個人セルフホストであるため、当面の実害は小さい) |

金額での定量化は行わない。本案件は金銭支出を伴わず、収益化の意図も現時点でないため、算定の根拠となる数字が存在しない。

## 影響

**この決定によって得られるもの:**

- 第三者が Filetto をフォークして SaaS 化した場合、改変部分のソース公開義務が及ぶ。ネットワーク越しの利用でも還元を求められる
- 後続の Chat / Auth を含め、統合環境全体を AGPL で揃えられる。コンポーネントごとにライセンスが違う状態を避けられる
- 将来の収益化(デュアルライセンス化)の選択肢が残る。許諾型で出すとこの経路は塞がる

**トレードオフ:**

- **企業採用の障壁になる**。AGPL は社内利用の承認が下りない組織が実在する。これは企画書の事業リスク表に「法務・規制」区分で記載し、**受容**した
- **「ヘッドレス UI で各利用者が自由に UI を変えられるようにする」という方針と緊張関係にある**。AGPL 下では、Filetto を組み込んだ UI をネットワーク越しに提供する第三者にもソース公開義務が及ぶ。個人セルフホストが主戦場である限り実害は小さいが、この緊張は解消されていない
- **G-6(独立レビュー)の未達解消が遅れる可能性がある**。調達先を「リポジトリ公開によるコミュニティレビュー」としているが、AGPL は採用の裾野を狭めるため、レビュアが集まりにくい方向へ働く

**この決定で解決しないこと:**

- 上記の緊張(ヘッドレス UI 方針との衝突)は解決していない。企業採用を取りに行く段階で本 ADR を見直す
- 依存 OSS のライセンス互換性は個別に確認する必要がある。本 ADR は「AGPL-3.0 を選ぶ」ことのみを決めており、個々の依存の可否を決めていない
- ドキュメントのライセンス(CC BY 4.0)との関係は現状維持であり、再検討していない
