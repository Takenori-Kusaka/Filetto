# ADR-0002: 対外インターフェース契約(REST / MCP)

## ステータス

採用(2026-08-12)

## コンテキスト

Filetto は同一のファイル資産に対して、人向けの入口(WebUI / REST)と AI 向けの入口(MCP)を提供する。**この2つが同じ実体を共有していることが本プロダクトの価値である**(`context/projects/P-001.md`)。

本 ADR は G-3(技術設計判断)の判定対象だが、**G-2 の受入基準に直接影響する**。外部が何を指し、何を返すかが決まらないと、F-001〜F-003 の受入基準を検証可能な形で書けない。このため G-3 に先行して執筆する。

決めるべき論点は4つあった。

| # | 論点 | 決まっていなかったこと |
| --- | --- | --- |
| 1 | 外部が指す識別子 | パスを識別子にするか、パスとは別の識別子を置くか |
| 2 | ファイル内容の受け渡し | 本文を直接返すか、URL を返すか |
| 3 | MCP の提供形態 | HTTP か stdio か |
| 4 | 初回構築中の扱い | 索引が未完成のときに何を返すか |

論点1 には下位論点があった。[S0-004](../../docs/spikes/S0-004-rag-fitness.md) のミラー構成は**内容ハッシュを主キー**としており、対外の識別子をこの主キーそのものにするかが未決だった(`context/projects/P-001.md` 未決の論点8)。**S0-005 の重複排除検証は、同一内容で別パスのファイルが実際に存在することを確認している。** 内容ハッシュを対外の識別子にすると、この2ファイルは対外的に同一の識別子を持つ。

論点4 は設計標準 [[calm-technology]] の「黙って空を返すと利用者は『無い』と誤解する」に対応する。

## 決定

### 1. 外部が指す識別子は安定 ID とする。パスは属性にすぎない

REST / MCP のいずれにおいても、ファイルを指す識別子は**安定 ID**である。パスは安定 ID に付随する属性として返す。パスを識別子として受け付ける API を公開しない。

### 2. 安定 ID は内容ハッシュとは別に発行する論理 ID とする

`index.sqlite` の主キーである内容ハッシュを、そのまま対外の安定 ID にしない。

| 段 | 対応 |
| --- | --- |
| 1 | 原本パス → 安定 ID(論理 ID) |
| 2 | 安定 ID → 現在の内容ハッシュ |
| 3 | 内容ハッシュ → 派生物(テキスト・構造化 JSON・埋め込み) |

[S0-004](../../docs/spikes/S0-004-rag-fitness.md) が提案した2段構成に対し、1段を追加する。**第3段(内容ハッシュ → 派生物)は変更しない。** 派生物のキーは内容ハッシュのままであり、重複排除の利得は失われない。

安定 ID の発行規則は次のとおり。

- パスが初めて索引に入った時点で発行する
- 発行後、そのファイルの移動・改名・内容の上書きによって変化しない
- 原本が消えても安定 ID は残る(S0-004 が「昔あったはずの資料を探せることは価値」としている)

**同一内容で別パスの2ファイルは、別々の安定 ID を持つ。** 利用者が「別々に置いた2つのファイル」と認識している実態に合わせる。

### 3. ファイル内容は本文直返しと署名付き URL の両方で受け渡す

| 経路 | 用途 |
| --- | --- |
| 本文直返し | 小さいテキスト。往復を減らす |
| 署名付き URL | 大きいファイル。本文に載せない |

どちらを返すかの境界値(バイト数)は本 ADR では定めない(下記「この決定で解決しないこと」)。

### 4. MCP は HTTP を主とし、stdio も提供する

主たる利用形態は常駐サーバへの接続である。stdio はローカル単体利用の経路として残す。**どちらか一方のみを提供しない。**

### 5. 初回構築中のファイルは候補に含めず、未完了 N 件を明示する

索引の構築が完了していないファイルを検索結果・一覧の候補に含めない。**同時に、未完了の件数とその理由を応答に必ず載せる。**

#### REST

検索・一覧応答のトップレベルに `meta` を置き、結果本体と同居させる。

```json
{
  "items": [ ... ],
  "meta": {
    "pending_count": 12,
    "pending_reason": "initial_index_building"
  }
}
```

Elasticsearch の非同期検索が `is_partial` / `is_running` を結果と同じ応答オブジェクトに置く構造と同型である([Run an async search](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-async-search-submit))。

#### MCP

検索・一覧ツールの結果に、**件数と理由の両方**を機械可読なメタデータとして載せる。REST の `meta` と同じ構造を用いる。

ログ検索の Axiom が `total_matching` / `returned_rows` / `truncated` / `truncation_reason` をデータ本体と併記する構造がこれにあたる。**件数だけでなく理由を持たせる**ことが本決定の要件である。「まだ読めていない」と「そもそも存在しない」を利用者と AI エージェントが区別できるようにするためである。

`isError: true` は用いない。MCP 仕様において `isError` はツール実行エラー(API 失敗・入力検証エラー・ビジネスロジックエラー)を表す。**「結果は取得できたが一部が未完了」は成功した応答であり、`isError` の意味論に当たらない。**

### 6. 本 ADR が決めないこと(スコープ外)

- **認証・認可の設計。ADR-0004 の対象である。** JWT クレームの設計、スコープの表現、検証の責務分界を本 ADR では扱わない
- エンドポイントの完全な一覧と OpenAPI 定義(実装工程の対象)
- MCP ツールの具体的な引数スキーマ(F-001〜F-003 の機能仕様の対象)

## 検討した選択肢

理由欄は価値責任者(takenori-kusaka)が記入した(2026-08-12)。

### 論点1: 外部が指す識別子

| 案 | 採らなかった理由 |
| --- | --- |
| **パスを識別子にする** | **利用者はファイルを移動・改名する。パスを識別子にすると外部の参照が壊れる。** |
| **安定 ID を識別子にする(採用)** | — |

### 論点1の下位論点: 安定 ID を何にするか

先行事例を調査したうえで判断した(2026-08-12)。

| 案 | 採らなかった理由 |
| --- | --- |
| **内容ハッシュをそのまま対外 ID にする** | **内容を上書きするとハッシュが変わり、外部参照が切れる。** また、同一内容で別パスの2ファイルが対外的に同一 ID となり、利用者が「別々に置いた2つのファイル」と認識している実態と食い違う。 |
| **内容ハッシュとは別の論理 ID を発行する(採用)** | — |

**先行事例の整理**(判断の材料として調査したもの。各案の性質であり、選択の理由ではない):

| システム | 方式 | 内容ハッシュとの関係 |
| --- | --- | --- |
| [Perkeep(旧 Camlistore)](https://perkeep.org/doc/schema/permanode) | permanode(署名付き乱数)+ blobref(内容ハッシュ) | 意図的に分離。permanode は不変の安定参照、指し先のハッシュは変わってよい |
| Git | blob ハッシュは内容アドレスのみ | ファイルの同一性は tree のパスと commit 履歴が担う。rename は事後的なヒューリスティック検出 |
| [IPFS / CID](https://docs.ipfs.tech/concepts/content-addressing/) | CID = 内容ハッシュ | 同一内容は同一 CID。変化する対象への安定参照は [IPNS](https://docs.ipfs.tech/concepts/ipns/) を別レイヤーで用意 |
| Google Drive | fileId は内容ハッシュと独立 | rename / move でも fileId は不変。内容の重複排除は別レイヤー |
| restic / borg | チャンク層(内容アドレス)とアーカイブ層(論理ファイル) | 重複排除とファイル同一性判定は完全に別レイヤー |

**内容の同一性と論理的な同一性を分離する設計は、Perkeep・IPNS・クラウドストレージ・重複排除バックアップのいずれにも共通して現れる。**

### 論点2: ファイル内容の受け渡し

| 案 | 採らなかった理由 |
| --- | --- |
| **本文直返しのみ** | **大きいファイルを本文に載せることになる。** MCP 経由では AI エージェントの文脈をファイル本文が占有する |
| **署名付き URL のみ** | **小さいテキストにも往復が発生する。** 検索結果の断片を読むだけで毎回 URL の取得と取り出しの2回を要する |
| **両方を提供する(採用)** | — |

### 論点3: MCP の提供形態

| 案 | 採らなかった理由 |
| --- | --- |
| **stdio のみ** | **主たる利用形態は常駐サーバへの接続である。** stdio のみでは常駐構成から使えない |
| **HTTP を主とし stdio も提供(採用)** | — |

### 論点4: 初回構築中の扱い

| 案 | 採らなかった理由 |
| --- | --- |
| **未完了のファイルを候補に含める** | **索引が未完成のファイルは検索の質を担保できない。** 読めていないテキストに対する検索結果は誤りである |
| **候補に含めず、黙って結果を返す** | **利用者は「無い」と誤解する。** [[calm-technology]] が明示的に禁じている |
| **候補に含めず、未完了 N 件を明示する(採用)** | — |

### 論点4の下位論点: 未完了 N 件をどこにどう載せるか

REST と MCP のそれぞれについて、先行事例を調査したうえで判断した(2026-08-12)。

**REST**

| 案 | 採らなかった理由 |
| --- | --- |
| **専用ステータスエンドポイント**(Meilisearch の `isIndexing` 型) | **呼ばなければ気づけない。** 利用者に追加の操作を課すことになり、[[calm-technology]] の「利用者に管理タスクを暗黙に課さない」と衝突する |
| **HTTP レスポンスヘッダ** | **見落とされやすい。** 多くのクライアントはボディのみを読む。調査した範囲でこの方式の採用例は確認できなかった |
| **ページネーション統合型**(Dropbox の `has_more` / Google Drive の `nextPageToken`) | **「続きがあるか」と「まだ読めていないか」は意味が異なる。** 混同すると、利用者は続きを取得すれば全件揃うと解釈する |
| **トップレベル meta(採用)** | — |

**MCP**

MCP の実装事例を横断的に調査した。Web 検索系(Brave / Tavily / Exa)、ドキュメント検索系(Notion / Atlassian / Slack)、コード検索系(GitHub)、ベクトル検索系(Weaviate / Pinecone / Chroma)、ログ検索系(Axiom)を対象とした。

| 案 | 採らなかった理由 |
| --- | --- |
| **専用ツールに分離する**(Qdrant 系コミュニティ実装の `get_index_status` 型) | **REST の専用エンドポイント案と同じ理由。** 呼ばなければ気づけない |
| **`isError: true` を用いる** | **意味論上の誤用である。** 一部が未完了でも応答自体は成功している |
| **自然文のみで表現する**(Exa の `autopromptString` 型) | **AI エージェントが構造化データとして扱えない。** 件数を機械的に取り出せない |
| **件数のみを載せ、理由を載せない** | **「まだ読めていない」と「そもそも存在しない」を区別できない。** 区別できることが論点4 の目的である |
| **理由付きメタデータを結果に併記する(採用。Axiom 型)** | — |

**調査から得られた事実として記録する:**

- **「検索結果が不完全であることを伝える」問題に、MCP において確立した単一の業界標準パターンは存在しない。** REST の世界(Elasticsearch / Meilisearch / Dropbox / Google Drive)には確立したパターンが複数あるのに対し、MCP の実装はばらついている
- 理由まで含めて機械可読に持つ実例は Axiom の1件のみであり、**主流とは言えない**
- MCP 仕様の `structuredContent` は任意の JSON 構造をツール結果に持たせる正当な仕組みだが、**Claude Code を含む複数のクライアント実装で無視・欠落するバグが報告されている**([anthropics/claude-code#15412](https://github.com/anthropics/claude-code/issues/15412))。仕様自体も「後方互換のため同じ内容を `TextContent` としても返すべき(SHOULD)」としている
- [Atlassian 公式 MCP サーバ](https://github.com/atlassian/atlassian-mcp-server/issues/118)は `nextPageToken` / `isLast` を設計上持つ想定でありながら、実装のバグで応答に含まれずページングが機能していない。**フィールドを定義することと実際に機能させることの間にはギャップが生じる**

## 可逆性

| 項目 | 内容 |
| --- | --- |
| 後から変えられるか | **決定によって異なる。決定2(安定 ID)が最も変えにくい** |
| 変えるとしたら必要なこと | 決定2 を変えると、**外部が保持しているすべての参照が無効になる**。安定 ID を発行した後に方式を変える経路は、旧 ID から新 ID への恒久的な対応表を持つ以外にない。決定3(受け渡し)・決定4(MCP 形態)・決定5(未完了の明示)は応答スキーマの変更で済む |
| いつまでなら安く変えられるか | **決定2 は、外部が安定 ID を保持し始める前まで**(初回リリース前)。それ以降は、外部の参照を壊すか対応表を永続的に持つかの二択になる |

**決定2 を最初に固定する理由がここにある。** 他の決定は後から変えられるが、識別子だけは外部の手に渡った時点で変えられなくなる。

## 非機能への影響

| 項目 | 影響 |
| --- | --- |
| 性能 | 決定2 により `index.sqlite` の参照が1段増える(パス → 安定 ID → 内容ハッシュ)。**派生物の重複排除は第3段で保たれるため、ディスク消費は増えない**。決定3 の署名付き URL は、大きいファイルの本文が応答を占有することを防ぐ |
| 可用性 | 決定5 により、索引が未完成でも検索 API は応答を返す(未完了件数を添えて)。**構築完了を待たせない** |
| セキュリティ | 決定3 の署名付き URL は有効期限と対象を限定する。**ただし署名方式・有効期限・認可との関係は ADR-0004 の対象であり、本 ADR では定めない** |
| 運用 | 決定2 の安定 ID は原本が消えても残る。**残り続ける安定 ID の掃除方針を持たないと、`index.sqlite` が単調増加する**(下記「この決定で解決しないこと」) |

## 事業への影響

| 項目 | 内容 |
| --- | --- |
| 顕在化が分かる兆候 | 決定2 が誤りだった場合の兆候は、**外部の参照が壊れたという報告**である。決定5 が不十分だった場合の兆候は、**「検索しても出てこない」という報告**(実際には索引の構築中である) |
| 回復に要する時間 | 決定3・4・5 は応答スキーマの変更で **1〜2日**。**決定2 は初回リリース後には実質的に回復できない**(旧 ID の対応表を恒久的に抱えることになる) |
| 影響を受ける利用者・業務 | 決定2 は外部連携を行うすべての利用者。決定5 は初回構築を経験するすべての利用者(全員が一度は通る) |

## 影響

**この決定によって得られるもの:**

- **外部の参照が、ファイルの移動・改名・内容の上書きで壊れない**(決定1・2)
- **同一内容の別ファイルを別のものとして扱える**(決定2)。重複排除の利得は派生物の層で保たれる
- **索引の構築完了を待たずに検索 API を提供できる**(決定5)
- **「読めていない」と「存在しない」を、人と AI エージェントの双方が区別できる**(決定5)

**トレードオフ:**

- **`index.sqlite` のマッピングが2段から3段に増える**(決定2)。S0-004 の提案より複雑になる
- **安定 ID の発行機構を実装する必要がある**(決定2)。内容ハッシュをそのまま使えば不要だった
- **REST と MCP で同じメタデータ構造を二重に維持する**(決定5)。片方だけを変更すると両者が乖離する
- **決定5 の MCP 側は、確立した業界標準に乗っていない。** 実例が1件しか確認できていない構造を採る

**この決定で解決しないこと:**

- **本文直返しと署名付き URL を切り替える境界値**(バイト数)は対象外。実装着手時に定める
- **署名付き URL の有効期限・署名方式**は対象外。認可と不可分であり ADR-0004 の対象
- **安定 ID の具体的な形式**(UUID か連番か、文字列表現)は対象外。実装着手時に定める
- **原本が消えた後の安定 ID の保持期間**は対象外。ADR-0003 のゴミ箱の保持期間(既定30日)とは別の論点である
- **`meta` の具体的なフィールド名とスキーマ**は F-001〜F-003 の機能仕様で確定する。本 ADR は「件数と理由の両方を、結果と同じ応答に載せる」ことのみを定める
- **MCP の `structuredContent` を用いるか、テキスト content 内の JSON とするか**は対象外。クライアント側の欠落実績(上記)を踏まえ、実装着手時に測って定める
