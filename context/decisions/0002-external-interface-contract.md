# ADR-0002: 対外インターフェース契約(REST / MCP)

## ステータス

採用(2026-08-12)

## コンテキスト

Filetto は同一のファイル資産に対して、人向けの入口(WebUI / REST)と AI 向けの入口(MCP)を提供する。**この2つが同じ実体を共有していることが本プロダクトの価値である**(`context/projects/P-001.md`)。

本 ADR は G-3(技術設計判断)の判定対象だが、**G-2 の受入基準に直接影響する**。外部が何を指し、何を返すかが決まらないと、F-001〜F-003 の受入基準を検証可能な形で書けない。このため G-3 に先行して執筆する。

決めるべき論点は4つあった。

| # | 論点 | 決まっていなかったこと |
| --- | --- | --- |
| 1 | 外部が指す識別子 | パスを識別子にするか、パスとは別の識別子を置くか |
| 2 | ファイル内容の受け渡し | 本文を直接返すか、URL を返すか |
| 3 | MCP の提供形態 | HTTP か stdio か |
| 4 | 初回構築中の扱い | 索引が未完成のときに何を返すか |

論点1 には下位論点があった。[S0-004](../../docs/spikes/S0-004-rag-fitness.md) のミラー構成は**内容ハッシュを主キー**としており、対外の識別子をこの主キーそのものにするかが未決だった(`context/projects/P-001.md` 未決の論点8)。**S0-005 の重複排除検証は、同一内容で別パスのファイルが実際に存在することを確認している。** 内容ハッシュを対外の識別子にすると、この2ファイルは対外的に同一の識別子を持つ。

さらに、既存の ADR との接続面に3つの未決があった。**いずれも識別子の契約に属し、外部が参照を保持し始めた後には変えられない。**

| # | 未決だったこと | 関係する ADR |
| --- | --- | --- |
| 5 | ゴミ箱にあるファイルを、対外から安定 ID で参照できるか | [ADR-0003](./0003-reversible-file-operations.md)(削除は論理削除。ゴミ箱の中身は検索から除外) |
| 6 | 過去の版を対外からどう指すか | [ADR-0008](./0008-lore-as-versionstore.md)(版の保管に Lore を採用) |
| 7 | 原本が消えた後の安定 ID をいつまで残すか | ADR-0003(ゴミ箱の保持期間は既定30日) |

論点4 は設計標準 [[calm-technology]] の「黙って空を返すと利用者は『無い』と誤解する」に対応する。

## 決定

### 1. 外部が指す識別子は安定 ID とする。パスは属性にすぎない

REST / MCP のいずれにおいても、ファイルを指す識別子は**安定 ID**である。パスは安定 ID に付随する属性として返す。パスを識別子として受け付ける API を公開しない。

### 2. 安定 ID は内容ハッシュとは別に発行する論理 ID とする

`index.sqlite` の主キーである内容ハッシュを、そのまま対外の安定 ID にしない。

| 段 | 対応 |
| --- | --- |
| 1 | 原本パス → 安定 ID(論理 ID) |
| 2 | 安定 ID → 現在の内容ハッシュ |
| 3 | 内容ハッシュ → 派生物(テキスト・構造化 JSON・埋め込み) |

[S0-004](../../docs/spikes/S0-004-rag-fitness.md) が提案した2段構成に対し、1段を追加する。**第3段(内容ハッシュ → 派生物)は変更しない。** 派生物のキーは内容ハッシュのままであり、重複排除の利得は失われない。

安定 ID の発行規則は次のとおり。

- パスが初めて索引に入った時点で発行する
- 発行後、そのファイルの移動・改名・内容の上書きによって変化しない
- 原本が消えても安定 ID は残る(S0-004 が「昔あったはずの資料を探せることは価値」としている)

**同一内容で別パスの2ファイルは、別々の安定 ID を持つ。** 利用者が「別々に置いた2つのファイル」と認識している実態に合わせる。

**「移動・改名によって変化しない」を成立させる同一性判定の方式は、本 ADR では定めない。** Filetto はファイルシステムを観測する側にあり、移動・改名を API として受け取らない。したがって「初めて見るパス」が新規ファイルなのか既存の安定 ID の移動先なのかを判定する機構が要る。この機構の設計は実装工程の対象とする(下記「この決定で解決しないこと」)。**本 ADR が定めるのは、対外的に安定 ID が不変であるという契約のみである。**

### 2-1. 安定 ID から引ける状態を3つに分ける

対外 API は、安定 ID に対して次の3状態を区別して返す。

| 状態 | 対外 API の応答 | 検索結果の候補 |
| --- | --- | --- |
| 利用可能 | ファイルの実体を返す | 含める |
| ゴミ箱にある | **実体を返さない。ゴミ箱にある事実と、復元の可否を返す** | 含めない |
| 存在しない | 見つからないことを返す | 含めない |

**ゴミ箱にあるファイルを「存在しない」と同じ扱いにしない。** ADR-0003 決定3 はゴミ箱の中身を検索インデックスから完全に除外すると定めており、検索の候補に含めない点は変わらない。**しかし安定 ID を指定した直接の参照では、「消えた」と「捨てた」を区別できるようにする。** 区別できないと、利用者は復元できるものを復元できないと判断する([[calm-technology]])。

ゴミ箱の保持期間(ADR-0003 決定4。既定30日)を過ぎて完全削除されたファイルは、「存在しない」へ遷移する。

### 2-2. 過去の版は安定 ID と版指定の組で指す

版ごとに別の安定 ID を発行しない。安定 ID は版をまたいで不変であり、過去の版は**安定 ID に版の指定を添えて**指す。

ADR-0008 により版の保管は Lore が担う。**Lore が内部で用いるチャンクのハッシュ体系は対外へ出さない。** 対外に出すのは安定 ID と版の識別子のみであり、Lore の識別子を Filetto の対外契約へ漏らさない(ADR-0008 決定5 の `VersionStore` 境界と同じ扱い)。

版の識別子の形式(連番か、時刻か、内容ハッシュか)は本 ADR では定めない。

### 2-3. 原本が消えた後の安定 ID を無期限に残さない

安定 ID は原本の消失後も残るが、**残す期間を無期限にしない。** 期間の既定値は ADR-0003 のゴミ箱の保持期間と同様に設定で指定できるものとし、既定値を持たせる。

**この規則を置く理由は、静かな蓄積を設計標準が禁じているためである。** [[calm-technology]] は「静かに蓄積し、閾値を超えた時点で警告する」状態をカームでないと判定している。安定 ID と、それが指していた派生物を無期限に残す設計は、この判定に該当する。ADR-0003 は同じ標準の下でゴミ箱の保持期間に既定30日を与えており、本 ADR だけが答えを持たない状態にしない。

具体的な既定値と、派生物を解放する条件は実装工程で定める(下記「この決定で解決しないこと」)。

### 3. ファイル内容は本文直返しと署名付き URL の両方で受け渡す

| 経路 | 用途 |
| --- | --- |
| 本文直返し | 小さいテキスト。往復を減らす |
| 署名付き URL | 大きいファイル。本文に載せない |

**どちらを返すかは、要求する側が指定する。サーバが公開されない閾値で暗黙に切り替えない。**

- 要求側が表現を指定しなかった場合の既定の表現を定める(実装工程)
- **要求された表現を返せない場合、別の表現へ黙って切り替えない。** 返せないことを明示する
- 応答は常に本文の欄と URL の欄の両方を持ち、用いない側を空とする。**欄そのものが状況によって消える形にしない**

**この規則を置く理由は、サーバ側の暗黙の分岐が実際に破綻しているためである。** GitHub Contents API は 1MB を超えると `content` が空文字列になる設計であり、クライアント実装がこれに気づけず空のデータを下流へ流す事故が複数報告されている([n8n#16417](https://github.com/n8n-io/n8n/issues/16417)、[hub4j/github-api#1558](https://github.com/hub4j/github-api/issues/1558)、[palantir/go-githubapp#227](https://github.com/palantir/go-githubapp/issues/227))。**エラーではなく成功応答の形が変わるため、クライアントが検出できない。**

切り替えの境界値(バイト数)は**設定で指定できるものとし、既定値を持たせる**。定数にしない。[[extensibility]] 要求1 は「導入先ごとに違う可能性はあるか」で設定化を判定するとしており、切り替えの境界値は利用者の回線とクライアントの事情で変わる。

### 4. MCP は HTTP を主とし、stdio も提供する

主たる利用形態は常駐サーバへの接続である。stdio はローカル単体利用の経路として残す。**どちらか一方のみを提供しない。**

MCP 仕様が定めるトランスポートは stdio と Streamable HTTP の2つである。HTTP+SSE は非推奨となっており、採らない。

**MCP 仕様は認証の責務をトランスポートごとに分けている。** HTTP は OAuth 2.1 に基づく認可を要求し、stdio は仕様に従わず環境から資格情報を取得すべきものとしている([Authorization](https://modelcontextprotocol.io/specification/draft/basic/authorization))。**本決定により、ADR-0004 は2つの異なる認証モデルを扱う必要がある。** この制約を ADR-0004 へ引き継ぐ。

### 5. 初回構築中のファイルは候補に含めず、未完了 N 件を明示する

索引の構築が完了していないファイルを検索結果・一覧の候補に含めない。**同時に、未完了の件数とその理由を応答に必ず載せる。**

#### REST

検索・一覧応答のトップレベルに `meta` を置き、結果本体と同居させる。

```json
{
  "items": [ ... ],
  "meta": {
    "pending_count": 12,
    "pending_reason": "initial_index_building"
  }
}
```

**`pending_count` は、その要求の対象範囲における未完了件数とする。** システム全体の未処理件数ではない。利用者が知りたいのは「いま行った検索が取りこぼしているか」であり、倉庫全体にいくつ未処理があるかではない。

Elasticsearch の非同期検索が `is_partial` / `is_running` を結果と同じ応答オブジェクトに置く構造と同型である([Run an async search](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-async-search-submit))。**Elasticsearch の `is_partial` も、システム全体ではなくそのクエリが対象としたシャードにスコープされている。**

**`meta` というキー名は [JSON:API](https://jsonapi.org/format/) から借りる。ただし JSON:API に準拠しない。** `data` / `type` / `id` といった JSON:API の他の規約は採らず、結果本体は `items` とする。借用するのはキー名のみである。

#### MCP

検索・一覧ツールの結果に、**件数と理由の両方**を機械可読なメタデータとして載せる。REST の `meta` と同じ構造・同じスコープ(要求の対象範囲)を用いる。

ログ検索の Axiom が `total_matching` / `returned_rows` / `truncated` / `truncation_reason` をデータ本体と併記する構造がこれにあたる。**件数だけでなく理由を持たせる**ことが本決定の要件である。「まだ読めていない」と「そもそも存在しない」を利用者と AI エージェントが区別できるようにするためである(決定2-1 の3状態に対応する)。

`isError: true` は用いない。MCP 仕様において `isError` はツール実行エラー(API 失敗・入力検証エラー・ビジネスロジックエラー)を表す。**「結果は取得できたが一部が未完了」は成功した応答であり、`isError` の意味論に当たらない。**

### 6. 本 ADR が決めないこと(スコープ外)

- **認証・認可の設計。ADR-0004 の対象である。** JWT クレームの設計、スコープの表現、検証の責務分界を本 ADR では扱わない
- エンドポイントの完全な一覧と OpenAPI 定義(実装工程の対象)
- MCP ツールの具体的な引数スキーマ(F-001〜F-003 の機能仕様の対象)

## 検討した選択肢

各案の採否は takenori-kusaka が選択した(2026-08-12)。論点1・2 の採否は価値責任者として、下位論点(安定 ID を何にするか / 未完了 N 件をどこにどう載せるか)および論点3 の採否は技術判断者として選択している。

**理由欄の文章は AI が起草し、選択者が内容を確認したうえで採用した。先行事例の調査も AI が実施し、判断の材料として提示したものである。**

### 論点1: 外部が指す識別子

| 案 | 採らなかった理由 |
| --- | --- |
| **パスを識別子にする** | **利用者はファイルを移動・改名する。パスを識別子にすると外部の参照が壊れる。** |
| **安定 ID を識別子にする(採用)** | — |

### 論点1の下位論点: 安定 ID を何にするか

先行事例を調査したうえで判断した(2026-08-12)。

| 案 | 採らなかった理由 |
| --- | --- |
| **内容ハッシュをそのまま対外 ID にする** | **内容を上書きするとハッシュが変わり、外部参照が切れる。** また、同一内容で別パスの2ファイルが対外的に同一 ID となり、利用者が「別々に置いた2つのファイル」と認識している実態と食い違う。 |
| **内容ハッシュとは別の論理 ID を発行する(採用)** | — |

**先行事例の整理**(判断の材料として調査したもの。各案の性質であり、選択の理由ではない):

| システム | 方式 | 内容ハッシュとの関係 |
| --- | --- | --- |
| [Perkeep(旧 Camlistore)](https://perkeep.org/doc/schema/permanode) | permanode(署名付き乱数)+ blobref(内容ハッシュ) | 意図的に分離。permanode は不変の安定参照、指し先のハッシュは変わってよい。**ただし permanode はパスの初出で自動発行されるものではなく、明示的に作られる**([`pk-put --permanode` は既定 false](https://perkeep.org/cmd/pk-put)) |
| Git | blob ハッシュは内容アドレスのみ | ファイルの同一性は tree のパスと commit 履歴が担う。rename は事後的なヒューリスティック検出 |
| [IPFS / CID](https://docs.ipfs.tech/concepts/content-addressing/) | CID = 内容ハッシュ | 同一内容は同一 CID。変化する対象への安定参照は [IPNS](https://docs.ipfs.tech/concepts/ipns/) を別レイヤーで用意 |
| Google Drive / Dropbox | fileId は内容ハッシュと独立 | rename / move でも fileId は不変。内容の重複排除は別レイヤー |
| restic / borg | チャンク層(内容アドレス)とアーカイブ層(論理ファイル) | 重複排除とファイル同一性判定は完全に別レイヤー |
| [Syncthing](https://github.com/syncthing/syncthing/issues/5689) / [Nextcloud デスクトップ](https://github.com/nextcloud/desktop/issues/6500) | 論理的な同一性を**ファイルシステムの観測から推定する** | 移動・改名の検出を自前で行う。**両者とも検出の不具合を長期の課題として抱えている** |

**内容の同一性と論理的な同一性を分離する設計は、Perkeep・IPNS・クラウドストレージ・重複排除バックアップのいずれにも共通して現れる。**

**ただし、これらは2つのクラスに分かれる。** Google Drive・Dropbox・Perkeep は、移動や改名を **API として受け取る**か、明示的な宣言として受け取る立場にあり、同一性を推定する必要がない。Syncthing・Nextcloud デスクトップは、ファイルシステムを**観測して推定する**立場にある。

**Filetto は後者である。** 利用者の資料倉庫を読み取り専用で観測する設計(S0-004)であり、移動・改名を API として受け取らない。**したがって、安定 ID の不変性は「宣言すれば成立するもの」ではなく、推定機構の実装によって初めて成立する。** 決定2 の末尾でこの機構を実装工程の対象とした理由である。

### 論点2: ファイル内容の受け渡し

| 案 | 採らなかった理由 |
| --- | --- |
| **本文直返しのみ** | **大きいファイルを本文に載せることになる。** MCP 経由では AI エージェントの文脈をファイル本文が占有する |
| **署名付き URL のみ** | **小さいテキストにも往復が発生する。** 検索結果の断片を読むだけで毎回 URL の取得と取り出しの2回を要する |
| **両方を提供する(採用)** | — |

#### 論点2の下位論点: どちらの表現を返すかを誰が決めるか

| 案 | 採らなかった理由 |
| --- | --- |
| **サーバが閾値で自動的に切り替える**(GitHub Contents API 型) | **クライアントが分岐に気づけない。** 応答の形が黙って変わるため、小さいファイルで動作確認した実装が大きいファイルで空のデータを流す。GitHub Contents API で実際に複数の事故が報告されている |
| **常に一方に固定する**(Slack 型 = 常に URL / S3 型 = 常に本文) | **論点2 の決定(両方を提供する)と矛盾する** |
| **要求する側が指定する(採用)** | — |

調査した実在 API(GitHub Contents の `Accept` メディアタイプ、Google Drive の `alt=media`、Slack、Amazon S3)では、**表現の選択権はいずれもクライアントにあるか、一方に固定されている**。サーバが公開しない閾値で暗黙に切り替える例は確認できなかった。

### 論点3: MCP の提供形態

| 案 | 採らなかった理由 |
| --- | --- |
| **stdio のみ** | **主たる利用形態は常駐サーバへの接続である。** stdio のみでは常駐構成から使えない |
| **HTTP を主とし stdio も提供(採用)** | — |

### 論点4: 初回構築中の扱い

| 案 | 採らなかった理由 |
| --- | --- |
| **未完了のファイルを候補に含める** | **索引が未完成のファイルは検索の質を担保できない。** 読めていないテキストに対する検索結果は誤りである |
| **候補に含めず、黙って結果を返す** | **利用者は「無い」と誤解する。** [[calm-technology]] が明示的に禁じている |
| **候補に含めず、未完了 N 件を明示する(採用)** | — |

### 論点4の下位論点: 未完了 N 件をどこにどう載せるか

REST と MCP のそれぞれについて、先行事例を調査したうえで判断した(2026-08-12)。

**REST**

| 案 | 採らなかった理由 |
| --- | --- |
| **専用ステータスエンドポイント**(Meilisearch の `isIndexing` 型) | **呼ばなければ気づけない。** 利用者に追加の操作を課すことになり、[[calm-technology]] の「利用者に管理タスクを暗黙に課さない」と衝突する |
| **HTTP レスポンスヘッダ** | **見落とされやすい。** 多くのクライアントはボディのみを読む。調査した範囲でこの方式の採用例は確認できなかった |
| **ページネーション統合型**(Dropbox の `has_more` / Google Drive の `nextPageToken`) | **「続きがあるか」と「まだ読めていないか」は意味が異なる。** 混同すると、利用者は続きを取得すれば全件揃うと解釈する |
| **トップレベル meta(採用)** | — |

**MCP**

MCP の実装事例を横断的に調査した。Web 検索系(Brave / Tavily / Exa)、ドキュメント検索系(Notion / Atlassian / Slack)、コード検索系(GitHub)、ベクトル検索系(Weaviate / Pinecone / Chroma)、ログ検索系(Axiom)を対象とした。

| 案 | 採らなかった理由 |
| --- | --- |
| **専用ツールに分離する**(Qdrant 系コミュニティ実装の `get_index_status` 型) | **REST の専用エンドポイント案と同じ理由。** 呼ばなければ気づけない |
| **`isError: true` を用いる** | **意味論上の誤用である。** 一部が未完了でも応答自体は成功している |
| **自然文のみで表現する**(Exa の `autopromptString` 型) | **AI エージェントが構造化データとして扱えない。** 件数を機械的に取り出せない |
| **件数のみを載せ、理由を載せない** | **「まだ読めていない」と「そもそも存在しない」を区別できない。** 区別できることが論点4 の目的である |
| **理由付きメタデータを結果に併記する(採用。Axiom 型)** | — |

**調査から得られた事実として記録する:**

- **「検索結果が不完全であることを伝える」問題に、MCP において確立した単一の業界標準パターンは存在しない。** REST の世界(Elasticsearch / Meilisearch / Dropbox / Google Drive)には確立したパターンが複数あるのに対し、MCP の実装はばらついている
- 理由まで含めて機械可読に持つ実例は Axiom の1件のみであり、**主流とは言えない**
- MCP 仕様の `structuredContent` は任意の JSON 構造をツール結果に持たせる正当な仕組みだが、**Claude Code を含む複数のクライアント実装で無視・欠落するバグが報告されている**([anthropics/claude-code#15412](https://github.com/anthropics/claude-code/issues/15412))。仕様自体も「後方互換のため同じ内容を `TextContent` としても返すべき(SHOULD)」としている
- [Atlassian 公式 MCP サーバ](https://github.com/atlassian/atlassian-mcp-server/issues/118)は `nextPageToken` / `isLast` を設計上持つ想定でありながら、実装のバグで応答に含まれずページングが機能していない。**フィールドを定義することと実際に機能させることの間にはギャップが生じる**

## 可逆性

| 項目 | 内容 |
| --- | --- |
| 後から変えられるか | **決定によって異なる。決定2(安定 ID)が最も変えにくい** |
| 変えるとしたら必要なこと | 決定2 を変えると、**外部が保持しているすべての参照が無効になる**。安定 ID を発行した後に方式を変える経路は、旧 ID から新 ID への恒久的な対応表を持つ以外にない。決定3(受け渡し)・決定4(MCP 形態)・決定5(未完了の明示)は応答スキーマの変更で済む |
| いつまでなら安く変えられるか | **決定2 は、外部が安定 ID を保持し始める前まで**(初回リリース前)。それ以降は、外部の参照を壊すか対応表を永続的に持つかの二択になる |

**決定2 を最初に固定する理由がここにある。** 他の決定は後から変えられるが、識別子だけは外部の手に渡った時点で変えられなくなる。

## 非機能への影響

| 項目 | 影響 |
| --- | --- |
| 性能 | 決定2 により `index.sqlite` の参照が1段増える(パス → 安定 ID → 内容ハッシュ)。**派生物の重複排除は第3段で保たれるため、ディスク消費は増えない**。決定3 の署名付き URL は、大きいファイルの本文が応答を占有することを防ぐ |
| 可用性 | 決定5 により、索引が未完成でも検索 API は応答を返す(未完了件数を添えて)。**構築完了を待たせない** |
| セキュリティ | 決定3 の署名付き URL は有効期限と対象を限定する。**ただし署名方式・有効期限・認可との関係は ADR-0004 の対象であり、本 ADR では定めない** |
| 運用 | 決定2 の安定 ID は原本が消えても残る。**決定2-3 により保持期間を設定で持たせ、無期限に残さない。** 既定値と派生物の解放条件は実装工程で定める |

## 事業への影響

| 項目 | 内容 |
| --- | --- |
| 顕在化が分かる兆候 | 決定2 が誤りだった場合の兆候は、**外部の参照が壊れたという報告**である。決定5 が不十分だった場合の兆候は、**「検索しても出てこない」という報告**(実際には索引の構築中である) |
| 回復に要する時間 | 決定3・4・5 は応答スキーマの変更で **1〜2日**。**決定2 は初回リリース後には実質的に回復できない**(旧 ID の対応表を恒久的に抱えることになる) |
| 影響を受ける利用者・業務 | 決定2 は外部連携を行うすべての利用者。決定5 は初回構築を経験するすべての利用者(全員が一度は通る) |

## 影響

**この決定によって得られるもの:**

- **外部の参照が、ファイルの移動・改名・内容の上書きで壊れない**(決定1・2)
- **同一内容の別ファイルを別のものとして扱える**(決定2)。重複排除の利得は派生物の層で保たれる
- **索引の構築完了を待たずに検索 API を提供できる**(決定5)
- **「読めていない」「捨てた」「存在しない」の3つを、人と AI エージェントの双方が区別できる**(決定2-1・決定5)
- **過去の版を、安定 ID を保ったまま指せる**(決定2-2)
- **クライアントが応答の形を予測できる**(決定3)。大きいファイルで黙って空のデータを受け取ることがない

**トレードオフ:**

- **`index.sqlite` のマッピングが2段から3段に増える**(決定2)。S0-004 の提案より複雑になる
- **安定 ID の発行機構と、移動・改名の推定機構を実装する必要がある**(決定2)。内容ハッシュをそのまま使えば不要だった。**Syncthing・Nextcloud デスクトップが長期の課題として抱えている領域であり、実装の難所である**
- **本文直返しと署名付き URL の2経路を維持する**(決定3)。片方だけを変更すると挙動が乖離する
- **MCP のトランスポートを2つ維持する**(決定4)。認証モデルが異なる(HTTP は OAuth 2.1、stdio は環境から取得)ため、実装は分岐する
- **REST と MCP で同じメタデータ構造を二重に維持する**(決定5)。片方だけを変更すると両者が乖離する
- **決定5 の MCP 側は、確立した業界標準に乗っていない。** 実例が1件しか確認できていない構造を採る

**この決定で解決しないこと:**

実装工程で定めるもの:

- **移動・改名を推定する同一性判定の方式**(決定2)。ファイルシステムの識別子を用いるか、内容ハッシュとの併用とするか。**単一の識別子のみに依拠する方式は採らない**(削除後の識別子の再利用により、別のファイルが同じ識別子を持ちうる)
- **ファイル監視の経路と、監視が取りこぼした場合の再走査の設計**(決定2)。**再走査の経路でも同一性判定が成立することを要件とする**
- **一時ファイル経由の置換(保存時に別名で書いてから置き換える方式)の扱い**(決定2)。同一パスでファイルシステムの識別子が変わるため、上書きとして扱うか新規として扱うかを定める
- **派生物を解放する条件**(決定2-3)。同一内容を指す安定 ID が複数あるため、1つの安定 ID の消失で派生物を削除すると、生存している側の検索が壊れる
- **安定 ID の保持期間の既定値**(決定2-3)
- **本文直返しと署名付き URL を切り替える境界値の既定値**(決定3)。設定で変更できるものとする
- **安定 ID の具体的な形式**(UUID か連番か、文字列表現)。**発行の機構は差し替えられる境界の背後に置く**([[extensibility]] 要求2)
- **版の識別子の形式**(決定2-2)

他の ADR が扱うもの:

- **署名付き URL の有効期限・署名方式**。認可と不可分であり ADR-0004 の対象
- **MCP の2つの認証モデル**(HTTP の OAuth 2.1 / stdio の環境からの取得)。ADR-0004 の対象

機能仕様(F-001〜F-003)が扱うもの:

- **`meta` の具体的なフィールド名とスキーマ**
- **応答における本文の欄と URL の欄の具体名**

本 ADR が扱わないもの:

- **コンテナ構成(単一イメージか複数か)。** `context/projects/P-001.md` 未決の論点5 は期限を本 ADR としているが、Issue #14 の受入基準に含まれていない。**本 ADR では決めない。** P-001 側の期限の記載を更新する必要がある
- **`meta` の具体的なフィールド名とスキーマ**は F-001〜F-003 の機能仕様で確定する。本 ADR は「件数と理由の両方を、結果と同じ応答に載せる」ことのみを定める
- **MCP の `structuredContent` を用いるか、テキスト content 内の JSON とするか**は対象外。クライアント側の欠落実績(上記)を踏まえ、実装着手時に測って定める
