# ADR-0004: VersionStore が Lore へつなぐ形を配置ごとに決める

## ステータス

提案(2026-10-27)。起案は AI の担い手(Claude)。採否と「採らなかった理由」の記入は技術判断者(G-3)が行う。

## コンテキスト

F-001 の前提1(`specs/F-001/spec.md`)は「`loreserver` が同一の `docker compose` 内で常駐する」であり、受入基準22(`loreserver` へ接続できない場合は 503 を返し、検索と閲覧を継続する)もこれを前提にしている。この前提は 2026-08-12 の判断(旧 ADR-0008。2026-08-14 に ADR のディレクトリを廃した際、決定の実体を仕様へ移した)に由来する。そこでは `loreserver` の常駐による +1 コンテナを受け入れている。

一方、Task-8(#184・#185)の `LoreVersionStore` は、Lore の Python SDK `lore-vcs` 0.11 の**オフラインのローカル保管**(`offline=True`)で実装した。S0-005 の時点(JS SDK 0.8.6)では「ライブラリ単体では成立せず、サーバが必須」だったが、0.11 の Python SDK ではサーバ無しでリポジトリを作り、保存・履歴・取り出しができることを手元で確かめた。**この実装は前提1 から外れており、前提1 に合わせるか、前提1 を改めるかが決まっていない。**

Task-11(受入基準22)の実装はこの決定に依存するため、Task-11 の前に決める。あわせて、利用者から AWS(Lambda・S3)での配置の可能性が挙がっている(2026-10-26)。

制約(Takenori Kusaka、2026-10-27): **利用していないときの維持費を極小にする。** 費用をかけられるなら、より良い検索エンジンを選べるため。常時起動の計算資源(ECS / Fargate など)は選択肢にならない。

## 検討した選択肢

各案の性質は AI の担い手が整理した。**採らなかった理由の欄は人が書く**(`.claude/skills/adr-write/SKILL.md` 手順4)。調べた事実と出典は[検討の材料](#関連)にまとめた。

判断は2段に分かれる。企画書(`docs/project-brief.md`)は初版を「`docker compose up` で手元に立てる」「運用時の金銭コスト $0」「実行時の外部通信なし」とし、S3 等のクラウドストレージ対応を初版の範囲外としている。

1. **初版(compose・手元)で Lore へどうつなぐか**(A・B)。Task-11 が依存するため、いま決める
2. **AWS に置く配置の型で版をどう保管するか**(C・D・F・G)。初版の範囲外。1 の決定を縛らないが、`VersionStore` の境界の保ち方に効く

### 初版(compose・手元)

| 案 | 性質 | 採らなかった理由 |
| --- | --- | --- |
| A. 前提1 のとおり、`loreserver` を compose に常駐させ、アプリはサーバの遠隔(`lore://HOST:PORT/NAME`)へつなぐ。オフラインのローカル保管は検査用にだけ使う | 仕様・受入基準22 を変えずに済む(サーバ停止で 503)。コンテナが 1 つ増え(公式 Dockerfile は Rust のソースビルド。イメージの大きさと起動時間は未測定、S0-005)、UDP 41337 を使う。**`lore-vcs` 0.11 から遠隔へつなぐ動作は未確認**。`loreserver` が単一障害点になる | |
| B. 前提1 を改め、Lore のオフライン保管をアプリと同じボリュームに置く(Task-8 の実装のまま) | コンテナが増えない。オフライン保管は Lore の公式に想定された使い方(Lore System Design §3.1・§6.3・§9.2)で、遠隔は後から足せる設計。受入基準22 は前提を失い、「保管が読めないとき 503、検索と閲覧は継続」等への書き換え(**仕様の変更。価値責任者の判断**)を要する。複数のアプリのプロセスから同じ保管を触る場合の排他は未確認 | |

手元の compose では、使っていない間の金銭の費用はどちらの案もゼロである。

### AWS に置く配置の型(初版の範囲外)

使っていない間の費用を極小にするには、計算を Lambda、状態を S3 と従量課金のサービスに置くことになる。NAT Gateway・インターフェース型の VPC エンドポイント・KMS の顧客管理鍵は、使っていなくても月額がかかる。

| 案 | 性質 | 採らなかった理由 |
| --- | --- | --- |
| C. `loreserver` を ECS / Fargate / EC2 で動かし、保管を S3 + DynamoDB にする(Lore の公式の AWS 構成の型) | Lore の公式の AWS 構成は EC2 のエッジ + ECS の書き込み層 + S3 + DynamoDB で、常時起動の計算資源が前提。利用がなくても計算資源の費用がかかる | 利用していないときの維持費を極小にする制約に反する。常時起動の ECS / Fargate は選択肢にならない(Takenori Kusaka、2026-10-27) |
| D. AWS Lambda で `loreserver` を動かす | **成立しない**。主な接続が QUIC(UDP)で、Lambda は UDP の着信を受けられない。常駐の受け口を前提にした設計で、Lambda の実行モデルと合わない(S0-005) | |
| F. `VersionStore` の別実装として、原本のバケットの S3 バージョニングを使う(Lore を使わない) | 使っていない間の費用は旧版の保管料だけ。境界(save / versions / read)は版 id・一覧・取得で満たせる見込み。上書きは S3 が自動で残すため、上書きの走査(Task-8 の `OverwriteWatcher`)が不要になる。受入基準20・21 の多くは S3 の耐久性とチェックサムに置き換わる(受入基準の読み替えを要する)。**重複排除が無い**(版ごとに全体を保管。Lore は S0-005 で単純加算の 9.6%)。古い版はライフサイクルで安い層へ移せる。実装と検査が2系統になる。旧 ADR-0008 の「履歴管理を自前で持たない」には、S3 の機能を使う形なので反しない見込みだが未確認 | |
| G. アプリを Lambda に置き、Lore のオフライン保管を S3 Files(2026-04 GA。EFS を土台にした NFS v4.2)の上に置く | 使っていない間の費用は保管料と、期限切れで 0 へ戻る高速層のキャッシュ(約 $0.30/GB-月)。Lambda を VPC に置く必要がある(S3 はゲートウェイ型エンドポイントで足りる)。アクセスは 1 回 32KB が最小の課金で、Lore の保管(小さいファイルが多い)とは割高になりやすい。ファイルシステムから S3 への反映は約 60 秒遅れ、NFS のロックは S3 API からの書き込みを止めない。**Lore のオフライン保管が NFS 上で動くか、同時に起動した複数の Lambda から同じ保管を触ったときの排他は未確認**。旧版の E(保管ディレクトリを S3 と自前で同期する)は、この案に含めた | |

## 可逆性

| 項目 | 内容 |
| --- | --- |
| 後から変えられるか | 変えられる。`VersionStore` の境界の背後にあり、API 層・走査・検証は境界だけを使う |
| 変えるとしたら必要なこと | つなぐ形の切り替え(設定)と、既存の保管からの移し替え。オフラインの保管と `loreserver` の保管の間で版を移す手順は未確認 |
| いつまでなら安く変えられるか | 本番の保管に版が積み上がる前(初回の出荷まで) |

## 非機能への影響

| 項目 | 影響 |
| --- | --- |
| 性能 | 未測定(A はコンテナ網越し、B は同じホストのファイル。G は NFS 越し、F は S3 API 越し) |
| 可用性 | A は `loreserver` が単一障害点になり、受入基準22 の 503 が働く場面がある。B は保管のボリュームの可用性にだけ依る。F は S3 の可用性に依る |
| セキュリティ | A は `loreserver` をコンテナ網の内側に閉じ、ホストへ公開しない(旧 ADR-0008)。AWS の型(F・G)は API が公開の入口になるため、認証(F-003 では既定で無効)と権限設計が加わる |
| 運用 | A は保管パス(または S3)の明示設定を怠ると版が消える(S0-005)。どの案でも定期検証と `.~loretemp` の掃除(Task-10)を回す配線が要る |

## 事業への影響

| 項目 | 内容 |
| --- | --- |
| 影響を受ける利用者・業務 | 版の履歴を使う利用者。閲覧・検索だけの利用者は、A でも受入基準22 により影響を受けない |
| 顕在化が分かる兆候 | 版の保存・取り出しの失敗や 503 の頻発、検証で記録される破損の件数(Task-10 の `corrupt_versions`) |
| 回復に要する時間 | 未見積もり(設定の切り替えは数時間〜1日、保管の移し替えは保管量と手順の確認しだいで数日〜) |
| 取り消しの可否 | 人手で戻せる(出荷前)。出荷後は保管の移し替えを伴う |
| 影響する必達基準 | F-001 受入基準15〜22 |
