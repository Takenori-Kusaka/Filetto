# ADR-0004: VersionStore が Lore へつなぐ形を配置ごとに決める

## ステータス

提案(2026-10-27)。起案は AI の担い手(Claude)。採否と「採らなかった理由」の記入は技術判断者(G-3)が行う。

## コンテキスト

F-001 の前提1(`specs/F-001/spec.md`)は「`loreserver` が同一の `docker compose` 内で常駐する」であり、受入基準22(`loreserver` へ接続できない場合は 503 を返し、検索と閲覧を継続する)もこれを前提にしている。この前提は 2026-08-12 の判断(旧 ADR-0008。2026-08-14 に ADR のディレクトリを廃した際、決定の実体を仕様へ移した)に由来する。そこでは `loreserver` の常駐による +1 コンテナを受け入れている。

一方、Task-8(#184・#185)の `LoreVersionStore` は、Lore の Python SDK `lore-vcs` 0.11 の**オフラインのローカル保管**(`offline=True`)で実装した。S0-005 の時点(JS SDK 0.8.6)では「ライブラリ単体では成立せず、サーバが必須」だったが、0.11 の Python SDK ではサーバ無しでリポジトリを作り、保存・履歴・取り出しができることを手元で確かめた。**この実装は前提1 から外れており、前提1 に合わせるか、前提1 を改めるかが決まっていない。**

Task-11(受入基準22)の実装はこの決定に依存するため、Task-11 の前に決める。あわせて、利用者から AWS(Lambda・S3)での配置の可能性が挙がっている(2026-10-26)。

制約(Takenori Kusaka、2026-10-27): **利用していないときの維持費を極小にする。** 費用をかけられるなら、より良い検索エンジンを選べるため。常時起動の計算資源(ECS / Fargate など)は選択肢にならない。

## 検討した選択肢

各案の性質は AI の担い手が整理した。**採らなかった理由の欄は人が書く**(`.claude/skills/adr-write/SKILL.md` 手順4)。

| 案 | 性質 | 採らなかった理由 |
| --- | --- | --- |
| A. 前提1 のとおり、本番は `loreserver` を compose に常駐させる。オフラインのローカル保管は検査用にだけ使う | 仕様・受入基準22 を変えずに済む。`LoreVersionStore` にサーバへつなぐ形(`lore://HOST:PORT/NAME`)を足す必要がある。**`lore-vcs` 0.11 からサーバへつなぐ動作は未確認**。公式 Dockerfile は Rust のソースビルドで、イメージの大きさと起動時間は未測定(S0-005)。`loreserver` が単一障害点になる | |
| B. 前提1 を改め、本番もオフラインのローカル保管にする(`loreserver` を置かない) | コンテナが増えない。保管はアプリと同じボリュームに置く。受入基準22 は前提を失うため、**仕様の変更(価値責任者の判断)を要する**。複数のアプリのプロセスから同じ保管を触る場合の排他は未確認 | |
| C. A に加えて、AWS へ置く場合は `loreserver` を ECS / Fargate / EC2 で動かし、保管を S3 + DynamoDB にする(`mode = "aws"`) | `loreserver` のソースに S3 + DynamoDB の実装と設定の受け口がある(S0-005)。**実際の稼働は未測定**で、AWS 用の設定の見本は同梱されていない。`loreserver` が常時起動するため、利用がなくても計算資源の費用がかかる | 利用していないときの維持費を極小にする制約に反する。常時起動の ECS / Fargate は選択肢にならない(Takenori Kusaka、2026-10-27) |
| D. AWS Lambda で `loreserver` を動かす(microVM を含む) | S0-005 の調べでは**成立しない**。主な接続が QUIC(UDP 41337)で、Lambda は UDP の着信を受けられない。常駐する受け口を前提にした設計で、Lambda の実行モデルと合わない。Lambda の `/tmp` は揮発する | |
| E. アプリを Lambda に置き、版の保管は B の形で S3 に置く(Lore の保管ディレクトリを S3 と同期する等) | Lore のオフライン保管はローカルのファイルシステム前提で、S3 を直接の保管先にする口は SDK に見当たらない。同期を自前で持つことになり、同時実行時の整合を Filetto が引き受ける。**未検討に近い** | |
| F. 配置ごとに `VersionStore` の実装を替える。compose では Lore(A または B)、Lambda では S3 のバージョニングを使う実装を足す | `VersionStore` の境界(save / versions / read)は S3 のオブジェクトのバージョニング(版の id・一覧・取得)で満たせる見込み。利用がないときの費用は保管量だけ。**重複排除が無い**(版ごとに全体を保管する。Lore は S0-005 で単純加算の 9.6%)。実装が2つになり、検査も2系統になる。旧 ADR-0008 の「履歴管理を自前で持たない」には、S3 の機能を使う形なので反しない見込みだが未確認 | |
| G. アプリを Lambda に置き、B のオフライン保管を EFS に置く | 利用がないときの費用は EFS の保管量だけ。Lore のオフライン保管がネットワークのファイルシステム上で動くか、同時に起動した複数の Lambda から同じ保管を触ったときの排他は**未確認**。Lambda を VPC に置く必要がある | |

## 可逆性

| 項目 | 内容 |
| --- | --- |
| 後から変えられるか | 変えられる。`VersionStore` の境界の背後にあり、API 層・走査・検証は境界だけを使う |
| 変えるとしたら必要なこと | つなぐ形の切り替え(設定)と、既存の保管からの移し替え。オフラインの保管と `loreserver` の保管の間で版を移す手順は未確認 |
| いつまでなら安く変えられるか | 本番の保管に版が積み上がる前(初回の出荷まで) |

## 非機能への影響

| 項目 | 影響 |
| --- | --- |
| 性能 | 未測定(A・C はネットワーク越し、B は同じホストのファイル) |
| 可用性 | A・C は `loreserver` が単一障害点になり、受入基準22 の 503 が働く場面がある。B は保管のボリュームの可用性にだけ依る |
| セキュリティ | A は `loreserver` をコンテナ網の内側に閉じ、ホストへ公開しない(旧 ADR-0008)。C は AWS の権限設計が加わる |
| 運用 | A・C は保管パス(または S3)の明示設定を怠ると版が消える(S0-005)。どの案でも定期検証と `.~loretemp` の掃除(Task-10)を回す配線が要る |

## 事業への影響

| 項目 | 内容 |
| --- | --- |
| 影響を受ける利用者・業務 | 版の履歴を使う利用者。閲覧・検索だけの利用者は、A・C でも受入基準22 により影響を受けない |
| 顕在化が分かる兆候 | 版の保存・取り出しの失敗や 503 の頻発、検証で記録される破損の件数(Task-10 の `corrupt_versions`) |
| 回復に要する時間 | 未見積もり(設定の切り替えは数時間〜1日、保管の移し替えは保管量と手順の確認しだいで数日〜) |
| 取り消しの可否 | 人手で戻せる(出荷前)。出荷後は保管の移し替えを伴う |
| 影響する必達基準 | F-001 受入基準15〜22 |
