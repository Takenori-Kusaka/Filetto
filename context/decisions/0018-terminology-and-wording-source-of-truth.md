## 決定

**判定者が既に方向を示しています。** **本 ADR はその方向のもとで、具体を確定させるものです。**

> **文言表はちゃんとプログラミング言語的に管理すること。label.ts のように用語を定数化したり、文章を作成したりする場合はそういった用語セットを変数参照して利用できるようにする**

**「ソースコード化する」という方向に反する案は、選択肢として並べません。** **並べると、既に済んだ判断をもう一度させることになります。**

### 1. `context/glossary.md`(ドメイン用語)と文言表(利用者へ見せる文)の関係

**同一の形式・別ファイルとし、名前空間で分ける(案 1-D)。**

| ファイル | 名前空間 | 対象 |
| --- | --- | --- |
| `context/terms.json` | `term.*` | **ドメイン用語**(用語 / コード上の名前 / 定義 / 使わない語) |
| `context/labels.json` | `label.*` | **利用者へ見せる文**(付記の文言を含む) |
| `context/mappings.json` | `map.*` | **機械が使う写像**(字形の対応表 / 形式ごとの位置の表現) |

**3つに分ける理由**: **要求される属性が重ならないためです。** 用語は「使わない語」を持ち、文言は基準11-3 が求める「主語」「対象を指す語」を持ち、写像は左辺と右辺だけを持ちます。**1ファイルに統合すると、項目ごとに空欄の欄が生じます。**

**読み書きの道具は1組で済みます。** 形式が同じだからです。

**`context/glossary.md` は残します。** **`terms.json` から生成する読み物とします。** **正本は `terms.json` です。**

### 2. 正本の形式

**JSON(案 2-A)。**

| 制約 | JSON での充足 |
| --- | --- |
| **Python から読める** | **標準ライブラリ `json`。追加の依存が0** |
| **TypeScript から読める** | **`JSON.parse`。追加の依存が0** |
| **形式を機械で検査できる** | **JSON Schema。基準11-3 の起動時検査に使える** |
| 運用に依存する値を定数にしない | ファイルとして外にある |

**「実装から変数参照できる」形は、生成物で実現します。**

| 生成物 | 用途 |
| --- | --- |
| **`src/filetto/labels.py`**(定数と型) | **Python 側。IDE の補完と型検査が効く** |
| **`web/src/labels.ts`**(定数と型) | **TypeScript 側。判定者が挙げた `label.ts` の形** |

**実行時は正本の JSON を読みます。** **生成物はキーと型のためのものであり、値の正本ではありません。** **基準11-2 が求める「保管先を環境変数から読む」形と両立します。**

**生成物と正本の乖離は検査で止めます**(決定4)。

### 3. 文書側の参照方法

**文書は正本を参照しません。転記のまま、一致を検査します(案 3-A)。**

**Markdown から定数を参照する標準的な手段はありません。** **独自の記法を持ち込むと、リポジトリ上の文書がそのままでは読めなくなります。**

**転記した箇所には目印を付けます**(案 3-D)。

```markdown
<!-- from: label.unreadable_page -->
> 3ページ目の表を、私は読み取れませんでした
<!-- /from -->
```

**`spec-lint` の除外区間([PL-0006](../../docs/platform/PL-0006-spec-lint-scope.md))と同じ形です。** **既にある仕組みの延長であり、新しい記法を1つも増やしません。**

**目印を付け忘れた箇所は検査されません。** **これは受け入れます。** **目印の付いた箇所を確実に検査するほうが、全文を推測で検査するより誤検出が少ないためです。**

### 4. 揺れを検出する検査

**2つを置きます。**

| # | 検査 | 何を検出するか | G-5 の合否条件にするか |
| --- | --- | --- | --- |
| **4-C** | **生成物と正本の乖離** | `labels.py` / `labels.ts` が `*.json` と食い違ったこと | **する。** 機械的に判定でき、判断を要しない |
| **4-A** | **「使わない語」の出現** | `terms.json` の「使わない語」に登録した語が、文書・実装に現れたこと | **する。** 登録した語との突合であり、判断を要しない |
| 4-B | 転記の一致 | 目印の付いた区間が正本と1文字でも違うこと | **する**(決定3 の目印がある箇所のみ) |

**4-C は `session-definition-drift` と同型です。** 既に稼働している検査と同じ作りにします。

**いずれも「対象が0件のときは0件であることを出力」します**(`CLAUDE.md` 検査の原則2)。

**4-D(形態素解析で未登録語を検出)は採りません。** **一般名詞と区別がつかず、除外一覧の維持が続きます。** **`CLAUDE.md`「運用に依存する値を定数にしない」に照らして、除外一覧そのものが新しい運用負荷になります。**

**検出できないものを明記します。**

| 検出できないもの |
| --- |
| **「使わない語」に登録されていない揺れ。** 新しい言い換えは検出できない |
| **目印を付けていない転記** |
| **正本そのものの中の揺れ**(同じ概念に2つのキーを作った場合) |

**これらは検査で止まりません。** **レビューで見ます。**

## 検討した選択肢

### 論点1: ドメイン用語と文言の関係

| 案 | 採らなかった理由 |
| --- | --- |
| 1-A 同一の正本に統合する | **項目ごとに空欄の欄が生じる。** 用語の「使わない語」、文言の「主語」「対象を指す語」、写像の左辺右辺は重ならない |
| 1-B 別々の正本とし、文言表から用語を参照する | **参照が解決できない場合の扱いを別に決める必要がある。** 初版で持ち込む複雑さに見合わない |
| 1-C 別々の正本とし、相互に参照しない | **同じ概念が2箇所で別の語になっても検出されない。** D-002 が指摘した事象そのもの |

### 論点2: 正本の形式

| 案 | 採らなかった理由 |
| --- | --- |
| 2-B YAML | **Python 側に `PyYAML` の追加が要る**(現在の依存は空)。**インデントの誤りが黙って別の構造になる** |
| 2-C TOML | **TypeScript 側に追加の依存が要る。** 入れ子の表現が読みにくい |
| **2-D Markdown の表を正本とする** | **判定者の指示に反する。** 「プログラミング言語的に管理する」ことが条件であり、Markdown を正本にすると機械可読な形が生成物になる。**制約2(正本が2箇所にある状態を作らない)にも触れる** |
| 2-E gettext | **用語集(定義 / 使わない語)を表す欄が無い。** 多言語化は決裁に含まれていない |
| 2-F Project Fluent | **Python 実装が追加の依存。** 用語集の欄を表せない |

**JSON がコメントを書けない点は受け入れます。** **各項目に `note` の欄を持たせます。**

### 論点3: 文書側の参照方法

| 案 | 採らなかった理由 |
| --- | --- |
| 3-B プレースホルダを展開してコミットする | **展開前と展開後の2つが版管理に入る**(制約2) |
| 3-C 静的サイト生成時に展開する | **リポジトリ上の文書がそのままでは読めない。** 本案件に静的サイト生成の経路は無い |

**3-A と 3-D は排他ではありません。** **両方を採りました**(転記のまま置き、目印を付けて検査する)。

### 論点4: 揺れを検出する検査

| 案 | 採らなかった理由 |
| --- | --- |
| 4-D 形態素解析による未登録語の検出 | **一般名詞と区別がつかない。** 除外一覧の維持が続き、**それ自体が新しい運用負荷になる** |

## 可逆性

| 項目 | 内容 |
| --- | --- |
| **後から変えられるか** | **形式(JSON)は変えられる。** 生成物を通して参照しているため、**実装側の参照は生成器を差し替えれば追随する**。**文書側の転記は手で直す** |
| 変えるとしたら必要なこと | **正本の形式を変える場合、生成器と検査を書き換える。** 参照箇所が増えるほど高くなる |
| **いつまでなら安く変えられるか** | **F-003 の実装着手前。** 実装が文言表を参照し始めると、参照箇所の書き換えが加わる |

## 非機能への影響

| 項目 | 影響 |
| --- | --- |
| 性能 | **起動時に JSON の読み込みが1回加わる。** 実行中の増加は無い |
| 可用性 | **保管先が読めない場合、起動を中止する。** 基準11-3 と同じ扱いとする。**この経路は現在の受入基準に無く、F-003 の `plan.md` で扱う** |
| セキュリティ | **正本は利用者へ表示される文である。** 外部から差し替えられる場所へ置くと表示内容を差し替えられる。**保管先の書き込み権限が実質的な統制になる** |
| 運用 | **文言の変更が、実装の変更なしに行える。** 一方で**変更の記録が PR に残らない経路**(環境変数の指す先を直接編集する)が生じる |

## 事業への影響

| 項目 | 内容 |
| --- | --- |
| 顕在化が分かる兆候 | **同じ概念が、企画書と `spec.md` と UI で別の語で書かれていることが、レビューや利用者からの指摘で見つかること。** 現時点で `glossary.md` の登録は1件であり、**揺れが起きていないのではなく、記録されていない状態** |
| **回復に要する時間** | **正本の形式を変える場合、生成器と検査の書き換えで半日程度。** **文書側の転記の直しは、転記箇所の数に比例する。現時点では0件** |
| 影響を受ける利用者・業務 | **WebUI と MCP の応答を読むすべての利用者。** および `spec.md`・企画書・ADR を読む後任者 |

## 影響

**この決定によって変わること:**

- **`context/terms.json` / `labels.json` / `mappings.json` が正本になる。** `context/glossary.md` は生成物になる
- **`specs/F-002/spec.md` 基準15(字形の対応表)と基準33(位置の表現)、`specs/F-003/spec.md` 基準11-2(付記文言表)の保管先が、この正本に統一される**
- **CI に検査が2件増える**(生成物の乖離 / 「使わない語」の出現)

**トレードオフ:**

- **正本を1つにするほど、変更の影響範囲が広がる。** 1語の変更が実装と全文書へ及ぶ
- **検査を厳しくするほど、引用や外部資料の転記が引っかかる。** [PL-0006](../../docs/platform/PL-0006-spec-lint-scope.md) が同じ問題に除外区間を用意した経緯がある

**この決定で解決しないこと:**

- **既に書かれた文書の揺れの是正**。本 ADR は正本の持ち方を決めるものであり、**過去の文書の一括修正は別の作業**
- **`glossary.md` への用語の登録そのもの**。現在1件であり、**形式が決まっても中身は自動では埋まらない**
- **多言語化**。決裁に含まれていない
