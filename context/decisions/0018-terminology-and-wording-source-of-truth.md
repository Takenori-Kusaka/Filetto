## コンテキスト

**2026-08-14 の G-2 再判定(F-003)で、判定者が判断2 に条件を付けました。**

> **文言表はちゃんとプログラミング言語的に管理すること。label.ts のように用語を定数化したり、文章を作成したりする場合はそういった用語セットを変数参照して利用できるようにする、といった形をとり、あらゆる資料で表現や用語の揺れが起きないようにすること**

**判定そのものは通過です。** 条件は通過の効力に付随します。技術負債台帳の **[D-002](../../docs/debt-ledger.md)**(区分: 未解決事項 / 標準 7.3.2)として登録され、対処の期限は **F-003 の `plan.md` 作成前**です。

| `specs/F-002/spec.md` 基準15 | **字形の対応表**をソースコード内の定数として持ってはならない | **利用者へ見せる文ではない**(OCR の字形の写像) |

### 条件が求める範囲は、基準11-2 を超えています

| | 範囲 |
| --- | --- |
| **基準11-2** | **付記の文言表**を、環境変数から読む外部の場所へ置く。ソースコード内の定数として持たない |
| **本 ADR が扱うもの** | **案件全体の用語・文言の単一正本。** 実装だけでなく、`spec.md`・企画書・ADR・UI のすべてが同じ正本を参照する |

**G-2 の判定基準は「受入基準が検証可能な形で書かれているか」です。** **用語管理の方式は判定基準に含まれません。** そのため判定へ後から足さず、本 ADR で決めます。

## 検討した選択肢

**理由欄は技術判断者が記入します。** 以下は選択肢の列挙と、各案の性質の整理です。**「したがってこの案を推奨します」は書いていません。**

### 論点1: ドメイン用語と文言の関係

| 案 | 性質 | 採らなかった理由 |
| --- | --- | --- |
| **1-A 同一の正本に統合する** | 参照経路が1つになる。`glossary.md` の4欄(用語 / コード上の名前 / 定義 / 使わない語)と、文言表が基準11-3 で要求される属性(主語 / 対象を指す語)は**重ならない**。統合すると片方で空欄になる欄が生じる | <!-- 技術判断者が記入 --> |
| **1-B 別々の正本とし、文言表から用語を参照する** | 文言の中の語が用語集の項目を指す形。**用語の変更が文言へ波及する経路ができる**。参照が解決できない場合の扱いを別に決める必要がある | <!-- 技術判断者が記入 --> |
| **1-C 別々の正本とし、相互に参照しない** | いまの状態に近い。**同じ概念が2箇所で別の語になっても検出されない**(D-002 が指摘した事象そのもの) | <!-- 技術判断者が記入 --> |
| **1-D 同一の形式・別ファイルとし、名前空間で分ける** | 読み書きの道具が1組で済む。**ファイルは2つのため、どちらに置くかの判断が項目ごとに発生する** | <!-- 技術判断者が記入 --> |

**F-002 基準15 の字形の対応表をどう扱うかも、この論点に含まれます。** **字形の対応表は利用者へ見せる文ではありません**(OCR が誤認した字を正しい字へ写す表)。**同じ正本に属するかは判断が要ります。**

### 論点2: 正本の形式

**すべての案が制約1(定数にしない)を満たします。** 差は、実装からの参照のしやすさと、人が編集するときの誤りにくさに出ます。

| 案 | 性質 | 採らなかった理由 |
| --- | --- | --- |
| **2-A JSON** | 標準ライブラリだけで読める(Python `json` / TS `JSON.parse`)。**コメントを書けない**。**行末のカンマで壊れる**。基準11-3 の起動時検査は JSON Schema で書ける | <!-- 技術判断者が記入 --> |
| **2-B YAML** | 人が編集しやすい。コメントを書ける。**Python は `PyYAML` の追加が要る**(現在の依存は空)。**インデントの誤りが黙って別の構造になる** | <!-- 技術判断者が記入 --> |
| **2-C TOML** | Python 3.11+ は `tomllib` で標準。**TS 側は追加の依存が要る**。**入れ子の表現が読みにくい** | <!-- 技術判断者が記入 --> |
| **2-D Markdown の表を正本とし、機械可読な形へ変換する** | **`glossary.md` の現在の形をそのまま使える**。文書からそのまま読める。**変換の生成物が正本と2箇所になる**(制約2)。生成物の乖離検出が別に要る | <!-- 技術判断者が記入 --> |
| **2-E gettext(`.po` / `.mo`)** | 翻訳の業界標準。道具が揃っている。**用語集(定義・使わない語)を表す欄が無い**。**多言語化の予定は決裁に無い** | <!-- 技術判断者が記入 --> |
| **2-F Project Fluent(`.ftl`)** | 文言に条件分岐や複数形を書ける。**Python 実装(`fluent.runtime`)は追加の依存**。**用語集の欄を表せない** | <!-- 技術判断者が記入 --> |

**「実装から変数参照できる」形にするには、正本から言語ごとの生成物を出すか、実行時に正本を読むかのいずれかになります。**

| 方式 | 性質 |
| --- | --- |
| **生成物を出す**(`labels.py` / `label.ts`) | 判定者が挙げた `label.ts` の形。**IDE の補完と型検査が効く**。**生成物が正本と乖離しうる**(制約2)。乖離の検出は `session-definition-drift` と同型の検査で行える |
| **実行時に読む** | 乖離が起こらない。**存在しないキーを参照しても実行時までわからない**。基準11-2 が求める「環境変数から保管先を読む」形と直接つながる |

**この2つは排他ではありません。** 実行時に読みつつ、キーの一覧だけを生成物として出す形も取れます。

### 論点3: 文書側の参照方法

**Markdown から定数を参照する標準的な手段はありません。** 以下はいずれも独自の仕組みになります。

| 案 | 性質 | 採らなかった理由 |
| --- | --- | --- |
| **3-A 文書は正本を参照しない。転記のまま、一致を検査する** | 文書は読める状態のまま。**追加の仕組みが要らない**。検査が唯一の担保になる(論点4 と一体) | <!-- 技術判断者が記入 --> |
| **3-B プレースホルダ記法を書き、展開した文書をコミットする** | 文書に `{{term.stable_id}}` のような記法が現れる。**展開前と展開後の2つが版管理に入る**(制約2) | <!-- 技術判断者が記入 --> |
| **3-C 静的サイト生成時に展開する** | 版管理には記法だけが入る。**リポジトリ上の文書がそのままでは読めない**。**本案件に静的サイト生成の経路は現在ない** | <!-- 技術判断者が記入 --> |
| **3-D 引用ブロックへ「正本からの転記」の目印を付け、区間の一致を検査する** | **`spec-lint` の除外区間([PL-0006](../../docs/platform/PL-0006-spec-lint-scope.md))と同じ形**。既存の仕組みに近い。**目印を付け忘れた箇所は検査されない** | <!-- 技術判断者が記入 --> |

### 論点4: 揺れを検出する検査

**制約3 により、正本を置くだけでは足りません。** 検査が無い場合、正本は「守られているはずのもの」になります。

| 案 | 何を検出できるか | 何を検出できないか | 採らなかった理由 |
| --- | --- | --- | --- |
| **4-A 「使わない語」の出現検出** | `glossary.md` の「使わない語」欄に登録した語が文書・実装に現れたこと | **登録されていない揺れ**。新しい言い換えは検出できない | <!-- 技術判断者が記入 --> |
| **4-B 正本の文言と、文書中の転記の一致検査** | 転記した文言が正本と1文字でも違うこと | **転記だと宣言していない箇所**(案3-A / 3-D の目印に依存) | <!-- 技術判断者が記入 --> |
| **4-C 生成物と正本の乖離検査** | `labels.py` / `label.ts` が正本と食い違ったこと。**`session-definition-drift` と同型** | 正本そのものの揺れ | <!-- 技術判断者が記入 --> |
| **4-D 未登録語の検出(形態素解析で名詞を抽出し、用語集に無いものを出す)** | 用語集に無い新しい語が入ったこと | **一般名詞との区別がつかない**。除外一覧の維持が要る。**janome は F-002 基準18 で既に依存に入る見込み** | <!-- 技術判断者が記入 --> |

**検査の失敗を G-5 の合否条件にするかどうかも、この論点に含まれます。** **標準 5.7.4 は「記述の実質性を機械的に判定して、承認の可否を自動的に決めてはならない」と定めています。** [PL-0006](../../docs/platform/PL-0006-spec-lint-scope.md) は、同じ論点で `spec-lint` の適用範囲を目的へ合わせた記録です。

## 非機能への影響

| 項目 | 影響 |
| --- | --- |
| 性能 | **実行時に正本を読む方式を採った場合、起動時に1回の読み込みが加わります。** 生成物を出す方式では実行時の増加はありません |
| 可用性 | **正本の保管先が読めない場合の挙動が要ります。** 基準11-3 は形式の誤りに対して起動中止を定めていますが、**保管先が存在しない場合の扱いは基準にありません** |
| セキュリティ | **正本は利用者へ表示される文です。** 外部から差し替えられる場所へ置くと、表示内容を差し替えられます。基準11-2 が求める「環境変数から読む」形では、**保管先の書き込み権限が実質的な統制になります** |
| 運用 | **文言の変更が、実装の変更なしに行えるようになります。** 一方で**変更の記録が PR に残らない経路**(環境変数の指す先を直接編集する)が生じます |
