# ADR-0005: 中核の検索構成を案B(パース + BM25 / e5-small、LLM はオプション層)とする

## ステータス

採用(2026-08-12)

「検討した選択肢」の理由欄は判定者(takenori-kusaka)が記入した(2026-08-12)。案A を採らない理由は判定者の記述である。OCR エンジン・`.xlsx` のパース・検索方式の理由欄は S0 の実測にもとづく事実の記述であり、判定者が確認した。

## コンテキスト

S0 探索(S0-001 / S0-002 / S0-003 / S0-004 / S0-006)により、中核の検索構成を決める材料が揃った。

企画の前提として、**費用の最小化は訴求の言い換えではなく目的そのもの**である(`context/projects/P-001.md`)。一定以上の費用が掛かる時点で有償 SaaS より良い選択肢にならず、経営層観点での差別化が消滅する。**この前提が、構成の選択に対する最大の拘束になる。**

加えて 2026-08-12、価値責任者は対象利用者を **日本国内の利用者と日本語文書**と定めた。日本語の文書に対して中国語字形を返す挙動は、特定用途の制約ではなく中核体験の欠陥として扱う。

探した先でやることは RAG である。**RAG に取り込めないなら、見つけても意味がない。** S0-004 は、検索精度 10/10 の構成が RAG 適合性では 15問中 4問しか正答できないことを実測した。**探せることと使えることは別である。**

## 決定

### 1. 構成は案B とする

```
層A パース(初回のみ・派生物はミラーへ保存)
  PDF・画像   → Docling + RapidOCR(force_full_page_ocr=True、既定の PP-OCRv6)
                 → 抽出後に字形正規化を1段挟む
  .xlsx       → ExStruct(--mode light、座標付き JSON を行単位テキストへ線形化)
  .docx/.pptx → Docling
  .xls/.doc   → xlrd / olefile
層B 検索
  janome + BM25  と  multilingual-e5-small を 3:7 で統合
層C RAG
  上の抽出テキストをそのまま文脈として渡す。LLM はオプション層に置く
```

### 2. LLM を中核に置かない

LLM は層C のオプションとする。**LLM を持たない利用者でも、検索と抽出テキストの取得は完結する。**

| 項目 | 実測 |
| --- | --- |
| 運用時の金銭コスト | **$0**(S0-004) |
| 実行時の外部通信 | **なし**(S0-004) |
| 初回ダウンロード | 約 **1.04 GB** |
| RAG 適合性 | **15/15**(S0-004。字形正規化を挟む前の測定) |
| 検索精度 | **10/10**(S0-003 の 10 クエリ) |

### 3. OCR は既定モデルのまま、抽出後に字形正規化を挟む

S0-006 の実測による。**認識モデルを日本語向けへ差し替える案は採らない。**

| 経路 | 字形の混入 | 6件の所要時間 | 正解到達 |
| --- | --- | --- | --- |
| **既定(PP-OCRv6)+ 字形正規化** | **0** | **72.7s** | **9/9** |
| 既定(PP-OCRv6)のみ | 13 | 72.7s | 9/9 |
| japan_PP-OCRv4_rec_mobile | 0 | 128.8s | **8/9** |
| Docling VLM | 0 | 2,060.7s | 9/9 |

字形正規化の対応表は、**左辺を「CP932 へエンコードできない CJK 漢字」に限定する。** 日本語の文書組版に出現しない字形だけを置換対象とするため、置換によって正しい日本語の字が壊れることは構造上ありえない(原本テキスト層へ適用して 0文字変化を実測)。

**対応表は運用に依存する値である。コード内の定数にしない**(設計標準 [[extensibility]])。

### 4. 検出できない誤読が残ることを、決定の一部として記録する

**字形正規化が消せるのは「日本語に存在しない字が出る」誤りだけである。** S0-006 は、日本語モデルが `日` を `目` と読み違えて「7日以内」を失う事例を実測した。**日本語にある字への誤読は検出できない。**

したがって次を層A の責務とする。

- 混入を検出した件数を派生物のメタデータへ記録する
- 対応表で直せなかった混入を、検索結果でその旨とともに提示する(設計標準 [[calm-technology]]「黙って空のまま索引に入れない」)

### 5. インデクサ抽象化インターフェースを置く

層B の実装(BM25 / 埋め込みモデル)は境界の背後に置く。**具体的なシグネチャは G-3 で決める**(`context/projects/P-001.md` 未決の論点2)。

## 検討した選択肢

理由欄は判定者(takenori-kusaka)が記入した(2026-08-12)。

### 中核の構成について

| 案 | 採らなかった理由 |
| --- | --- |
| **案A パース + BM25 のみ** | **JTC な文書への対応不足のため棄却。** 参考となる実測: S0-002 は BM25 のみで 8/10、S0-003 はハイブリッド(3:7)で 10/10 |
| **案B 案A + LLM をオプション層(採用)** | — |
| **案C GraphRAG 系** | **LLM 必須であり、費用の前提と衝突するため採らない**(価値責任者の記述、`context/projects/P-001.md` 未決の論点0)。加えて S0-001 で Graphify は LLM 必須かつ 8/10 に留まり、`.pptx` / `.xls` / `.doc` に非対応であることを実測した |

### OCR エンジンについて

理由欄は S0-006 の実測にもとづく事実の記述である。

| 案 | 採らなかった理由 |
| --- | --- |
| **RapidOCR 既定 + 字形正規化(採用)** | — |
| RapidOCR 既定のみ | 日本語文書に中国語字形が 13件(0.159%)混入する。「共通事**项**」「参加資格審**查**」「書類**閱**覧」「勤労者世**带**」「電子処方**笺**」といずれも語の中核であり、対象利用者の前提と合わない |
| japan_PP-OCRv4_rec_mobile へ差し替え | 字形の混入は 0 になるが、**`日` を `目` と読み違えて「7日以内」を失った**(到達 8/9)。速度も 1.77 倍。**検出できる誤りを、検出できない誤りと引き換えにしている** |
| EasyOCR(ja) | スキャン PDF 4問すべて回答不能。回収率 16% / 9%。全ページ OCR を付けても 316 / 690 文字に留まり、RapidOCR の 4.4 倍遅い(S0-004) |
| Docling VLM(granite-docling 258M) | 字形 0・到達 9/9 を満たすが、**16 倍遅く(270秒/ページ)、モデルは 52 倍大きい**。**予備手段としては残す**(RapidOCR が失敗した特定のファイルに対して) |
| YomiToku | **CC BY-NC-SA 4.0** で商用利用ができない(S0-004) |
| MarkItDown | スキャン PDF・画像に対して 0 文字。画像は LLM クライアントを渡さない限り何も返さず、ローカル完結の制約を満たさない(S0-004) |

### .xlsx のパースについて

| 案 | 採らなかった理由 |
| --- | --- |
| **ExStruct(--mode light)(採用)** | — |
| openpyxl 全セル読み | 神エクセル 2/3。**項番 `４` と `７` が別セルにあることを解釈できず連結し、「項番47」と答えた**。項目名は正しいため利用者は気づけない(S0-004) |
| Docling の .xlsx 経路 | 神エクセル 1/3。結合セルを全スパンに複製展開し、出力が 76 倍に膨張する。項目名と選択肢が離れ、隣の項目の選択肢を拾う誤答が出た(S0-003 / S0-004) |
| Excel COM(xlwings 経由) | Excel の導入を利用者に要求する。ローカル完結・課金なしの前提と合わない |

### 検索の方式について

| 案 | 採らなかった理由 |
| --- | --- |
| **BM25 + multilingual-e5-small(3:7)(採用)** | — |
| BM25 のみ | 8/10(S0-002) |
| cl-nagoya/ruri-v3-30m | 精度が e5-small に届かない(S0-003) |
| 視覚ベース検索(ColPali 系) | **成立しない。** ローカル CPU で 16.7 秒/ページ・日本語 2/5。ColPali v1.3 の base は 5.8GB かつ **gemma ライセンス**、colqwen2 の base は 8.8GB(S0-004) |

## 可逆性

| 項目 | 内容 |
| --- | --- |
| 後から変えられるか | **変えられる**(層A・層B の実装)/ **変えにくい**(LLM を中核に置かないという方針) |
| 変えるとしたら必要なこと | 層A・層B の差し替えはインターフェースの背後で行える。**ただし派生物(抽出テキスト・埋め込み)の再構築が要る。** 50 ファイルで約 25 分という実測から、数千件では数時間から十数時間かかる。**LLM を中核へ移すと、運用時 $0 という前提が崩れ、企画の中核訴求が消滅する**(`context/projects/P-001.md` 費用に関する事業上の前提) |
| いつまでなら安く変えられるか | **利用者の倉庫が育つ前まで。** 再構築のコストは保管量に比例する |

## 非機能への影響

| 項目 | 影響 |
| --- | --- |
| 性能 | **初回構築が重い。** 50 ファイルで約 25 分(純 Python パースの約58倍)。スキャン PDF の多い倉庫ではさらに延びる。**検索と埋め込みは軽い**(50 文書の埋め込みで 5.4 秒) |
| 可用性 | 外部 API に依存しないため、ネットワーク断で検索が止まらない。**初回のモデル取得時のみ通信が要る** |
| セキュリティ | **実行時の外部通信が無い。** 文書の内容が外部へ出ない。これは費用の前提とは独立した価値である |
| 運用 | 派生物は原本の約 25%(50 ファイル 16MB に対しテキスト 4.0MB)。**ページ画像は保存しない**(視覚ベース検索を採らないため保存する理由がない)。**重いのは時間であって容量ではない** |

## 事業への影響

| 項目 | 内容 |
| --- | --- |
| 顕在化が分かる兆候 | 初回構築の所要時間を理由に利用者が離脱すること。または字形の混入・誤読の報告が出ること |
| 回復に要する時間 | **3日**(層A のパース経路を差し替え、派生物を再構築する。倉庫の規模に比例して延びる) |
| 影響を受ける利用者・業務 | スキャン PDF を多く持つ利用者(初回構築が延びる)。原文どおりの文字列を要する利用者(引用・法務) |

## 影響

**この決定によって得られるもの:**

- **運用時 $0・外部通信なしで、RAG に使える抽出テキストが得られる。** これが本プロダクトの中核訴求そのものである
- LLM を持たない利用者でも検索が成立する
- 字形の混入を 0 にしたまま、速度・抽出量・モデル構成を S0-004 のまま保てる

**トレードオフ:**

- **初回構築が重い。** 数千件で数時間から十数時間。**企画の訴求に直結する**(前提6・未検証)
- **原文どおりの文字列を保証できない。** 字形正規化は「日本語に存在しない字」しか直せない
- **字形正規化の対応表は、実測で出た5字種にしか対応していない。** 網羅性は表に依存する

**この決定で解決しないこと:**

- **インデクサ抽象化インターフェースの具体形**は G-3 の対象(未決の論点2)
- **ミラーディレクトリの構成と対外 ID との対応**は ADR-0002 の対象(未決の論点8)
- **手書き・低解像度スキャン・縦書き文書**は判定していない。コーパスに含まれず、スコープ外と書く根拠がない
- **日本語にある字への誤読**は検出できない。決定4 で記録に留める
