| 項目 | 記載 |

## 自社が勝てる理由(観点2)

3点ある。いずれも既に手元にある資産で、他者が同じ形で持っていないもの。

1. **ピットイン方式(AI協調型ソフトウェア開発プロセス標準)を自ら策定・運用している**。process-compass および pit-in-template は本人が著者であり、AI を実装の主体に置いたときに人がどこで触るべきかの設計を、標準として持っている。1名体制で AI に実装を任せながら品質を落とさない運用を、他者より低い摩擦で実行できる。
2. **AI エージェント側の要求を、利用者としてではなく設計者として理解している**。Claude Code をはじめとするエージェントが「ファイルをどう参照したいか」「MCP で何を返してほしいか」を、実際の運用から把握している。既存のファイル管理 OSS はこの視点を持たずに設計されている。
3. **合成先の全体像を自分で持っている**。Chat / Auth を含む統合アーキテクチャを自分で描いているため、Filetto の対外インターフェース(REST / MCP / JWT クレーム)を、後で必要になる形から逆算して切れる。単体の OSS を作る他者は、この逆算ができない。

## 目的と価値仮説(観点3)

**誰の**: 自分の PC に資料を溜めている個人。エンジニアである必要はない。

**何が変わるか**: 現在、AI に資料を読ませたい人は、都度ファイルをチャット画面へアップロードするか、エンジニアに RAG 環境を構築してもらうかのいずれかを選んでいる。前者は毎回やり直しで、資料が増えるほど破綻する。後者は依頼できる相手がいなければ成立しない。

Filetto を導入すると、**フォルダにファイルを置くという既存の習慣のまま**、そのファイル群が人にも AI にも検索可能な状態になる。

**どれだけ変わるか**(観測できる形):

| 観測する事象 | 導入前 | 導入後の目標 |
| --- | --- | --- |
| AI に資料を参照させるまでの手順数 | 資料1件ごとにアップロード操作が発生する | フォルダへ置いた後、追加の操作が発生しない |
| 資料を探す手段 | ファイル名とフォルダ階層のみ | 日本語の自然文で内容を検索できる |
| 環境構築に要する他者の関与 | RAG 環境の構築を他者へ依頼する | `docker compose up` のみ。他者の関与なし |
| 月額の維持費用 | 外部 SaaS または API 従量課金 | **0 円。実行時の外部通信なし・API キー不要**([S0-004](./spikes/S0-004-rag-fitness.md) 実測) |
| 資料を投入してから検索できるまで | 即時(アップロードのつど) | **初回のみ待つ。50 ファイルで約 25 分**([S0-003](./spikes/S0-003-parser-and-hybrid.md) 実測) |

### 「無料」と書かない

**ゼロなのは金銭だけである。**

| 項目 | 実測 |
| --- | --- |
| 運用時の金銭コスト | **$0** |
| 実行時の外部通信 | **なし** |
| 初回のモデルダウンロード | 約 **1.04 GB** |
| 初回構築の所要時間 | 50 ファイルで約 **25 分**。数千ファイルなら数時間から十数時間 |

**本書では「無料」ではなく「課金なし・自分のマシンで完結」と書く。** 初回構築の所要時間を利用者が受け入れるかは**未検証であり、訴求に直結する**(下記「未検証の前提」)。

## コア機能の候補

「事業上致命的で、人の理解維持が必須の機能」を指定する。全部コア・全部非コアとしない。

| 区分 | 機能 | 理由 |
| --- | --- | --- |
| **コア** | セマンティック検索と MCP インターフェース(F-003) | 本プロダクトの価値そのもの。ここが動かなければ、ただのファイルマネージャになる |
| **コア** | **抽出テキストの質(層A パース)** | **探した先でやることは RAG である。RAG に取り込めないなら、見つけても意味がない。** [S0-004](./spikes/S0-004-rag-fitness.md) は検索 10/10 の構成が RAG 適合性 4/15 でありうることを実測した。**検索精度とは別の基準として持つ** |
| **コア** | 削除・リネーム・移動の可逆性(ゴミ箱方式) | 安全重要度を CL1 から CL0 へ下げた根拠そのもの。壊れると危害の前提が変わる |
| **コア** | 対外インターフェース(REST API / MCP / JWT クレーム)の契約 | 後続の Chat / Auth が依存する境界。あとから変えると全サービスへ波及する |
| 非コア | ファイル一覧・階層表示の UI 装飾 | 差し替え可能。ヘッドレス UI の方針により、見た目は利用者が変えられる |
| 非コア | プレビュー表示 | 欠けても倉庫としての価値は成立する |
| 非コア | インデクサのプラグイン機構(実装の差し替え) | **初版は案B の構成に単一固定**(パース + BM25 / e5-small)。インターフェース定義のみ行う([ADR-0005](../context/decisions/0005-indexer-selection.md)) |

## スコープ外

この企画でやらないこと。

- **認証基盤そのもの**。Filetto は JWT クレームを検証してファイルアクセススコープを制御するのみ。ユーザー登録・パスワード管理・多要素認証は別マイクロサービス(Auth)の責務とする
- **Chat / LLM 連携の UI**。別マイクロサービス(Chat)の責務
- **マルチテナント**。初版はシングルユーザー。localhost bind を前提とする
- **インデクサの複数実装**。インターフェースは定義するが、実装は案B の構成のみ
- **1リポジトリ内でファイルごとに異なるインデクサを混在させること**。初版は非対応と明記する
- **S3 等のクラウドストレージ対応**。初版はローカルディスクのみ
- **Windows Explorer からのマウント**(WebDAV / SMB 等)
- **既存の統合型ファイルエクスプローラー OSS(Filestash / Pydio Cells / Seafile)のフォーク**。いずれも AGPL v3 だが、それ以前に設計思想が異なるため採らない

### 実測にもとづくスコープ外(v2.0 で追加)

[S0-004](./spikes/S0-004-rag-fitness.md) 検証5 および [S0-006](./spikes/S0-006-ocr-glyph.md) で**実際に確認したものだけ**を挙げる。

| # | 扱わないこと | 実測された挙動 | 根拠 |
| --- | --- | --- | --- |
| 1 | **原文どおりの文字列を保証する用途(引用・法務)** | 字形正規化で「日本語に存在しない字」は直せるが、**日本語にある字への誤読は検出できない**(`日`→`目` の実例) | S0-006 |
| 2 | 文字がほとんど無い図・グラフ画像 | fig-kakei-02.png は全経路で **56 文字**しか取れず、表題以上を答えられない | S0-004 |
| 3 | レガシー `.doc` の罫線レイアウト | olefile による断片抽出で文字は拾えるが、**表の構造は復元されない**(205〜236 文字) | S0-003 / S0-004 |
| 4 | ページ画像そのものを対象にした意味検索 | ローカル CPU で **16.7 秒/ページ・日本語 2/5**。ColPali v1.3 の base は gemma ライセンスかつ 5.8GB | S0-004 |
| 5 | 表の完全な意味理解を無条件に約束すること | ExStruct + LLM で 3/3 になったが、**評価は 3 問**。一般化できる根拠がない | S0-004 |

### 判定していないこと(スコープ外と書かない)

**根拠が足りないため、対応しないとは書かない。**

- 手書き文字を含む帳票
- 極端に低解像度のスキャン
- 縦書き文書

いずれも S0 のコーパスに含まれず、判定できていない。

### なぜ star で判定しないか

**star は「良さそう」の表明であり、「使った」の証拠ではない。** 本案件が埋めたい未達は2つで、どちらも**使った人からの反応**を要する。

| 未達 | 要るもの |
| --- | --- |
| G-6 独立レビュー | **コードを読んだ第三者の指摘** |
| 市場・顧客仮説の検証 | **自分の資料で試した第三者の反応** |

**star はどちらも埋めない。** 数が増えても未達は未達のまま残る。**判定に使う指標を取り違えると、未達が埋まったと誤認する。**

### ③を経路に含める理由

**ピットイン方式の読者は、本案件の記録そのものに関心を持ちうる層である。**

本案件は S0 探索の記録・ADR・ゲート判定記録を公開リポジトリへ残している。**製品に関心を持たない読者でも、プロセスの適用事例には関心を持ちうる。** そして**プロセスの記録を読む者は、コードを読む動機を持ちやすい。** G-6 の未達を埋める経路として、②③は①より近い。

### この経路が抱える弱点

**①②③のいずれも、本人の発信に依存する。** 発信が止まれば経路も止まる。**第三者が第三者へ伝える経路を持っていない。**

**AGPL-3.0 はこの弱点と掛け算になる**([[0001-license-agpl-3]])。企業経由の伝播が期待できないため、個人から個人への伝播だけが残る。

**この弱点は解消していない。** 未決の論点7 として残し、公開後の実測で見直す。

### 前提として置いていること

- **AGPL-3.0 は採用の裾野を狭める**。企業採用の障壁になることは v1.0 のリスク表で受容済み
- **G-6(独立レビュー)の未達と、市場・顧客仮説の未検証は、調達先が同一である**。いずれも「公開してコミュニティの反応を観測する」であり、**片方が埋まらなければもう片方も埋まらない構造**(`context/projects/P-001.md` 未決の論点6)
- 中止条件1 は「本人が日常的に使っていない」であり、**第三者へ広げる前に本人の利用が先に立つ**。**したがって公開の時期は、本人が日常的に使い始めた後とする**
