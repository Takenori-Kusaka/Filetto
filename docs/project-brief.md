## 自社が勝てる理由(観点2)

3点ある。いずれも既に手元にある資産で、他者が同じ形で持っていないもの。

1. **ピットイン方式(AI協調型ソフトウェア開発プロセス標準)を自ら策定・運用している**。process-compass および pit-in-template は本人が著者であり、AI を実装の主体に置いたときに人がどこで触るべきかの設計を、標準として持っている。1名体制で AI に実装を任せながら品質を落とさない運用を、他者より低い摩擦で実行できる。
2. **AI エージェント側の要求を、利用者としてではなく設計者として理解している**。Claude Code をはじめとするエージェントが「ファイルをどう参照したいか」「MCP で何を返してほしいか」を、実際の運用から把握している。既存のファイル管理 OSS はこの視点を持たずに設計されている。
3. **合成先の全体像を自分で持っている**。Chat / Auth を含む統合アーキテクチャを自分で描いているため、Filetto の対外インターフェース(REST / MCP / JWT クレーム)を、後で必要になる形から逆算して切れる。単体の OSS を作る他者は、この逆算ができない。

## 目的と価値仮説(観点3)

### 主訴求(v4.0 で入れ替え)

> **Filetto は、あなたのフォルダの中だけを見て答える、手元の書棚です。**

| | v3.0 まで | **v4.0** |
| --- | --- | --- |
| 主訴求1 | 外に出せない層のための製品 | **あなたのフォルダの中だけを見て答える** |
| 主訴求2 | フォルダに置くだけ | **確かめるべき箇所へ、1クリックで到達できる** |
| 第二訴求 | — | **「置くだけ」「外に出ない」をここへ降ろす** |

**「置くだけ」と「外に出ない」を捨てたのではない。主訴求から第二訴求へ降ろした。** 導入の摩擦を説明する材料としては残す。

**入れ替えの根拠は5本ある**([正本 第3章](decisions/P-001-kickoff-decision.md))。**要点は3つ。**

| # | 実測 | 訴求への影響 |
| --- | --- | --- |
| 1 | **障壁の一位は「誤った回答を信じてしまう」**(IPA。日本40.5% 対 米独19.6%。**この数値は図表画像内にあり未検証**) | 「使い方がわからない」を主訴求にしない |
| 2 | **「どの業務で使えるか不明」は3年で ▲21%、「正確性への懸念」は増加**(総務省。全1,788団体・回答率100%) | **用途の発想を主訴求にすると、縮小中の市場を追うことになる** |
| **3** | **引用元へのクリックは訪問の1%**(Chapekis et al., IC2S2 2026)。**確かめる手間を実際に下げた設計だけが判断を改善する**(Vasconcelos et al., CSCW 2023。5実験・N=731) | **「表示します」では足りない。「1クリックで到達できます」まで要る** |

**日本は AI を過信していない。** 検証せずに依存する割合(56% 対 世界66%)も AI 起因のミス(40% 対 56%)も世界平均より低い(KPMG / メルボルン大学。47か国・48,000人超)。**低いのは信頼(28% 対 46%)とリテラシーである。**

**したがって訴求の向きはこうなる。** **「過信を防ぎます」ではない。それは起きていない問題を解く提案である。**

### 誰の

**誰の**: 自分の PC に資料を溜めている個人。

**2026-08-13、G-2 の判定で価値責任者が対象を定義し直しました。**

> **非エンジニアユーザはこの Filetto を部品として組み込んだシステム、ソリューションを利用するユーザの話であり、Filetto を部品として組み込むユーザはエンジニアである**

| 層 | 誰か | Filetto に触れるか |
| --- | --- | --- |
| **Filetto の利用者** | **エンジニア。** Filetto を部品として自分のシステムへ組み込む | **触れる。`docker compose up` を実行する** |
| その先の利用者 | 非エンジニア。組み込まれたシステムを使う | **触れない** |

**v2.0 まで「エンジニアである必要はない」と書いていましたが、これは2つの層を1つに混ぜていました。**

**何が変わるか**: 現在、AI に資料を読ませたい人は、都度ファイルをチャット画面へアップロードするか、エンジニアに RAG 環境を構築してもらうかのいずれかを選んでいる。前者は毎回やり直しで、資料が増えるほど破綻する。後者は依頼できる相手がいなければ成立しない。

Filetto を導入すると、**フォルダにファイルを置くという既存の習慣のまま**、そのファイル群が人にも AI にも検索可能な状態になる。

**どれだけ変わるか**(観測できる形):

| 観測する事象 | 導入前 | 導入後の目標 |
| --- | --- | --- |
| AI に資料を参照させるまでの手順数 | 資料1件ごとにアップロード操作が発生する | フォルダへ置いた後、追加の操作が発生しない |
| 資料を探す手段 | ファイル名とフォルダ階層のみ | 日本語の自然文で内容を検索できる |
| 環境構築に要する他者の関与 | RAG 環境の構築を他者へ依頼する | `docker compose up` のみ。他者の関与なし |
| 月額の維持費用 | 外部 SaaS または API 従量課金 | **0 円。実行時の外部通信なし・API キー不要**([S0-004](./spikes/S0-004-rag-fitness.md) 実測) |
| 資料を投入してから検索できるまで | 即時(アップロードのつど) | **初回のみ待つ。50 ファイルで約 25 分**([S0-003](./spikes/S0-003-parser-and-hybrid.md) 実測) |
| **答えの根拠を確かめる手順**(v4.0 で追加) | **元のファイルを自分で開き、該当箇所を探す** | **答えに付いた印から、原文の該当箇所へ1クリックで到達する** |

### 投資の正当化 — 収益で説明しない

**収益モデルを持たない案件である。** 一次資料は、それを前提とした説明の枠組みを持つ。

> OSPO が直接的・分離可能な形で帰属可能な収益を生むことは稀である。財務的貢献は **コスト回避・効率・無駄の削減** を通じて見えることのほうが多い。**これが企業環境で価値を表現する最も信頼できる方法の一つである**

## 例外の経路の振り分け(v4.1 で新設 / G-1 基準2)

**標準 7.3.1 は、どの事象をどの経路へ送るかの判断基準を、企画承認(G-1)の時点で記録することを求めている。**

**本節がその記録である。** 置き場所を本書としたのは、**G-1 の判定対象に含めるため**である。`docs/D-0-governance.md` へ置くと、G-1 の前提条件となり判定されない。

### 判定の順序 — 上から順に当てはめ、最初に当てはまった経路を採る

| 順 | 問い | Yes のとき |
| --- | --- | --- |
| **1** | **当該ゲートの判定基準を、いま満たしていないか** | **7.3 例外承認** |
| **2** | **判定基準は満たしているが、判断の土台にした前提が崩れたか** | **7.10 前提の受容** |
| **3** | **判定基準に含まれないが、放置できない事項か** | **7.3.2 未解決事項** |
| — | いずれでもない | **経路に載せない。通常の作業として扱う** |

**1 を最初に置く理由**: **最も重い経路を先に当てるためである。** 標準は「経路の選択を事後の裁量にすると、最も軽い経路が選ばれる」と述べている。**軽い経路から当てると、重い経路が使われなくなる。**

### 迷いやすい3組の切り分け

| 組 | 問い | 判定 |
| --- | --- | --- |
| **7.3 か 7.3.2 か** | **その事項を、当該ゲートの判定基準の項目番号で指せるか** | **指せる → 7.3。指せない → 7.3.2** |
| **7.10 か 7.3.2 か** | **過去に通過したゲートの判定が、その事項によって成り立たなくなるか** | **なる → 7.10。ならない → 7.3.2** |
| **経路に載せるか、通常の作業か** | **記録しないと消えるか**(担当者が忘れたときに、他の誰も気づかない) | **消える → 載せる。消えない → 通常の作業** |

**「項目番号で指せるか」を基準にする理由**: 標準 7.3 の要求事項2 が「満たさない基準の**項目番号**と、その理由を記録する」と定めており、**項目番号を書けない事項は 7.3 の記録要件を満たせない。**

### なぜ star で判定しないか

**star は「良さそう」の表明であり、「使った」の証拠ではない。** 本案件が埋めたい未達は2つで、どちらも**使った人からの反応**を要する。

| 未達 | 要るもの |
| --- | --- |
| G-6 独立レビュー | **コードを読んだ第三者の指摘** |
| 市場・顧客仮説の検証 | **自分の資料で試した第三者の反応** |

**star はどちらも埋めない。** 数が増えても未達は未達のまま残る。**判定に使う指標を取り違えると、未達が埋まったと誤認する。**

### ③を経路に含める理由

**ピットイン方式の読者は、本案件の記録そのものに関心を持ちうる層である。**

本案件は S0 探索の記録・ADR・ゲート判定記録を公開リポジトリへ残している。**製品に関心を持たない読者でも、プロセスの適用事例には関心を持ちうる。** そして**プロセスの記録を読む者は、コードを読む動機を持ちやすい。** G-6 の未達を埋める経路として、②③は①より近い。

### この経路が抱える弱点

**①②③のいずれも、本人の発信に依存する。** 発信が止まれば経路も止まる。**第三者が第三者へ伝える経路を持っていない。**

**AGPL-3.0 はこの弱点と掛け算になる**(ADR-0001)。企業経由の伝播が期待できないため、個人から個人への伝播だけが残る。

**この弱点は解消していない。** 未決の論点7 として残し、公開後の実測で見直す。

### 前提として置いていること

- **AGPL-3.0 は採用の裾野を狭める**。企業採用の障壁になることは v1.0 のリスク表で受容済み
- **G-6(独立レビュー)の未達と、市場・顧客仮説の未検証は、調達先が同一である**。いずれも「公開してコミュニティの反応を観測する」であり、**片方が埋まらなければもう片方も埋まらない構造**(`context/projects/P-001.md` 未決の論点6)
- 中止条件1 は「本人が日常的に使っていない」であり、**第三者へ広げる前に本人の利用が先に立つ**。**したがって公開の時期は、本人が日常的に使い始めた後とする**
