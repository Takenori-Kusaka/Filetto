## 判定に際して確認した重要事項

### 1. 「維持コストゼロ」の訴求は書き換えが必要

実測: **50ファイルの初回構築に約25分**(パース1505.5秒)。純 Python パースの約58倍。数千ファイルの資料倉庫では**数時間から十数時間**。モデルのディスク使用量は約 1.07 GB。

**ゼロなのは金銭だけです。** 企画書の「維持費 0 円」「月額の維持費用 0 円」という記述は、**「課金なし・自分のマシンで完結」へ書き換えます**。「無料」と読める表現を残しません。

これは企画の否定ではありません。**訴求の正確化です。** 外部 API・ベクトル DB・従量課金を必要としないという中核の主張は、実測で成立しています。

### 2. スキャン PDF は「探せる」が「読める」とは言えない

OCR の回収率は **16% / 9%**。「ください」→「くだきい」等の誤認識があり、検索でヒットさせるには足りるが、内容提示には足りません。

~~企画書のスコープに「スキャン文書の内容提示は約束しない」を明記します。~~ → **本項の結論は不十分でした。「移行の条件」の追記を参照してください。**

### 3. 表の行見出し×列見出しの交差は、どのパーサでも解けていない

openpyxl / Docling / ExStruct の3条件すべてで復元できず。**神エクセルの意味構造の完全な理解は未解決**です。

~~約束の範囲から外し、次の探索課題として記録します。~~ → **テキスト抽出の路線で解けていないだけであり、別の路線が未検証でした。「移行の条件」の追記を参照してください。**

### 4. 実装スタックが Python に確定した

中核構成がすべて Python です。`/process-init` で選んだアダプタ `node` は誤りでした。**`python` への切り替えが必要**です。

この選択は「構想メモを根拠に選び、判断として記録しなかった」ものであり、順序の誤りではなく記録の欠落でした(標準チームの確認による)。**ADR として補います。**

### 5. Dev による自己訂正を2件受領した

- **S0-002 の 8/10 は、pypdf が3件の PDF の日本語を壊した状態での値だった**。Q7 の真因は語彙の類似ではなく文字化けであり、「BM25 では原理的に分離できない」は誤りだった
- **ExStruct は xlrd を追加導入すれば .xls も扱える**。「レガシー .xls は範囲外」は不正確だった

いずれも自らの過去の記述を訂正するものであり、**判定の信頼性を上げる報告として評価します**。

## 追記(同日): 上記2・3 の結論を訂正し、追加の探索を発注する

価値責任者との確認により、**本記録の重要事項2・3 の結論が不十分であること、および発注側(PO)の受入基準に設計の誤りがあったこと**が判明しました。**SG-0 の判定(S1 へ移行)は維持します**が、移行の条件へ1件を追加します。

### 誤り1: 受入基準が検索精度しか測っていなかった

[#1](https://github.com/Takenori-Kusaka/Filetto/issues/1) / [#5](https://github.com/Takenori-Kusaka/Filetto/issues/5) で PO が定めた受入基準は「期待ファイルが上位3件に入るか」のみでした。**これは検索の基準であって RAG の基準ではありません。**

本プロダクトの目的は「探す」ことではなく、**探した先で LLM が中身を使えること**です。**RAG に取り込めないなら、見つけても意味がありません。** 回収率 16% のテキストを文脈として渡せば、LLM は誤答するか「情報がない」と答えます。

外部研究がこの構造を裏づけています。

| 出典 | 知見 |
| --- | --- |
| [OCR Hinders RAG (arXiv:2412.02592)](https://arxiv.org/html/2412.02592v4) | 標準 OCR を検索と生成の両方に使うと正答率が完全テキスト比 **25.8% 低下**。**検索側のみマルチモーダル化で 70% 回復** |
| [When Good OCR Is Not Enough (ACL 2026)](https://aclanthology.org/2026.acl-industry.60/) | **OCR 精度が高くても RAG 精度は保証されない**(OCR 82.9% → RAG 53.0% の例) |

したがって「スキャン文書の内容提示を約束しない」とスコープを狭める前に、**RAG 基準で測り直す**必要があります。

### 誤り2: 設計自由度を不必要に狭めていた

価値責任者より、**利用者が格納するファイル群とは別に、インデックス用・RAG 検索用のミラーディレクトリ / ファイルを作ってよい**との判断がありました。

これにより次が可能になります。テキスト抽出の路線で解けなかった課題(重要事項3)は、**別の路線が未検証だっただけ**です。

- 原本を保持したまま、正規化済みテキスト・ページ画像・構造化 JSON を別領域に持つ
- 神エクセルを全シート画像化してローカル VLM に読ませる
- [MarkItDown](https://github.com/microsoft/markitdown)(MIT)等の別経路を併用する

### 事業上の前提の明確化

**費用の最小化は、訴求の言い換えではなく目的そのものです。**

同種の機能は有償 SaaS として既に存在します。**費用を出せるならそちらでよい**というのが利用者の合理的判断であり、「一定以上の費用が掛かり、採算性の面で有償 SaaS より良い選択肢にならない」時点で、**本 OSS の経営層観点での差別化は消滅します**。

技術者観点(組み込み容易性・拡張性・自由度)での優位は残りうるが、それだけでは中核訴求を支えられません。**ローカル完結(外部 API なし・従量課金なし)は制約として維持します。**
