## 価値責任者が判断する項目 — 2点

### 判定基準2 — タスク分解の粒度が1タスク=1レビュー単位か

**機械が数えられるのは行数とファイル数までです。「30分で読み切れるか」は人が判断します。**

**見ていただきたいのは `specs/F-001/plan.md` の「タスク」表(11行)です。**

**判断の材料として、粒度に関わる設計上の選択を3つ挙げます。結論は書きません。**

| # | 選択 | 事実 |
| --- | --- | --- |
| 1 | **Task-8 が最大**(240行 / 7ファイル) | `VersionStore` の定義・利用・Lore の設定・起動時検査・`docker-compose.yml` を1タスクに含む。**基準15・17・18・19 の4件を担う** |
| 2 | **基準4(物理削除 API を公開しない)を Task-3 へ置いた** | Task-2 の時点では MCP の経路が無く、**経路が無いことによって基準が成立してしまう**。両経路が揃ってはじめて検証できる |
| 3 | **`VersionStore` の定義と利用を分けなかった** | `CLAUDE.md`「分割しすぎない」が、新しいインタフェースの追加はその利用箇所を同じ変更に含めることを求めているため |

**1 が判断の分かれ目です。** `plan.md` は超過時に2分割する条件を書いていますが、**着手前に分けるかどうかは判定者の判断です。**

### 判定基準5 — 範囲の判定(SC-P)が妥当か

**11タスクすべてが `SC-P` です。**

| 事実 | 内容 |
| --- | --- |
| 根拠 | `specs/F-001/spec.md` の frontmatter が `scope: SC-P`。**本計画で範囲を変えていない** |
| SC-B(調整枠)へ動かしたタスク | **0件** |
| 範囲外としたタスク | **0件** |

**判断していただきたいのは「11件すべてが SC-P でよいか」です。**

**この判断を機械に委ねません。** 自動生成した候補を人手で検証させた実験(2010年)では、**初期の精度が高い候補を与えられた分析者は品質を下げました。** 機械の出力を人が追認する構成は、人の判断を機械の出力へ引き寄せます。

## 判定の成立に、理由の記入は要りません

**標準 5.7.3(選択肢の比較。理由を人が記入する)は「リスク区分 R1 の決定、および例外承認」に限定された条項です。** 本案件は安全重要度 CL0 であり、**F-001 の実装計画は R1 の決定にも例外承認にも当たりません。**

**この扱いは [ADR-0014](../../context/decisions/0014-standard-scope-misapplication.md) で是正したものです。** G-3 では PO が 5.7.3 を適用範囲ごと確認せずに課し、判定者に44行の記入を求めました。**同じことを繰り返しません。**
