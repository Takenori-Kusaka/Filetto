# 技術負債台帳

**本台帳は、標準 第7章 7.3(例外承認)・7.3.2(未解決事項)・7.10(前提の受容)の登録先です。**

**新しい台帳を作りません。** 標準が「登録先は技術負債台帳と同一。区分欄により 7.3 由来のものと区別する」と定めているためです。

**G-7 出荷判定は「受容した負債が台帳に記録されているか」を確認します。** **判定基準は記録漏れが0件であることです。負債の量そのものは判定しません。**

## 経路の区分

| 区分 | 標準 | 定義 |
| --- | --- | --- |
| **例外** | 7.3 例外承認 | **判定基準を満たさないまま進める。** 承認者の記名・満たさない基準の項目番号・影響と対処・回収期限と回収責任者・継続報告の**5要件すべて**が要る。1つでも欠ければ例外は無効 |
| **未解決** | 7.3.2 未解決事項 | **判定基準に含まれないが放置できない事項。** 判定を阻害しない周辺課題 |
| **前提** | 7.10 前提の受容 | **判定基準は達成しているが、判断の土台にした前提が崩れた** |

**期限までに解消しない未解決事項は、7.3 と 7.10 のいずれへ送るかを改めて判定します。**

## 状態欄の語

| 語 | 意味 |
| --- | --- |
| 未返却 | **対処していない** |
| **記録済み** | **対処の成果物は `main` にある。ただし、それを判定するゲートを通っていない** |
| 返却済み | **対処の成果物が `main` にあり、判定も済んでいる** |

**「記録済み」と「返却済み」を分けます。** **記録が存在することと、判定を経たことは別です。**

## この台帳を作った経緯

**2026-08-14 まで、本案件に技術負債台帳が存在しませんでした。**

**`templates/03-debt-ledger.md` は最初から置かれていましたが、実体を作っていませんでした。** **G-2 再判定(F-003)で条件が付いたときに、登録先が無いことが判明しました。**

**このとき、条件を `spec.md` へ「通過(条件付き)」と転記しかけました。** **標準はこれを認めていません。**

> **「条件付き通過」を設けません。** 条件を付して先へ進める手続は第7章 7.3 の例外承認です。**回収の期限と回収責任者を伴わない通過の経路を作らないため**です

**判定は通過です。** **条件は未解決事項として本台帳へ登録し、回収の期限と責任者を定めました。**

## 未解決事項は「判定を避ける先」ではありません

**標準は 7.3.2 に暫定マークを付けています**(EV-0030 / 根拠の水準 E1 / 見直し 2027-02)。

> **解消率の低いまま件数が積み上がる状態は、置き場を「判定を避ける先」として使っていることを示します**

**根拠とした事例(JAXA JMR-004D / 英国 Gateway / NASA の RID/RFA)は、いずれも独立した追跡組織を持つ体制です。** **少人数の案件で同じ効果が得られるという測定を、標準は持っていません。**

**本案件は1名体制であり、追跡する独立組織がありません。** **したがって次を自らに課します。**

| # | 課すこと |
| --- | --- |
| 1 | **未解決事項の件数と、期限までに解消した件数を、ゲート判定のたびに数える** |
| 2 | **期限を過ぎた未解決事項は、7.3(例外承認)と 7.10(前提の受容)のいずれへ送るかを、その時点で判定する。放置しない** |

## 判定値は「通過」「差し戻し」の2値です

**未解決事項が残っていることは、通過を妨げません**(ADR-0036 決定2)。

**「条件付き通過」という判定値はありません。** 判定記録の結果欄に書けるのは通過と差し戻しだけです。
