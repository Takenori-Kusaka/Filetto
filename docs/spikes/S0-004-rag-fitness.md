## 推奨する中核構成(受入基準5)

```
層A パース(初回のみ・派生物はミラーへ保存)
  PDF・画像 → Docling + RapidOCR(force_full_page_ocr=True)
  .xlsx     → ExStruct(--mode light、座標付き JSON を行単位テキストへ線形化)
  .docx/.pptx → Docling
  .xls/.doc → xlrd / olefile
層B 検索
  janome + BM25  と  multilingual-e5-small を 3:7 で統合
層C RAG
  上の抽出テキストをそのまま文脈として渡す
```

**ローカル完結: 満たします。** 実行時の外部通信は 0、API キー不要、従量課金なし。初回のみモデルを取得します。

## 検証2: スキャン PDF の内容取得を複数経路で比較

### 経路ごとの実測(受入基準3)

対象はスキャン PDF 2 件と図表画像 4 件。すべてローカル完結です。

| 経路 | scan-kaminokawa-03 | scan-kochi-04 | 6件の合計時間 | RAG(スキャン+画像 8問) |
| --- | --- | --- | --- | --- |
| 1. Docling + EasyOCR(ja) 既定 | 306 文字 | 621 文字 | — | **3/8 正答** |
| 1'. 同 + `force_full_page_ocr` | 316 文字 | 690 文字 | **588.8s** | 未測定 |
| 2. Docling VLM(granite-docling 258M) | 1,283 文字 | 3,641 文字 | **2,060.7s** | **8/8 正答** |
| 3. **Docling + RapidOCR 全ページ** | **1,622 文字** | **3,538 文字** | **133.9s** | **8/8 正答** |
| 4. MarkItDown(MIT) | **0 文字** | **0 文字** | 0.1s | 0/8 |
| 5. ページ画像 + ローカル VLM | 経路2 と同一実装のため統合 | | | |

原本のテキスト量は 1,971 / 6,664 文字です。**RapidOCR の回収率は 82% / 53%** で、EasyOCR の 16% / 9% から大きく改善しました。

### 分かったこと

**1. 差を生んだのは OCR エンジンで、全ページ OCR の設定ではありません。**

`force_full_page_ocr=True` を EasyOCR にも付けた対照実験では 316 / 690 文字にしかならず、しかも 588.8 秒(RapidOCR の **4.4 倍**)かかりました。**S0-003 で EasyOCR を選んだのは誤りでした。** RapidOCR が「日本語で空を返す」と報告しましたが、それは領域単位 OCR での挙動で、全ページ OCR では正常に動作します。

**2. Docling VLM は RapidOCR と同じ 8/8 に達しますが、15.4 倍遅いです。** granite-docling 258M で 6 件を通したところ **2,060.7 秒**(RapidOCR は 133.9 秒)。3 ページの scan-kaminokawa-03.pdf 単体で 807.5 秒(約 270 秒/ページ)でした。

| | RapidOCR 全ページ | Docling VLM |
| --- | --- | --- |
| RAG(スキャン+画像 8問) | **8/8** | **8/8** |
| 6 件の所要時間 | **133.9s** | 2,060.7s(**15.4 倍**) |
| scan-kaminokawa-03 | 1,622 文字 | 1,283 文字 |
| scan-kochi-04 | 3,538 文字 | **3,641 文字** |
| モデルサイズ | 62MB | 506MB |

**取得できる内容は同等です。** 文字数は文書によって前後します(scan-kochi-04 では VLM がわずかに上)。**RAG 基準では差がつきませんでした。** したがって選択の理由は速度とモデルサイズになり、**RapidOCR を採ります**。VLM 経路は「RapidOCR が失敗した特定のファイルに対する予備手段」として残す価値があります。

**3. MarkItDown はスキャン PDF・画像に対して 0 文字です。** PDF は pdfminer.six のテキスト層のみ、画像は LLM クライアントを渡さない限り何も返しません。**ローカル完結の制約下では使えません。**

### 品質の実際

RapidOCR の出力です。

```
## 1）共通事项（契約保証金） 鏡（表紙）の「5.契約保証金」の欄は次のとおり記入してください。
- ·500万円未満の工事 - ・現金のとき :免除 ：現金の金額を記入する
現金のときは事前手続きが必要ですので、その旨事前に連絡ください。
```

「事项」(中国語字形)のような揺れは残りますが、**金額・条件・手順は読めています。** RAG の文脈として機能する水準です。

## 検証4: 視覚ベース検索(ColPali 系)の実現可能性

**成立しませんでした。** ローカル CPU では実用になりません。

### モデルの実測

| モデル | ライセンス | 重み | CPU 実行 |
| --- | --- | --- | --- |
| **vidore/colSmol-256M** | **MIT**(base も MIT) | 42MB + base 436MB = **478MB** | **可**(実測) |

### 実測(colSmol-256M / CPU)

| 項目 | 実測 |
| --- | --- |
| モデル読み込み | 22.8 秒 |
| ページ画像の埋め込み | **16.7 秒/ページ**(16 枚で 267.5 秒) |
| クエリ処理 | 0.3 秒/件 |
| 日本語クエリの検索精度 | **2/5** |

正答は「債権譲渡の対象となる工事の請負代金の額」と「電子カルテの標準化」の 2 件だけで、後者は期待ページが 3 位でした。「契約書は落札日から何日以内に提出するか」「県外の業者の入札参加資格審査の要綱」「消費支出の前年同月比」はいずれも無関係なページを上位に返しました。

### 判定

- **精度**: BM25 + e5-small の **10/10** に対し **2/5**。比較になりません
- **速度**: 16.7 秒/ページ。50 ファイル(推定 300 ページ)なら埋め込みだけで **約 83 分**。現行構成の埋め込みは 50 文書 5.4 秒です
- **より大きいモデル**: 5.8〜8.8GB でローカル CPU の想定を超えます

外部研究が報告する「検索側をページ画像に差し替えると回復する」効果は、**英語文書 + GPU が前提**です。日本語・CPU・ローカル完結という条件では、現時点で再現しませんでした。

## ミラーディレクトリの構成(受入基準7)

PO から解放された設計自由度に対する提案です。**本検証では実装せず、測定結果から導ける構成だけを記述します。**

```
<利用者の資料倉庫>/            ← 原本。Filetto は読み取りのみ
.filetto/                      ← ミラー(派生物)。単一ディレクトリに閉じる
  index.sqlite                 ← 原本パス・サイズ・mtime・内容ハッシュ・派生物の対応表
  text/<hash>.txt              ← 正規化済みテキスト(層Aの出力)
  struct/<hash>.json           ← ExStruct の構造化 JSON(.xlsx のみ)
  embed/<hash>.npy             ← 埋め込み
```

### 原本との対応の取り方

**内容ハッシュを主キーにします。** パスではありません。理由は 3 つです。

1. 利用者はファイルを移動・改名します。パスを主キーにすると、そのたびに再構築が必要になります
2. 同一内容の別ファイルが複数ある実態を確認しています(S0-005 の重複排除検証)。ハッシュなら派生物を 1 つで済ませられます
3. 原本が消えても派生物は残せます。**「昔あったはずの資料」を探せることは価値です**

`index.sqlite` に (原本パス → ハッシュ) と (ハッシュ → 派生物) の 2 段で持ち、パス変更はハッシュ側を触らずに更新します。

### calm-technology の観点

`context/standards/calm-technology.md` の「利用者の注意を奪わない」に対して、測定から言えることです。

- **派生物のサイズは小さい。** 50 ファイル 16MB のコーパスに対し、テキスト派生物は **4.0MB**。原本の 25% 程度で、静かに溜まっても問題になりません。ページ画像を保存すると 8.0MB/16 枚と一気に増えるため、**ページ画像は保存しない**(検証4 の結果からも保存する理由がありません)
- **重いのは時間で、容量ではありません。** 初回構築が問題です。RapidOCR は 6 件で 133.9 秒。スキャン PDF の多い倉庫では時間がかかります。**利用者を待たせない設計**(投入時に順次処理し、未処理分は「まだ読めていない」と明示する)が要ります
- **「後で叫ばない」ために、失敗を溜めない。** OCR が 56 文字しか取れなかったファイル(fig-kakei-02.png)のようなものは、**その場で「読めなかった」と記録**し、検索結果でもその旨を出すべきです。黙って空のまま索引に入れると、利用者は「無い」と誤解します

## PO へ伝えるべきこと

1. **「スキャン PDF は探せるが読めない」は取り下げます。** OCR エンジンを差し替えるだけで 4/4 正答になりました。約束できます
2. **ただし文字列の同一性は保証できません。** RapidOCR は「事項」を「事项」と出すことがあります。**引用・法務用途はスコープ外**にしてください
3. **神エクセルの列方向の対応も解けました。** ExStruct + LLM で 3/3。ただし**評価は 3 問**で、一般化の根拠は足りません
4. **視覚ベース検索は現時点で成立しません。** ローカル CPU で 16.7 秒/ページ・精度 2/5。外部研究の効果は英語 + GPU 前提です
5. **誤答は実在します。** 途中経路で 2 件出ました。どちらも「項目名は合っているが項番が違う」「隣の項目の選択肢を拾う」という気づきにくい誤りです。**最終構成では 0 ですが、評価セットを増やせば再び出ます**

export PYTHONUTF8=1 TORCHDYNAMO_DISABLE=1     # Windows では必須
