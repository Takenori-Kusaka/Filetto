# S0-006 日本語文書の OCR で中国語字形が混入しない経路を実測する

Issue [#12](https://github.com/Takenori-Kusaka/Filetto/issues/12) の検証記録です。**基準1・2・3・4・6・7 を判定しました。基準5(RAG 適合性の再測)は LLM を使う形では実施できず、代替測定に留めています。** 理由は「判定できなかった項目」に書きます。

## 結論を先に

**推奨は「RapidOCR 既定(PP-OCRv6)+ 出力後の字形正規化」です。RapidOCR を捨てる必要はありません。**

日本語の認識モデル(`japan_PP-OCRv4_rec_mobile`)への差し替えでも混入は 0 になります。**しかしこちらは採りません。** 日本語モデルは `日` を `目` と読み違え、**正解に必要な文字列を失いました**(検証5)。字形の混入を消す代わりに、より悪い誤読を招いています。

| 経路 | 文字数 | 混入 | 混入率 | 6件の時間 | 正解到達 |
| --- | --- | --- | --- | --- | --- |
| RapidOCR 既定(PP-OCRv6) — S0-004 の推奨 | 8,181 | **13** | 0.159% | **72.7s** | **9/9** |
| **RapidOCR 既定 + 字形正規化(推奨)** | 8,181 | **0** | **0%** | **72.7s** | **9/9** |
| RapidOCR + japan_PP-OCRv4_rec_mobile | 8,280 | **0** | **0%** | 128.8s | **8/9** |
| Docling VLM(granite-docling 258M) | 7,968 | **0** | **0%** | 2,060.7s | **9/9** |
| EasyOCR 全ページ | 3,203 | 0 | 0% | 588.8s | 4/9 |
| (対照)原本のテキスト層 | 513,069 | 202 | 0.039% | — | — |

**字形正規化は追加の計算を伴いません。** 文字列置換であり、モデルも増えません。速度・抽出量・到達可能性のいずれも既定経路のまま、混入だけが 0 になります。

**対照の 202件は、すべてレガシー `.doc` 3件(inashiki-07 / 09 / 10)に集中しています。** これは olefile の断片抽出による文字化けで、S0-004 が既に「表の構造は復元されない」と報告したファイル群です。**この3件を除くと、原本のテキスト層の混入は 0件です。** したがって **0% は到達可能な目標であり、判定基準として妥当です。**

## 判定方法(基準1)

**CJK 統合漢字のうち、CP932 へエンコードできない文字を「日本語の文書組版に出現しない字形」とみなしました。**

| 項目 | 内容 |
| --- | --- |
| 対象の符号位置 | U+4E00–U+9FFF(統合漢字)、U+3400–U+4DBF(拡張A)、U+F900–U+FAFF(互換漢字)、U+20000 以降(拡張B以降) |
| 判定 | `str.encode("cp932")` が `UnicodeEncodeError` を送出する文字を混入とする |
| 裏取り | 同じ判定を EUC-JP でも行い、件数が一致することを確認した(全経路で不一致 0) |

CP932 は日本語 Windows の標準文字集合(JIS X 0208 + NEC / IBM 拡張)であり、簡体字・中国語専用字形はここに含まれません。**辞書の版に依存せず、決定的に判定できます。**

### この判定方法の限界

**中国語字形が日本語にも存在する字へ化けた場合は検出できません。** たとえば OCR が「聲」を「声」と出しても、「声」は CP932 に含まれるため混入として数えません。**本検証が測ったのは「日本語に存在しない字が出る」ことだけです。** 誤読そのものの検出ではありません。

## 検証1: 現行経路の混入を数える(基準1)

対象はスキャン PDF 2件・図表画像 4件。S0-004 の `route-rapidocr-text` の出力をそのまま数えました。

| ファイル | 文字数 | 混入 | 混入した字形 |
| --- | --- | --- | --- |
| scan-kaminokawa-03.pdf | 1,622 | 1 | 项 |
| scan-kochi-04.pdf | 3,538 | 6 | 查 ×5 / 閱 |
| fig-digital-01.png | 1,169 | 1 | 笺 |
| fig-digital-02.png | 1,164 | 0 | — |
| fig-kakei-01.png | 632 | 5 | 带 ×5 |
| fig-kakei-02.png | 56 | 0 | — |
| **合計** | **8,181** | **13** | **5字種** |

実際に混入した文脈です。

```
[scan-kaminokawa-03] ## 1）共通事项（契約保証金） 鏡（表紙…      项 → 項
[scan-kochi-04]      する建設業者）参加資格審查要綱 (趣旨)…       查 → 査
[scan-kochi-04]      高知県建設業者許可書類閱覧所等において…      閱 → 閲
[fig-kakei-01]       《家計収支編》 勤労者世带(3,351)…          带 → 帯
[fig-digital-01]     ## ②電子処方笺の促進 2023年（令和…        笺 → 箋
```

**いずれも語の中核をなす漢字です。**「事項」「審査」「閲覧」「世帯」「処方箋」。S0-004 が「金額・条件・手順は読めています」と評価した水準の出力であっても、**検索の一致・引用の正確さの双方に効きます。**

## 検証2: 認識モデルを日本語向けへ差し替える(基準2)

**RapidOCR は日本語向けの認識モデルを指定できます。** ただし到達までに2段階ありました。

| 試行 | 指定 | 結果 |
| --- | --- | --- |
| 1 | `Rec.lang_type = JAPAN` のみ | **無効。** ログ上のモデルは `PP-OCRv6_rec_small.onnx` のままで、混入は 13件で変わらない |
| 2 | 上記 + `Rec.ocr_version = PP-OCRv5` | **起動しない。** `ValueError: Invalid OCR configuration.` |
| 3 | 上記 + `Rec.ocr_version = PP-OCRv4`、`Rec.model_type = MOBILE` | **成立。** `japan_PP-OCRv4_rec_mobile.onnx` を取得し、**混入 0件** |

**日本語の認識モデルは PP-OCRv4 系にしか存在しません。** `rapidocr/default_models.yaml` を走査したところ、`japan_` を含むモデルは PP-OCRv4 の rec のみでした。**言語指定だけでは既定のバージョン(PP-OCRv6)が優先され、黙って多言語モデルが使われます。** これが S0-004 で混入が出た理由です。

### 実測(基準2)

```python
RapidOcrOptions(
    force_full_page_ocr=True,
    rapidocr_params={
        "Rec.lang_type": LangRec.JAPAN,
        "Rec.ocr_version": OCRVersion.PPOCRV4,
        "Rec.model_type": ModelType.MOBILE,
    },
)
```

| --- | --- | --- | --- | --- |
| scan-kaminokawa-03.pdf | 1,622字 | **1,652字** | 1 | **0** |
| scan-kochi-04.pdf | 3,538字 | **3,545字** | 6 | **0** |
| fig-digital-01.png | 1,169字 | **1,184字** | 1 | **0** |
| fig-digital-02.png | 1,164字 | **1,180字** | 0 | **0** |
| fig-kakei-01.png | 632字 | **660字** | 5 | **0** |
| fig-kakei-02.png | 56字 | 59字 | 0 | **0** |
| **合計** | **8,181字** | **8,280字** | **13** | **0** |

**抽出量は落ちません。** 6件すべてで日本語モデルのほうが多く取れました。

### 速度

**同一マシン・同一セッションでの比較では、日本語モデルは 1.77 倍遅いです。**

| 経路 | 6件の所要時間 |
| --- | --- |
| 既定(PP-OCRv6 rec small) | 72.7s |
| 日本語(japan_PP-OCRv4_rec_mobile) | 128.8s |

**S0-004 が記録した既定経路の 133.9s と比べると、日本語モデルの 128.8s はほぼ同等です。** 72.7s との差は実行時の機械の状態によるものと考えられます。**Docling VLM の 2,060.7s とは 16 倍の開きがあり、この差のほうが判断に効きます。**

### 出力の一致度

日本語モデルの出力は、既定モデルの出力と**同一ではありません**。

| ファイル | 文字列の一致度 |
| --- | --- |
| scan-kaminokawa-03.pdf | 0.798 |
| scan-kochi-04.pdf | 0.888 |

**13文字を置き換えただけの差ではなく、認識そのものが変わっています。** この差が実際に何をもたらしたかは検証5 で測りました。**結果は劣化でした。**

## 検証3: Docling VLM 経路の混入(基準3)

**混入 0件です。** S0-004 の `route-vlm-text` の出力を同じ方法で数えました。

| 項目 | Docling VLM | RapidOCR 日本語 |
| --- | --- | --- |
| 文字数 | 7,968 | 8,280 |
| 混入 | **0** | **0** |
| 6件の所要時間 | **2,060.7s** | **128.8s** |
| 1ページあたり | 約 270秒 | — |
| モデルサイズ | 506MB | 9.8MB |
| RAG(スキャン+画像 8問) | 8/8(S0-004 実測) | **未測定** |

**字形の観点では VLM も条件を満たします。** ただし 16 倍の時間差とモデルサイズ 52 倍の差があり、**字形だけを理由に VLM を採る根拠はありません。**

## 検証4: 出力後の字形正規化(基準4)

**混入を 0 にでき、原文の正しい字は 1文字も壊れませんでした。**

対応表の左辺を「**CP932 へエンコードできない CJK 漢字**」に限定しました。日本語の文書組版に出現しない字形だけを置換対象にするため、**置換によって正しい日本語の字が壊れることは構造上ありえません。** これを実測でも確認しました。

| 対応 | 件数 |
| --- | --- |
| 带 → 帯 | 5 |
| 查 → 査 | 5 |
| 笺 → 箋 | 1 |
| 项 → 項 | 1 |
| 閱 → 閲 | 1 |

| 測定 | 結果 |
| --- | --- |
| RapidOCR 既定経路の混入 | **13 → 0** |
| 原本のテキスト層へ同じ正規化を当てたときの変化(レガシー `.doc` を除く) | **0文字** |
| 原本のテキスト層の混入(レガシー `.doc` を除く) | **0件** |

### 正規化を採る場合の限界

**この対応表は、実測で出現した 5字種にしか対応していません。** 別の文書で別の字形が出れば、そのつど表へ追加する必要があります。**「混入を検出して警告する」ことは網羅的にできますが、「正しい字へ直す」ことは表の網羅性に依存します。** 検出と修正は別の保証水準です。

## 検証5: 正解へ到達できるかを測る(基準5 の代替測定)

**LLM を使わずに測れる範囲だけを測りました。** S0-004 の 15 問のうち、**OCR の差し替えが影響するのは R01〜R08 の8問**です(スキャン PDF 2件・図表画像 4件)。R09〜R15 は `.xlsx` / `.docx` / 通常 PDF であり、本変更の影響を受けません。

### 測り方

**「正解に到達するために必要な文字列が、抽出テキストに存在するか」だけを数えました。** NFKC 正規化で全角半角の揺れを吸収し、空白を除去したうえで部分一致を見ます。

**これは RAG 適合性の下限であって、LLM 判定の代替ではありません。** 存在しなければ確実に答えられません。存在しても答えられるとは限りません。R05 は正解の表現が複数箇所に分かれるため3つ、R08 は表題の一致を2通りで見たため、判定は9件になっています。

### 結果

| 経路 | 到達可能 | 欠落した問い |
| --- | --- | --- |
| RapidOCR 既定(PP-OCRv6) | **9/9** | — |
| **RapidOCR 既定 + 字形正規化** | **9/9** | — |
| RapidOCR + japan_PP-OCRv4_rec_mobile | **8/9** | **R01(「7日」が無い)** |
| Docling VLM | **9/9** | — |
| EasyOCR 全ページ | 4/9 | R01 / R02 / R03 / R04 / R06 |

### 日本語モデルが R01 を落とした理由

**`日` を `目` と読み違えています。**

| 経路 | 出力 |
| --- | --- |
| 既定(PP-OCRv6) | 落札日（入札日）より**7日以内**（初日不算入·町の休日を 除く） |
| 日本語(PP-OCRv4) | 落札日（入札目丿より**７目以内**（初日不算入・町の休目を 除く」 |

同一ファイル内で `日` の出現は 8件から 5件へ減り、`目` が 0件から 3件へ増えました。**「落札日から何日以内に契約書を提出するか」という問いに対して、日数の単位そのものが失われています。**

**字形の混入(事项)は「日本語に無い字が出る」誤りで、検出できます。`日`→`目` は日本語にある字への誤読で、検出できません。** 後者のほうが危険です。S0-004 が「もっともらしい誤りは回答不能より危険」と報告した性質と同じものです。

### この測定の限界

- **9件はすべて存在の有無だけを見ています。** 文脈として使えるかは判定していません
- **R09〜R15 は測っていません。** OCR の変更が影響しないためですが、「影響しない」こと自体は実測していません
- **LLM 判定との一致は未確認です。** S0-004 の 15/15 と本測定の 9/9 は別の指標であり、直接は比較できません

## 判定(基準7)

**基準7 の差し戻し条件には該当しません。** 混入率 0% の経路が3つ見つかりました(既定 + 字形正規化 / 日本語モデル / Docling VLM)。

**そのうち速度と正解到達を同時に保つのは「既定 + 字形正規化」だけです。**

| 経路 | 混入0 | 速度そのまま | 正解到達 9/9 |
| --- | --- | --- | --- |
| **既定 + 字形正規化** | **満たす** | **満たす** | **満たす** |
| 日本語モデル | 満たす | 満たさない(1.77倍) | 満たさない(8/9) |
| Docling VLM | 満たす | 満たさない(16倍) | 満たす |

## 判定できなかった項目

| 項目 | 理由 |
| --- | --- |
| **基準5 の本来の測り方(LLM による 15問の判定)** | **判定に使う LLM を呼べませんでした。** S0-004 は Claude を API 経由で呼び、原本を知らないインスタンスへ文脈だけを渡す方法を採っています。本検証の実行環境に API キーが設定されておらず、同じ方法を再現できませんでした。**本セッションの担当者を判定に使うことはできません**(S0-004 の記録を読んでおり、15問の正解を既に知っているため、原本を知らないインスタンスという前提が崩れます)。**代替として文字列の存在だけを機械的に測りました**(検証5) |
| R09〜R15 の再測 | OCR の変更が影響しない範囲のため測っていません。**「影響しない」こと自体は実測していません** |
| PP-OCRv5 系の日本語モデル | **存在しません。** `default_models.yaml` に `japan_` を含む項目は PP-OCRv4 の rec のみでした |
| 手書き・低解像度・縦書き | コーパスに含まれず、判定できません(S0-004 と同じ) |
| 検出モデル(det)を PP-OCRv4 へ揃えた場合 | 未測定。認識モデルの差し替えが到達可能性を下げたため、この方向を追っていません |

## 再現手順

```bash
export PYTHONUTF8=1 TORCHDYNAMO_DISABLE=1     # Windows では必須

# 検証1・3: 既存の出力に対する混入の測定(モデル不要)
python glyph_audit.py

# 検証2: 認識モデルを日本語向けへ差し替えて再抽出
python route_rapidocr_ja4.py

# 検証4: 字形正規化と副作用の測定(モデル不要)
python glyph_fix.py

# 検証5: 正解文字列の到達可能性(モデル不要・LLM 不要)
python answer_presence.py
```

使用した実行環境は S0-004 と同一です(`rapidocr 3.9.2` / `docling 2.119.0` / `onnxruntime 1.20.1`)。コーパス・評価セットも S0-004 と同一のものを使いました。

## PO へ伝えるべきこと

1. **RapidOCR を捨てる必要はありません。中核構成は S0-004 のままで、抽出後に文字列置換を1段挟むだけです。** 速度・抽出量・モデル構成は変わらず、混入だけが 13件から 0件になります
2. **日本語の認識モデルへ差し替える案は採りません。** 混入は 0 になりますが、**`日` を `目` と読み違えて「7日以内」を失いました**。速度も 1.77 倍になります。**字形の混入を消す代わりに、検出できない誤読を招いています**
3. **S0-004 で混入が出たのは、言語指定だけでは既定のバージョンが優先され、黙って多言語モデルが使われるためでした。** 設定の書き方の問題であり、RapidOCR の限界ではありません
4. **RAG 適合性の LLM 判定は実施できていません。** 代替として文字列の到達可能性を測り、推奨経路は 9/9 でした。**S0-004 の 15/15 と同じ指標ではありません。** LLM 判定を行うなら API キーの用意についてご判断ください
5. **Docling VLM も混入 0 かつ 9/9 ですが、16 倍遅くモデルは 52 倍大きいです。** 予備手段として残す価値はありますが、中核に据える根拠はありません
6. **字形正規化の対応表は、実測で出た5字種にしか対応していません。** 「混入を検出して警告する」ことは網羅的にできますが、「正しい字へ直す」ことは表の網羅性に依存します。**検出と修正は別の保証水準です**
7. **本検証が測ったのは「日本語に存在しない字が出る」ことだけです。** 中国語字形が日本語にも存在する字へ化けた場合(聲→声)は検出できません。**`日`→`目` がまさにその例で、字形の判定では素通りしました**
