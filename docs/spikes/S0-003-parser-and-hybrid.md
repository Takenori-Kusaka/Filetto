# S0-003 Docling / ハイブリッド検索 / 神エクセル評価セットの実測

Issue #5 の検証記録です。検証1〜3 をすべて実施しました。時間箱内に収まっています。

## 推奨する中核構成(受入基準5)

**次の1構成を推奨します。**

```
層A パース:  PDF・画像 → Docling(OCR: EasyOCR ja)
             .xlsx      → openpyxl 全セル読み(+ 神エクセル増強に ExStruct)
             .xls/.doc  → xlrd / olefile
層B 検索:    janome 形態素 + BM25  と  multilingual-e5-small の埋め込みを 3:7 で統合
```

**この構成は「維持コストゼロ(外部 API なし・通信なし)」を満たします。** 実行時の外部通信は 0 件、API キーは不要、従量課金は発生しません。

満たす、と書ける根拠と、その但し書きを先に置きます。

| 項目 | 実測値 |
| --- | --- |
| 金銭コスト | **$0**(推論はすべてローカル CPU) |
| 実行時の外部通信 | **なし**(初回のみモデル取得) |
| 初回ダウンロード | 約 **1.07 GB**(Docling レイアウト 342MB + heron 164MB + EasyOCR 96MB + e5-small 471MB) |
| 50 ファイルの初回構築 | **約 25 分**(パース 1505.5 秒 + 索引 33 秒 + 埋め込み 5.4 秒) |
| 検索の正答数 | **10/10**(S0-002 の 8/10 から改善) |

**「ゼロ」なのは金銭だけです。** CPU 時間とディスクは掛かります。50 ファイルで 25 分ということは、数千ファイルの資料倉庫では初回構築に数時間から十数時間かかります。この点は企画の書き方に反映する必要があります(後述)。

## 検証3: 神エクセル評価セット

### 評価セット

現行コーパスから、結合セルを多く含む 3 ファイルを選びました。

| ファイル | 内容 | 結合セル数 |
| --- | --- | --- |
| kochi-14.xlsx | 経営事項審査 別紙三(方眼紙・項目が数百列にまたがる) | **313** |
| kakei-06.xlsx | 家計調査 第2表(多段ヘッダ) | **202** |
| kochi-03.xlsx | 担い手確保 誓約書 様式 | 26 |

**クエリ 5 件は測定前に確定し、以後変更していません**(`kami-queries.json` に記録)。正解は openpyxl でセル座標を人が確認して決めました。判定は「アンカー語と期待値が線形化出力上で 200 文字以内に共起するか」です。

### 結果

| # | 問い | openpyxl | Docling | ExStruct |
| --- | --- | --- | --- | --- |
| G1 | 建設業退職金共済制度加入の有無 の選択肢は何か(答: 〔1.有、2.無 〕) | HIT | **MISS** | HIT |
| G2 | 項番7の審査項目は何か(答: 若年技術職員の継続的な育成及び確保) | HIT | HIT | **MISS** |
| G3 | 若年技術職員の割合は何を何で割った値か(答: 技術職員数) | HIT | HIT | HIT |
| G4 | 集計世帯数はいくつか(答: 3883) | HIT | **MISS** | HIT |
| G5 | 実績記入表の列見出しは何か(答: 取組内容の詳細) | HIT | HIT | HIT |
| | **合計** | **5/5** | **3/5** | **4/5** |

### 判定の内訳

**openpyxl 全セル読みが 5/5 で最良でした。** 行単位で値を並べるため、同一行のセルが出力上も隣接するからです。素朴な実装が最も強いという結果です。

**ExStruct の G2 は、全角数字の正規化による不一致です。** ExStruct は「７」を「7」へ正規化します。committed した判定は全角「７」をアンカーにしていたため MISS になりました。半角「7」で判定し直すと **HIT** で、**構造としては 5/5 相当が保持されています**。判定基準を後から動かさないため、表は 4/5 のまま残します。

**Docling の 2 件の MISS には明確な原因があります。** Docling は結合セルを「またがる全セルに同じ値を複製する」形で展開します。実際の出力です。

```
| 建設業退職金共済制度加入の有無 | 建設業退職金共済制度加入の有無 | 建設業退職金共済制度加入の有無 | ...(以下 16 回繰り返し)
```

この結果、kochi-14.xlsx の出力は **227,479 文字**(openpyxl は 2,994 文字)、kochi-12.xlsx は **508,190 文字**(同 920 文字)に膨張し、項目名と選択肢が 200 文字以上離れてしまいます。**Docling は Excel には向きません。**

### 全条件が解けなかったこと

補足として、G4 の**列**方向の対応(列見出し「うち勤労者世帯」と値 3883 の近接)も測りました。

| openpyxl | Docling | ExStruct |
| --- | --- | --- |
| × | × | × |

**3 条件とも保持していません。** 行の対応は取れても、多段ヘッダの列の対応は誰も復元できていません。「表の行見出しと列見出しの交差が示す値」を答えるには、いずれのパーサでも不十分です。これは本検証で見つかった**未解決の課題**です。

### ExStruct の付随的な利点

| 観点 | openpyxl | ExStruct |
| --- | --- | --- |
| kochi-14.xlsx の出力量 | 2,994 文字 | **5,626 文字**(座標付き) |
| セル座標の保持 | なし | **あり**(`r30: I=... \| CD=7 \| CM=...`) |
| 図形・グラフ・印刷範囲 | 取れない | **取れる** |
| .xls への対応 | xlrd で可 | **xlrd を入れれば可** |

**ExStruct が .xls を扱えることは、README の対応表から読み取れる範囲を超えていました。** `exstruct input.xls` は既定では `Import xlrd failed` で失敗しますが、`xlrd` を追加導入すると正常に処理できます。S0-002 で「対象は .xlsx / .xlsm で、レガシー .xls は範囲外」と書いたのは不正確でした。訂正します。

ExStruct の処理時間は kochi-14.xlsx(313 結合)で 12.9 秒、kakei-06.xlsx で 2.7 秒でした。Excel COM は使わず `--mode light` で動作しています(S0-002 で COM が停止した問題は回避できます)。

## 推奨構成の根拠と、採らなかった選択肢

### 採る構成

| 層 | 選択 | 理由 |
| --- | --- | --- |
| PDF・画像 | **Docling(EasyOCR ja)** | 純 Python が壊していた 3 件を正しく読み、スキャン PDF と図表画像を唯一読める。BM25 を 8→9 に上げた |
| .xlsx | **openpyxl 全セル読み**(神エクセルは ExStruct を併用) | 神エクセル評価で 5/5。Docling は 3/5 で出力が 76 倍に膨張する |
| .xls / .doc | **xlrd / olefile** | Docling も ExStruct(既定)も非対応。実測で問題なし |
| 検索 | **BM25 + e5-small を 3:7** | 10/10。埋め込みは 50 件 5.4 秒で無視できるコスト |

### 採らなかった選択肢

- **Docling で Excel も処理する**: 結合セルの複製展開で出力が膨張し、行の対応が壊れる(3/5)。採らない
- **ExStruct を Excel の既定にする**: 座標保持と圧縮率は優れるが、1 ファイル 12.9 秒とコストが高い。**結合セルの多い神エクセルに限って併用**する
- **ruri-v3-30m を埋め込みに使う**: 日本語特化だが本コーパスでは e5-small(8/10 と 7/10、Docling 上では未測定)に劣った。サイズは 1/3 なので、軽量化が要るときの候補として残す
- **LLM を検索に使う**: 10/10 に達しているため、現時点で必要がない。S0-002 の案B(オプション層)として温存する

## PO へ伝えるべきこと

1. **維持コストゼロは満たします。**ただし「金銭がゼロ」であって、**初回構築に CPU 時間が掛かります**(50 件で 25 分)。数千ファイルなら数時間から十数時間です。企画の書き方を「無料」ではなく「課金なし・自分のマシンで完結」に寄せる必要があります
2. **スキャン PDF の内容提示は約束できません。** 検索でヒットさせることはできますが、OCR の回収率は 1 割前後です。「スキャン文書も探せる」とは言えますが「読める」とは言えません
3. **表の行見出し×列見出しの交差は、どのパーサでも解けていません。** 神エクセルの「意味構造の完全な理解」は現時点で未達です。約束の範囲から外すか、次の探索課題にしてください
4. **S0-002 の記述 2 点を訂正しました。** pypdf の文字化け(Q7 の真因)と、ExStruct の .xls 対応です
