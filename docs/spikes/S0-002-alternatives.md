# S0-002 Graphify 以外の構成案と、実測による比較

S0-001 は Graphify という**特定の実装**を検証したもので、企画そのものの成否を決めるものではありませんでした。本書は「では何なら成立するか」を並べ、うち 1 案を実測します。

## 結論を先に

**企画は破綻していません。** むしろ S0-001 で使った Graphify は、この用途には過剰かつ不適合でした。

同じコーパス 50 件・同じ 10 クエリで、**パース層を自前に持ち、日本語形態素 + BM25 で検索するだけの構成**を実測したところ、次の結果になりました。

| 構成 | 正答数 | 初回構築 | API 費用 | 外部依存 |
| --- | --- | --- | --- | --- |
| Graphify(素の日本語クエリ) | 3/10 | 2分11秒 | $1.23 | LLM バックエンド必須 |
| Graphify(スキル手順どおり) | 8/10 | 2分11秒 | $1.23 | LLM + ホストエージェント |
| **パース + 日本語BM25(本書の実測)** | **8/10** | **31秒** | **$0** | **なし** |

**LLM もベクトル DB も外部 API も一切使わない構成が、Graphify の最良値と同点でした。** しかも所要時間は 1/4、費用はゼロ、対応形式は .xls / .doc / .pptx を含みます(Graphify はこの 3 形式が非対応)。

「維持コストゼロ」という企画の中核訴求は、**Graphify を捨てることで初めて成立します**。

## 問題を 2 層に分ける

S0-001 の失敗は、2 つの別問題を 1 つのツールに任せたことに起因します。

| 層 | やること | 日本固有の難しさ |
| --- | --- | --- |
| **A. パース / 正規化** | ファイル → テキスト・構造 | 神エクセル、Word 罫線様式、レガシー .xls/.doc、スキャン PDF、縦書き |
| **B. 検索 / 意味づけ** | テキスト → 質問に答える | 語の区切りが無い、表記ゆれ、同義語 |

Graphify は B に強い設計(ナレッジグラフ)を持ちますが、A は薄く、しかも B の入口(クエリ照合)が英語前提でした。**日本語の資料倉庫では、効くのは圧倒的に A です。**

## 層A: パース / 正規化の候補

| 候補 | ライセンス | 対応 | 評価 |
| --- | --- | --- | --- |
| **Docling**(IBM) | **MIT** | PDF / DOCX / PPTX / XLSX / HTML / 画像、スキャン PDF の OCR、表構造・読み順解析 | 本命。商用可、64k stars、活発 |
| **ExStruct** | **BSD-3-Clause** | .xlsx / .xlsm を、セル値+結合+図形+グラフ+SmartArt+印刷範囲まで JSON 化 | 神エクセル専用の増強として有力 |
| **YomiToku** | **CC BY-NC-SA 4.0** | 日本語特化 OCR。縦書き・手書き・複雑な表 | **商用利用不可。**採用は要判断 |
| kami_excel_extractor | **ライセンス表記なし** | VLM で帳票を構造化 | **採用不可**(後述) |
| Office COM / LibreOffice 変換 | — | レガシー .xls/.doc → OOXML | 補助。無人運用に難あり(後述) |

### Docling を本命に置く理由

MIT で商用制約がなく、Filetto が必要とする形式をほぼ単体で覆います。スキャン PDF の OCR と表構造認識まで含むため、S0-001 で 0 ノードだったスキャン PDF もここで解決できます。

### ExStruct の位置づけ(ご提示の情報を一部訂正します)

「Windows + Excel が必須」は**現在は正確ではありません**。リポジトリの README を確認したところ、非 COM 環境向けに 2 段の代替経路があります。

> - COM/Excel 環境 ではリッチ抽出
> - 非 COM 環境 では LibreOffice runtime があればセル・テーブル候補・図形・グラフ（best-effort）
> - Excel COM または LibreOffice runtime が不在でもプロセスは落ちず、OOXML直接解析に切り替えます

ライセンスは BSD-3-Clause、187 stars、最終更新 2026-06。ただし**対象は .xlsx / .xlsm** で、行政サイトに多いレガシー .xls は範囲外です。

### YomiToku は「OSS だが商用不可」

ライセンスは **CC BY-NC-SA 4.0**。README に明記があります。

> 本リポジトリ内のソースコードおよび本プロジェクトに関連する HuggingFace Hub 上のモデルの重みファイルは、**CC BY-NC-SA 4.0** ライセンスの下で提供されています。非商用での個人利用・研究目的での利用は自由に行っていただけます。

商用には別途 YomiToku-Pro 契約が必要です。加えて **SA(継承)** 条項があるため、組み込み方によっては Filetto 側の配布条件に波及します。個人利用ツールとして出すなら使えますが、**将来の収益化を捨てない限り、中核には置けません**。

### kami_excel_extractor は採用できません

`chottokun/kami_excel_extractor` を確認したところ、**リポジトリに LICENSE ファイルが存在しません**(star 0、最終更新 2026-07-01)。ライセンス表記のないコードは既定で著作権が全面留保され、**再利用・再配布が法的に許されません**。技術的な出来にかかわらず、依存先には選べません。同じ発想を採るなら、Docling や ExStruct のライセンスが明確なものを使うべきです。

### Office COM 正規化は無人運用に向きません(実測)

レガシー .xls / .doc を OOXML へ正規化する前処理を、この環境の Excel COM で実際に試しました。**9 件中 2 件を変換したところでプロセスが停止し、10 分のタイムアウトに達しました**(Excel が対話ダイアログを出したまま応答しなくなったものと見られます)。強制終了して復旧しています。

自動処理の常時経路に COM を置くのは危険です。レガシー形式は後述の純 Python パーサ(xlrd / olefile)で読むか、LibreOffice をヘッドレスで使う方が安全です。

## 層B: 検索 / 意味づけの候補

| 候補 | ライセンス | LLM 依存 | 評価 |
| --- | --- | --- | --- |
| **BM25 + 日本語形態素** | — | **なし** | 本書で実測。8/10、$0 |
| ローカル埋め込み(multilingual-e5 / ruri 等) | Apache-2.0 系 | なし(モデルはローカル) | BM25 の弱点(言い換え)を補う。未実測 |
| Microsoft GraphRAG | MIT | **必須かつ高コスト** | 後述 |
| LightRAG | MIT | 必須 | GraphRAG より軽量。未検証 |
| Graphify | Apache-2.0 / MIT | 必須(またはホストエージェント) | S0-001 の対象 |

### Microsoft GraphRAG は、この企画とは逆を向いています

MIT ライセンスで、35k stars、活発に開発されています。ただし README 冒頭に次の警告があります。

> GraphRAG indexing can be an expensive operation, please read all of the documentation to understand the process and costs involved, and **start small**.

GraphRAG は全文書を LLM に通してエンティティ・関係・コミュニティ要約を生成する設計で、**インデックス構築コストは Graphify より一桁重くなります**。入力も基本は非構造テキストで、PDF / Office のパースは自前です(つまり層 A は別途必要)。

「維持コストゼロ」を捨てて「深い問い(横断的な要約、なぜ系の質問)に答えられること」を取るなら候補になりますが、**現在の企画の訴求とは正面から衝突します**。採るなら企画の書き換えとセットです。

## 実測: パース + 日本語BM25

### 条件

S0-001 と**同一のコーパス 50 件・同一の 10 クエリ・同一の判定基準**(期待ファイルが上位 3 件)。クエリは S0-001 で確定したものをそのまま使い、変更していません。

パース層は純 Python のみで構成しました(外部プロセスなし、API なし)。

| 形式 | 使用ライブラリ |
| --- | --- |
| .pdf | pypdf |
| .docx | python-docx(段落 + 表セル) |
| .xlsx | openpyxl(全シート・全セル) |
| .pptx | python-pptx(全図形 + 表) |
| .xls | xlrd(レガシー binary) |
| .doc | olefile + cp932/utf-16 断片抽出(簡易) |
| .md / .txt | 直接読み |

検索は janome で形態素解析(名詞・動詞・形容詞の原形のみ採用)し、rank-bm25 の BM25Okapi。

### 結果

```
parsed 50 files in 15.1s; 6 produced <20 chars:
   fig-digital-01.png / fig-digital-02.png / fig-kakei-01.png / fig-kakei-02.png
   scan-kaminokawa-03.pdf / scan-kochi-04.pdf
tokenized+indexed in 15.5s
```

**テキストを取り出せなかったのは画像 4 件とスキャン PDF 2 件だけ**です。S0-001 で Graphify が丸ごとスキップした **.xls 6 件 / .doc 3 件 / .pptx 3 件は、すべて読めています**。

| # | クエリ | 上位3件 | 判定 |
| --- | --- | --- | --- |
| Q1 | 仲裁合意書の様式はどこ | **inashiki-06.docx** / digital-02 / digital-01 | 合格 |
| Q2 | 入札書はどうやって折って提出するのか | kaminokawa-02 / kochi-05 / digital-01 | 不合格 |
| Q3 | 消費支出が前年同月比でどれくらい減ったか | **kakei-02** / **kakei-04** / **kakei-03** | 合格 |
| Q4 | 障害者を雇用していることを誓約する書類 | **kochi-01.docx** / kochi-05 / digital-01 | 合格 |
| Q5 | コンプライアンス基本方針のひな形 | **kochi-06** / **kochi-07** / **kochi-08** | 合格 |
| Q6 | 電子納品のやり方を定めた要領 | **kaminokawa-05** / kochi-05 / digital-01 | 合格 |
| Q7 | 県外の業者が入札に参加するときの資格審査の要綱 | kochi-05 / inashiki-06 / mhlw-01 | 不合格 |
| Q8 | デジタル社会の実現に向けた重点計画 | **digital-01** / digital-02 / digital-04 | 合格 |
| Q9 | 介護保険制度の改正について説明したスライド | **mhlw-01.pptx** / digital-01 / digital-03 | 合格 |
| Q10 | 袋とじの作り方 | **kaminokawa-04** / chisou-01 / digital-01 | 合格 |

**8/10。基準2(7/10)を満たします。所要 31 秒、費用 $0、外部通信なし。**

外した 2 件には原因があります。

- **Q2**: 期待した kaminokawa-01.pdf は本文 119 文字しかなく、BM25 は短文書に不利です。1 位になった kaminokawa-02.pdf も「入札執行上の注意」で無関係ではありません
- **Q7**: 1 位の kochi-05.pdf は「**県内**に主たる営業所を有する業者」の要綱、期待した kochi-04.pdf は「**県外**」版です。語彙がほぼ同一で、BM25 では原理的に分離できません

Q9 は Graphify では .pptx 非対応のため原理的に到達不能でしたが、ここでは 1 位です。

### この実測が示していること

1. **日本語の資料倉庫では、勝負はパース層で決まります。** 検索側は BM25 で足ります
2. **Graphify のナレッジグラフは、この 10 問に対して価値を出していません。** 同点なら、構築 4 倍・費用 $1.23・API 必須の側を選ぶ理由がありません
3. **Q7 型の失敗(語彙が同じで属性だけ違う)はグラフでも BM25 でも解けません。** ここが本当に難しい部分で、埋め込みや LLM リランクの出番です

## 推奨する 3 案

### 案A: パース層 + BM25(推奨)

```
[Docling / ExStruct / 純Pythonパーサ] → テキスト+構造 → [janome + BM25] → 検索結果
```

- **維持コストゼロが本当に成立します。** 外部 API なし、モデルなし、通信なし
- 実測 8/10、50 件 31 秒
- 弱点: 言い換えに弱い(Q2)、属性違いの分離ができない(Q7)
- 追加投資: ローカル埋め込み(multilingual-e5 / ruri)を足してハイブリッド検索にすれば Q2 型は改善が見込めます。モデルは数百 MB、CPU で動きます

### 案B: 案A + 任意で LLM 層

案 A を土台に、**LLM は「あると良くなる」オプション**に降格します。Claude Code / Ollama / API キーのいずれかがある人だけが、要約・横断質問・リランクを使えます。

- 訴求は「API なしで動く。あれば賢くなる」に変わります。**ゼロコストの約束を守りつつ上限を上げられます**
- Graphify を使うならここです。中核ではなく強化レイヤとして

### 案C: GraphRAG 系へ全面移行

「維持コストゼロ」を捨て、深い横断的な問いに答えることへ企画を書き換えます。

- Microsoft GraphRAG(MIT)または LightRAG(MIT)
- 層 A は結局自前で必要です
- **企画の書き換えが前提**であり、S0 の判断を超えます

## PO に判断していただきたいこと

S0-001 の「前提は成立しない」は、**Graphify という実装に限った話**でした。判断は次に置き換わります。

1. **中核を案A(パース + BM25)に置き換えてよいか。** これを採れば「維持コストゼロ」は実測で成立します
2. **LLM をオプション層(案B)として残すか、完全に排するか**
3. **スキャン PDF / 手書きへの対応をどこまで約束するか。** ここだけは OCR が要り、日本語で最も強い YomiToku は**商用不可**です。Docling の OCR で妥協するか、非商用に限定するか
4. **レガシー .xls / .doc をどこまで保証するか。** 純 Python パーサで読めていますが、.doc は簡易実装で、罫線レイアウトの意味までは復元していません

## 次にやるべき検証(S0-003 案)

1. **Docling を実際に通す。** 同じ 50 件で、パース品質(特にスキャン PDF・神エクセル)と所要時間を測る
2. **ローカル埋め込みを足したハイブリッド検索**で Q2 / Q7 が救えるかを測る
3. **神エクセル特化の評価セット**を作る。今回のコーパスは様式・要綱が中心で、結合セルの意味構造そのものを問うクエリが含まれていません。ExStruct の価値はそこで初めて測れます

いずれも 1〜2 日の時間箱で判定できます。
