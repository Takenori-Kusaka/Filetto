## 2. 先に技術判断者へ返す論点(ADR-0004 を書く前に潰す必要があるもの)

**調査の過程で、既存の受入基準・ADR に5件の矛盾または未決を発見しました。** いずれも ADR-0004 の内容を左右します。**これらを放置したまま ADR-0004 を採用すると、実装工程で必ず差し戻しが発生します。**

### 2-1. 初版にトークンの発行者が存在しない(最も重い)

| 事実 | 出典 |
| --- | --- |
| JWT が付与されていない要求には HTTP 401 を返さなければならない | F-003 基準24 |
| **システムは JWT の発行を行ってはならない** | F-003 基準27 |
| 認証基盤は別マイクロサービス Auth の責務。**Auth は Filetto 完了後に開発する** | F-003 スコープ外 / P-001「案件の目的」 |

**この3つは同時に成立しません。** 初版の Filetto を `docker compose up` で起動した利用者は、JWT を発行する主体を持ちません。基準24 に従えば、すべての要求が 401 になります。**「1コマンドで立てられ、ファイルを置いた瞬間から検索可能になる」(P-001 案件の目的)が初版で成立しません。**

取りうる方向を4つ挙げます。**いずれも F-003 の受入基準の改訂を伴うため、G-2 / G-4(価値責任者)の判定対象です。ADR-0004 単独では解決できません。**

| # | 方向 | 触れる基準 |
| --- | --- | --- |
| ア | 利用者が自分で JWT を作り、環境変数で与える(事前共有鍵または公開鍵を設定) | 基準24 は満たす。**利用者に鍵管理を課す**(`calm-technology` の「管理タスクを暗黙に課さない」と緊張) |
| イ | 認可の適用有無を設定で切り替える(既定を「適用しない」にし、localhost bind を前提とする) | **基準24 を条件付きにする改訂が要る** |
| ウ | 「発行しない」を「利用者向けの認証情報の発行を行わない」と読み替え、起動時のブートストラップトークンは別扱いとする | **基準27 の改訂が要る**。ADR-0002 の「Filetto は認証基盤ではない」という位置づけに触れる |
| エ | 初版では認可を実装せず、Auth の合成時に導入する | **基準24〜27 を初版のスコープから外す改訂が要る**。ADR-0003 の「ゴミ箱にもアクセス制御が要る」と衝突 |

**この論点は §5(検証の責務分界)と不可分です。** §5 の各案は、この論点の答えによって成立する / しないが変わります。

### 2-2. 基準6(404)と基準25(403 + 存在秘匿)が矛盾する

| 基準 | 内容 |
| --- | --- |
| F-003 基準6 | 存在しない安定 ID が指定された場合、HTTP **404** を返さなければならない |
| F-003 基準25 | JWT のスコープが対象ファイルを含まない場合、HTTP **403** を返し、**当該ファイルの存在を応答から判別できないようにしなければならない** |

**404 と 403 を打ち分けた時点で、要求元は「403 が返った = そのファイルは存在する」と判別できます。** 基準25 の後半が、基準25 の前半によって満たされません。

**この構造は GitHub が 404 で統一している理由そのものです。** ADR-0004 は「スコープ外のファイルにどの状態コードを返すか」を決める必要があり、それは ADR-0002 決定2-1 の3状態(利用可能 / ゴミ箱 / 存在しない)の見せ方にも波及します。**ゴミ箱にあるファイルへスコープ外からアクセスしたとき何を返すか**は、ADR-0002 と ADR-0003 のどちらにも書かれていません。

### 2-3. 対外へ出す「スコープの対象単位」が決まっていない

ADR-0002 決定2 は安定 ID の発行規則を「**パスが初めて索引に入った時点で発行する**」と定めています。これはファイル単位の記述であり、**ディレクトリに安定 ID を発行するかは書かれていません。**

論点2 のうち、対象をディレクトリ(ルート)で指す案は、**ディレクトリ側の安定 ID が存在することを前提とします。** 存在しない場合、その案は「ADR-0002 の改訂を伴う案」になります。

### 2-4. 「実行時の外部通信なし」に同一 `docker compose` 内の通信が含まれるかの定義がない

P-001 は「運用時 $0・実行時の外部通信なし・API キー不要は S0-004 が実測で確認した」と記述しています。**S0-004 の文脈は外部 API・クラウド推論への依存の不在であり、同一ホスト内のプロセス間通信を禁じたものとは読めません。** 実際、ADR-0008 で `loreserver` への常駐接続を受け入れています。

**しかし正本にその定義がありません。** §5 の下位論点(鍵配布を JWKS 取得で行うか)は、この定義に依存します。F-003 基準12 は「システムは**検索の実行時に**外部ネットワークへ接続してはならない」と対象を検索に限定しており、認可の経路には及んでいません。

### 2-5. (ADR-0004 の対象外)ADR-0002 決定3 と F-003 基準13・14 が矛盾する

調査中に発見したため記録します。**ADR-0004 の対象ではありません。**

ADR-0002 決定3 は「**どちらを返すかは、要求する側が指定する。サーバが公開されない閾値で暗黙に切り替えない**」と定め、GitHub Contents API の事故を根拠に挙げています。一方 F-003 基準13・14 は「サイズが上限以下なら本文」「上限を超えるなら署名付き URL」と、**サーバがサイズ閾値で切り替える**設計を要求しています。**ADR-0002 が明示的に否定した方式そのものです。**

## 3. 論点1 — クレーム名(名前空間と命名規則)

### 3.1 調査で確定した事実

| # | 事実 | 一次情報 |
| --- | --- | --- |
| 1 | 新しいクレーム名は IANA 登録**または** Collision-Resistant Name と**する**べき(should)。**MUST ではない** | [RFC 7519 §4.2](https://www.rfc-editor.org/rfc/rfc7519.html)(May 2015 / 確認 2026-08-13) |
| 2 | Private Claim Name は MAY で許容されるが「**衝突しうるので慎重に使うべき**」 | RFC 7519 §4.3 |
| 3 | Collision-Resistant Name の例は**ドメイン名・OID・UUID**。URI に限定されない | RFC 7519 §2 |
| 4 | **`scope` / `roles` / `groups` / `entitlements` / `client_id` / `act` / `may_act` / `cnf` / `authorization_details` は IANA 登録済み** | [IANA JWT Claims](https://www.iana.org/assignments/jwt/jwt.xhtml)(Last Updated 2026-07-20 / 確認 2026-08-13) |
| 5 | `scope` の定義元は **RFC 8693 §4.2**。値は「**スペース区切りの単一 JSON 文字列**」であり配列ではない | [RFC 8693 §4.2](https://www.rfc-editor.org/rfc/rfc8693.txt)(Jan 2020) |
| 6 | IANA レジストリに意味が定義済みの属性は、**対応するクレーム名で符号化すべき(SHOULD)** | [RFC 9068 §2.2.2](https://www.rfc-editor.org/rfc/rfc9068.html)(Oct 2021) |
| 7 | **「クレーム名が collision-resistant であるか、または access token が private subsystem 内でのみ使われる限り」任意の属性を返してよい(MAY)** | RFC 9068 §2.2 |
| 8 | OpenID Connect Core §5.1.2 は衝突耐性名を **RECOMMENDED** とし、「衝突可能性が低ければ Private Claim Name を安全に使える」と明記。**MUST ではない** | [OIDC Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html) errata set 2(2023-12-15) / 検証は [OIDF-Japan 公式訳](https://openid-foundation-japan.github.io/openid-connect-core-1_0.ja.html) |
| 9 | **URI 名前空間を事実上強制するのは Auth0 のみ。** Okta / Firebase / Cognito / Keycloak は要求していない | 各社ドキュメント(§9) |
| 10 | **Auth0 では制限名を使った独自クレームがエラーなく消える**(トランザクションは成功する) | [Auth0 Create Custom Claims](https://auth0.com/docs/secure/tokens/json-web-tokens/create-custom-claims) |
| 11 | Okta / Firebase では予約名の使用は**エラーになる** | [Okta 予約クレーム一覧](https://support.okta.com/help/s/article/list-of-reserved-claim-names) / [Firebase Custom Claims](https://firebase.google.com/docs/auth/admin/custom-claims) |
| 12 | **Keycloak は claim.name 中のドットをネストとして解釈する。** URI 形式のクレーム名はバックスラッシュエスケープが要る | [Keycloak Server Admin Guide 26.7.1](https://www.keycloak.org/docs/latest/server_admin/index.html) |
| 13 | **Okta はスコープを `scp`(配列)で返す。** IANA 登録名 `scope`(スペース区切り文字列)と名前も型も異なる | Okta ドキュメント(§9) |
| 14 | Firebase の独自クレームは**ペイロード 1000 バイト上限**。超過はエラー | Firebase ドキュメント |

### 3.2 反証 — 各案を崩しにかかった記録

**反証1「第三者が自分の IdP を繋ぐ」観点。** P-001 は AGPL-3.0 で公開し第三者の採用を狙う案件です(D-0 第3節「第三者が使う」仮説は**未達として宣言済み**)。第三者は Auth を待たず、手持ちの Keycloak / Auth0 / Authelia を繋ぐ可能性があります。

- **短い独自名(案1-C)への反証**: `roles` / `groups` / `permissions` は Auth0 の制限名であり、**エラーにならず黙ってトークンから消えます**。利用者は「認可が効かない」ではなく「なぜか常に権限がない」という形で遭遇します。デバッグが極めて困難です。
- **URI 名前空間(案1-B / 1-D)への反証**: **Keycloak ではドットがネストとして解釈されます。** `https://filetto.example/claims/scope` をそのまま claim.name に置くと `https://filetto` の下に `example/claims/scope` が入る形になり、Filetto 側のパーサと一致しません。URI 名前空間は「安全な選択」ではなく、**IdP ごとに別の壊れ方をする選択**です。
- **IANA 登録名のみ(案1-A)への反証**: **Okta は `scope` ではなく `scp`(配列)を返します。** RFC 8693 §4.2 準拠のパーサは Okta のトークンを読めません。登録名を使えば相互運用できるという前提自体が、実装の現実では成立していません。

**反証2「Filetto は private subsystem か」観点。** RFC 9068 §2.2 の例外は「access token が private subsystem 内でのみ使われる」ことを条件にしています。**Filetto は AGPL で公開され、第三者が任意の IdP と組み合わせる前提の部品です。** 「private subsystem」と主張できるのは、Filetto + Auth が同一の `docker compose` に閉じている構成に限られます。**この例外に依拠する案(1-C)は、その構成の外へ出た瞬間に根拠を失います。**

**反証3「監査で追える必要がある」観点。** F-003 非機能は「JWT をログへ出力してはならない」と定めています。**クレーム名が長い(案1-B)ほど、トークンを出さずに何が起きたかを記録する設計が要ります。** 一方、名前空間をオブジェクトで束ねる案1-D は、監査ログへ「どの名前空間の版で判定したか」を1つの値で記録できます。

### 3.3 案の一覧

#### 案1-A: 独自クレームを置かず、IANA 登録済みの `scope` のみを用いる

例: `{"iss":..., "sub":..., "aud":..., "exp":..., "scope":"files:read files:write"}`

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | **スコープ以外の情報を JWT で運ぶ能力**。対象範囲・ルート・版・UI ヒントを載せられない。**論点2 で構造化を選ぶ案(2-C)とは併用できない** |
| **リスクの見積** | ① 情報を載せられないため、`scope` 文字列へ押し込む圧力が生じる(→ §4 の案2-B / 2-D へ誘導される)。② Okta のような `scp` 実装との非互換は解決しない |
| **兆候** | 「スコープ文字列にコロンを増やして意味を詰め込む」変更が実装工程で出てくること。第三者から「自分の IdP のトークンが通らない」という報告が出ること |
| **ライセンス** | 該当なし(仕様上の選択。実装ライブラリは §6) |
| **可逆性** | **高い。** 後から独自クレームを追加する方向は、既存の検証を壊さない(未知のクレームは無視される)。**いつまでなら安いか: 常時** |
| **一次情報** | RFC 7519 §4.1 / RFC 8693 §4.2 / RFC 9068 §2.2.2・§2.2.3(いずれも確認 2026-08-13) |

#### 案1-B: URI 名前空間を持つ Public Claim Name をフラットに置く

例: `{"https://filetto.example/claims/file_scope": ...}`

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | **トークンの簡潔さ**(名前だけで40〜60バイト)。**Keycloak との素直な相互運用**(エスケープが要る)。**ドメインを恒久的に保有する前提**を負う |
| **リスクの見積** | ① Keycloak でドットがネスト解釈され、設定者が気づかないまま検証が落ちる。② クレームが増えるたびに URI が増え、Firebase の 1000 バイト上限へ近づく。③ ドメインを失うと、名前空間の管理権(RFC 7519 §4.2 が求める「その名前空間を自分が管理していることの合理的な確認」)を失う |
| **兆候** | Keycloak 利用者からの「クレームが読まれない」報告。トークンサイズに関する報告 |
| **ライセンス** | 該当なし |
| **可逆性** | **中。** 名前を変えると、発行側と検証側を**同時に**変える必要がある。移行期間に両方を受け付ける実装を挟めば緩和できる。**いつまでなら安いか: 第三者が自分の IdP 設定に名前を書き込む前まで(初回リリース前)** |
| **一次情報** | RFC 7519 §4.2 / Auth0 Create Custom Claims / Keycloak Server Admin Guide 26.7.1 |

#### 案1-C: 短い Private Claim Name を用いる(RFC 9068 §2.2 の private subsystem 例外に依拠)

例: `{"flt_scope": ...}` あるいは `{"filetto_scope": ...}`

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | **外部 IdP との相互運用性の保証**。「Filetto は private subsystem である」という前提を負い、**その前提は AGPL 公開と第三者採用の方針と緊張する** |
| **リスクの見積** | ① Auth0 の制限名(`roles` / `groups` / `permissions` を含む)と衝突すると**エラーなく消える**。② 将来 IANA に同名が登録されると意味が衝突する(`groups` / `roles` / `entitlements` は実際に RFC 9068 で標準化され登録された前例がある)。③ 「private subsystem」の境界が案件の方針(公開・第三者採用)と食い違ったまま残る |
| **兆候** | 第三者から「権限が常に無い」という報告(Auth0 の黙殺パターン)。IANA レジストリに近い名前が登録されること |
| **ライセンス** | 該当なし |
| **可逆性** | **低〜中。** 名前を変えると互換が切れる。**いつまでなら安いか: 初回リリース前** |
| **一次情報** | RFC 9068 §2.2 / RFC 7519 §4.3 / Auth0 制限クレーム一覧 |

#### 案1-D: 単一の名前空間キーの配下にオブジェクトで束ねる

例: `{"https://filetto.example/claims": {"scope": ..., "roots": [...], "v": 1}}`

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | **フラットなクレームを前提とする既製ミドルウェアとの素直な連携**(ネストの参照が要る)。標準の `scope` クレームを使わない場合、RFC 9068 §2.2.3 の SHOULD から外れる |
| **リスクの見積** | ① Keycloak のドットネスト解釈の影響を案1-B と同様に受ける。② 中身の構造に版が要る(`v` を持たないと後方互換の判断ができない)。③ 名前空間キーは1つで済むため、**トークンサイズは案1-B より小さい**(これは案1-B に対する相対的な利点であり、選択の理由ではない) |
| **兆候** | 案1-B と同じ。加えて「構造の版が上がったときに旧トークンをどう扱うか」が実装工程で未定のまま出てくること |
| **ライセンス** | 該当なし |
| **可逆性** | **中〜高。** 名前空間キーが安定していれば、**中身は非破壊に拡張できる**。キー自体を変える場合は案1-B と同じ費用。**いつまでなら安いか: キーは初回リリース前まで。中身は常時** |
| **一次情報** | RFC 7519 §4.2 / RFC 9068 §2.2 |

#### 案1-E: RFC 9396 の `authorization_details`(IANA 登録済み)を用いる

例: `{"authorization_details": [{"type":"filetto_files","identifier":"...","actions":["read"]}]}`

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | **単純さ**。`authorization_details` は本来トークン**要求時**のパラメータであり、Auth 側が RAR(Rich Authorization Requests)を実装することを前提にする。**Auth の要求仕様が増える** |
| **リスクの見積** | ① 対応する IdP が少ない。第三者が Keycloak / Auth0 で RAR を使える保証がない。② **MCP の `ext-auth` 拡張に RAR / `authorization_details` の拡張は存在しない**(2026-08-13 時点で確認)。標準から外れる側になる。③ `type` の値自体が独自名になるため、命名の問題が1段ずれて残る |
| **兆候** | Auth の設計時に「RAR を実装するコストが払えない」と判明すること |
| **ライセンス** | 該当なし |
| **可逆性** | **中。** 構造の中で拡張できるが、Auth 側の実装を伴うため変更費用は Filetto 単独では収まらない |
| **一次情報** | [RFC 9396](https://www.rfc-editor.org/rfc/rfc9396.html)(May 2023)§2・§2.2 / IANA JWT Claims / [modelcontextprotocol/ext-auth](https://github.com/modelcontextprotocol/ext-auth)(確認 2026-08-13) |

### 3.4 論点1 の比較

| 案 | 標準への準拠 | 第三者の IdP 互換 | トークンサイズ | 可逆性 |
| --- | --- | --- | --- | --- |
| 1-A 登録名のみ | 最も高い | Okta の `scp` 問題は残る | 最小 | 高 |

### 4.2 反証 — 各案を崩しにかかった記録

**反証1「日本語ファイル名」観点(制約6)。これが最も強い反証です。**

- **案2-D(パス文字列をスコープ値に入れる)への反証**: RFC 6749 §3.3 の `scope-token` は **%x21〜%x7E に限られ、%x80 以上をすべて除外します。** 「議事録.pdf」「稲敷市_令和6年度.xlsx」といった**日本語のパスは scope 値として表現できません。** パーセントエンコードで回避しようとしても、RFC 6749 は scope-token の符号化規則を定義していないため、発行側と検証側で解釈が一致する保証がありません。さらに**スペースを含むパス(`/My Documents/`)は区切り文字と衝突し、1つのトークンが2つに割れます。回避不能です。**
- **案2-B(スコープ値に安定 ID を入れる)への反証**: 安定 ID を ASCII に限れば文字集合の問題は消えます。**しかし RFC 8707 §1 が名指しで否定した「scope に『どこで』を多重定義する」形そのものです。** また RFC 6749 §3.3 は認可サーバが **スコープを一部無視してよい(MAY)** と定めており、対象と操作を1トークンに詰めた設計では、部分的に落とされたときの意味論が壊れます。
- **案2-A(動詞のみ)への反証**: 文字集合の問題を完全に回避します。**しかし F-003 基準25「JWT のスコープが対象ファイルを含まない場合」という判定が成立しません。** スコープが対象を含まない設計だからです。**基準25 の書き換えが要ります。**
- **案2-C(構造化)への反証**: JSON 文字列なので日本語も表現できます。**しかし「表現できる」ことと「安全に比較できる」ことは別です。** 対象をパス文字列で持てば、CWE-41 / 178 / 289 と NFD/NFC の問題はそのまま残ります。**構造化は文字集合の問題を解くだけで、同一性判定の問題は解きません。**

**反証2「Filetto はファイルシステムを観測する側である」観点。** ADR-0002 決定2 の末尾が明記するとおり、Filetto は移動・改名を API として受け取らず、観測して推定します。**スコープの対象をパスで指すと、利用者がファイルを移動した瞬間に権限が変わります。** これは ADR-0002 決定1「パスを識別子にすると外部の参照が壊れる」と同じ理由で、認可においても壊れます。**Google Drive がファイル ID 単位の同意を採り、「My Drive では一意のパスが存在しない」と明記しているのは同じ問題への対処です。**

**反証3「ゴミ箱」観点(制約8)。** ADR-0003 は削除を「ゴミ箱への移動」として実装すると定めています。**パスで対象を指すスコープは、削除の瞬間に対象のパスが変わるため、ゴミ箱内のファイルへ「通常のファイルと同一の規則」(F-003 基準26)を適用できません。** 安定 ID で指す案(2-B / 2-C)はこの問題を受けません。

**反証4「粗いスコープは MCP の指針に反しないか」観点。** MCP の Common Mistakes は「ワイルドカードや包括スコープ(`*` / `all` / `full-access`)」を挙げています。**案2-A の `files:read` はワイルドカードではありませんが、事実上すべてのファイルを対象とします。** ただし**同じ Common Mistakes は「トークン内で主張されたスコープを、サーバ側の認可ロジックなしに十分とみなすこと」も挙げており、これは案2-A と組み合わせた「Filetto 側のポリシー解決」(§5 案3-B)を支持する向きに働きます。** 反証が両方向に効くため、この観点だけでは案を絞れません。

### 4.3 案の一覧

#### 案2-A: 動詞のみの粗いスコープ。対象範囲は JWT に載せない

例: `"scope": "files:read files:write files:delete trash:read trash:restore"`

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | **JWT だけでファイルの範囲を絞る能力**。範囲は Filetto 側の設定(監視ルート)で決まる。**F-003 基準25 の「スコープが対象ファイルを含まない場合」という判定が成立しないため、基準25 の改訂が要る** |
| **リスクの見積** | ① 部分委譲(「このフォルダだけ AI に読ませる」)を後から足すとき、スコープ体系を拡張する必要がある。**広い→狭いへの変更は後方非互換**。② MCP の「包括スコープを避けよ」という指針に対して説明を要する。③ 監査でトークンだけを見ても、どの範囲へのアクセスが許されていたか分からない |
| **兆候** | 「このフォルダだけ共有したい」という要望が出ること。監査時に「このトークンで何ができたか」を再構成できないこと |
| **ライセンス** | 該当なし |
| **可逆性** | **高い(足す方向)/ 低い(狭める方向)。** 新しいスコープ名を足すのは非破壊。既存スコープの意味を狭めると、発行済みトークンの権限が変わる。**いつまでなら安いか: 意味を狭める変更は初回リリース前まで** |
| **一次情報** | RFC 6749 §3.3 / RFC 8693 §4.2 / MCP 2026-07-28 Authorization(`files:read` / `files:write` の例示) |

#### 案2-B: 動詞 × 対象識別子を、scope 文字列の1トークンへ詰める

例: `"scope": "files:read:r-01HXYZ files:write:r-01HABC"`(識別子は ASCII の安定 ID / ルート ID)

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | **人間可読性**。**ディレクトリ側の安定 ID を発行する前提**を負う(§2-3 の未決)。**scope 文字列の長さがトークンサイズを直接押し上げる** |
| **リスクの見積** | ① **RFC 8707 §1 が名指しで否定した「what と where の多重定義」そのもの。** ② RFC 6749 §3.3 の「認可サーバはスコープを一部無視してよい(MAY)」により、部分的に落とされると意味論が壊れる。③ **識別子の体系を変えると発行済みトークンがすべて無効になる**(ADR-0002 決定2 の安定 ID と同じ不可逆性を、認可の層にも持ち込む)。④ 対象が増えるとスコープ文字列が線形に伸びる。**Firebase の 1000 バイト上限は数十件で到達しうる**(未実測 → §7) |
| **兆候** | トークンが HTTP ヘッダのサイズ上限に当たること。「一部のファイルだけ権限が効かない」という報告(AS の partial ignore) |
| **ライセンス** | 該当なし |
| **可逆性** | **低い。** 識別子が発行済みトークンに載った時点で、体系の変更は全トークンの失効を伴う。**いつまでなら安いか: 初回リリース前まで** |
| **一次情報** | RFC 6749 §3.3 / RFC 8707 §1 / GitHub fine-grained PAT(リポジトリ集合 × permission の構造) |

#### 案2-C: 構造化クレームで {対象識別子 × 操作} を表現する

例: `{"...": {"grants": [{"target":"r-01HXYZ","actions":["read","write"]}], "v":1}}`(RFC 9396 §2.2 の `identifier` / `actions` に倣う)

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | **標準の `scope` 文字列だけを読む既製ミドルウェアとの素直な連携**。**論点1 で案1-A(登録名のみ)を採ると成立しない**(相互依存)。トークンサイズが案2-A より大きい |
| **リスクの見積** | ① 構造に版が要る。版を持たないと後方互換の判断ができない。② 対象が増えるとトークンが肥大する(案2-B と同じ)。③ **構造化は文字集合の問題を解くだけで、対象の同一性判定の問題は解かない**。対象をパス文字列で持てば CWE-41 / 178 / 289 と NFD/NFC の問題が残る。④ Auth 側に「この構造を組み立てる」責務が生じる(→ §5 案3-A へ誘導される) |
| **兆候** | トークンサイズに関する報告。構造の版を上げるときに旧トークンの扱いが未定であることが判明すること |
| **ライセンス** | 該当なし |
| **可逆性** | **中〜高。** 版を持たせれば構造の中で非破壊に拡張できる。**いつまでなら安いか: 版の仕組みを最初に置けば常時。置かなければ初回リリース前まで** |
| **一次情報** | RFC 9396 §1・§2.2 / Microsoft Graph Selected permissions(appId × resourceId × role の3つ組) / Google Drive `drive.file`(ファイル ID 単位) |

#### 案2-D: パス接頭辞をスコープ値に入れる

例: `"scope": "files:read:/work/docs"`

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | **日本語ファイル名(表現不能)**、**スペースを含むパス(区切りと衝突)**、Windows の `\`。**ADR-0002 決定1「パスは属性にすぎない」との整合**。**制約6(日本語文書が対象)そのもの** |
| **リスクの見積** | ① **RFC 6749 §3.3 の文字集合により、日本語パスは表現できない。回避不能。** ② スペースを含むパスは1トークンが2つに割れる。**回避不能。** ③ CWE-41(パス等価性)/ CWE-178(大小)/ CWE-289(名前による認証)/ CWE-59(リンク追跡)。**Deno(CVE-2026-49401)・setuptools(CVE-2026-59890)・Android(CVE-2024-43093、KEV 収載)で実際に破られている。** ④ 利用者がファイルを移動すると権限が変わる(反証2)。⑤ ゴミ箱へ移動した瞬間にパスが変わり、F-003 基準26 が満たせない(反証3) |
| **兆候** | **兆候を待つ設計ではありません。** 日本語ファイル名を1つ置いた時点で表現できないことが判明します |
| **ライセンス** | 該当なし |
| **可逆性** | **低い。** パス文字列が発行済みトークンに載ると、体系の変更は全トークンの失効を伴う |
| **一次情報** | RFC 6749 §3.3 / RFC 8707 §1 / CWE-41・178・289 / NVD(上記 CVE) |

### 5.2 反証 — 各案を崩しにかかった記録

**反証1「Auth が未着手である」観点(§2-1)。** Auth は Filetto 完了後に開発します。**「Auth が細粒度スコープを発行する」案(3-A)は、Auth の設計が決まっていない段階で Auth の実装仕様を先に固定します。** ADR-0004 は Filetto 側の ADR であり、Auth 側の判定者は存在しません。**Filetto の ADR で Auth の責務を確定させる構図そのものが、責務分界として妥当かが論点です。**

**反証2「Filetto は単体 OSS である」観点。** P-001 の目的は「1コマンドで立てられる」単体 OSS です。**前段プロキシに認可を委ねる案(3-C)は、`docker compose` のコンテナをさらに増やします。** Lore の採用で既に +1 が確定しており(P-001 判断2 条件1)、Docker 起動の前提(P-001 暗黙の前提4「未検証」)への負荷が積み上がります。

**反証3「トークンの scope を鵜呑みにするな」観点。** MCP の Common Mistakes は「**トークン内で主張されたスコープを、サーバ側の認可ロジックなしに十分とみなすこと**」を挙げています。**これは案3-A(Auth が細粒度スコープを発行し、Filetto は検証のみ)への直接の反証です。** Filetto 側に認可ロジックが要ることは、MCP 仕様の側から要求されています。

**反証4「共有鍵は発行能力を与える」観点。** 下位論点3-1 の (a) HS256 共有鍵は、**検証側が同じ鍵で発行できます。** F-003 基準27「システムは JWT の発行を行ってはならない」は実装上の禁止ですが、**鍵の配置としては発行可能な状態になります。** 基準27 を「能力として持たない」と読むなら (a) は成立せず、「実装として行わない」と読むなら成立します。**この読みの確定が要ります。**

**反証5「JWKS 取得は可用性を下げる」観点。** 下位論点3-1 の (c) JWKS 取得は、Filetto の起動・検証を Auth の可用性に結びつけます。**F-001 基準22 は `loreserver` 停止時にも「検索と閲覧を継続しなければならない」と定めています。** Auth 停止時に検索が止まる設計は、同じ考え方から見て一貫しません。**一方、鍵を静的配布する (b) はローテーションが手動になり、`extensibility` 要求1(運用に依存する値を定数にしない)との緊張が生じます。**

### 5.3 主論点の案 — スコープを誰が解決するか

#### 案3-A: Auth が対象識別子まで含む細粒度スコープを発行し、Filetto は検証のみを行う

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | **Auth と Filetto の疎結合。** Auth が Filetto の内部構造(ルート ID / 安定 ID の体系)を知る必要がある。**Filetto がファイル構造を変えるたび、Auth の発行ロジックが追随する** |
| **リスクの見積** | ① **MCP の Common Mistakes「トークン内の scope をサーバ側の認可ロジックなしに十分とみなす」に該当しうる**。② Auth が未着手のため、**Filetto 側の ADR で Auth の実装仕様を先に固定することになる**。③ Filetto の安定 ID 体系が Auth へ漏れる。ADR-0002 決定2-2 が「Lore の識別子を Filetto の対外契約へ漏らさない」とした境界の考え方と逆向き |
| **兆候** | Auth の設計時に「Filetto のファイル構造を知らないとスコープを発行できない」と判明すること。Filetto の内部変更が Auth の変更を強制すること |
| **ライセンス** | 該当なし |
| **可逆性** | **低い。** 2サービスにまたがる契約であり、変更には両方の同時改修が要る |
| **一次情報** | MCP 2026-07-28 security-considerations(Common Mistakes)/ Microsoft Graph Selected permissions(付与を別 API で明示的に行う構造) |

#### 案3-B: Auth は主体と粗い権限のみを発行し、Filetto がローカルポリシーで対象へ解決する

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | **「JWT を見れば何が許されるか分かる」性質。** 監査でトークンだけを見ても、どの範囲へのアクセスが許されていたかは分からない。**ポリシーの版を併せて記録する必要がある** |
| **リスクの見積** | ① Filetto 側にポリシーの保管先が増える(設定ファイルまたは `index.sqlite`)。**その保管先が認可の正本になり、保護が要る**。② ポリシーの記述形式が新たな設計対象になる(**パス文字列で書けば §4 反証1 の問題がポリシー側へ移動するだけ**)。③ シングルユーザーの初版ではポリシーが1件しかなく、**過剰設計に見える**(→ `extensibility` 要求4「拡張点を削る場合は判断記録を残す」の対象) |
| **兆候** | ポリシーの記述形式が実装工程で二転三転すること。監査ログからアクセス可否の判断根拠を再構成できないこと |
| **ライセンス** | 該当なし |
| **可逆性** | **高い。** ポリシーは Filetto 内部に閉じており、対外契約(JWT の形)を変えずに差し替えられる。**`extensibility` 要求2 の「境界の背後に置く」に沿う** |
| **一次情報** | MCP 2026-07-28 security-considerations / RFC 9700 §2.3 |

#### 案3-C: Filetto の前段に認可プロキシを置き、Filetto は認証済みを前提に動く

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | **F-003 基準24(JWT なし → 401)を Filetto 自身が満たさなくなる。** 単体 OSS としての完結性。**`docker compose` のコンテナがもう1つ増える** |
| **リスクの見積** | ① P-001 暗黙の前提4(利用者は Docker を起動できる。**未検証**)への負荷が積み上がる。② プロキシを迂回して Filetto へ直接到達できる経路が残ると、認可が完全に無効になる。③ **F-003 基準24〜27 の大幅な改訂が要る**(§2-1 と同じく G-2 / G-4 の判定対象) |
| **兆候** | 「プロキシを外したら全部読めた」という報告。コンテナ数に関する利用者の離脱 |
| **ライセンス** | プロキシ実装を依存に加える場合、ADR-0007 の許可一覧に照らす必要がある(**未調査** → §7) |
| **可逆性** | **中。** Filetto 本体を変えずにプロキシを差し替えられるが、基準24〜27 の改訂は元へ戻しにくい |
| **一次情報** | MCP 2026-07-28 Authorization(サーバがリソースサーバとして検証する前提) |

### 5.4 下位論点3-1 — 署名鍵をどう配布するか

| 案 | 捨てるもの | リスクの見積と兆候 | 費用 / 外部通信 | 可逆性 |
| --- | --- | --- | --- | --- |
| **(a) HS256 の共有鍵を環境変数で配布** | **検証と発行の分離。** 同じ鍵で発行できる | **RFC 8725 §2.2(弱い対称鍵)。** F-003 基準27 の読み(能力として持たないか、実装として行わないか)が確定しないと成立の可否が決まらない。**兆候: 鍵が Filetto 側から漏れた場合、任意のトークンを偽造できる** | $0 / 通信なし | 高(鍵の入れ替えのみ) |
| **(b) 非対称鍵の公開鍵を環境変数で静的配布** | **鍵ローテーションの自動化。** 手動更新になる | **`extensibility` 要求1(運用に依存する値を定数にしない)との緊張。** 環境変数であれば定数ではないが、**ローテーション手順が利用者の管理タスクになる**(`calm-technology`「管理タスクを暗黙に課さない」)。**兆候: 鍵の更新が放置されること** | $0 / 通信なし | 高 |
| **(c) 非対称鍵 + JWKS を Auth から取得** | **Auth からの独立性。** 検証が Auth の可用性に依存する | **F-001 基準22(loreserver 停止時も検索を継続)と同じ考え方から見て一貫しない。** Auth 停止時に全 API が 401 になる。キャッシュを持てば緩和できるが、失効の反映が遅れる。**§2-4 の「外部通信なし」の定義に依存する。兆候: Auth 再起動時に全要求が失敗すること** | $0 / **同一 compose 内の通信**(定義が未確定) | 中 |

**(a) と (b)(c) を併用する構成は、攻撃面を自ら作ります。** PyJWT の CVE-2026-48526(high)は「**公開鍵 JWK が HMAC の秘密鍵として受理され、HS256 で偽造できる**」というものであり、RFC 8725 §2.1 が記述した攻撃そのものが 2026年に主要ライブラリで成立しました(§6.0)。**ADR-0004 が対称鍵と非対称鍵のどちらか一方に固定するか、両方を許すかは、この攻撃面の有無を決めます。**

**MCP 仕様は (c) の方向を要求しています。** RFC 9728(Protected Resource Metadata)の実装を MUST とし、クライアントが認可サーバを発見する経路を求めています。**ただしこれは「MCP の HTTP トランスポートを OAuth 2.1 のリソースサーバとして提供する場合」の要求であり、Filetto が MCP の認可仕様に準拠すると宣言するかどうか自体が、この論点の一部です。**

### 5.5 下位論点3-2 — 署名付き URL の権限をどう表すか

ADR-0002 決定3 が本文直返しと署名付き URL の両方を要求し、署名方式・有効期限を ADR-0004 の対象としています。

| 案 | 捨てるもの | リスクの見積と兆候 | 可逆性 |
| --- | --- | --- | --- |
| **(a) JWT 自体をクエリ文字列に載せる** | **体系の分離**。JWT が URL に露出する | **F-003 非機能「署名付き URL をログへ出力してはならない / JWT をログへ出力してはならない」の**両方**に同時に触れる**。ブラウザ履歴・Referer・プロキシログへ残る。**JWT の有効期限は URL の有効期限より長いのが通常であり、URL の漏洩が API 全体の権限漏洩になる。兆候: アクセスログに URL が残っていること** | 低 |
| **(b) 対象1件・操作1つ・短命の別 HMAC 署名(S3 型)** | **体系の一本化**。鍵が2種類になる | 鍵管理の対象が増える。**S3 の presigned URL は「生成した主体の資格情報」に由来するため、生成時点の権限が期限まで凍結される**。生成後にスコープを剥奪しても URL は生き残る。**兆候: 権限剥奪後もダウンロードできること** | 高(体系が Filetto 内部に閉じる) |
| **(c) `aud` を配信エンドポイントに固定した短命の子 JWT** | **単純さ**。子トークンの発行は F-003 基準27 に触れる | **RFC 8725 §3.12(同一発行者が複数種類の JWT を出すなら検証規則は相互排他でなければならない MUST)への対応が必須になる**。`typ` の使い分けが要る(RFC 9068 §2.1 / RFC 8725 §3.11)。**基準27「JWT の発行を行ってはならない」と正面から衝突する。兆候: 子トークンが親の代わりに API へ通ってしまうこと** | 中 |

### 5.6 下位論点3-3 — stdio の扱い

MCP 仕様は「stdio を用いる実装は**本仕様に従うべきではなく(SHOULD NOT)**、代わりに環境から資格情報を取得すべきである」と定めています。

| 案 | 捨てるもの | リスクの見積と兆候 |
| --- | --- | --- |
| **(a) stdio でも JWT を環境変数から読み、HTTP と同じ検証を通す** | **仕様の推奨からの逸脱ではないが、stdio 利用者に鍵管理を課す** | §2-1 の「発行者不在」問題が stdio でも同じく発生する。**兆候: stdio 起動時に常に 401 になること** |
| **(b) stdio はプロセス境界を信頼し、認可を適用しない** | **F-003 基準21(HTTP と stdio で同一のツール定義)と基準26(ゴミ箱にも同一規則)の一貫性** | **ADR-0003 の「削除したファイルが権限の緩い経路から読めてはならない」に正面から抵触する。** stdio が「権限の緩い経路」になる。**兆候: stdio 経由でスコープ外のファイルが読めること** |
| **(c) stdio 用の資格情報を Filetto が起動時に生成する** | — | **F-003 基準27 と衝突する**(§2-1 の方向ウと同じ) |

**ADR-0002 決定4 は「認証モデルが異なるため実装は分岐する」とトレードオフに明記しています。** ADR-0004 はこの分岐を具体化する必要があり、**F-003 基準21「HTTP と stdio のいずれの経路でも同一のツール定義を提供しなければならない」がツール定義に限られ、認可の規則に及ばないのかを確定させる必要があります。**

### 6.0 ライブラリ選定は ADR-0004 の論点ではないが、下位論点3-1 の判断材料になる

**PyJWT と Authlib は、2026年に署名検証バイパス相当の脆弱性を複数計上しています。** RFC 8725 §3.1(アルゴリズムの許可集合を指定できなければならない MUST)は理論上の要求ではなく、**主要ライブラリが実際に破られている領域です。**

| 勧告 | 対象 | 深刻度 | 内容 |
| --- | --- | --- | --- |
| CVE-2026-48526 | PyJWT `<2.13.0` | **high** | **公開鍵 JWK が HMAC の秘密鍵として受理され、HS256 でトークンを偽造できる** |
| CVE-2026-48523 | PyJWT `>=2.9.0,<2.13.0` | medium | PyJWK / PyJWKClient 使用時にアルゴリズム許可リストが回避される |
| CVE-2026-48522 | PyJWT `>=2.0.0,<=2.12.1` | medium | PyJWKClient のスキーム許可リスト欠如(`file://` / `data:` 経由の SSRF + 偽造) |
| CVE-2026-32597 | PyJWT `<=2.11.0` | **high** | 未知の `crit` ヘッダ拡張を受理する |
| CVE-2026-27962 | Authlib `<=1.6.8` | **critical** | JWS の JWK ヘッダインジェクションによる署名検証バイパス |
| CVE-2026-28802 | Authlib | **high** | **`alg: none` と空署名で検証を回避できる** |
| CVE-2026-49852 | joserfc `<=1.6.7` | **high** | HS256/384/512 が空または nil の HMAC 鍵を受理する |
| CVE-2024-33663 | python-jose `<3.4.0` | **critical** | OpenSSH ECDSA 鍵によるアルゴリズム混同 |
| CVE-2024-23342 | python-jose の依存 `ecdsa` | **high** | Minerva タイミング攻撃(P-256)。**`first_patched_version` が NONE、すなわち未修正** |

**この事実は下位論点3-1 に直接効きます。** CVE-2026-48526 は「**非対称鍵の公開鍵が HMAC の共有秘密として使われる**」というもので、RFC 8725 §2.1 が記述した攻撃そのものです。**対称鍵(HS256、案(a))と非対称鍵(案(b)(c))を同一システムで併用する構成は、この攻撃面を自ら作ることになります。** ADR-0004 が下位論点3-1 で1方式に固定するか、両方を許すかは、この攻撃面の有無を決めます。

**FastAPI 公式は 2024-05-20 に python-jose から PyJWT へ乗り換えています**([該当コミット](https://github.com/fastapi/fastapi) / チュートリアル `## Install PyJWT`)。公式テンプレート `full-stack-fastapi-template` の `backend/pyproject.toml` は **`pyjwt<3.0.0,>=2.13.0`** と、CVE-2026-48526 の修正版を下限に固定しています。**python-jose は公式ドキュメントから外れ、以後アップストリームも停止しています。**

### 6.1 発見した問題 — `cryptography` が `ip-clearance` を通らない可能性がある

`process.config.json` の `allowedLicenses` には **`Apache-2.0 OR BSD-2-Clause`** が入っていますが、**`Apache-2.0 OR BSD-3-Clause` は入っていません。** `cryptography` の `license` 欄は後者です。

**ADR-0007 が対処した表記不一致と同じ構造の問題が、`cryptography` について未対処のまま残っています。** ADR-0007 は「表記の吸収(暫定)」として `Apache-2.0 OR BSD-2-Clause` を追加していますが、`OR BSD-3-Clause` の組み合わせは列挙されていません。

**JWT 検証はどの案を採っても署名検証を伴い、`cryptography` は PyJWT(RSA / EdDSA を使う場合)・Authlib・joserfc のいずれからも依存として入ります。** ADR-0004 の実装着手時に `ip-clearance` が失敗する見込みです。

**これは ADR-0004 の論点ではなく、ADR-0007 の期限管理と `pit-in-template#13` に属する問題です。** 判断の材料として記録します。

### 6.2 PEP 639 移行に伴う不確実性

**PyJWT と cryptography は `License ::` classifier を持たず、PEP 639 の `license_expression` 欄のみを持ちます**(両者とも classifier を削除済み)。ADR-0007 が対処した問題は「`pip-licenses` が classifier 文字列を報告する」ことでしたが、**classifier を持たないパッケージについて `pip-licenses` が何を報告するかは確認していません**(§7.2-8)。

**classifier のみを読む検査系では、PyJWT と cryptography は `UNKNOWN` 判定になります。** ADR-0007 の暫定的な表記吸収が、これらのパッケージに対して機能する保証はありません。**ADR-0007 の期限(pit-in-template#13 の修正後に表記吸収分を削除する)を検討する際、「classifier ではなく `license_expression` を読む」ことが本来の解であることが、この2件から確認できます。**

また `Authlib` / `joserfc` の classifier は総称の `BSD License` であり、**3-Clause と 2-Clause を区別しません。** SPDX を正確に取るには `license` 欄または LICENSE 本文を読む必要があります。**ADR-0007 が「表記の吸収分だけ判定が緩くなる」と記録したリスクの具体例です。**
