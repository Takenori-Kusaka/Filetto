## 1. 判定に用いた基準(標準 3.8.1)

```
R1 | 外部との契約・公開インタフェース・データ形式を変更し、取り消しに相手方の同意を要する。
     認証・認可・個人データの取扱いに影響する。事業継続に影響する
R2 | 取り消しに人手の作業を要するが、自組織の判断のみで戻せる。限定した実利用者に影響する
R3 | 取り消しが自動化された手段で完結する。影響が組織内に留まる
```

### 1.1 R1 の該当条件を3つに分解する

**条文は3つの独立した条件を「。」で区切って並べています。いずれか1つに該当すれば R1 です。**

| 記号 | 条件 | 構造 |
| --- | --- | --- |
| **(a)** | 外部との契約・公開インタフェース・データ形式を変更し、**取り消しに相手方の同意を要する** | **連言**。変更の存在だけでは足りず、取り消しに相手方の同意を要することまで必要 |
| **(b)** | 認証・認可・個人データの取扱いに影響する | **単独条件。相手方の存在を要件にしていない** |
| **(c)** | 事業継続に影響する | 単独条件 |

**(a) と (b) の構造の差が、本案件の判定を分けます。** 初版がシングルユーザー・localhost bind であることは (a) の後半を弱めますが、**(b) には何の影響も与えません。**

**この分解自体が読みであり、確定は人間が行います。** 「。」区切りを独立条件と読まず、全体を1つの連言と読む解釈も文面上は排除できません。その読みを採る場合、本書の R1 草案はすべて崩れます。**どちらの読みを採るかは技術判断者が決めるべき事項です。**

### 2.3 「初版はシングルユーザー・localhost bind」が R1 判定にどう効くか

**依頼の注意点2 への回答です。**

| 条件 | 効き方 |
| --- | --- |
| **(a) 外部との契約・公開インタフェース** | **効く(弱める)。** localhost bind かつリリース 0 件のため、**契約に依存している相手方が現時点で存在しません。**「取り消しに相手方の同意を要する」の後半が未充足になります |
| **(b) 認証・認可・個人データ** | **効かない。** (b) は相手方の存在を要件にしていません。認可を「適用しない」と決めることも認可の取扱いの決定です |
| **(c) 事業継続** | **効かない。** 利用者数と事業継続は別の軸です |

**ただし (a) について、必須制約1・2(E7)が「契約として固定する」と明記していることを、次のように扱いました。**

> **契約として固定する意図があることは、相手方が既に存在することと同じではありません。**

**現時点の相手方は存在しない(E2・E6)。しかし相手方が現れる時点は特定できます**(初回リリース、または Auth の実装着手)。**したがって本書は、これらの決定を「いま R2、時点 X 以降 R1」として草案し、時点 X を各節の「再判定が要る条件」に明記します。**

**この扱いには反証があります**(第7節 反証3)。**「固定を意図した契約は、固定を決めた時点で R1 として扱うべきだ」という読みも成立します。** どちらを採るかは技術判断者の判断事項です。

## 4. 決定ごとの根拠と反証

### 4.1 ADR-0004 JWT クレーム契約 — 草案 R1(大半の決定)

#### 観測可能な事実

| # | 事実 | 出典 |
| --- | --- | --- |
| 1 | 本 ADR の主題は **JWT クレームの契約・スコープの表現・検証の責務分界**である | ADR-0004 論点1〜3 |
| 2 | F-003 基準24〜27(401 / 403 / 認可 / JWT 発行禁止)が本 ADR に依存する | ADR-0004 コンテキスト / F-003 前提2 |
| 3 | 下位論点3-1 の案の組合せが**署名検証バイパスの攻撃面を作る**(PyJWT CVE-2026-48526) | ADR-0004 §5.4 |
| 4 | 下位論点3-2 の案 (a) は、署名付き URL と JWT をログ・ブラウザ履歴・Referer へ露出させる | ADR-0004 §5.5 |
| 5 | 論点1 のクレーム名は、**第三者が自分の IdP 設定へ書き込んだ時点**で変えにくくなる | ADR-0004 可逆性の骨格 |
| 6 | 必須制約2 が「JWT クレームの契約を ADR で固定する」と定めている | E7 |

#### 草案

**R1。根拠は (b)「認証・認可の取扱いに影響する」。**

**事実1 が条件文と正面から一致します。** (b) は相手方の存在も、取り消し可能性も要件にしていません。**「認証・認可の取扱いに影響する」という単独条件のみです。**

#### 反証 — 「初版では認可を適用しない(方向イ)なら R1 ではない」

**依頼の注意点3 への回答です。この反証は成立しません。理由は3つあります。**

| # | 反証の反証 |
| --- | --- |
| 1 | **方向イは「認可を適用しない」ではなく「適用有無を設定で切り替え、既定を適用しないにする」です**(Issue #55)。切り替え機構の設計、既定値の選定、既定が「適用しない」であるときの localhost bind への依存関係は、**すべて認可の取扱いの決定です** |
| 2 | **「既定で認可を適用しない」は、認可の取扱いに関する最も影響の大きい決定です。** 「影響しない」と読むのは、影響の向きと有無を取り違えています |
| 3 | **方向イを採っても論点1・2・3 は消えません。** 設定を有効にした利用者には契約が適用されます。**適用有無の切り替えは、契約の不在ではなく契約の条件付き適用です** |

**さらに、方向イは R1 判定を強める方向にも働きます。** 既定を「適用しない」にすることは、**localhost bind という運用条件を安全性の前提に組み込む決定**です。この前提が破られた導入(誤ってポートを公開する)は、認可が一切ない状態を作ります。

#### 反証 — 「R1 の条件は『変更』を前提とするから、新規の制定には当たらない」

**この反証は判定できません。** (b) の動詞は「影響する」であって「変更する」ではありません。文面上は新規の制定も含むと読めます。**ただし条文が新規制定を意図しているかは、標準本文からは確定できません**(第8節 未確認事項 U2)。

#### 2-4(「外部通信なし」の定義)だけは R3 と見立てる理由

**この決定は用語の定義であり、認証・認可の機構そのものを変えません。** 定義を変える取り消しは文書の書き換えで完結します。**ただし下位論点3-1 の案 (c) の可否がこの定義で決まるため、案 (c) を選ぶ場合は 3-1 の R1 判定に吸収されます。**

#### 再判定が要る条件

| # | 条件 |
| --- | --- |
| 1 | **区分が確定した後に変更しません。**(b) は相手方の有無に依存しないため、状況が変わっても R1 のままです |
| 2 | 逆に、**論点1・2 を初版のスコープから完全に外す**(方向エ相当)決定を採る場合、認可の機構そのものが初版に存在しなくなるため、再判定の余地があります |

### 4.2 ADR-0010 データベース層 — 草案 R3(3論点とも)

#### 論点1: 初版のメタデータ保管に何を使うか — 草案 R3

| # | 観測可能な事実 | 出典 |
| --- | --- | --- |
| 1 | **実装コードが存在しない。保管されているデータが 0 件である** | E3 |
| 2 | 保管対象のうち**安定 ID の発番以外はすべて原本と派生物から再構築できる** | E8 |
| 3 | F-003 基準1 の `index.sqlite` は**対外から観測できず、テストで区別できない** | ADR-0010 コンテキスト |
| 4 | 実利用者は本人1名 | E5 |

**事実1・2 により、いま取り消すことは「ファイルを書き換えて再構築を走らせる」で完結します。** 自動化された手段の範囲であり、R3 の条件に当たります。

#### 反証1 — 「データ形式を決めるのだから (a) の R1 だ」

**崩れます。** (a) は「**外部との**契約・公開インタフェース・データ形式」であり、事実3 のとおり**メタデータの保管形式は対外から観測できません。** 加えて (a) は「取り消しに相手方の同意を要する」まで含む連言であり、相手方が存在しません(E2)。

#### 反証2 — 「初回リリース後は利用者のディスク上にデータが存在するから R3 ではない」

**成立します。** リリース後の変更は、利用者の既存データの移行を伴います。移行は自動化しうるものの、**失敗時の回復に人手を要します。** これは R2 の条件「取り消しに人手の作業を要するが、自組織の判断のみで戻せる」に当たります。

**→ 草案を「いま R3。初回リリース後は R2」とします。**

#### 反証3 — 「安定 ID の発番だけは再構築できない(E8)から R1 だ」

**部分的に成立します。** 安定 ID を失う移行方式を選ぶと、**外部が保持している参照がすべて無効になります**(ADR-0002 可逆性欄)。これは (a) に当たりうる決定です。

**ただしこれは論点1 の決定そのものではなく、移行方式の決定です。** 本 ADR が移行方式を定めない限り、論点1 は R3 のままです。

**→ 一覧表に「安定 ID を持ち越さない移行方式を選ぶ場合は R1」の行を独立させました。**

#### 論点2: 外部化の境界 — 草案 R3

| # | 事実 |
| --- | --- |
| 1 | 境界は Filetto 内部の構造であり、対外 API に現れない |
| 2 | **初版では境界の正しさを検証できない**(境界の向こうに動く実装が無い) |
| 3 | 実装コードが存在しない(E3) |

**事実2 は、この決定が「取り消せない」のではなく「正しさを確かめられない」ことを示します。** 別の軸であり、リスク区分を上げる根拠にはなりません。

**反証:** 案2-C(厚い境界)は**実装量が最大**であり、後から案2-A へ戻すと書いたコードが無駄になります。**しかし「戻すと損をする」は R2 の条件(取り消しに人手を要する)であって、リリース前の現時点では実装量が 0 です。** R3 のままとします。

#### 論点3: 埋め込みベクトルの保管場所 — 草案 R3

| # | 事実 |
| --- | --- |
| 1 | 埋め込みは派生物であり、原本から再構築できる |
| 2 | どの受入基準も保存形式を指定していない |
| 3 | 再構築には 50 ファイルで約 25 分、数千件で数時間から十数時間(S0-003) |

**反証:** 事実3 は「再構築が高くつく」ことを示します。**利用者の倉庫が育った後は、再構築を人手で監督する必要が生じます(R2)。** ただし現時点でデータは 0 件です。

**→ 「いま R3。利用者の倉庫が育った後は R2」とします。**

#### 再判定が要る条件(ADR-0010 共通)

| # | 条件 |
| --- | --- |
| 1 | **初回リリースを行った時点**(利用者のディスク上にデータが生じる)→ R2 |
| 2 | **安定 ID の持ち越しを伴わない移行方式を採る決定をした時点** → その決定は R1 |
| 3 | ADR-0002 本文の `index.sqlite` 2箇所へ手を入れる決定をした場合、**ADR-0002 決定2 の R1 判定に触れるかを別途判定する** |

| # | 理由 |
| --- | --- |
| 1 | **他の決定と違い、決定2 には「安く戻せる窓」が明示的に閉じる時点があります**(初回リリース)。窓が閉じた後に区分を上げても、**上げた時点では既に取り消せません** |

#### **遡及確認 — 5.7.3 が適用されるべきだったか**

**依頼の「遡って確認してください」への回答です。**

| **3.8.3** | 起案・意見・決定の分離。決定者は1名 | 全役割が同一人物。**既知の抵触1・2 と同じ構造** |

**結論として、R1 と確定した決定が1件でもあれば、D-0 に R1 の運用が定義されていない状態が露出します。**

**これは区分を下げる理由になりません。** 手続が用意できないことを理由に区分を下げると、区分の判定が「観測可能な事実」ではなく「運用の都合」で決まります。**標準 3.8.1 が禁じている方向です。**

**採りうる経路は次の3つです(採否は技術判断者・事業決裁者)。**

| # | 経路 | 捨てるもの |
| --- | --- | --- |
| 1 | D-0 v1.5 で R1 の運用(3.9.2 / 3.10.2 / 3.10.5 への対応づけまたは未達宣言)を定義する | 判定の前に D-0 の改訂が入り、G-3 が遅れる |
| 2 | R1 の手続のうち満たせないものを**未達として宣言する**(G-6 と同じ形式) | 未達が増える。**ただし現に満たせない事実を記録する形式としては既に前例がある** |
| 3 | 例外承認(第7章 7.3)として進める | **例外承認には 5.7.3 が適用される**(D-0 v1.4)。理由の記入が必要になる |

**なお 3.9.2(持ち回り決議の禁止)は、1名体制で R1 を判定できるかという構造的な問いを含みます。標準側へ返す論点になりうると見ています**(既存の抵触1・2 と同種)。

## 7. 判定できないもの

**依頼の制約「判定できないものは判定できないと書く」への回答です。**

| # | 判定できないもの | 理由 |
| --- | --- | --- |
| **1** | **ADR-0003 決定1 の区分** | 標準 3.8.1 の「**事業継続**」に対応する観測可能な事実が本案件で定義されていない。「組織の事業活動」と読めば不該当、「当該案件の継続」と読めば該当。**どちらの読みを採るかは案件側で定義する事項** |
| **2** | **ADR-0005 決定1・2 の区分** | 同上 |
| **3** | **ADR-0011 案2-C が (b)「個人データの取扱い」に当たるか** | 利用者自身の資料を、利用者自身が選んだクライアントへ返す構成が「個人データの取扱いに影響する」に当たるかが標準本文から確定できない。**データ主体と運用者が同一である場合の扱いが定義されていない** |

**加えて、第1.1節の分解(R1 の条件を3つの独立条件と読むこと)自体が読みです。** 全体を1つの連言と読む解釈を採る場合、**本書の R1 草案はすべて崩れ、相手方が存在しない現時点ではすべて R2 以下になります。** この読みの確定が、他のすべての判定に先行します。
