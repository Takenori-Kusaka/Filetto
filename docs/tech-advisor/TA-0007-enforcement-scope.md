### 実測で分かった、範囲設計と独立な2件の欠陥

論旨の是非とは別に、**範囲をどう決めても効かない経路**が2件あります。

**(a) Windows では大文字小文字を変えると全パターンを迂回できる。**

```
.claude/GUARD.json      → hook rc=0(通過)
PROCESS-profile.md      → hook rc=0(通過)
```

同一 FS 上で `.claude/guard.json` と `.claude/GUARD.json` は `stat` の `ino` が一致(`1688849861782511`)し、**同じファイル**です。`globToRegExp` が大文字小文字を区別する正規表現を返すためです。本案件の開発環境は Windows 11(NTFS)であり、**現在の遮断は1文字の変更で全面的に無効化できます。** 範囲を A+B に絞ろうが12件のままだろうが、この経路は塞がりません。

**(b) Bash 経由の書き込みはどちらの層も止めない。**

hook の matcher は `Edit|Write|MultiEdit|NotebookEdit` であり、`Bash` を含みません。公式ドキュメントも `Read`/`Edit` の deny ルールについて「**They don't apply to arbitrary subprocesses that read or write files indirectly, like a Python or Node script that opens files itself**」と明記しています([permissions](https://code.claude.com/docs/en/permissions.md)、取得日 2026-08-13)。hooks ガイドも「Claude can also create or modify files by running shell commands. If your hook must see every file change ... add a `Stop` hook that scans the working tree once per turn」と述べています([hooks-guide](https://code.claude.com/docs/en/hooks-guide.md)、同日)。

`P-001.md` の「**Bash 経由での迂回はしない**」は、**強制層ではなく誘導層の規則です。** 標準 3.11.3 は「遵守が必須の規則を誘導層に書いてはなりません」と定めています(`roles-responsibilities.md` l.688-702)。

**したがって現在の遮断は、範囲の広狭にかかわらず「協力的なエージェントに対してのみ働く」水準にあります。** これを「敵対的な回避も防ぐ」と読むと過大評価になります。逆に「協力的なエージェントの事故と、指示の見落としを止める」目的なら、現在の水準でも意味はあります。**どちらの目的で置くかが未確定であることが、範囲の議論が収束しない一因です。**

### 遮断の発生記録は、範囲を決めるに足りない

`.claude/denied.log` を5つのワークツリー(po / dev / qm / platform / audit)すべてで確認しました。

| ワークツリー | 記録 |
| --- | --- |
| Filetto-po | 6行。うち5行は**本書の測定によるもの**。実運用由来は 2026-08-12 の `PROCESS-PROFILE.md` 1件のみ |
| Filetto-dev / qm / platform / audit | **ファイルなし(0件)** |

**論旨の発端である `scripts/gate/**` の遮断は、denied.log に1件も記録されていません。** Platform レーンは hook に当たる前に、`guard.json` / `P-001.md` の記述を読んで自己抑制し、`cp` の手順へ回っています。

この事実は2通りに読めます。**両方を残します。**

- **読み方1(論旨に有利)**: hook に当たっていないだけで、当たれば止まった。摩擦は実在した。
- **読み方2(論旨に不利)**: 摩擦を生んだのは**遮断機構ではなく記述**である。`P-001.md` 運用上の注意3 は「本項は 2026-08-12 まで『`.claude/**`』と広く誤記していた。**誤記1行が、複数のロールを巻き込んで工程を止めた**」と、同型の事故を既に記録している。**同じ失敗が2度起きた**と読める。

**加えて、`denied.log` は git 管理外(`git ls-files` で0件、`.gitignore` にも未記載)であり、ワークツリーごとに分断されています。遮断が実務をどれだけ止めているかの測定値が、構造的に蓄積されません。** 範囲を「摩擦が大きいから縮める」という理由で動かす場合、その摩擦の大きさを示す一次データが本案件には存在しません。

## 1. 検証1 — C を既定から外すと何が起きるか

### 調査

論旨の C は `scripts/gate/**` `adapters/**` `.github/workflows/**` `.github/rulesets/**` `.claude/hooks/**` `scripts/vendor/**` です。根拠は「変更は PR の差分に出るので G-6 で見られる」。

### 反証 — 標準の3か所が、この論法を名指しで否定している

| # | 一次情報 | 記述 |
| --- | --- | --- |
| 1 | `phase4-process-design/developer-guide.md` E.7 l.135 | 「**差分からの事後検出だけでは、指摘の確認を省いた運用で層が働きません**」 |
| 2 | `phase5-implementation/agent-trace-control.md` l.76-80 | 基準値の引き下げ・**検査の除外設定**は「**G-5 を通過させない**。分離した変更として技術判断者の承認を要する」「これらの変更は、**以後のすべての通過を無効化します**。機能の変更と同じ経路で通してはなりません」 |
| 3 | `phase5-implementation/template-repository.md` l.97-100 | テンプレートが遮断する対象は「**強制層そのもの(設定・フック・ワークフロー・ルールセット・ゲートのスクリプト)**」 |

**3 が決定的です。** 既定12件は思いつきの列挙ではなく、標準の1文を機械可読へ落としたものです。C を既定から外すことは、**プロダクト側のテーラリングではなく標準本文の変更**にあたります。標準側 Issue として起票されているのは適切ですが、**Filetto 側で先に適用した #65 は、標準からの逸脱を宣言せずに実施した状態**です(テーラリング要求 `tailoring-guide.md` l.18-24「標準から外した項目、簡略化した項目を、理由とともに宣言する」)。

**2 はさらに強い反証です。** 標準は検査の除外設定を「G-6 で見る」対象ではなく「**G-5 で機械的に止める**」対象に置いています。論旨は受け皿を G-6 に置き換えていますが、標準はそもそも人のレビューに委ねていません。

### 反証 — 本案件では G-6 が存在しない

`docs/D-0-governance.md` v1.3 第2節 抵触2 / `process.config.json` の `unmet[]`: **G-6 は未達**。`reviewSourcing` は「リポジトリを AGPL-3.0 で公開し、コミュニティのレビューを受ける」であり、**公開までの期間は独立レビューが不在のまま進む**と明記されています。

標準の代償措置の規定(`tailoring-guide.md` l.79-96、ADR-0028)は「代償措置は**記録しても未達の解消として扱わない**」「代償措置として置けるのは、**未検証であることの記録と、見直しの期日の設定に限られます**」です。

**したがって「G-6 で見る」は、本案件では「誰も見ない」と同義です。** 論旨の C の根拠は、本案件に限れば成立していません。標準テンプレート一般(G-6 が機能する組織)については成立しうる、という非対称があります。

なお、「G-6 未達の組織では差分レビュー論法が無効である」と名指しした条文は標準に**存在しません**(調査済み)。上記は E.7 と ADR-0028 からの合成です。

### 反証 — 自己判定の閉路が実際に成立している(実測)

`.github/workflows/gate-g5.yml` を読み、次を確認しました。

- トリガは `on: pull_request`。GitHub Actions はこのイベントで**PR の head 側のワークフロー定義**を用います。したがって **PR は自分を判定するワークフローを、その PR の実行に対して変更できます。**
- 全検査ジョブが `node scripts/gate/*.mjs` を実行します(`coverage-check` `spec-lint` `verify-gate-contract` `double-encoding-check` `license-check` `dependency-diff`、および `adapter.mjs` 経由の test / lint / audit / licenses / secretScan)。**判定ロジックの全量が `scripts/gate/**` にあります。**
- 必須ステータスチェックは集約ジョブ `gate-g5` 1つに固定されています。ファイル冒頭のコメントが理由を書いています。

  > 必須ステータスチェックの名前は gate-g5 に固定します。個々の検査ジョブではなく、集約ジョブ1つを必須にすることで、**検査を足しても保護設定を変えずに済みます。**

  **同じ性質により、検査を「減らして」も保護設定を変えずに済みます。** `needs:` から1件外しても、必須チェック名は `gate-g5` のまま緑になります。ブランチ保護側には何の痕跡も出ません。
- 閾値は `scripts/gate/coverage-check.mjs:15` が `config.ci?.coverageThreshold ?? 80` として `process.config.json` から読みます。**しかし `?? 80` というフォールバック値が、閾値の第2の所在地です**(同型の記述が `scripts/gate/adapter.mjs:64` にもある)。`process.config.json` を遮断しても、この行を書き換えれば閾値は動きます。→ 検証2 の論点でもあります。
- `adapters/*.json` の `secretScan` は空文字で、`adapter.mjs:44` が「コマンドが空のため実施しません」の notice を出して**通過**します。`P-001.md` 運用上の注意1 が既に記録している状態です。**空にする変更は差分では1文字の削除にしか見えず、CI は緑のまま、実害の現れ方は「秘密情報が漏れたとき」です。**

**まとめると、`scripts/gate/**` `adapters/**` `.github/workflows/**` を書けるエージェントは、自分の合否判定を、その PR の中で、必須チェック名を変えずに書き換えられます。** これは `CLAUDE.md` 禁止事項3(テストの失敗をテスト側の変更で解消する)と同一の構造です。禁止事項3 は `selfHealLockFile` + `testPatterns` として強制層に降ろされていますが(標準 E.7 l.129-135「本項はこれを強制層へ降ろします」)、**検査スクリプト側は #65 以降その保護がありません。**

### 反証 — 「差分に出る」と「気づかれる」が乖離する条件

論旨は両者を同一視しています。**乖離の条件を整理すると次のようになります。**

| 条件 | 「差分に出る」=「気づかれる」か | 本案件 |
| --- | --- | --- |
| 差分を読む独立した人がいる | 成立しうる | **不在**(G-6 未達) |
| 変更の意味が差分の局所で読み取れる | 成立しうる | ワークフローの `needs:` 削除は**依存グラフを読まないと意味が分からない** |
| 変更の効果が即座に観測される | 成立しうる | `secretScan: ""` の実害は**数か月後**。`?? 80` の書き換えはカバレッジ低下時まで**現れない** |
| 変更が緑/赤の別として現れる | 成立しうる | 検査を外すと**より緑になる**。赤くならない変更は注意を引かない |
| PR が小さく単一の関心事 | 成立しうる | #65 は ip-clearance の機能変更と遮断範囲の変更を**同一 PR に混ぜている**(`CLAUDE.md` 禁止事項6・標準 E.6 l.113 が禁じている形) |

**本案件は5条件すべてで不利側にあります。** 論旨の「差分に出るので G-6 で見られる」が成立する組織像と、本案件の実態が最も離れた位置にある、というのが調査の結論です。

### 反証 — 遮断の縮小そのものが不可逆4操作にあたる

`phase5-implementation/label-mailbox.md` 4.2 設計原則4(l.34-39):

> 不可逆4操作はオーナー(価値責任者)へエスカレーションする:
> - **削除(検証ゲート、ガード, 重要テストの削除を含む)**

同 l.61: 「強制層の変更が必要になった場合は `state:needs-owner` ではなく `state:needs-platform`。**不可逆4操作に該当する場合のみ、あわせて `state:needs-owner` を付与する**」

**「ガードの削除」は不可逆4操作の1つ目に明示列挙されています。** 論旨は「変えないこと」として「不可逆4操作と `state:needs-owner` の運用」を挙げていますが、**提案1そのものが不可逆4操作に該当します。** D-0 v1.3 第2節 摩擦5(「不可逆4操作は、事業決裁者の追認を要する」)も同じ経路を指します。

本案件では起票者と事業決裁者が同一人物のため実務上の追加手続は軽いですが、**記録上「不可逆4操作として扱った」形跡が現時点でありません**(`docs/gates/` 未確認、`state:needs-owner` の付与も未確認 → 「確認できなかったこと」参照)。

### 論旨が持ちこたえた点(反証が通らなかった箇所)

**公平のため記します。**

1. **「`cp` 1行は判断の質を上げない」は正しい。** 標準にも「人が写経すれば統制になる」という規定はありません。遮断は「人に代行させる」ためではなく「変更を別経路へ分離する」ためのものです(E.6 l.113「機能の変更とは別の変更として分離し、技術判断者の承認を得なければならない」)。**分離の手段が `cp` である必然性はなく、ここは論旨の指摘どおりです。**
2. **A と C の性質が違うという分類は妥当。** A を書けると B も C も無効になる、という依存関係の指摘は、後述の実測(検証2)で裏付けられました。**分類そのものは正しく、争点は「C の受け皿を何に置くか」に絞られます。**
3. **既定値が固定される構造の指摘は正しい**(検証5で実測)。

### 整理 — 案

**すべての案について、A(自己言及)は既定で塞ぐ前提です。** そこは論旨と一致しており、争点になっていません。

#### 案1-α: C を既定で遮断したまま維持する(#65 を巻き戻す方向)

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | Platform レーンの自走。検査スクリプトを書くたびに人の適用操作(`docs/platform/proposed/` 経由)が入る。#60 で発生した摩擦がそのまま残る |
| **リスク** | Platform の作業が滞留する。**兆候**: `docs/platform/proposed/` に未適用のファイルが2件以上溜まる、`state:needs-platform` の滞留日数が3日を超える |
| **リスク** | 遮断を「人の写経」で回避する運用が常態化し、写経を挟んだこと自体が統制の証拠だと誤認される。**兆候**: PL-NNNN の記録に「内容は変更していない」だけが書かれ、検証の実測出力が無くなる |
| **可逆性** | 高い。`guard.json` の1ファイル。いつでも安い |
| **標準適合** | `template-repository.md` l.99 に一致。逸脱の宣言が不要 |

#### 案1-β: C を既定から外し、受け皿を G-5 の機械検査へ置く

論旨の C 除外を採るが、受け皿を G-6(未達)ではなく標準 `agent-trace-control.md` l.76-80 が指定する **G-5 側**に置く。強制層に該当するパスの差分を検出したら、そのパスの変更が単独 PR であること・技術判断者の承認記録が付いていることを CI が確認する形。

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | 「書けない」という単純な保証。以後は「書けるが、検出されて分離を要求される」に変わる。**検出漏れの可能性が新たに入る** |
| **リスク** | **その検査自身が `scripts/gate/**` に置かれ、遮断対象外になる**という循環。検査が自分を無効化する変更を検出できるかは、検査の書き方に依存する。**兆候**: `scripts/gate/` 配下の変更を含む PR で、当該検査が skip / notice で通過している |
| **リスク** | 実装工数。既存の `verify-gate-contract.mjs` の拡張で済むか未検証(「確認できなかったこと」参照) |
| **リスク** | G-6 未達下では、検出後の「技術判断者の承認」が自己承認になる。**分離はされるが、独立はしない** |
| **可逆性** | 中。検査を書く工数が沈む。ただし検査を消せば案1-γ に落ちるだけなので、後戻り自体は安い |
| **標準適合** | `agent-trace-control.md` l.76-80 に一致。ただし「既定から外す」部分は `template-repository.md` l.99 からの逸脱であり、**宣言が要る**(`tailoring-guide.md` l.18-24) |

#### 案1-γ: C を既定から外し、受け皿を置かない(#65 の現状を追認する)

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | 「エージェントが自分の合否条件を書き換えられない」という保証を全面的に。以後は誘導層(`CLAUDE.md` の指示)のみで保つ |
| **リスク** | 標準 3.11.3「**遵守が必須の規則を誘導層に書いてはなりません**」に正面から抵触する。7.10.3 の劣化事象 **A-K3「強制層の規則が CI から参照されていない」**に該当しうる。**兆候**: `denied.log` が全ワークツリーで0件のまま推移する(現に0件) |
| **リスク** | 自己修正ループが検査側の変更で失敗を解消する。**兆候**: 同一 PR に実装の修正と `scripts/gate/` または `adapters/` の変更が同時に入る。カバレッジ実測値が閾値のすぐ上に張り付く |
| **リスク** | 検査の空洞化が長期に発覚しない。**兆候**: `secretScan` のような「実施しません」notice が2件以上になる |
| **可逆性** | 高い(設定を戻すだけ)。**ただし、その間に通過した PR の判定は遡って回復できない。** 標準 E.6「以後のすべての通過を無効化します」の意味において不可逆 |
| **標準適合** | 逸脱。宣言と、7.3 例外承認の5要求(記名承認・逸脱項目番号・影響と対処・**回収期限と回収責任者の技術負債台帳登録**・継続報告)が掛かる |

#### 案1-δ: 性質で C を二分する

C を一律に扱わず、「**差分の局所で意味が読み取れるもの**」と「**依存グラフや実行時の意味を読まないと分からないもの**」で分ける。前者(`scripts/gate/**` の判定ロジック、`scripts/vendor/**`)は既定から外し、後者(`.github/workflows/**` の `needs:` 構造、`.github/rulesets/**`、`adapters/**` のコマンド定義)は既定で残す。

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | 分類の単純さ。「差分に出るか」という一本の基準ではなく「差分で意味が読めるか」という判断を要する。**新規参加者に説明しにくい** |
| **捨てるもの** | #60 の摩擦は `scripts/gate/**` と `adapters/**` の両方で起きた。`adapters/**` を残すと摩擦は半分しか解けない |
| **リスク** | 境界が曖昧で、時間とともに侵食される。**兆候**: 「これは差分で読めるから」を理由にパターンを1件ずつ外す PR が繰り返される |
| **リスク** | `scripts/gate/**` を外した時点で案1-γ と同じ閉路が成立する(判定ロジックの全量がここにある)。**分割しても最大の穴は塞がらない** |
| **可逆性** | 高い |

**案1-α と案1-γ は現状に対する両端です。案1-β と案1-δ が中間にあります。**

## 2. 検証2 — A + B の6件で十分か

### 調査・実測

#### `.claude/hooks/**` を A に含めなくてよいか → **含めないと A が成立しない(実測)**

論旨は `.claude/hooks/**` を C に分類しています。**しかし A の定義(「これを書ければ他の遮断がすべて無効になる」)を、hooks は満たします。**

- `guard-write.mjs` は遮断の実装そのもの。書き換えれば `guard.json` を読まなくできる(`main()` の先頭で `process.exit(0)` するだけで全遮断が消える)。
- **かつ、実装を触らなくても、`.claude/settings.json` の `hooks.PreToolUse` の登録を消せば hook は起動しません。**

そして公式ドキュメントが決定打です([settings](https://code.claude.com/docs/en/settings.md)、取得日 2026-08-13):

> Claude Code **watches settings files and reloads them automatically** when they change. Most settings apply to the running session without restart:
> - ✅ Reload immediately: `permissions`, `hooks`, `apiKeyHelper`, `env`

**`hooks` は実行中セッションへ即時反映されます。** つまり `.claude/settings.json` を書けるエージェントは、**同一セッション中に**、hook の登録を外し、以後の全書き込みを素通しにできます。`guard.json` が保護されていても、読む主体が居なくなれば無意味です。

**本リポジトリの現状(実測)**: `.claude/settings.json` は hook rc=0(書ける)、`permissions.deny` は0件。**この連鎖は現在成立しています。**

したがって A の閉包は、最低限:

| 対象 | A に要る理由 |
| --- | --- |
| `.claude/settings.json` | hook の**登録**と permissions の正本。即時リロードされる |
| `.claude/guard.json` | 遮断の**範囲**の正本 |
| `.claude/hooks/**` | 遮断の**実装**。登録が残っていても実装を空にすれば無効 |

**3つのうち1つでも欠けると、残り2つの保護は迂回可能です。** 論旨の A(2件)も、現状(1件)も、この閉包を満たしていません。

**反証の反証**: 「hooks を A に戻すと、hook 自体を改良できなくなる」という反論は成立します。ただし hook の改良は稀な操作であり、#60 型の日常的な摩擦(検査スクリプトを毎回書く)とは頻度が違います。**A に戻す費用は C に戻す費用より小さい**、というのが調査の見立てです(頻度の実測値は持っていません。「確認できなかったこと」参照)。

#### `.github/rulesets/**` と `scripts/vendor/**` はどこか → **論旨は C に分類している(落ちていない)**

Issue #19 の本文を取得して確認しました(`gh issue view 19 --repo Takenori-Kusaka/pit-in-template`、2026-08-13)。C の行に両方とも列挙されています。**依頼文の「どの分類にも入っていない」は、依頼文側の読み落としです。**

ただし `.github/rulesets/**` については別の論点があります。標準 `gate-criteria.md` G-6 基準4(l.367)は「レビュアが作成の指示者本人でない|**ブランチ保護で機械強制**」と定め、`template-repository.md` l.113 は契約検査がブランチ保護の `require_last_push_approval` 欠落と `gate-g5` 未登録を検出すると定めています。**ブランチ保護は標準が「変更を分離する対象」ではなく「強制層に置く対象」として扱っており**、その変更経路は `state:needs-platform`(+不可逆4操作なら `state:needs-owner`)です(`label-mailbox.md` l.56, 61)。**「差分に出るから C」という論法を、ブランチ保護定義に適用してよいかは、標準の建て付け上疑わしい**というのが反証です。

なお実測上、`.github/rulesets/*.json` はリポジトリ内のファイルにすぎず、GitHub 側の設定へは別途 API 適用が要ります。**ファイルを書き換えても即座には効かない**ため、A/B/C の「即効性」という軸では C 寄りです。**この2つの見方が衝突しています。**

#### B の3件で足りるか — 閾値は `process.config.json` だけに書かれているか → **書かれていない(実測)**

リポジトリ全体を検索した結果:

| 場所 | 内容 |
| --- | --- |
| `process.config.json` | `ci.coverageThreshold: 90` / `ci.failOnSeverity: [critical, high]` / `task.maxChangedLines: 400` ほか |
| **`scripts/gate/coverage-check.mjs:15`** | `const threshold = config.ci?.coverageThreshold ?? 80;` |
| **`scripts/gate/adapter.mjs:64`** | `PIT_IN_COVERAGE_THRESHOLD: String(config.ci?.coverageThreshold ?? 90)` ※既定値が2ファイルで **80 と 90 に食い違っている** |
| **`scripts/init/generate-profile.mjs:178`** | `coverageThreshold: ciStrengthened ? 90 : 80`(生成規則の正本) |
| **`adapters/*.json`** | `commands.*` — **どのコマンドを実行するかの正本**。`secretScan: ""` は「検査を実施しない」という判定の正本にあたる |
| **`.github/workflows/gate-g5.yml`** | 集約ジョブ `needs:` — **どの検査を合否に算入するかの正本** |

**「合否条件の正本」を B の定義とするなら、B は3件では閉じません。** 少なくとも `adapters/**` と `.github/workflows/**` の `needs:` は、`process.config.json` と同じ意味で合否条件の正本です。**論旨は両者を C に置いていますが、B の定義に照らすと B です。**

さらに `?? 80` / `?? 90` のフォールバックは、`process.config.json` を遮断しても閾値を動かせる第2経路であり、**かつ両者が食い違っています**(`adapter.mjs` は 90、`coverage-check.mjs` は 80)。設定が失われたときに 80 と 90 のどちらで判定されるかがファイル依存です。これは範囲設計とは独立の欠陥ですが、**「正本が1つである」という B の前提が既に崩れている**証拠です。

### 整理 — 案

#### 案2-α: A を「遮断の定義・登録・実装」の3点閉包にする

`.claude/settings.json` / `.claude/guard.json` / `.claude/hooks/**` を A とする。

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | hook 自体の改良をエージェントが行えなくなる。テストの追加も同様(現在 hook にテストは**存在しない** — 実測) |
| **リスク** | hook にテストが無いまま人手適用のみになると、hook の欠陥(大文字小文字の件)が放置される。**兆候**: `globToRegExp` に関する Issue が起票されても着手されない |
| **可逆性** | 高い |

#### 案2-β: A を最小(`guard.json` のみ)にし、実効性は別手段に求める

現状の追認。遮断は「協力的なエージェントへの標識」と位置づけ、実効的な統制は CI とブランチ保護(GitHub 側、エージェントから触れない)に寄せる。

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | ローカルでの機械的強制。標準 `agent-trace-control.md` 要求4「**設定の変更が、エージェント自身の操作では行えない**」「要求4を満たさない基盤では、遮断は成立しません」を満たさない状態を明示的に受け入れる |
| **リスク** | **標準が「遮断は成立しません」と明記した状態に該当する。** これを採るなら 7.3 例外承認(5要求)または 7.10 の受容決裁が要る。**兆候**: 監査(G-8)で A-K3 の劣化として検出される |
| **可逆性** | 高い |

#### 案2-γ: B を「合否条件の正本」の定義どおりに閉じる

`process.config.json` `PROCESS-PROFILE.md` `CODEOWNERS` に加えて `adapters/**` と `.github/workflows/**`(少なくとも集約ジョブの `needs:`)を B とする。

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | #60 の摩擦のうち `adapters/python.json` 側は解けない。C の縮小効果が半減する |
| **リスク** | ワークフローはファイル単位でしか遮断できず、`needs:` 行だけを守ることはできない。**ジョブ追加のような無害な変更も止まる**。**兆候**: 検査を足す PR が人手適用待ちで滞留する |
| **可逆性** | 高い |

#### 案2-δ: フォールバック値を持たない構成へ寄せ、正本を1つにする

## 3. 検証3 — 二重遮断(`settings.json` の deny と `guard.json` の hook)

### 調査 — 一次情報で挙動を確定させた

出典はいずれも [code.claude.com/docs](https://code.claude.com/docs/en/permissions.md)、取得日 **2026-08-13**。

| 論点 | 公式の記述 |
| --- | --- |
| 評価順 | 「Rules are evaluated in order: **deny, then ask, then allow**. The first match in that order determines the outcome, and rule specificity doesn't change the order.」 |
| PreToolUse の発火 | 「`PreToolUse` hooks fire **before any permission-mode check, in every permission mode**, including `dontAsk`. A hook that returns `permissionDecision: "deny"` blocks the tool **even in `bypassPermissions` mode or with `--dangerously-skip-permissions`**.」([hooks-guide](https://code.claude.com/docs/en/hooks-guide.md)) |
| exit code 2 | 「**Exit code 2 is the blocking signal.** It blocks the tool call unconditionally」([hooks](https://code.claude.com/docs/en/hooks.md)) |
| hook は permission を上書きしない | 「Hook decisions don't bypass permission rules. Claude Code evaluates deny and ask rules **regardless of what a PreToolUse hook returns**」 |
| deny の適用範囲 | 「Read and Edit deny rules apply to Claude's built-in file tools and to file commands Claude Code recognizes in Bash, such as `cat`, `head`, `tail`, and `sed`. **They don't apply to arbitrary subprocesses** that read or write files indirectly, like a Python or Node script that opens files itself.」 |
| Bash パターンの信頼性 | 「**Bash permission patterns that try to constrain command arguments are fragile.**」(オプション順・プロトコル・リダイレクト・変数・余分な空白で外れる例を列挙) |

### 反証 — 「二重」ではなく「非対称な2層」である

**論旨は両者を冗長な二重化として扱っていますが、実測すると担当範囲が異なります。**

| 経路 | `permissions.deny` | `guard.json` + hook |
| --- | --- | --- |
| `Read` の遮断(`.env` / `*.pem` / `.ssh/**`) | **できる** | **できない**(matcher が Edit/Write のみ) |
| `Bash` コマンドの遮断(`gh pr merge`、`git push --force`) | **できる** | **できない** |
| `Write` ツールでの新規作成 | テンプレートの deny は `Edit(...)` が主で、`Write(...)` は `scripts/vendor/**` の1件のみ → **多くのパスで穴** | **できる**(ツール種別に依存しない) |
| 遮断理由をエージェントへ日本語で返す | できない | **できる**(`protectedReason`) |
| 拒否の記録を残す | できない | **できる**(`denied.log`。ただし git 管理外) |
| `.gemini/**` を含む他ランタイム | **効かない**(Claude Code 固有) | **効かない**(PreToolUse も Claude Code 固有) |
| `python -c` / `node -e` 経由の書き込み | 効かない(公式明記) | 効かない(matcher 外) |

**テンプレートの deny が `Edit(./scripts/vendor/**)` と `Write(./scripts/vendor/**)` の**両方**を列挙し、他のパスは `Edit` のみである点は、作者自身が Edit だけでは足りないと認識しつつ、1件しか対応できていなかった痕跡です。** つまり deny 側は当初から不完全であり、hook がそれを補っていました。**「片方だけ緩めても効かない」のではなく、「片方だけでは元々塞げていなかった」が実態に近いです。**

### 反証 — 他ランタイムについての依頼文の前提

依頼文は「`.gemini/**` を含む他のランタイムには `settings.json` の deny が効かない(PR #42 が確認済み)。hook 側だけが効く経路があるか」と問うています。

**hook 側だけが効く経路はありません。** `PreToolUse` は Claude Code の機構であり、`.claude/settings.json` の `hooks` に登録されて初めて起動します。他ランタイムから見れば `guard-write.mjs` はただの Node スクリプトです。

**したがって、他ランタイムを併用する構成では、どちらの層も効きません。** 他ランタイムに対する統制は、ランタイム非依存の層(git の pre-commit フック、CI、ブランチ保護)に置く以外にありません。**これは範囲設計では解けない論点です。**

### 整理 — 案

#### 案3-α: 層ごとに役割を分けて記述する(deny = Read と Bash、hook = ファイル書き込み)

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | 「1か所を見れば範囲が分かる」という単純さ。2ファイルを読む必要が残る |
| **リスク** | 役割分担を記録しないと、次の変更で再び「二重だから片方消す」が起きる。**兆候**: #65 と同様に、性質の違うものが1つの線引きで一括変更される |
| **可逆性** | 高い |

#### 案3-β: hook 側へ寄せ、deny は Claude Code 固有の項目(Read の秘匿・Bash)だけに残す

hook を `PreToolUse` の `permissionDecision: "deny"` 形式へ拡張し、Bash の matcher も足して、遮断の正本を `guard.json` 1つにする。

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | 標準テンプレートとの構成の一致。テンプレート更新の取り込みが難しくなる |
| **リスク** | Bash コマンドの解析を自前で書くことになる。公式が「Bash パターンは fragile」と警告している領域を、より弱い実装で再実装する危険。**兆候**: hook のテスト(**現在0件**)を書かないまま matcher を広げる |
| **リスク** | hook のタイムアウトは現在 15 秒。matcher を広げると全 Bash 呼び出しに Node 起動のコストが乗る(実測していない) |
| **可逆性** | 中。実装が沈む |

#### 案3-γ: ランタイム非依存の層(pre-commit / CI / ブランチ保護)へ主たる強制を移す

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | 「書く前に止まる」という即時性。commit / push の時点まで検出が遅れ、エージェントは無駄な作業をしてから差し戻される |
| **リスク** | ローカルの pre-commit は `--no-verify` で外せる。CI は PR 単位でしか効かない。**兆候**: `--no-verify` を含むコマンドが履歴に現れる |
| **リスク** | 費用は $0(GitHub Actions 無料枠)だが、実行時間は増える |
| **可逆性** | 中〜高 |
| **利点** | **他ランタイム(`.gemini/**` 等)にも効く唯一の案** |

## 4. 検証4 — `permissions.ask` の既定値

### 調査 — 「ask は bypass でも止まる」は**公式ドキュメントで裏付けられた**

[permissions](https://code.claude.com/docs/en/permissions.md)(取得日 2026-08-13)の permission modes 表:

> `bypassPermissions` — Skips permission prompts, **except those forced by explicit `ask` rules**, connector tools ... and MCP tools marked `requiresUserInteraction`. Root and home directory removals such as `rm -rf /` also still prompt as a circuit breaker...

同ページの Warning:

> A few prompts still fire in this mode. **Explicit `ask` rules** ... still prompt.

**論旨の主張は正しいです。反証は通りませんでした。** ADR-0009 の前提も正しかったことになります。

permission mode の一覧は `default` / `acceptEdits` / `plan` / `auto` / `dontAsk` / `bypassPermissions` の6つで、依頼文が挙げた4つより多い点も記録しておきます。

### 反証 — 「取り消せる操作」の定義で結論が変わる

論旨は「`git push` / `gh pr create` はいずれも取り消せる操作」としています。**分解すると一様ではありません。**

| 操作 | 取り消せるか | 備考 |
| --- | --- | --- |
| `git push`(fast-forward、force なし) | **リポジトリ状態は取り消せる**(revert / reset + force push) | ただし取り消しの手段が force push であり、それ自体が別の不可逆操作 |
| **`git push --force` / `-f`** | **取り消せない**(上書きされた履歴は失われる) | **`Bash(git push:*)` は `Bash(git push *)` と等価であり、`git push --force` にマッチします**(公式明記)。#65 で `Bash(git push --force:*)` の deny が消えたため、**現在 force push は allow 側に該当します(実測: deny 0件、allow に `Bash(git push:*)`)** |
| `gh pr create` | **PR は閉じられるが、通知は取り消せない** | 依頼文の指摘どおり。外部の目に触れた事実は戻らない |
| `gh pr comment` / `gh issue comment` | 編集・削除できるが通知は残る | 同上 |
| `curl` / `wget` | **副作用に依存**。GET なら実質可逆、POST/PUT なら不可逆になりうる | `Bash(curl:*)` は現在 allow。**公式が「Bash パターンで引数を制約するのは fragile」と警告している対象そのもの** |
| `npm publish` | **取り消せない**(unpublish には期限と条件がある) | 現在 **allow** に入っている(実測) |

**したがって「ask を廃す」判断は、`git push` と `gh pr create` については論旨のとおり妥当ですが、`npm publish` と `curl` については論旨自身の基準(「既定は不可逆な操作だけに絞る」)に反しています。**

### 実測 — #53 が実際に変えたもの

`git show 8be045b` を確認しました。**#53 は `ask` の5件を全て `allow` へ移しました。**`npm publish` `curl` `wget` を含みます。ADR-0009 の PR 本文は「ask の5件をすべて allow へ移す」と正確に書いていますが、**Issue #19 の「既定は不可逆な操作(`npm publish` / `twine upload` を含む公開系)だけに絞るのが妥当」という自らの結論とは逆の適用**になっています。

さらに `git show 4e1e615` により、**#65 が `deny` を空配列にした**ことを確認しました。#53 の PR 本文は「**deny は変更しない**(`--force` push、`gh pr review`/`merge`、rulesets、強制層の編集)」と書いていますが、その約1時間後の #65 でその deny が全て消えています。

### 整理 — 案

## 5. 検証5 — 提案2(reason フィールド)と提案3(`/process-init` での選択)の実現性

### 実測 — 提案2 の後方互換は「成立する」が、**逆方向で静かに壊れる**

`guard-write.mjs` の該当箇所は次のとおりです。

```js
for (const p of guard.protectedPatterns ?? []) {
  if (match(p, rel)) deny(guard.protectedReason, 'protected');
}
```

`match` → `globToRegExp(glob)` は `for (let i = 0; i < glob.length; i++)` で文字を走査します。**オブジェクトを渡すと `glob.length` が `undefined` になり、ループが0回、生成される正規表現は `^$` になります。**

実測結果:

```
match({pattern: ".claude/guard.json", reason: "x"}, ".claude/guard.json")
  → false   (例外は投げない)
```

**評価:**

| 方向 | 挙動 |
| --- | --- |
| 新しい hook(オブジェクト対応)+ 古い `guard.json`(文字列配列) | **成立する。** `typeof p === 'string' ? p : p.pattern` の1行で済む |
| **古い hook + 新しい `guard.json`(オブジェクト配列)** | **静かに全パターンが無効化される。** 例外もログも出ない。`denied.log` は0件のまま、通過するだけ |

**後者は現実に起こりえます。** `guard.json` は遮断対象(rc=2)ですが `.claude/hooks/**` は現状**遮断対象外**(rc=0)です。テンプレート更新の取り込み順序や、部分的なチェリーピックで、**新しい設定と古い実装の組み合わせが成立します。** そのとき遮断は「無い」のではなく「**あるように見えて無い**」状態になります。

**加えて、`guard-write.mjs` に対するテストはリポジトリに1件も存在しません**(`tests/` および `scripts/` を検索、`globToRegExp` / `guard-write` の参照0件)。この形式変更を検出する自動検証がありません。

なお `globToRegExp` の `**` の扱い自体は正しく動作することを実測で確認しました(`.claude/hooks/**` が `.claude/hooks/sub/x.mjs` に一致、`scripts/gate` のようなディレクトリ自身には不一致)。**欠陥は大文字小文字のみです(第0節)。**

### 反証 — ただし提案3 の根拠は標準に無い
