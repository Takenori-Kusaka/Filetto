### 3.2 反証(2段目) — 各案を能動的に崩す

#### 反証1: PGlite は Python から使えない

**価値責任者が名指しした候補ですが、ADR-0006(Python バックエンド)と正面から衝突します。**

- PGlite は「a WASM Postgres build packaged into a TypeScript/JavaScript client library」であり、対応ランタイムは browser / Node.js / Bun / Deno のみ([pglite.dev/docs/about](https://pglite.dev/docs/about))
- **README・ドキュメントに Python への言及はありません**(2026-08-13 確認)
- Python から使う唯一の経路は `@electric-sql/pglite-socket`(0.2.7 / 2026-07-02)が提供する `pglite-server` で、Postgres ワイヤプロトコルの TCP サーバを立てて `psycopg` から繋ぐ形になります([pglite.dev/docs/pglite-socket](https://pglite.dev/docs/pglite-socket))
- **この経路を採ると Node ランタイムを含むコンテナが +1 必要になり、素の PostgreSQL コンテナを立てるのとコンテナ数が変わりません**
- 公式記載の制約: **SSL 非対応**(`PGSSLMODE=disable` 必須)。既定は1コネクション。`--max-connections=N` で多重化できるが「PGlite is a single-connection database … achieved through a multiplexer … **not all use cases are guaranteed to work**」
- README 原文: 「PGlite is single user/connection」。WASM 上では Postgres の fork ができないことが理由([GitHub](https://github.com/electric-sql/pglite))

**したがって「PGlite にしない理由」は、少なくとも次の形で存在します: 本案件のバックエンドは Python であり、PGlite は Python から直接使えない。使うには Node プロセスを1つ立てることになり、それは PostgreSQL コンテナを立てるのと同じコストである。** ただし**この事実は ADR に記録されていないため、判断としては存在しません。**

PGlite が本来効くのは「TypeScript フロントエンドの中で Postgres を動かす」構成です。本案件のフロントは表示層であり、3段のマッピングを持つ層ではありません。

#### 反証2: SQLite の WAL はネットワークファイルシステム上で動かない

SQLite 公式が明記しています([sqlite.org/wal.html](https://www.sqlite.org/wal.html))。

> All processes using a database must be on the same host computer; WAL does not work over a network filesystem.

**これは本案件に直撃しうる制約です。** F-002 基準1 は派生物を `.filetto/` 配下に置くと定めており、F-002 前提3 は「原本ディレクトリと同じディスクに `.filetto/` を作成できる」としています。**利用者の資料倉庫が NAS・SMB 共有・OneDrive 上にある場合、`.filetto/index.sqlite` も同じ場所に置かれます。** 「自分の PC に資料を溜めている個人」(F-001 背景)が主対象ですが、NAS 利用を排除する記述はどの仕様にもありません。

WAL を使わない(`journal_mode=DELETE`)選択で回避できますが、その場合は読み書きの同時実行性が落ちます。**この分岐は、どの ADR にも受入基準にも記録がありません。**

#### 反証3: SQLite に既知のデータ競合バグがあり、Docker イメージが同梱する版を確認していない

2026-03-03 に WAL-reset のデータ競合が発見され、**3.7.0〜3.51.2 が影響、3.51.3 で修正**(3.44.6 / 3.50.7 へバックポート)されています([sqlite.org](https://www.sqlite.org/))。複数コネクションが別スレッド/プロセスで同時に書き込みとチェックポイントを行う場合に破損しうるものです。

Python の `sqlite3` は「SQLite 3.15.2 以降を要求」としか書いておらず、**同梱される版はビルド依存です**([Python docs](https://docs.python.org/3/library/sqlite3.html))。`python:3.x-slim` イメージは Debian の libsqlite3 にリンクします。

**本環境(Windows / CPython 3.14.6)の実測は `sqlite3.sqlite_version == 3.50.4` であり、これは修正前の版です。** Docker イメージ側の版は**未確認**(§7)。

#### 反証4: LMDB は許可ライセンス一覧に載っていない

py-lmdb のライセンスは **OLDAP-2.8**(OpenLDAP Public License 2.8)です。ADR-0007 が定めた許可一覧(MIT / Apache-2.0 / BSD-2-Clause / BSD-3-Clause / ISC / MPL-2.0 / PSF-2.0 / AGPL-3.0-or-later + 暫定の classifier 表記)に**含まれていません。**

採用するには ADR-0007 の改訂が要ります。**ADR-0007 は D-0 v1.3 摩擦5 の「対外契約・ライセンス」に該当し、事業決裁者の追認を要する領域です。**

加えて LMDB はキーバリューのみで、クエリ言語・二次索引・JOIN を持ちません。3段マッピングの逆引き(内容ハッシュから安定 ID の一覧を引く、パスの前方一致でディレクトリを引く)をすべて自前の索引で実装することになります。

#### 反証5: DuckDB は履歴とキューの書き込みに向かないと公式が書いている

DuckDB 公式([duckdb.org/docs/current/guides/performance/indexing.html](https://duckdb.org/docs/current/guides/performance/indexing.html))。

> Changes on indexed tables perform worse than their non-indexed counterparts.
> Do not define explicit indexes unless you have highly selective queries and enough memory available.

並行性([duckdb.org/docs/current/connect/concurrency.html](https://duckdb.org/docs/current/connect/concurrency.html))。

- 1プロセスのみが読み書き可能。プロセス内では MVCC + 楽観ロックで複数ライタースレッド可
- 「any transactions that modify the same rows at the same time will cause a transaction conflict error」→ **リトライが公式推奨**
- **複数プロセスからの書き込みはネイティブファイル形式では不可**

本案件のワークロードは「3段マッピングの点参照と小さな更新」「操作履歴の追記」「キューの出し入れ」であり、**分析クエリではありません。** DuckDB が得意とする領域と一致しません。

#### 反証6: 素のファイル + JSON はトランザクションを持たない

F-001 の可逆性は「削除・リネーム・移動はメタデータの更新のみで完了する」(非機能)ことに依存します。**メタデータの更新が途中で落ちた場合、ゴミ箱の実体と履歴が食い違います。** ADR-0003 が定めた可逆性は、この食い違いを許しません。

書き込みの原子性を自前で作ることはできますが、それは「履歴管理を独自実装することは技術負債にしかならない」(ADR-0008 の判断)と同じ構図です。

#### 反証7: PostgreSQL コンテナはコンテナ数を3にする

`docker compose up` 一発という前提は維持されますが、Filetto 本体 + `loreserver` + `postgres` の3コンテナになります。ADR-0008 は「コンテナ数の最小化という目標は、この1個ぶん後退する」と記録しており、**もう1個後退することになります。**

加えて、永続ボリューム1個、`healthcheck` / `depends_on` による起動順の依存、DB 資格情報の管理が増えます。P-001 の暗黙の前提4「利用者は Docker を起動できる」は既に未検証であり、**Lore 採用でコンテナが1個増えたことが P-001 に明記されています。**

## 4. 論点2: 外部の DB へ差し替えられる境界をどう置くか

### 4.1 調査(1段目) — 名指しされた2つの差し替え先が何を要求するか

#### Aurora DSQL(PostgreSQL 16 互換 / GA 2025-05-27)

#### 2つの差し替え先の距離

| 観点 | Aurora DSQL | DynamoDB |
| --- | --- | --- |
| モデル | リレーショナル(PG16 互換) | キーバリュー / ドキュメント |
| クエリ | SQL(FK・トリガ・PL/pgSQL・拡張を除く) | 主キー参照 + 定義済み索引のみ。JOIN なし |
| トランザクション | 3,000行 / 10MiB / 5分、OCC リトライ必須 | 100アイテム / 4MB、実効コスト2倍 |
| ベクトル | **載らない**(推定) | **載る**(ただし無料枠外・FGAC 非対応) |
| 整合性 | Repeatable Read 固定 | 既定は結果整合。GSI は常に結果整合 |

**「どちらも受け止める境界」は、この2つの交わりの上に立つことになります。** 交わりは「主キーによる点参照と、明示的に定義した索引による範囲参照だけを行い、JOIN も横断集計も行わず、書き込みは小さく分割し冪等でリトライ可能にする」というものです。

### 4.2 反証(2段目)

#### 反証1: 「両方受け止める境界」は、初版で正しさを確かめられない

ADR-0008 が Lore を境界の背後に置いたとき、**境界の向こうには実際に動く実装(Lore)がありました。** 本件では、Aurora DSQL も DynamoDB も**初版では実装されません。**

**実装が1つしかない境界は、その境界が正しいかどうかを検証できません。** `context/standards/extensibility.md` 要求2 は「実装が1つしかない段階でも、インターフェースを先に定義する」と定めており、境界を切らないことは認めていません。**しかし「切った境界が実際に差し替えを受け止めるか」は、切っただけでは分かりません。**

DynamoDB Local は Docker で動き $0 ですが、公式に開発・テスト専用と明記され、`TransactionConflictException` を投げない点を含め、本番と挙動が異なります。**Aurora DSQL にはローカルエミュレータが公式に存在しません。**

#### 反証2: 厚い境界は、初版の機能そのものを削る

DynamoDB まで受け止めると、次が境界の外へ出ます。

| 機能 | 影響 |
| --- | --- |
| **F-001 基準11(ゴミ箱の残日数表示)** | 「保持期間内のもの」を範囲で引く。DynamoDB では GSI か TTL 属性の設計が要る |
| **F-001 基準7(保持期間経過で完全削除)** | 期限切れの走査。DynamoDB TTL は削除タイミングを保証しない |
| **F-002 基準22・23(キューと未処理件数)** | 件数を数える操作。DynamoDB に `COUNT(*)` はない。カウンタを別途持つ |
| **ADR-0002 決定5(`pending_count` は要求の対象範囲の未完了件数)** | **範囲を絞った件数**であり、単純なカウンタでは出せない |
| **F-002 基準18(BM25 索引)** | もともと DB の仕事ではないが、境界を厚くすると「索引はどこにあるか」が曖昧になる |

**ADR-0002 決定5 の `pending_count` は、「システム全体ではなく要求の対象範囲」と明示的に定めています。** これは範囲指定つきの件数であり、KV 最大公約数の上では自前で持つことになります。

#### 反証3: 薄い境界でも、初版の実装形が外部化を妨げうる

Aurora DSQL の「1トランザクション 3,000 行」は、境界の形とは無関係に効きます。**初回構築で数千ファイルを1トランザクションで投入する実装を書くと、境界がどれだけ綺麗でも書き直しになります。**

同じく OCC のリトライは、境界の背後ではなく**呼び出し側の設計**(冪等性・再実行可能性)に現れます。境界を切っただけでは移りません。

**つまり「境界を置く」と「移行可能な書き方をする」は別の要求です。** 前者だけでは後者は満たされません。

#### 反証4: 外部化は制約1(外部通信なし・$0)を崩す

Aurora DSQL も DynamoDB も、実行時に AWS のリージョンエンドポイントへ接続します。

**P-001 は「実行時の外部通信なし」を S0-004 の実測で確認した価値として記録しており、ADR-0005 は「実行時の外部通信が無い。文書の内容が外部へ出ない。**これは費用の前提とは独立した価値である**」と書いています。**

**したがって外部化は、初版の中核訴求のうち「外部通信なし」を捨てる選択です。** 費用は無料枠内なら $0 を保てますが、通信は保てません。**この文書は「外部化を前提とする」という指摘に対し、外部化それ自体が既存の価値主張と衝突する事実を記録します。判断は技術判断者と価値責任者に属します。**

なお「差し替えられるようにしておく」ことと「差し替える」ことは別です。**前者は制約1 を崩しません。**

### 4.3 整理(3段目) — 案の提示

#### 案2-A: 薄い境界(ドメイン語彙のリポジトリのみ)

`MetadataStore` を Python の `Protocol` として、ドメインの語彙で定義します(例: `resolve_stable_id(path)` / `record_operation(...)` / `list_trash(...)` / `enqueue(...)`)。SQL は実装クラスの内側に閉じます。移行可能性のための追加の規律は課しません。

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | ・**外部化の容易さ**。移行時に実装クラスを1つ書けばよいが、その実装が DSQL / DynamoDB の制約(3,000行・OCC・JOIN なし)を満たせるとは限らない<br>・移行可能性の検証手段 |
| **リスクと兆候** | ・**リスク1**: 呼び出し側が「1回の呼び出しで全件入る」前提で書かれ、3,000行制限で破綻。**兆候**: 移行検討時に初回構築の経路を全面的に書き直す見積が出る<br>・**リスク2**: 境界のメソッドが SQL の形に引きずられる(例: `execute_query(sql)` のような穴)。**兆候**: 境界の引数に SQL 文字列や `WHERE` 句が現れる |
| **実装量** | 最小。境界の定義 + 実装1つ |
| **可逆性** | 中。**境界があるので実装は差し替えられるが、呼び出し側の書き方は移らない**(反証3) |
| **確認できなかったこと** | 具体的なメソッド数の見積(**調べていない**。3段マッピング + 履歴 + ゴミ箱 + キューで概算 15〜25 と見込むが、根拠のある数字ではない) |

#### 案2-B: 中位の境界(薄い境界 + 移行可能性の規律)

案2-A に加えて、**初版の実装が守る規律を明文化します。** 規律の候補は次のとおりです。

| # | 規律 | 由来 |
| --- | --- | --- |
| 1 | 外部キー制約・トリガ・ビュー・手続き言語・一時テーブル・`TRUNCATE` を使わない | Aurora DSQL 非対応 |
| 2 | 1トランザクションの変更行数を設定値以下に保つ(既定を 3,000 未満に置く) | DSQL の 3,000 行 |
| 3 | 1トランザクションの書き込みサイズと実行時間に上限を持つ | DSQL の 10 MiB / 5分 |
| 4 | すべての書き込みを冪等かつリトライ可能にする | DSQL の OCC(`40001`) |
| 5 | 主キーをランダム性のある値にする(連番の末尾集中を避ける) | DSQL 公式の推奨 |
| 6 | 参照整合性をアプリケーション層で担保する | DSQL に FK がない |

**規律2 は `context/standards/extensibility.md` 要求1 の「運用に依存する値を定数にしない」に該当します**(導入先の DB によって違う値であるため)。

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | ・**SQLite / PostgreSQL の便利な機能**。FK による整合性、トリガによる履歴の自動記録、ビュー<br>・**「とりあえず全部1トランザクションで書く」という単純さ**。バッチ分割の実装が初版から要る<br>・**DynamoDB への移行**。この規律は DSQL 相当のリレーショナル移行先までしか受け止めない |
| **リスクと兆候** | ・**リスク1**: 参照整合性をアプリで持つと、バグでマッピングが壊れても DB が止めてくれない。**兆候**: 孤児レコード(派生物を指さない安定 ID、安定 ID を持たない内容ハッシュ)の発生。**ADR-0002 が「派生物を解放する条件」を実装工程へ回しており、ここに直結する**<br>・**リスク2**: 規律が守られているかを機械的に検査する手段がない。**兆候**: レビューで都度指摘が出る<br>・**リスク3**: 規律が「使わない機能の一覧」として増え続け、実装の自由度を過剰に縛る。**兆候**: 単純な機能に不相応な実装量がかかる |
| **実装量** | 案2-A + バッチ分割 + リトライ + 冪等キー。**初版の実装量が増える** |
| **可逆性** | 高(リレーショナルな移行先に対して)。低(DynamoDB に対して) |
| **確認できなかったこと** | ・規律1〜6 を CI で機械検査できるか(**調べていない**)<br>・アプリ層での参照整合性担保が、本案件の規模で実際にどれだけの実装量になるか(**調べていない**) |

#### 案2-C: 厚い境界(キーバリュー最大公約数)

すべてのアクセスを「主キーによる点参照」と「事前に宣言した索引による範囲参照」に限定し、JOIN と横断集計を境界の外へ出します。件数・集計は自前のカウンタとして持ちます。

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | ・**SQL の表現力全部**。初版が SQLite の上に立っていても SQL を使えない<br>・**`ADR-0002` 決定5 の `pending_count` を DB に数えさせること**。範囲指定つきの件数を自前で持つ(反証2)<br>・**F-001 基準11(残日数)・基準7(期限切れ削除)の単純な実装**<br>・**初版の実装速度**。3論点で最も実装量が増える |
| **リスクと兆候** | ・**リスク1**: 自前カウンタが実体とずれる。**兆候**: `pending_count` が 0 にならない / 減らない報告。**ADR-0002 は Atlassian 公式 MCP サーバが「フィールドを定義しても実装のバグで機能しない」実例を既に記録している**<br>・**リスク2**: 実装量の増加が初版の完成を遅らせ、その間に前提(利用者が Docker を起動できるか、初回構築の時間を受け入れるか)の検証が進まない。**兆候**: 未検証の前提が未検証のまま残り続ける<br>・**リスク3**: DynamoDB のベクトル検索が **FGAC 非対応**であるため、F-003 基準25(存在を判別させない認可)を DynamoDB 上で満たせない可能性がある。**兆候**: 移行検討時に認可の設計をやり直すことになる。**この点は ADR-0004 の対象領域と重なる** |
| **実装量** | 最大 |
| **可逆性** | 最も高い(移行先の選択肢が最も広い)。**ただし初版の実装が最も重い** |
| **確認できなかったこと** | ・DynamoDB の `SearchVectors` が FGAC 非対応であることの、F-003 基準25 への正確な影響範囲(**調べたが分からなかった**。認可の設計が ADR-0004 で未確定のため判定できない)<br>・DynamoDB ベクトルインデックスの GA 日付(**調べたが分からなかった**。Developer Guide の Document History が 2025-10-30 で止まっており、ベクトル関連の項目を一切含まない) |

#### 案2-D: 境界を用途ごとに分ける

1つの `MetadataStore` にせず、性質の異なる3つに分けます。

| 境界 | 対象 | 性質 | 移行先の要求 |
| --- | --- | --- | --- |
| `IdentityMap` | 3段のマッピング | 点参照が中心。**対外契約に属し、再構築できない**(ADR-0002 決定2) | KV でも受け止められる |
| `OperationLog` | 操作履歴・監査ログ | **追記のみ**。範囲での読み出し | 追記なら DynamoDB でも自然 |
| `WorkQueue` | 未処理キュー・ゴミ箱の期限 | 状態遷移。件数を数える | ここだけが KV で難しい(反証2) |

検索索引(BM25 / 埋め込み)は **ADR-0005 決定5 のインデクサ抽象化インターフェースが既に担当**しており、`MetadataStore` に含めません。

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | ・**「DB は1つ」という単純さ**。3つの境界が同じ SQLite ファイルの上に立っていても、コード上は別物になる<br>・**境界をまたぐトランザクション**。「ファイルを削除してゴミ箱へ入れ、履歴を書く」を1トランザクションにできなくなる。**これは F-001 の可逆性に直接効く**(反証6 と同じ問題) |
| **リスクと兆候** | ・**リスク1**: 境界をまたぐ整合性が壊れる。**兆候**: 履歴にあるがゴミ箱にない、その逆。**F-001 の可逆性の根拠が崩れ、`q-criticality: cl0` の前提に影響する**(F-001 背景)<br>・**リスク2**: 3つの境界がどれも中途半端になる。**兆候**: 実装が境界を横断して直接 DB を触り始める<br>・**リスク3**: `WorkQueue` だけ移行できず、部分的な外部化になる。**兆候**: 移行検討時に「キューだけローカルに残す」判断が必要になる |
| **実装量** | 案2-A より多く、案2-C より少ない |
| **可逆性** | **境界ごとに異なる。** `IdentityMap` と `OperationLog` は高い、`WorkQueue` は低い |
| **確認できなかったこと** | ・境界をまたぐ整合性を、トランザクションなしでどう担保するか(**調べていない**。Outbox パターン等の適用可否を検討していない) |

### 4.4 4案の比較

| | 案2-A 薄い | 案2-B 中位 | 案2-C 厚い | 案2-D 分割 |
| --- | --- | --- | --- | --- |
| Aurora DSQL を受け止めるか | 実装次第 | **受け止める** | 受け止める | 境界ごとに異なる |
| DynamoDB を受け止めるか | 受け止めない | 受け止めない | **受け止める** | 一部のみ |
| 初版の実装量 | 最小 | 中 | 最大 | 中 |
| 初版で正しさを検証できるか | **できない** | **できない** | **できない** | **できない** |
| `extensibility.md` 要求2 を満たすか | 満たす | 満たす | 満たす | 満たす |

**「初版で正しさを検証できない」は4案に共通します。** 境界の向こうに動く実装が無いためです(反証1)。**検証したい場合、DynamoDB Local(Docker・$0・オフライン)で案2-C の境界を1つ実装するという選択肢は存在します。** ただし DynamoDB Local は開発・テスト専用と公式に明記され、本番と挙動が異なります。**Aurora DSQL には同等の手段がありません。**

### 5.2 反証(2段目)

#### 反証1: 実測すると、選ぶべき対象は「探索方式」ではなく「ロードの形」だった

**§6 の実測により、本案件の規模ではベクトル検索の計算そのものがボトルネックにならないことが分かりました。**

| N(チャンク数) | メモリ | top-10 取得(中央値) |
| --- | --- | --- |
| 10,000 | 14.6 MB | **2.20 ms** |
| 100,000 | 146.5 MB | **8.99 ms** |
| 1,000,000 | 1,464.8 MB | **79.68 ms** |

**100万チャンクでも総当たりで 80ms です。** ANN 索引(HNSW)が要る規模ではありません。

**一方、`embed/<hash>.npy` を1件ずつ読む形の代償は大きく出ました。**

| 方式 | 10,000件の読み出し |
| --- | --- |
| 個別 `.npy` 10,000ファイル(初回アクセス) | **504.50 s** |
| 個別 `.npy` 2,000ファイル(初回)→ 10,000件換算 | 99.71 s → **約 499 s** |
| 個別 `.npy` 2,000ファイル(2回目・キャッシュ温)→ 10,000件換算 | 0.82 s → **約 4.1 s** |
| 単一 `.npy`(連結配列) | **0.021 s** |
| **SQLite の BLOB 列から全件** | **0.076 s** |

**個別ファイル方式は、単一ファイル方式に対して初回で約 24,000 倍、キャッシュが温まった状態でも約 200 倍の時間がかかりました。**

**この差は測定環境(Windows ホスト + Defender の実時間スキャン)に強く依存します。** 初回 49.85 ms/件 に対し2回目 0.41 ms/件 という差はウイルス対策の初回スキャンで説明できます。**Linux コンテナ内での再測定は行っていません(§7)。** ただし本案件は `.filetto/` を利用者の倉庫の隣に置く設計であり(F-002 基準1)、**Windows ホストのファイルシステム上に数万個の小ファイルを作る構図は、実際に起こる構図です。**

#### 反証2: sqlite-vec は pre-1.0 で、しかも総当たりしか実装していない

公式の versioning ページ原文。

> `sqlite-vec` is pre-v1, so according to the rules of Semantic Versioning, so "minor" release like "0.2.0" or "0.3.0" may contain breaking changes.

KNN のドキュメントは `vec0` 仮想テーブルとスカラー関数による brute-force KNN の2方式のみを記載し、**ANN の記述がありません。** ANN は `ann` ブランチと `benchmarks-ann/` に計画があるのみで未リリースです。

**つまり sqlite-vec を入れても、探索方式は NumPy 総当たりと同じです。** 得られるのは SQL からの呼び出しとメタデータ絞り込み(等価・比較、最大16列)であり、速度の優位ではありません。

**加えて、拡張のロードが可能かは Python のビルドオプションに依存します。** 公式ドキュメント原文。

> The `sqlite3` module is not built with loadable extension support by default, because some platforms (notably macOS) have SQLite libraries which are compiled without this feature.

本環境(Windows / CPython 3.14.6)では `enable_load_extension` が存在することを実測しましたが、**Docker `python:3.x-slim` での有効性は未確認です(§7)。**

さらに ADR-0008 が Lore について記録した「pre-1.0 の依存を初版から抱える」というトレードオフが、**2つ目として加わります。**

#### 反証3: DuckDB VSS は永続化が実験的で、データ損失を公式が警告している

公式原文。

> HNSW indexes can only be created on tables in in-memory databases

ディスク DB で使うには `hnsw_enable_experimental_persistence` を有効にする必要があり、**「WAL recovery is not yet properly implemented for custom indexes」**のため、予期しないシャットダウン時に「data loss or corruption of the index」のリスクがあると明記されています。

**ADR-0003 が定めた「破壊的操作をすべて可逆にする」という方針と、公式がデータ損失を警告している機能を初版で使うことは、方向が逆です。**

#### 反証4: 外部化したとき、ベクトルは同じ経路に乗らない

| 移行先 | ベクトルが乗るか |
| --- | --- |
| **Aurora DSQL** | **乗らない。** `CREATE EXTENSION` も `vector` 型もサポート一覧に存在しない(⚠ 明示的な否定文は未確認)。サポートされる型は numeric / character / date-time / boolean / bytea / UUID / json / jsonb のみ。`bytea` は 1MiB でインデックス非対応 |
| **DynamoDB** | **乗る。** `SearchVectors` API。ただし**オンデマンドキャパシティ専用 = 無料枠の対象外**、`Query` / `Scan` 不可、ページネーション非対応、**FGAC 非対応** |
| PostgreSQL(自前ホスト) | 乗る(pgvector) |

**メタデータとベクトルを同じ層に置くと、Aurora DSQL への移行時にベクトルだけ別経路へ切り離すことになります。** 逆に別の層に置いておけば、外部化の対象がメタデータだけで済みます。

**この事実は、論点2 と論点3 が独立でないことを意味します。**

#### 反証5: 埋め込みは再生成できる。だからこの論点は3論点で最も可逆である

埋め込みは派生物であり、抽出テキスト(`text/<hash>.txt`)から再生成できます。**パースをやり直す必要はありません。**

S0-003 の実測は「50 文書の埋め込みで 5.4 秒」です。線形に外挿すると 10,000 文書で約 18 分ですが、**これは外挿であり実測していません(§7)。** 一方 ADR-0005 が記録した初回構築(パース込み)は 50 ファイルで約25分であり、**再構築の重さが2桁違います。**

**したがって、論点3 を後から変える費用は論点1・論点2 より一桁小さい可能性があります。** ただし「安定 ID」(ADR-0002 決定2)だけは再生成できず、論点1 で保管する対象の中で唯一不可逆です。

### 5.3 整理(3段目) — 案の提示

#### 案3-A: 派生物としてファイルに置く(S0-004 の提案どおり `embed/<hash>.npy`)

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | ・**起動時の速さ**。実測で 10,000件の初回読み出しが約 500 秒(§6)<br>・**メタデータとの整合性をトランザクションで守ること**<br>・SQL からの絞り込み |
| **リスクと兆候** | ・**リスク1**: ファイル数が原本数 ×(チャンク数)で増え、ファイルシステムを圧迫する。**兆候**: 起動が遅い / エクスプローラが固まる。**`calm-technology.md` 要求1「静かに蓄積して後で叫ぶ」に該当しうる**<br>・**リスク2**: ウイルス対策ソフトのスキャン対象が数万件になる。**兆候**: Windows 利用者だけ遅い<br>・**リスク3**: 派生物の削除(ADR-0002 決定2-3 の「派生物を解放する条件」)がファイル操作になり、メタデータとずれる。**兆候**: 孤児ファイルの蓄積 |
| **一次情報 / 実測** | §6 の実測(2026-08-13、本環境) |
| **ライセンス** | numpy = BSD-3-Clause(許可一覧内) |
| **可逆性** | 高(再生成できる) |
| **確認できなかったこと** | Linux コンテナ内での同一測定(**調べていない**) |

#### 案3-B: 連結した単一配列ファイル + 行番号をメタデータ DB に持つ

`embed.f32`(N×384 の連結)を1ファイル持ち、`hash → 行番号` の対応をメタデータ側に置きます。読み出しは `np.memmap` または全読み。

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | ・**1件ずつ独立に削除できること**。削除は tombstone + 定期的な再圧縮になる<br>・**ファイル1つ見れば1文書ぶんという分かりやすさ** |
| **リスクと兆候** | ・**リスク1**: 再圧縮を忘れるとファイルが縮まない。**兆候**: 削除しても `.filetto/` が小さくならない。**`calm-technology.md` 要求3「利用者に管理タスクを暗黙に課さない」に該当しうる**<br>・**リスク2**: 行番号とハッシュの対応が壊れると、検索結果が別の文書を指す。**兆候**: 検索結果の抜粋と実体が食い違う。**気づきにくい誤り**(ADR-0005 決定4 が記録した「気づきにくい誤り」と同型)<br>・**リスク3**: 書き込み中のクラッシュで末尾が壊れる |
| **実測** | 単一 `.npy` の読み出しは 10,000件で **0.021 s**(§6) |
| **ライセンス** | numpy = BSD-3-Clause |
| **可逆性** | 高(再生成できる) |
| **確認できなかったこと** | `np.memmap` を用いた場合の実測(**調べていない**。全読みのみ測定) |

#### 案3-C: メタデータ DB の BLOB 列に入れ、探索は NumPy 総当たり

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | ・**メタデータ DB の軽さ**。10,000件で約 15MB がメタデータ DB に加わる<br>・**外部化の単純さ**。Aurora DSQL は `bytea` が 1MiB 上限・インデックス非対応であり、DSQL へ移すときベクトル列だけ切り離すことになる(反証4)<br>・**DSQL の 1トランザクション 10 MiB 制限**に対して、ベクトルの一括投入がバッチ分割を要する |
| **リスクと兆候** | ・**リスク1**: メタデータと同じファイルに入れることで、DB ファイルが肥大し WAL のチェックポイントが重くなる。**兆候**: 初回構築中の書き込み遅延<br>・**リスク2**: 外部化時に「ベクトルだけ別」の例外が生まれる。**兆候**: 境界の実装に「ただしベクトルは」という分岐が現れる |
| **実測** | SQLite BLOB への 10,000件書き込み **2.58 s**、全件読み出し **0.076 s**(§6) |
| **ライセンス** | SQLite = パブリックドメイン、numpy = BSD-3-Clause |
| **可逆性** | 高(再生成できる) |
| **確認できなかったこと** | 数十万件規模での SQLite BLOB の挙動(**調べていない**) |

#### 案3-D: DB のベクトル索引を使う(sqlite-vec / pgvector / DuckDB VSS)

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | ・**依存の少なさ**。pre-1.0 の依存が1つ増える(sqlite-vec)、または PostgreSQL コンテナが要る(pgvector)<br>・**探索方式の優位**。sqlite-vec は総当たりのみであり、NumPy と同じ(反証2)<br>・**stdlib だけで動くこと**。拡張ロードの可否がビルドに依存する |
| **リスクと兆候** | ・**リスク1**(sqlite-vec): 0.2.0 で破壊的変更が入る。**兆候**: 更新でクエリが通らなくなる。**公式が明言している**<br>・**リスク2**(sqlite-vec): Docker の Python が拡張ロード非対応でビルドされている。**兆候**: 起動時に `enable_load_extension` が失敗。**未確認(§7)**<br>・**リスク3**(DuckDB VSS): 永続化が実験的でデータ損失の警告あり(反証3)<br>・**リスク4**: 外部化時に索引が移らない。Aurora DSQL に pgvector はない(反証4) |
| **ライセンス** | sqlite-vec = Apache-2.0(PyPI は MIT/Apache デュアル表記。**表記が一致しない**)/ pgvector = **PostgreSQL License(ADR-0007 の一覧外)** / DuckDB VSS = MIT |
| **可逆性** | 中。索引の構築コストが再生成に加わる |
| **確認できなかったこと** | ・sqlite-vec のライセンスの正確な形態(**調べたが分からなかった**。GitHub API は Apache-2.0 単独、PyPI と docs は MIT/Apache デュアル表記。LICENSE ファイル実体は未読)<br>・Docker `python:*-slim` の `--enable-loadable-sqlite-extensions` ビルドの有無(**調べていない**) |

#### 案3-E: 専用 ANN ライブラリ(faiss-cpu / hnswlib / usearch)

| 項目 | 内容 |
| --- | --- |
| **捨てるもの** | ・**依存の少なさ**。faiss-cpu はホイールで入るが、モデル 1.04GB に加えてさらにディスクを使う<br>・**単純さ**。索引の再構築・永続化・削除の扱いを持つことになる |
| **リスクと兆候** | ・**リスク1**: **本案件の規模では不要である可能性が高い**。100万件でも総当たりで 80ms(§6)。**兆候**: 索引の保守コストだけが残り、速度の利得が観測されない<br>・**リスク2**: ANN は近似であり、再現率が 100% ではない。**ADR-0005 決定4 が記録した「気づきにくい誤り」を1つ増やす**<br>・**リスク3**: 索引ファイルとメタデータの整合を別途持つ |
| **ライセンス** | faiss-cpu = MIT / hnswlib = Apache-2.0 / usearch = Apache-2.0(いずれも許可一覧内) |
| **可逆性** | 中 |
| **確認できなかったこと** | ・faiss の規模別インデックス選択に関する公式の推奨閾値(**調べたが分からなかった**)<br>・faiss-cpu の PyPI 配布主体が Meta 公式かコミュニティ(faiss-wheels)か(**調べていない**) |

## 6. 実測の記録

**測定日 2026-08-13。測定環境: Windows 11 Pro 26200、AMD(Family 23 Model 113)、CPython 3.14.6、NumPy 2.5.2、SQLite 3.50.4(CPython 同梱)。ホストのファイルシステム上で測定。Docker コンテナ内では測定していません。**

### 6-1. NumPy 総当たりの類似度計算(384次元 float32、正規化済み、top-10 抽出)

手順: `M (N×384)` と `q (384,)` の行列積 + `np.argpartition` で top-10。ウォームアップ1回、5回の中央値。

| N | メモリ | 中央値 | 最小 |
| --- | --- | --- | --- |
| 1,000 | 1.5 MB | 0.08 ms | 0.07 ms |
| 10,000 | 14.6 MB | 2.20 ms | 1.11 ms |
| 100,000 | 146.5 MB | 8.99 ms | 8.35 ms |
| 1,000,000 | 1,464.8 MB | 79.68 ms | 74.01 ms |

**BLAS 実装・スレッド数・CPU に強く依存します。他環境では再測定が要ります。**

### 6-2. `embed/<hash>.npy` 形式の読み書き(384次元 float32)

| 測定 | 結果 |
| --- | --- |
| 個別 `.npy` 10,000件の書き込み | 42.83 s |
| 個別 `.npy` 10,000件の読み出し(初回) | **504.50 s** |
| 個別 `.npy` 2,000件の読み出し(初回) | 99.71 s = **49.85 ms/件** |
| 個別 `.npy` 2,000件の読み出し(2回目) | 0.82 s = **0.41 ms/件** |
| 個別 `.npy` 2,000件の書き込み | 14.63 s = 7.32 ms/件 |
| 単一 `.npy`(10,000×384)の読み出し | **0.021 s** |
| ディスク上のサイズ(10,000件) | 15.9 MB(実データ 14.6 MB、オーバーヘッド 1.08倍) |

**初回と2回目の差(約120倍)は、ウイルス対策ソフトの初回スキャンで説明できます。** これは Windows ホスト固有の要因であり、**Linux コンテナ内では大幅に小さくなると見込まれますが、測定していません。**

### 6-3. SQLite(WAL / `synchronous=NORMAL`)

3段マッピング相当のテーブル(`sid INTEGER PRIMARY KEY, path TEXT UNIQUE, hash TEXT, mtime REAL, size INT` + `hash` に索引)。

| 測定 | 結果 |
| --- | --- |
| 100,000行の一括投入 | 6.04 s |
| 個別コミット 1,000回(パスの更新) | 0.46 s |
| パスによる点参照 1,000回 | 21.2 ms |
| DB ファイルサイズ(100,000行) | 22.5 MB |
| ベクトル 10,000件を BLOB 列へ投入 | 2.58 s |
| ベクトル 10,000件を BLOB 列から全件読み出し | **0.076 s** |

**100,000行の一括投入(6.04 s)は、Aurora DSQL の「1トランザクション 3,000 行」上限では34回以上に分割されます。**
