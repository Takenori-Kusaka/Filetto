# D-0 意思決定・エスカレーション体制図

企画承認(G-1)の前提条件です。`gate-entry` ワークフローが frontmatter と本文の空欄を機械的に検査します。

## 2. 兼務の可否と、本案件における抵触

| 組み合わせ | 標準の可否 | 本案件 |
| --- | --- | --- |
| 価値責任者 × 文脈オーナー | 可 | 兼務する |
| 技術判断者 × 開発者 | 可 | **兼務しない**(v1.2 で技術判断者が分離したため) |
| 技術判断者 × AI 維持管理者 | 可 | **兼務しない**(同上) |
| 価値責任者 × 技術判断者 | 5名未満のみ可 | **兼務しない**(同上) |
| 事業決裁者 × 価値責任者 | 小規模のみ可 | 兼務する |
| **作成を指示した本人 × 独立レビュア(同一成果物)** | **不可** | **抵触2**(下記) |
| **開発ライン × 出荷判定者(同一案件)** | **不可** | **抵触1**(下記) |
| **AI が技術判断者(A)を担うこと** | **不可** | **抵触3**(下記) |

**v1.2 で兼務が3件減りました。** 技術判断者を分離したためです。**兼務の削減は抵触3 の代償ではありません。** 抵触3 は別に代償措置を持ちます。

### 抵触1: 開発ライン × 出荷判定者

`/process-init` のテーラリングが `approverMode: value-owner-merged`(出荷判定は価値責任者が兼ねる)を導出しました。1名体制では価値責任者は同時に開発ラインでもあるため、標準の兼務規則に抵触します。

**代償措置**(テーラリングが同時に導出したもの):

| # | 措置 |
| --- | --- |
| 1 | G-7 の判定記録を必ず残す(`docs/gates/` へ。`/gate-record` を使う) |
| 2 | 出荷判定に限定的な抜き取り確認を追加する |
| 3 | CI 基準を厳格化する(カバレッジ下限 90% / critical・high で失敗) |

**この抵触は標準側へ論点として返しています**: [process-compass#209](https://github.com/Takenori-Kusaka/process-compass/issues/209)。標準の判断が出た時点で本節を見直します。

### 抵触2: 作成を指示した本人 × 独立レビュア

独立レビュアを確保できないため、G-6 は**未達**として記録しています(省略ではありません)。

**代償措置**: CI 基準の厳格化(`ci-strict`)およびリリース後監査(`post-release-audit`)。

**埋める方法**(`PROCESS-PROFILE.md` の未達節と同じ):

| # | 方法 | 本案件での見通し |
| --- | --- | --- |
| 1 | リポジトリを公開し、コミュニティのレビューを受ける | **本命**。AGPL-3.0 で公開する方針のため実行可能。ただし公開前の期間は G-6 が不在のまま進む |
| 2 | 他の個人開発者と相互レビューの取り決めをする | **成立しない**。あてになる相手が不在であることを確認済み(2026-08-12) |
| 3 | 有償のコードレビューを利用する | 費用を企画書の予算へ計上していないため、現時点では採らない |
| 4 | 体制が3名以上になったら `/process-init` を再実行する | 該当時に実行する |

**AI を独立レビュアの代替に置きません。** 同一のモデルを用いる限り、エージェントを分けても事前学習の知識という共通の原因が残るためです。

### 抵触3: AI が技術判断者(A)を担う

**2026-08-12、事業決裁者の判断により、技術判断者を人から AI サブエージェント(`tech-advisor`)へ移譲しました。**

**これは標準に抵触します。** 標準および本書 v1.1 は、技術判断を AI へ委譲しないことを定めていました。

| 出典 | 記述 |
| --- | --- |
| 本書 v1.1 第6節 | 技術判断者は「代行者なし。**AI へ代行させない**(技術判断は委譲できない)」 |
| `CLAUDE.md` 委譲できないもの | 「どの設計を採るか、何を捨てるか(技術判断)」 |
| `CLAUDE.md` | 「結果責任(A)は常に人に紐づきます。AI は実行(R)だけを担います」 |

**この抵触を隠しません。** 移譲を実行したうえで、抵触として記録し、代償措置を課します。

#### 移譲の範囲

| 対象 | 移譲 |
| --- | --- |
| G-3(技術設計判断)の判定 | **移譲する** |
| 技術選定の見解と ADR の執筆(理由欄を含む) | **移譲する** |
| 対外インターフェース契約・ライセンス・アーキテクチャの分割方針・採用済み ADR の置き換え | **移譲しない。事業決裁者の追認を要する** |
| 受入基準の作成・承認(G-2 / G-4) | 移譲しない。価値責任者に残る |
| 出荷判定(G-7)・独立レビュー | 移譲しない |
| 結果責任(A)そのもの | **移譲しない。事業決裁者に残る** |

**「判定の実行」を移譲し、「結果責任」は移譲していません。** 判定が誤っていた場合の帰結は事業決裁者が負います。

#### 代償措置

| # | 措置 |
| --- | --- |
| 1 | **調査 → 反証 → 総合の3段を経る。** 反証は推奨を崩しにかかる別の観点から行う。省略した場合は見解へ明記する |
| 2 | **可逆性の低い決定は事業決裁者の追認を要する**(上表の4項目 + 不可逆4操作) |
| 3 | **見解は必ず ADR として記録し、採らなかった選択肢とその理由を含める** |
| 4 | **技術判断者としての記入であることを ADR に明示する**(`templates/02-adr.md` の「理由欄は人が書きます」は技術判断者が人であった前提の記述であるため) |
| 5 | **実装(Dev)と技術判断を同一セッションで行わない** |
| 6 | **記録の完備を Audit の監査対象とする**(G-8) |

**代償措置を満たさない判定は、G-3 の判定として成立しません。**

#### 1 を課す理由

**同一のモデルに由来する偏りが、調査と結論の両方に同じ向きで乗るためです。** 本書 第2節 抵触2 で「AI を独立レビュアの代替に置かない」とした理由と同じ構造です。反証を別の段として分けることで、調査の枠内で完結する結論を避けます。

**これは独立レビューの代替にはなりません。** 抵触2 は依然として未達です。

#### この抵触は標準側へ返します

**標準は「技術判断は委譲できない」と定めるのみで、AI を技術判断者に置く場合の要件・代償措置を持ちません。** 1名体制で AI を実装の主体に置く前提と、技術判断を人に固定する要求は、実運用で衝突します。**論点として process-compass へ返します。**

## 3. 市場・顧客仮説の検証 — 未達

ADR-0031 により、市場・顧客仮説の検証は企画書の欄ではなく**体制と予算の側で担保**します。1〜2名の体制では「兼務で成立する」か「成立しない」かの二択であり、**省略は認められません**。

**本案件は「成立しない」と判断し、未達(`unmet`)として宣言します。** 判定日: 2026-08-12 / 判定者: takenori-kusaka(価値責任者)

### なぜ兼務成立としないか

任命基準は「自ら顧客に接する。**または**検証の設計と発注ができる」です。本案件の実態は次のとおりです。

| 検証すべき仮説 | 顧客接点 | 判定 |
| --- | --- | --- |
| **本人が使う**(個人が自分の資料倉庫として使い続ける) | あり。本人が実利用者 | 成立する |
| **第三者が使う**(他の個人が採用し、使い続ける) | **なし** | **成立しない** |

**「自分が使う」と「第三者が使う」は別の仮説です。** 企画書は差別化軸として「Onyx / AnythingLLM / RAGFlow / OpenDocuments に対してこう勝つ」と書いており、これは第三者の採用を前提とした主張です。**その主張を検証する経路を、現時点で持っていません。**

本人が実利用者であることをもって兼務成立と書くこともできますが、それは検証範囲を「本人が使う」仮説に狭めたうえで、狭めた事実を記録から消すことになります。採りません。

### 未達の3点

| # | 項目 | 内容 |
| --- | --- | --- |
| 1 | **未達の理由** | **顧客接点の不在と予算の不在の両方**。第三者の利用者・見込み利用者に接する経路がなく、調査を発注する予算も計上していない(企画書は金銭支出ゼロで構成) |
| 2 | **代償措置** | ①未検証であることを本書および企画書へ記録する ②見直し期日を 2026-11-12(本書の次回レビュー期日)に設定する。**これらは未達の解消として扱わない。仮説の当否はこれでは分からない** |
| 3 | **調達先** | リポジトリを AGPL-3.0 で公開し、**コミュニティの反応と利用の実績を観測する**。公開までの期間は検証が不在のまま進む |

### この未達が G-6 と同じ構造であること

独立レビュア(抵触2)と市場・顧客仮説の検証は、**どちらも「開発ラインの外にいる人からの反応」を必要とし、どちらも同じ調達先(公開とコミュニティの反応)に依存しています**。片方が埋まらなければ、もう片方も埋まらない可能性が高い構造です。

**さらに、その調達先の成否は「どう知ってもらうか」に依存しますが、標準にはチャネルに対応する欄が存在しません**(標準チームより共有、2026-08-12)。AGPL-3.0 は採用の裾野を狭める方向に働くため([[0001-license-agpl-3]])、この弱点と掛け算になります。**この構造的な弱点は企画書 v2.0 の事業リスク表へ1行として明示します。**

## 5. エスカレーションの経路

**1名体制のため、上位へのエスカレーション先は存在しません。** 経路の代わりに、**停止と再計画**を既定の動作とします。判断を保留したまま進む状態を作らないためです。

| 状況 | 誰へ | いつまでに |
| --- | --- | --- |
| 判定の期限を超過した | エスカレーション先なし。案件を停止し、`state:needs-po` を付けて滞留の原因を再計画する | 超過を認識した当日 |
| 判定者が不在(休暇・離任) | エスカレーション先なし。案件を停止する(第6節) | 不在が判明した時点 |
| 判定者どうしの見解が割れた | **v1.2 で技術判断者が分離したため発生しうる。** 価値責任者と `tech-advisor` の見解が割れた場合、両論を ADR へ併記し、事業決裁者が採る側を決める | 48時間以内 |
| 安全に関わる懸念が出た | 作業を停止し、`state:needs-owner` を付けて事業決裁者(本人)の判断を待つ | 即時 |
| 不可逆な操作が必要になった(削除・本番デプロイ・課金書き込み・スキーマ変更) | 作業を停止し、`state:needs-owner` を付ける | 即時 |

## 6. 代行者

**代行者は存在しません。** 1名体制のため、判定者が不在の間は判定が行われません。

| 役割 | 代行者 | 代行できる範囲 |
| --- | --- | --- |
| 価値責任者 | 代行者なし。不在中は案件を停止する | 代行できる範囲なし。**AI へ代行させない**(価値判断は委譲できない) |
| **技術判断者** | **`tech-advisor` が担う(v1.2 で移譲済み)。人の不在で判定は止まらない** | **G-3 の判定と ADR の執筆。ただし可逆性の低い決定は事業決裁者の追認を要する**(第2節 抵触3) |
| 出荷判定者 | 代行者なし。不在中は出荷しない | 代行できる範囲なし |

不在中に AI が実装を進めることは妨げません。ただし**ゲートの判定を伴う工程へは進めません**。判定待ちの成果物は `state:needs-po` を付けて滞留させ、復帰後に判定します。
