# 申し入れ: 事業フェーズに合わせた統制の段階的導入を、標準とテンプレートの正面から扱ってほしい

- 宛先: ピットイン方式(AI協調型ソフトウェア開発プロセス標準)を策定しているチーム(process-compass / pit-in-template)
- 差出人: Filetto(P-001)の価値責任者・事業決裁者 Takenori Kusaka
- 日付: 2026-10-11
- 基準: pit-in-template aab3b7a への再準拠(Filetto の ADR-0001)で得た実測にもとづく
- 起票の形: 標準側で Issue 化する場合は、本文をそのまま使ってよい

## 1. 依頼したいこと

事業フェーズ(PoC → MVP → グロース → 安定)に応じて、**どの統制を、どの強さで、いつから課すか**を、標準の本文とテンプレートの両方で「段階表」として定めてほしい。あわせて、**段階を戻す(例: MVP と答えたが実態は企画フェーズ)ときの手続**を定めてほしい。

Filetto は1名体制で、実態は企画フェーズ(PoC 相当)にある。一方で旧テンプレートの初期化時に MVP と答えており、再準拠のときに答え直そうとして、下の「2」の問題に当たった。

## 2. 現状の確認(aab3b7a で読んだ範囲)

段階的な導入が**無い**わけではない。次は既にある。

| 既にあるもの | 所在 |
| --- | --- |
| PoC では G-1 を簡略化し、G-2 を G-4 へ統合し、G-6 を省略する | `scripts/vendor/tailoring-kb.json` の規則 `r-b-poc` |
| MVP では G-6 をコア機能のみにし、G-7 を簡略化する | 同 `r-b-mvp` |
| グロース・安定で負債の返却と出荷判定を強める | 同 `r-b-growth`、`r-b-stable` |
| 強制層(`guard.enabled`)は、PoC 以外では既定で有効 | `scripts/init/generate-profile.mjs` の `guardEnabled = answers['q-biz-phase'] !== 'poc'` |
| ステージの移行を判定する関門 | `.claude/skills/gate/gates/SG.md`(SG-0〜SG-2) |

足りないと感じたのは次の4点である。

### 2.1 段階が粗く、強制層は PoC か否かの二値になっている

MVP と答えた瞬間に、強制層のパス保護が一斉に有効になった。Filetto は2026-08-12 の ADR-0015 で「序盤フェーズは遮断しない」と決めていたが、再生成が `.claude/guard.json` を `enabled: true` に書き換えた。1名・MVP の初期に、遮断を一度に全部掛けるのが適切か、段階を刻めないかを知りたい。

希望: 強制層の遮断を、項目ごと(テストへの書き込み・強制層の設定・構成の正本・判定の記録)にステージで切り替えられる、または警告から遮断へ上がる段階を持たせる。

### 2.2 「段階を戻す」が SG の語彙に無い

`axis` の変化点は、ステージを前へ戻すときに SG の判定記録(`sgRecord`)を要求する。一方、`SG.md` の判定の値は前へ進む方向(S1 へ移行 / 継続検証 / 中止 など)で、**「S0 へ戻す」に当たる値が無い**。既存の通過記録(Filetto では `sg0-P-001-2026-08-12.md`)は、戻す判定の根拠にならない。AI が判定記録を作ることもできない。

結果、実態に合わせて答えを直したいのに、直す手続の入口が定義されていない。

希望: 「S0 へ戻す」「S1 へ戻す」を SG の判定の値として定め、判定基準(何が崩れたら戻すか)と、戻したときに失効する記録(例: すでに通過した G-2)の扱いを書く。

### 2.3 戻す・緩める変更が、進行中の機能へ与える影響が事前に読めない

PoC へ戻すと G-1 が簡略化され、G-2 が G-4 へ統合される。dry-run は差分を出すが、**進行中の機能(Filetto では F-001〜F-003)の既存の判定記録がどう扱われるか**は出力から読めなかった。

希望: ステージの変更の dry-run に、進行中の機能ごとの影響(失効・再判定の要否)を出す。

### 2.4 再準拠のとき、プロジェクト独自の統制が黙って消える

テンプレートの置き換えは、`scripts/` と `.github/workflows/` を丸ごと差し替える手順になっている。Filetto が足していた独自のゲート(ライセンス検査、外部ホスト検査、判定記録の完全性、PR の基底の検査、投資の測定、独自の secret-scan)と、そのテスト10ファイルが消えた。さらに、独自の secret-scan が消えた結果、テンプレート側の `secretScan` が参照する `.secretlintrc.json` が無く、G-5 の secret-scan が動かなくなった。

これは「統制の弱化」に当たるが、手順上は置き換えの副作用として現れ、警告が出なかった。

希望: 再準拠の手順に「独自の統制の棚卸し」を加える。置き換え対象のうち、テンプレートに無いファイルの一覧を出し、廃止・移植・保持を選ばせる。

## 3. 段階表の案(たたき台。採否は策定チームが決める)

| ステージ | 強制層(遮断) | 工程ゲート | 検査(G-5) | 記録 |
| --- | --- | --- | --- | --- |
| S0 探索(PoC) | 警告のみ。構成の正本と判定の記録だけ遮断 | G-1 簡略、G-2 統合、G-6 省略 | 最小(テストとシークレット) | 判断の理由を残す |
| S1 価値確立(MVP) | テストと強制層を遮断 | G-6 はコア機能のみ | カバレッジ・静的解析・ライセンス | 判定記録を必須 |
| S2 スケール | 全項目を遮断 | 全ゲート | 全検査 + 脆弱性 | 負債の計画返却 |

この表は、Filetto が `r-b-*` の規則から読み取った構造に、強制層の段階を足した案である。値の根拠は持っていない。
